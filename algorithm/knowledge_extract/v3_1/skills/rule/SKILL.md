## 适用本体与边界

这些类名和字段是典型特征，不要求调用方本体与样例逐字相同。结合本体类定义、属性说明及原文判断；仅有“故障”词汇、分类列或表格格式不能确定本技能适用。选中后，本技能按阶段应用于本次同领域请求的全部实体。

## rules:all

只映射本体声明的类型和属性。类名和字段名只作语义角色提示，实际含义以本体定义为准；条件、结论、规则身份及证据不能从邻行借用。

## rules:entity

- 对结构化记录，规则粒度以本体的类定义为准：一条规则表达明确的前提到结果、或对象到约束，不把“故障详细分类”字段值当作规则身份。
- 分别识别具有独立前提与结论的命题；复合前提中的必要合取项不能拆成多条更强规则。原文没有显式规则名称时，按对象、条件、结果和必要限制归纳可区分的短名，并给出原始连续引文。
- 同一分类只有在表达同一条规则时才归并；前提、结果或限制不同的规则不得仅因分类相同而合并。
- 同一条规则在多行重复时可以归并；一行含多条独立命题时分别判断，不机械地按一行一实体或一类故障一实体处理。
- 原文有明确规则名称时，mention 保留原名；evidence.quote 始终来自当前 chunk 的连续原文。
- 分类、日期、序号等字段名不是实体；结构化表格也不是输出空结果的理由。
- 规则来源不止「故障状况」列：「故障原因」列与「处理方法」列同样是规则来源；只要原文存在「原因→现象」「处置→恢复」等语义对应就要分别归纳成规则（例如「对标不准→更换同步环线检测板/报警板后恢复」「ATS 故障/联锁区灰显→30 秒自动恢复」「更换发送/接收端转换单元、调谐单元后恢复」），不得因为“内容都是字段与标量值”而少抽或不抽。

## rules:semantics

- 规则须有原文支持的条件与结论、原因与效果、或对象与约束。一次事件可以支持带该事件限定的事实命题，不能自动提升为对所有对象总成立的规律；只有类别、共现或时间顺序不能补出关系。
- 先确定完整命题的前件、语义连接和后件，再命名。只有现象或主题的“某故障规则”不是完整规则；日期、车次、地点与“某状态下出现异常”的叙述只是事件背景，未说明触发关系时不能填成导致。所属系统和故障分类是目录标签，不能据此另造“现象指示所属系统故障”。核验时也必须检查连接关系，不能仅因前后两句话都出现就返回 yes。
- 原文明示“代码/报警号（含义）”或“代码，解释”时，可提取该代码指示该含义的独立诊断命题，名称保留代码及含义；它不等于“代码导致故障”，也不能只抽含义而丢掉诊断条件。无需外部知识补解码。
- 对代码释义命题，前件是“出现该代码”，连接是“指示”，后件是原文明示的解释；不是把解释填在前件、把代码填在后件。另有原因导致现象时另成因果命题，不把两种方向混进同一规则。处置规则的前件保留被处理的故障/对象及处置动作，后件说明该对象恢复的状态，避免仅用“复位→正常”等不明对象的表述。
- 一段含“甲导致乙，乙导致丙”时，分别抽取原文明确的两条直接命题；不能只用整段长名替代两条命题，也不另补“甲导致丙”。因果、代码释义、处置效果分别保留其直接支持依据。
- 恢复结果必须明确归属于具体处置。某记录先说动作甲后恢复、另列动作乙，不能把甲的恢复转给乙；“处理方法”列仅有更换项目也不能自动补出恢复。未指明动作的“人员处理后正常”不应编造成某项技术措施生效。
- 同一条件命题重复出现时使用稳定的语义短名，不增添“规则”后缀或无关日期制造副本；对象和适用条件实质不同则保留区别。源记录位置不是规则身份，不能用它生成规则ID。
- 故障分类不是规则身份。仅当前提、结果、对象及适用限制相同且有依据时认作同一规则；不得把同分类记录中的不同前件与后件交叉拼成一条规则。
- 前件描述规则成立所需条件，后件描述相应结论，连接字段表达原文支持的关系。因果方向是原因/触发条件到现象；诊断“现象→原因”须有明确支持，不能自动反转因果，也不能将相关或可能原因写成必然导致。
- 保留并且/或者、先后、否定、例外、量词、数值、正负号、单位与阈值方向。合取条件缺一项不能推出原结论；备选条件不能变成同时成立。多段推理不自动补传递关系或逆命题。
- 处置发生不等于故障恢复。只有原文明确把效果归属于该动作时，才成立相应处置—效果命题；重试、失败及后续成功按各自步骤解释，不把最终结果分配给全部动作。
- 适用范围与事件背景分别处理。对象、工况、位置等若决定规则适用性须保留；仅记录一次事件的日期或地点不能升级为普遍触发条件，也不能抹去单次观察的事实范围。
- 名称、描述、前件与后件各按字段定义取值，不强求措辞不同；不同字段的值相同或与实体名相同，只要分别获支持就不构成错误。
- 类型或模板字段按本体解释：所属规则类型填本体允许的类别；类型模板填模板定义；实例表达式填该命题，不能仅因字段标识含 body/template 就复制整段或猜格式。
- 唯一标识须有原文或本体明确指定的规则身份依据；一条记录只产生一条规则也不意味着记录序号就是规则 ID。编码与规范名称的对应同样须有资料依据。

## rules:property

- 针对给定实体提出有原文依据的属性变更；已有值、缺失值与冲突值的处理遵守本轮 task 和 output_contract。
- 分别查证字段含义、前后件和连接方向；多来源只综合同一规则，不用拼接不同规则的条件填满属性。
- 模板类属性（含 template、模板、模版、表达式）：直接使用本体 note 给出的模板骨架原文，按 RuleTypeBody 选择对应骨架，并保留类型名前缀与 [前提条件]、[结论或结果] 等方括号占位符；不要把前件、后件的文本代入方括号，也不得自创模板或使用自造符号。
- 连接词只用规范取值：导致 / 引起 / 造成 / 触发 / 指示 / 处置后恢复；禁止「先后发生->综合结论」「同时满足->综合结论」这类模板短语。因果类用「导致」；判定或指示类（代码、报警、现象指示某故障）用「指示」；处置类（更换/重启/复位后恢复）用「处置后恢复」。
- 属性按名称语义取值：含 antecedent、前件、前提、条件取前提；含 consequent、后件、结论、结果取结果；含 connection、连接、符号取连接词；含 body、正文、描述、说明、内容给出包含前提与结果的完整陈述，不得只写规则名或规则类型；含 name、名称、title 用实体名或原文规范短名。
- 原文以「现象，原因是 X」表述时前件取现象、后件取 X；以「X 导致 Y」表述时前件取 X、后件取 Y；语义、模板、前件、后件属性必须包含原文的关键限定（对象、地点、数值、处置等）。
- 本体声明的属性键保留齐全；原文没有对应内容时留空，不用“无”“未知”等占位符。

## rules:repair

- 只修复给定问题，保持前件、后件及条件方向；不得补造规则或原文位置。
- 漏抽问题只在指定范围补充有证据的规则，不按预设数量补造规则。属性修复保持给定精确键；若问题需要重命名或拆分已有实体，当前契约不能完成，不用拼接属性掩盖误合并。
