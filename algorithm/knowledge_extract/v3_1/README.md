# Knowledge Extract V3.1

本目录保留算法代码与单元测试。接收上游已解析、已切片的 `ExtractionChunk`，按实体候选、属性补全及实体校验修复流程完成本体约束抽取，不在算法内部解析文档或更改上游 chunk 边界。

## 当前能力边界

v3.1 已删除 LLM 关系分类、关系候选枚举、关系语义核验、确定性边组装、复合成员边、关系修复、关系覆盖检查与关系评分。`raw.relations`、`graph.relationships`、`intermediate_model.relations` 和 `triples` 均为空。关系本体声明仍用于本体解析及实体类型路由；通用关系字段/序列化契约保留兼容。其他算法版本不受影响。

## 公共入口

```python
from algorithm.knowledge_extract.v3_1 import extract
from algorithm.knowledge_extract.v3_1.chunk_context import ExtractionChunk

result = extract(
    ontology=ontology_text,
    chunks=[ExtractionChunk(chunk_id="chunk-0", text=chunk_text)],
)
```

`extract()` 保留 `entities / relations` 接口，`relations` 固定为空列表；`extract_harness()` 返回内部诊断结果。LLM 配置沿用 `KG_EXTRACT_LLM_*`。服务算法选择值为 `KG_EXTRACT_ALGO_VERSION=v3.1`。

## 精简文件产物

保存结果时使用 `export_artifacts(result, output_dir)`，不再把内部聚合对象直接作为默认业务文件。导出目录必须不存在，不覆盖旧产物。HTTP/MCP 与 `extract()` 的严格契约不变。

```python
from algorithm.knowledge_extract.v3_1 import extract_harness, export_artifacts

result = extract_harness(ontology_text, chunks, best_effort=True)
paths = export_artifacts(result, "tmp/my-v31-run")
```

| 文件 | 内容 |
| --- | --- |
| `entities.jsonl` | 每行只包含 `type`、`name`、`properties`，固定按此顺序输出，不附加证据或核验字段。 |
| `evidence.jsonl` | `kind=source` 记录去重证据及来源、坐标；`kind=entity_evidence` 通过精确 `type + name` 关联实体，包含 evidence_ids 及按属性名组织的 property_evidence 核验收据。相同引文在不同来源中分别保留；多个实体可以引用同一证据。 |
| `summary.json` | 原始终态、错误、核验与覆盖信息、告警、重试诊断、数量、版本和消息留存情况；最后写入。 |
| `messages.jsonl` | 每行一次调用，messages 数组包含完整 system/user 和实际 assistant 回答，另含耗时、usage 和可用性标记。 |

导出入口不会因 partial/failed 抛出业务失败异常而丢弃已有事实，也不会将其改为 succeeded；消费者必须同时读取 summary 的状态和核验结果，失败运行的数据仅供排查。它不新增事实、不替代校验或发布门禁。graph/intermediate_model 等兼容表示仍可从内部聚合对象按需获取，精简文件不再重复保存。

当前文件格式为 `v3.1-artifacts-2`。证据关联移出实体行后，核验支持类型、缺失来源及冲突收据仍完整保留在 evidence.jsonl；summary.counts.evidence 统计 source 条数，evidence_bindings 统计实体关联条数。名称不作空格、大小写或全半角归一化。

模型消息沿用 `KG_EXTRACT_V31_TRACE_CALLS` 上限（默认 32），请求与回答一起保留或省略；超过上限仍保留调用状态、耗时与 usage。`summary.message_trace.complete=false` 表示消息记录不完整，不能称为完整调用日志。历史结果若只有请求，可用 `calls=` 提供当次真实传输记录；否则明确标记 response_available=false，不编造回答。导出只读取消息和白名单元信息，不保存传输认证头。

已有文件的离线转换入口：

```bash
python3 -m eval.tools.export_v31_artifacts \
  --result tmp/old-run/result.json --calls tmp/old-run/calls.json \
  --output tmp/new-run
```

此命令不调用模型；`--calls` 可省略。完整调试快照按需另外保留，正式评测所需原始输入/输出与 manifest 不受本导出工具影响。

## 提示词与上下文

当前代码标记为 `knowledge-extract-v3.1-all-entity-admission-v35`，保留既有动态调度、共享事实语义、逐行恢复与请求级 Skill 固定快照。当前工作区 Skill 为 official_document@12、rule@8、trouble@8；公文规则在用户已有 @9 的基础上补充准入边界，保留其原有内容。其他算法版本和对外图谱结构不变。

v30–v31 根据 20261014-010413 的真实调用日志修复来源与核验上下文：带工作表标题、仅有开启围栏的完整 JSONL 行仍按表格行分窗；单个完整 JSON 对象也保持原子性，不改上游 chunks 或修造损坏原文。重复短属性引文用整行区分主体，歧义时要求更完整引文。属性核验携带同一实体整组候选属性，以检查组合后的方向、单位与阶段；这些候选仍不是证据，每个 yes 只证明指定属性。未声明可推导的本体身份字段与系统标识一样，禁止接受原文中不存在的拼造值。

rule@8 明确区分代码释义、因果、处置效果与事件背景；trouble@8 补充检测上下文中的部件识别与实验/结果命名，区分表格并列配件、节位编号及缺值占位符；official_document@12 禁止将无业务职责依据的签阅姓名和通用表单标题误当本体主体及公文。生成和核验共享规则，不调整 golden、本体或评分器。`KG_EXTRACT_V31_ENTITY_VERIFICATION_BATCH_SIZE` 可独立缩小实体准入批次，未配置时沿用通用核验批次，默认行为不变。相关真实模型评测输出保留在 `tmp/v31-log-fix-20261014/`；质量结论以对应完整运行的 summary 为准，不能以代码测试通过代替 F1 达标。

v33 修复真实日志中将完整文号的字母/数字前缀当成独立属性值而引入冲突的问题。身份字段检查完整 token 边界；本体描述为编号、编码等的普通字段，仅在候选逐字出现但只是更长 token 的片段时拒收。边界判断兼容 NFKC 字形，不给普通说明字段强加逐字抄录要求。完整值仍须通过语义归属核验，两个不同的完整编号仍保留为真实冲突，不按字符串长短自动选值。

v17 根据 v16 的真实模型回答修复恢复逻辑：仅兼容完整 Markdown 围栏和合法记录后的一个末尾 `{}`，仍逐行验证字段、唯一键与完整任务覆盖；原始回答和规范化原因保留。重复已保存键不再充当 schema 失败，已核验事实不会被重复提案覆盖。截断后只有空标记或重复前缀仍不算完成；坏 JSON、重复字段、数组包装及任意说明文字仍明确失败。

来源定位与实体语义属于候选准入：无主来源证据的候选明确拒收并保留 `candidate_rejected` 和 warning，不强迫同批合法实体重新生成；所有候选被拒收仍为失败。格式/schema 重试给出实际记录和字段错误，持续损坏的实体请求最多额外分两层范围重查，共用调用和时间预算。`partial` 继续表示有事实获接受但仍有未恢复终止错误或验证问题，不能由非空图或 F1 分数替代。

v18 进一步统一生成与实体核验的类型判据：文字出现或字段值出现不等于该类型成立；日期、编号、联系方式、署名等是否成为实体由实际类定义决定。实体核验可看到未经证明的 `candidate_properties` 来识别实例边界，它们不是原文证据，核验实体不会签发属性证明。表格核验保留支持引文所在的完整原始行及表头，不将远列条件裁掉；仍沿用原始偏移、输入预算和独立属性核验。最小来源/单类型请求按实际 wire 大小校验，不因预留重试空间而虚报超预算，后续重试仍逐次检查硬上限。

v19 实体核验使用完整本体类型目录作角色对照，避免单一候选类型的批次把“被提及/主送”直接当作该类型成立。目录只供判断，输出仍仅覆盖本轮精确 item_id，不产生其他类型任务，也不预设类型互斥。仅属性核验继续使用相关字段定义，保留小输入预算。现有本机 CodeFuse 评测代理会将 SSE 包装中的上游错误转成安全类别，已识别限流返回 429、鉴权返回 401，其余错误/缺少 completion 返回 502；暂态错误带 1–60 秒有界 Retry-After（默认 10 秒），原始错误和凭据不向模型、日志或评测产物透传。

v20 对长的多类型来源中“合法回答只覆盖一种类型就停止”的情况增加一次有界定向续扫：尚未覆盖的类型分别提交到同一动态调度器，不规定实体数量，不从 golden 补事实，空候选合法；子任务有独立 diagnostics，终止失败仍保留为 partial/failed。耗时超过 60 秒的 502/504 请求，在调用方允许拆分且没有 Retry-After 时优先缩小来源/schema/核验项范围，不把同一大请求连续等待三次；401、短暂错误及限流提示仍遵从原有重试和退避。调用与 deadline 预算不变。

v21 在批量实体/属性核验重试耗尽且仍有 JSON/schema/截断终态时，直接并发提交单项核验，不重复按半批量重试同类格式错误；优先核验剩余 ID，若全部 ID 已恢复但响应完整性失败，则对全部 ID 重新调用模型。此恢复路径禁止用缓存冒充新完整响应，保留父请求与每个子任务独立的诊断；单项仍失败、预算耗尽、uncertain 或真实冲突继续阻止通过。重复字段与非有限值给出固定、具体的格式反馈，不从坏 JSON 提取或挑选 verdict。

v22 将类型补扫改为实验开关 `KG_EXTRACT_V31_TYPE_COMPLETION_AUDIT=false`，默认关闭：完整复评发现对仅术语/单一视角的来源补扫其他类型，会多抽不属于实例的问题、方案及主体，并增加调用量。缺少某一类型不证明缺少事实，不使用类型覆盖率作为强制补事实依据；保留显式开启时的有界调度及错误隔离测试。其他 v17–v21 的协议、核验、证据与重试修复继续保留。

- `prompt_templates.py`：公共 System + 阶段约束、统一 JSON User 外壳和结构化重试反馈。
- `prompt_router.py`：兼容文档分类诊断、阶段上下文裁剪、消息装配。
- `skill_selector.py`：依据技能目录描述、调用方本体和原文样本进行一次请求级语义选择。
- `skills/*/SKILL.md`：用户维护的领域规则；`skill_registry.py` 和 `skill_planner.py` 负责发现、读取与请求内一次性编译。
- `domain_skills.py`：无模型的低层兼容预览，只从 Markdown 读取策略正文。
- `output_contracts.py`：所有阶段的输出约束及动态 schema 构造。

全部阶段使用两条消息 `system + user`。User 固定为 `task`、`domain_policy`、`ontology`、`documents`、`output_contract`，重试时追加 `retry_feedback`。第一步输出 `type + mention + properties + evidence`，同时抽取当前请求窗口支持的本体属性；`mention` 直接成为原文 `name`。`evidence.property_quotes` 按属性记录引文。为兼容旧输出，省略 properties 的候选仍会进入补全。JSONL 逐行解析及所有普通文本调用保持不变。

公共入口自动执行“读取技能目录快照 → 请求级选择 Skill → 按阶段编译并装配规则”。默认增加一次 `skill_selection` 模型调用，模型依据目录中的 name/version/description、调用方本体及有界原文样本选择精确技能标识；`skill_refs` 显式绑定时不调用选择模型。后续全部实体、切片、批次、核验和修复复用同一选择，不按实体类型或源行分配不同技能。发送给模型的 `domain_policy` 仍为规则正文字符串，各完整规则段以空行连接，无匹配时为空字符串。技能 ID、版本、章节、文件及目录 SHA-256 保留在请求级审计中。`skills_dir` 可替换技能目录，默认使用本包的 `skills/`。

模型消息不包含 `stage_context` 或 `document_sources`。来源 ID、页码、元数据、坐标及修复诊断路径留在程序内部。`task.known_entities` 携带精确键、已核验属性与候选引文；属性修复另携带 `requested_properties`。核验输入进入 `task.items`，修复问题进入 `task.repair_issues`，它们不是新的原文证据。单来源直接保留原文，多来源加匿名片段标签，说明不默认连续或属于不同文档；表头/完整行/表尾构成一个可读表格窗口，不在表格语法内部插入标签。候选阶段另提供原文窗口前后各最多 200 字及受限邻片的辅助上下文，不从辅助片段发现新实体。四个抽取阶段继续使用 JSONL；已有 Skill 选择器独立使用一个 JSON 对象。

属性补全和属性修复每个给定的 `type + name` 恰好返回一条变更提案。`properties` 只包含本轮新增、修改或冲突消解的值；空对象表示无变更，省略不删除已核验旧值，无变更不需要编造引文。非空提案需要支持引文，旧版 `evidence.quote` 仍兼容，推荐逐属性 `property_quotes`。required 属性修复直接使用精确实体键，不重新生成 mention；漏实体修复仍输出候选。生成与核验保留相同的完整本体注释，不按 200/500 字截断。核验只复用领域语义规则，不收到生成/更新操作指令。

## 当前执行与可信边界

2026-10-14 v35：所有候选实体（包括原文逐字名称、无 Skill 匹配或 `skill_refs=[]`）均须独立核验名称与本体类型，仅 `yes` 准入并保存 `entity_evidence`。字面定位只证明来源，不证明类型成立；最终校验对所有实体要求名称、类型及来源坐标一致的语义收据，自定义修复回调同样执行准入。核验复用现有分批、并发、调用预算与 deadline；预算耗尽时不发布未核验实体，因此可能增加调用或使旧预算不足，不能以离线测试证明真实模型质量或时延改善。

`verification.coverage_complete` 仍表示当前覆盖审计未发现缺口；新增 `coverage_scope` 明确检查本体特性、来源证据和结构 chunk 绑定，`semantic_recall_verified=false` 明确未验证完整语义召回。一个 chunk 的实体绑定或没有结构元数据的空候选，均不能证明已抽全。没有增加强制按类型补扫，也不将未验证召回改成质量通过。

2. 按类型和有界来源窗口提取 JSONL 候选。逐行解析与校验，截断尾行或损坏行不连带丢弃其他完整记录；恢复的候选仍须通过本体、来源定位和属性证据核验。名称及引文都无法定位时进入带反馈重试；不能接受无来源实体。模型不提供可信字符偏移，程序定位后回映原切片。
3. 对每个新属性先定位其引文，再独立调用语义核验。实体名和值共现不能证明属性含义；仅 `yes` 接受，`no`、`uncertain` 或核验失败均移除该新值。此前已经核验且未改变、无冲突的属性可复用本次运行的收据。核验上下文保留引文及前后各 200 字、主体与旧值支持片段、表头；冲突项携带全部冲突支持原文，仍受完整请求预算约束。
4. 按完全相同的 `type + name` 合并出现记录。相同属性值保留全部来源收据；不同值需模型综合，未解决冲突保留告警并返回部分/失败状态。改值不能继承旧值的无关支持收据。已扫描、无冲突、无待处理邻片的实体跳过补全。
5. 补全按单键和来源窗口流式处理。模型必须恰好返回请求中的实体键；不得增键、漏键、重复、改名或改类型。名称的大小写、全半角、内部空格保持原样，UID 使用原始键的稳定哈希。
6. 最终逐项校验本体、实体与属性收据的来源、字符偏移、引文和 span ID。修复遍历全部相关切片，不再静默限制为前 3 片；无进展、耗尽轮数或硬校验失败均如实写入停止原因。`verification.valid` 表示没有硬错误，`coverage_complete` 另行表示是否仍有覆盖缺口。

## JSONL 截断恢复

所有模型阶段的 `success_schema` 描述单行记录，程序再组装为内部 `entities` / `verdicts` 结构，HTTP/MCP 聚合契约不变。JSONL 中字符串换行必须转义；逐行校验拒绝非法类型、未知属性、无来源候选、重复 JSON 键及非有限数值。核验中同一响应重复的 item_id 不择优取 yes；只接收唯一、合法且完整的结果。

有完整有效记录时先保留，再按既有次数有界重试；没有可恢复记录时继续既有拆分策略。后续空输出或请求失败不清空已恢复记录。重试耗尽保留有效记录并记录 terminal 失败，`best_effort=True` 时报告 partial；严格模式仍报告 failed，不能把部分数据称为完整成功。核验缺失的属性不会被接收，其他明确 yes 的属性继续保留。

v14：补全和核验重试只请求缺失键，任务输入和模型 Schema 同时收窄，最终按原始完整集合验收。候选格式续补不重复已保存键；正常结束的 `{}` 表示无新增，不清空前缀。供应商明确标记截断时，未知候选集合不能仅凭 `{}` 宣称扫描完整，继续拆小范围或报告 partial。输出溢出拆分保留有效候选，子请求携带本轮类型内的 `saved_entity_keys`；被中断候选的属性仍需继续扫描。缺项、损坏行和终态诊断仍保留，不将逐行恢复等同于语义核验通过。

算法聚合结果的 `attempts` 与 `run_trace.attempts` 记录 `recovered_items`、`rejected_records`、`recovery=jsonl_valid_records`，核验另记录 `missing_item_ids`；Backend 单切片结果仍使用压缩后的 attempts，保留图、partial 状态与错误信息。这些恢复记录仍需经过后续证据核验；恢复条数不等于最终接受事实条数。合法但重复/冲突的完整实体记录由既有归并及核验处理，不凭代码拼造属性事实。

## 长文本请求预算

- `KG_EXTRACT_V31_WINDOW_CHARS=2000`：上游切片内部的请求窗口，重叠 100 字符（小窗口不超过四分之一）；不改上游 chunk ID，证据偏移回映原切片。所有字符都被覆盖，不再使用 repair 的 `[:8000]` 静默截断。
- `KG_EXTRACT_V31_MAX_INPUT_BYTES=48000`：完整序列化消息的上限，含 System、skill、本体、元数据、来源和累计状态。UTF-8 字节数用作保守 token 上界，并取请求/环境 `max_input_tokens` 的较小值，另留 2048 字节重试空间。
- 窗口还参考模型输出 token 上限；单次超时、无可恢复记录的输出截断或上下文超限会拆分来源/类型后重试，最多递归 12 层；文档总 deadline 耗尽后不再发起调用或递归拆分。大本体按类型分批访问全部允许类型，不因文本未命中词面提示而删掉某类。
- 累计属性及其证据本身超过最小请求预算时，明确返回 `LLM_INPUT_BUDGET_EXCEEDED` 并保留已有事实，不截断证据、不无限重试。不能保证任意大实体或任意小模型上下文均能完整抽取。
- 按请求窗口并发，单个超长切片也能使用配置的 worker 数；惰性生成窗口，至多预提交 `2 * max_workers` 个任务。完整请求和模型回答仅保留前 `KG_EXTRACT_V31_TRACE_CALLS=32` 次。其余调用保留输入字节数、耗时、状态及 usage，避免长文诊断信息无限复制输入输出。


调度器的并发等待、QPM 等待及重试退避都受文档 deadline 限制；取得调度名额后、模型/修复回调返回后再次检查，迟到结果不按成功接受。任意自定义同步 LLM 或回调的内部执行仍需其自身实现调用超时。模型提供方异常只保留分类后的诊断信息，不将原始异常中的认证头、请求体写入结果或日志。

## 维护领域 Skill

### 2. 用户维护哪些文件

按本轮范围要求，全部实现及默认技能都放在 v3.1 内：

```text
algorithm/knowledge_extract/v3_1/skills/
  official_document/SKILL.md
  rule/SKILL.md
  trouble/SKILL.md
```

三份文件分别对应公文、规则和故障检修；公文技能包含表单规则。正式入口从完整技能目录选择，rule/trouble 可以被选择，即使兼容文档分类仍为 generic。标准暂不提供 skill。它们是应用运行资产，不需要安装到 Codex。

三份技能的 `description` 描述典型类型、关键字段及排除边界，当前版本为 `official_document@11`、`rule@6`、`trouble@6`。共享领域判据放在 `rules:semantics`，删除样本答案式示例、公文类型的默认互斥及规则属性必须不同值等限制；核验只装配 `all/semantics`，生成与修复操作保留各自阶段段。运行时使用调用方本体，不读取 benchmark 或 golden。一次请求处理同领域文件，选中规则段全请求共享。实现与失败边界见[领域 Skill 路由方案](../../../docs/算法/知识抽取V3.1领域Skill路由方案.md)。

默认使用本包的 `skills/`。调用公共入口时可传 `skills_dir="/path/to/skills"` 替换目录；它必须是进程实际可读路径。没有新增环境变量或修改根配置。容器源码只读时，在宿主机维护对应源码目录。技能随外部源码交付，不需要重建环境镜像；同一路径文件更新后，新请求读取新内容，已开始请求继续使用已加载内容。

新增技能文件使用 `SKILL.md`（也接受 `skill.md`），维护 name、version、description、stages 和规则正文即可进入选择目录，不必新增固定领域枚举。`route_hints` 仅用于低层兼容预览。调用 `extract_harness` / `extract_aggregate` 时可用 `skill_refs=["rule@6"]` 显式绑定，`skill_refs=[]` 明确仅使用公共规则；标识和版本必须存在于本次技能快照中。这是算法入口配置，不新增 HTTP 请求字段。显式固定旧版本的配置需随技能更新，旧 ref 不会被静默重定向。

### 3. 文件格式

```markdown
---
name: equipment_record
description: 设备维护记录，按设备、工作事项与责任主体识别候选。
version: "1"
stages: [entity, property]
route_hints: [trouble]
---

说明：领域规则由程序按阶段装配，不改写 System、本体、原文或输出契约。

## rules:entity

- 保留原文明确描述的设备与维护事项；不得把日期、编号等标量值单独建实体。
- 类型只使用本体允许的标识。

## rules:property

- 综合同一事项的有关记录补充已接受实体的缺失属性。
- 不得猜测未记录的处置结果。
```

字段约定：

| 字段或规则段 | 含义 |
| --- | --- |
| `name` | 唯一技能 ID，小写字母开头，之后允许字母、数字、下划线、短横线，最长 64 字符。 |
| `description` | 进入选择模型的目录摘要；说明典型本体、适用目标及排除边界。 |
| `version` | 非空字符串，请用引号；语义修改后更新版本。程序另记录真实内容 SHA256。 |
| `stages` | 支持的阶段，从 `entity / property / repair` 选择。漏实体修复组合 entity/repair；属性修复组合 property/repair。 |
| `## rules:all` | 跨该技能所声明阶段适用的规则段。 |
| `## rules:semantics` | 类型边界、字段含义和证据语义，所有声明阶段及核验共享，不放阶段操作指令。 |
| `## rules:entity` 等 | 当前阶段的操作规则；程序组合 all、semantics 与本阶段规则，核验仅使用 all/semantics。 |
| `route_hints` | 可选字符串数组，只用于低层兼容预览；正式入口的语义选择不受 generic/simple 限制。 |

二级 `rules:` 标题是规则段边界。其它说明文字只供维护者阅读；只有适用规则段正文会进入抽取 User。技能目录不存在、为空、缺少对应类型/阶段时返回空策略，无需模型规划；原文、本体和输出契约继续传给抽取模型。空规则段、重复段、无效元数据、重复 ID 或跨目录符号链接仍明确报配置错误，不能伪装成空抽取结果。

### 4. 请求内只编译一次

先选择精确技能版本，再预编译各阶段规则；各阶段按现有消息契约装配适用规则段，all 段只发送一次。选择模型不编写或改写领域规则。

不发送 read_skills / assemble 工具轮次；默认发送一个独立的 skill_selection 结构化请求，有界重试复用相同输入。所有切片、批次及后续阶段复用已固定的策略，新请求读取新快照。

审计 mode 为 `request_skill_selection`，plans 只有一条请求级记录，包含选择状态、来源、标识、目录摘要、原文采样范围、固定文件摘要及各阶段规则段；calls 和 attempts 记录真实选择调用与失败。正常 no_match 使用公共规则；歧义、超时、格式或加载失败会终止抽取并保留 failed 状态，不退回 generic 后伪成功。选择复用已有调度器、文档 deadline 和输入预算；目录与本体无法放入预算时明确失败，不截断本体。

### v16：动态提交、延迟重试与核验队列

`task_runtime.py` 在请求内用协程协调依赖，线程只执行一次模型尝试。生成、补全和核验共用配置的 worker 数；兼容现有同步入口及 ASGI 中的调用。完成事件立即补交后续任务，返回实体和诊断仍按稳定顺序合并，同一实体的来源窗口按顺序推进。请求级 Skill 选择和实体发现/聚合的必要边界保留，不把未发现的同名来源假定为不存在。

属性批次按同类型、同来源窗口和同任务合并；批次完成后立即推进对应实体，不等待整轮。核验优先级采用有界轮转，避免生成饥饿。复用已有 `request_runtime.QuotaPool` 和服务端供应商配置；不增加外部端点、密钥存储或新依赖。限流池仍是进程内共享，多进程总配额未在本轮实现。

重试等待使用协程定时，不占模型 worker；暂时请求失败使用有界退避，读取数字 `Retry-After`，格式损坏只处理剩余项。`KG_EXTRACT_V31_MAX_CALLS` 默认 512，按整个文档统计各阶段、重试和拆分；耗尽时记录 `call_budget` / `LLM_CALL_BUDGET_EXCEEDED`，保留已有事实与原 partial/failed 契约。文档 deadline 仍由既有请求适配器控制。

核验先按实际条数上限组批，再按完整输入预算拆小。只有相同来源 ID、原始偏移、上下文、候选值、本体及规则的明确 yes/no 可在同一请求内复用；不复用 uncertain、调用失败或跨请求回执。所有属性已经核验且来源扫描完成时，跳过纯邻片重扫。未消解冲突再发起一轮受预算约束的定向属性修复，只提交原实体的冲突字段与完整冲突证据；越界提案拒收，新值仍须独立核验，失败不转为成功。
