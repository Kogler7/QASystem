# 知识抽取 V2.2 抽取逻辑

更新时间：2026-10-12。包路径是 `algorithm.knowledge_extract.v2_2`，运行时选择 `KG_EXTRACT_ALGO_VERSION=v2.2`。本文描述**当前代码**，不是待实施方案。

关系阶段按 [长文档关系抽取方案](知识抽取V3.1长文档关系抽取方案-20261012.md) 落在 v2.2：实体和属性流程保留，关系不再做切片内实体两两枚举。v3.1 仍是实体主流程，没有按该方案改关系抽取。

在不改实体抽取的前提下，关系阶段已加一轮**压多抽、保召回**门禁（弱共现跳过、签发/适用角色门禁、引文端点核对）。对照评测见第 7、8 节。

## 入口与边界

```python
from algorithm.knowledge_extract.v2_2 import extract
from algorithm.knowledge_extract.v2_2.chunk_context import ExtractionChunk

result = extract(
    ontology=ontology,
    chunks=[ExtractionChunk(chunk_id="chunk-0", text=chunk_text)],
)
```

算法只消费上游已经解析、切分好的 `ExtractionChunk`。它不接收整篇 Markdown，也不改 chunk 文本、chunk ID 或 `__source_range`。关系阶段里的句子和表格行只是 chunk 内的临时证据视图。

公开结果仍是 `entities` 与 `relations`。关系对外保留五个字段：`from_type`、`from_name`、`rel_type`、`to_type`、`to_name`。`rel_type` 使用本体里的原始标识，例如 `hasSubRule`，不是提示词里的规范名 `hassubrule`。

## 主流程

```text
ontology + chunks
  → 编译本体、建立上下文、解析文档路由
  → Pass 1：逐片抽取实体候选
  → 实体入池、合并
  → 确定性补充：文档实体、编号标题、公文结构单元、标准语义
  → pre-relation 候选过滤
  → 属性补全（身份已冻结，只补缺失属性）
  → 关系阶段：出现索引 → 签名召回（含角色门禁）→ Clef 预判 → 小批分类（含引文端点门禁）
  → 关系入池（同一事实的不同引文都保留）
  → 确定性组装：文档关系、层级、结构单元、标准语义、复合元素
  → post-relation 过滤
  → 校验；可修复问题最多两轮修复
  → mapping 评分，组装 graph / triples
  → 输出 entities / relations
```

领域差异来自本体指纹和 chunk 文本解析出的路由：`generic`、`official_document`、`standard`。调用方不传文档类型。

## 1. 编译本体与文档路由

`ontology_compiler` 解析类、属性、继承、关系签名、identity 和复合元素，得到 `ExtractionPlan` 与 JSON Schema。严格模式下编译错误直接失败；宽松模式把告警留在结果里。

`resolve_document_route` 根据本体类和文本决定路由，并带上对应提示词扩展。后续实体、属性和关系调用都使用同一条路由。

## 2. 实体候选

每个 chunk 单独做实体抽取。模型返回类型、名称、表面形式和证据。程序把能在原文中定位的 mention 记到实体上；规范名称仍在 `name`。

候选进入 `CandidatePool` 后按类型、范围、identity、别名和指代合并。合并时 mention 去重累加，证据按 span 追加，不互相覆盖。

## 3. 确定性补充

关系召回之前，程序先补上不依赖关系模型的实体：

- 文档封面和规范性引用中的文档实体。
- 编号 Markdown 标题。
- 公文路由下，正文里的结构单元（条、款等）。处理单不产生正文单元。这些实体的来源标记是 `official_structure`。
- 标准路由下的标准语义实体。

随后 `CandidateSelector.pre_relation` 拒绝无法映射到本体、以及没有文本支撑的候选。属性补全只允许给已经接受的实体填本体中缺失、且当前 chunk 能引用的属性。这一步之后实体身份和类型冻结，关系阶段不再改名或合并实体。

## 4. 关系阶段（当前实现）

入口是 `candidate_generation.relation_pass`，实际执行在 `relation_extraction.run_relation_stage`。没有可判断的关系签名时不调用模型，并记 `RELATION_NO_SCHEMA`。

关系阶段**不删实体、不改实体名**。端点一律来自上游 `accepted_entities()`；精度优化只发生在「签不签名进召回」「候选建不建」「正例引文收不收」三层。

### 4.0 阶段总览

```text
accepted_entities
  → build_relation_index          # 表面形式落证据单元
  → active_signatures             # 去掉结构边 + RELATED_TO
  → recall_candidates             # local / anchor / adjacent / cross_reference
        └─ _add → _role_gate      # 仅 ISSUED_BY / APPLIES_TO
  → Clef 预判（可选）              # 高置信否丢掉；高置信正例仍过引文门禁
  → 小批 LLM 分类（≤32）
        └─ supported → _bind_quote → _quote_covers_endpoints
  → 按 (from, rel, to, quote) 去重后入池
```

日志一行概括规模：`关系阶段: 候选=… 待模型=… 预判落地=… 未定位实体=…`。

### 4.1 出现索引

`build_relation_index` 只索引已接受实体。表面形式取规范名、mention 和证据引文，长度 2 到 180。每种形式在该实体所属文档的切片里查找，并落到包含它的证据单元上。

证据单元的切分顺序是：能解出至少两行的 JSONL 记录，否则管道表格行，否则句子，再否则保留整段非空文本。视图记录原 chunk 内的起止位置。

文档范围：

- 所有切片都没有 `document_id` 时，整批视为同一份文档，范围名是 `document`。
- 切片带了 `document_id` 时，按文档分开。
- 同一请求里既有明确文档、又有无法归属的切片时，无归属切片各自隔离，并告警 `RELATION_DOCUMENT_SCOPE_UNSUPPORTED`。

找不到原文位置、又不是文档锚点的实体记入覆盖缺口，只写日志，不因此中断抽取。文档锚点是 `source=document_anchor` 的实体，即使当前句没有它的字面，也可以和该句里出现的另一端配对。

相邻切片由 `local_previous`、`local_next` 和 `same_section` 决定。两边都有 `section_id` 且不相同，则不是邻居；任一边缺失时退化为按文档内距离判断。

### 4.2 哪些关系交给模型（签名过滤）

`relation_candidates.active_signatures`：本体签名先去掉结构组装已经负责的边和弱共现边，再按关系标识和两端类型去重。

跳过集合：

```text
skip = withheld_relation_tokens(route.kind) ∪ _WEAK_RELATION_TOKENS
     = 结构边黑名单 ∪ {relatedto}
```

具体规则：

| 类别 | 行为 | 原因 |
| --- | --- | --- |
| 结构边（全路由） | 跳过，例如 `hasPart`、`evidencedBy`、`hasClause` | 由确定性组装器按位置/跨度建边，模型再抽会重复 |
| 标准路由封面/定义边 | 额外跳过，例如 `issuedBy`、`defines`、`cites` | 标准组装会直接建这些边 |
| 公文 / 通用路由的封面、定义边 | **仍交给**关系分类 | 组装器不负责这些语义边 |
| **`RELATED_TO`（规范名 `relatedto`）** | **一律跳过** | 评测中几乎全是共现多抽；见 `_WEAK_RELATION_TOKENS` |

模型提示词里用规范名（如 `hassubrule`）；入库时 `rel_type` 用本体原始标识。

### 4.3 召回：四类候选，不是全文两两组合

`recall_candidates` 为每个「源实体 + 关系签名 + 尾实体 + 证据片段」生成一条候选。候选 ID 是 `c-` 加内容哈希前 12 位。自环不生成；中间隔着一行或一句、又没有条款号的实体对不生成。类型匹配沿父类展开。

| `scope_kind` | 何时生成 | 证据片段 |
| --- | --- | --- |
| `local` | 同一句或同一表格行里两端都出现，类型符合签名，且通过角色门禁 | 该证据单元 |
| `anchor` | 文档锚点与当前单元里出现的另一端；通过角色门禁 | 当前单元；带 `preserve_on_none` |
| `adjacent` | 相邻单元，两端分别落在边界两侧 | **同片**：两单元之间合成一条连续片段；**跨片**：仅邻居切片保留两个独立片段 |
| `cross_reference` | 当前单元写了「第 N 条」这类明确条款号 | 引用单元 + 最多 3 个被引用片段（已在邻接窗口的不再补） |

**不收缩**跨片邻接与条款引用——这两类直接服务召回。精度主要靠后面的角色门禁和引文门禁。

### 4.4 角色门禁（召回时，仅两条签名）

实现：`relation_candidates._role_gate`，在 `_add` 建候选前调用。  
**只作用于**规范名 `issuedby` / `appliesto`；其它签名一律放行，避免误伤召回。  
过滤依据是「目标实体名 + 当前证据文本」，**不是**删实体。

#### `ISSUED_BY`（谁签发 / 印发）

| 步骤 | 规则 |
| --- | --- |
| 拒绝 | 目标像联系人栏短署名（见下） |
| 接受 | 目标名含「办公室 / 办公厅 / 秘书处」 |
| 接受 | 原文含「签发 / 印发 / 来文单位 / 发文 / 发布」，且目标**不是**「各…公司/企业/单位」类收文对象 |
| 否则 | 拒绝（避免文档锚点与任意组织共现就建签发边） |

#### `APPLIES_TO`（适用对象）

| 步骤 | 规则 |
| --- | --- |
| 拒绝 | 目标像联系人栏短署名 |
| 拒绝 | 目标是办公室 / 办公厅 / 秘书处（签发主体不当适用对象） |
| 接受 | 目标名含「各 / 子公司 / 所属 / 单位 / 部门 / 企业」 |
| 接受 | 原文含「主送 / 抄送 / 报送 / 适用于 / 贯彻执行 / 落实」 |
| 否则 | 拒绝 |

#### 联系人噪声 `_looks_like_contact`

- 名称本身含「联系人 / 联系电话」→ 视为联系人。
- 否则：证据文本出现「联系人 / 联系电话 / 电话：」等栏目标记，且名称长度为 2–16、又不含办公室/各/子公司/集团有限公司等组织线索 → 视为短署名（如「信息公司张振威」）并拒绝挂到签发/适用边上。

### 4.5 Clef 预判

Clef 默认关闭。`clef=False` 或没有 `enabled` 时整段跳过。启用时，按证据片段分组，对片段文本做封闭选择：

- 高置信否定 → 不再送给生成模型。
- 高置信正例 → **仍须**引文落在候选片段内，并通过第 4.6 节端点门禁后才直接落地。
- 其余 → 进入生成模型。

Clef 看的是证据片段，不是整片 chunk。服务失败、超时或置信度不够时，候选回到生成模型，不当成否定。

### 4.6 小批分类与引文端点门禁

待判定候选按证据片段的 `(chunk_id, start, end)` 分组。同一组一次调用，单次最多 32 个候选；输出预算更紧时由 `output_batch_size(..., tokens_per_item=96, ceiling=32)` 再缩小。32 是单次上限，不是一篇文档的关系总数。

单个证据窗口的字符数超过 8000 时不发送，告警 `RELATION_INPUT_BUDGET`。

模型对每个 `candidate_id` 返回：

| status | 含义 |
| --- | --- |
| `supported` | 必须给出本次某个片段中的逐字引文，且引文要能支持该关系，不能只因为两个名称共现 |
| `not_supported` | 本组证据不支持；不表示整篇没有该边，也不擦掉其它窗口的正例 |
| `insufficient_evidence` | 指代不清、引用目标不在本次片段，或条件无法确定 |

缺了决策的候选重试一次。重试后仍缺失则告警 `RELATION_DECISION_MISSING`，不把缺项当成 `NONE`。

#### `_quote_covers_endpoints`（落地前强制核对）

`supported` 与 Clef 预判正例在 `_bind_quote` 成功后，还必须通过端点字面门禁；失败记 `RELATION_EVIDENCE_ENDPOINT_MISS`（引文不在片段内则是 `RELATION_EVIDENCE_INVALID`），该正例**不入库**。

| 候选类型 | 判定 |
| --- | --- |
| `local` | quote 必须**同时包含**源名和目标名 |
| `anchor` | quote 至少包含一侧名称（文档标题常不在当前句重复） |
| 同片 `adjacent`（合并成**一条**连续片段） | 与 local 相同：quote 须含两端名 |
| 跨片 `adjacent` / `cross_reference` | 两端名须出现在配对片段**并集**中；quote **至少点明一侧**（允许「该部门」指代，保住跨片召回） |

设计意图：挡住「模型只抄到一端名称、另一端靠共现脑补」的同片假正例；对跨片指代放宽，避免误伤召回。

#### 入池与去重

同一事实若来自多个窗口，按 `(from_id, rel_type, to_id, quote)` 去重后分别保留。关系入池时，新的证据 span 追加到已有证据后面，不替换整份证据列表。`RelationResolver` 仍负责签名、端点类型、基数和最终去重。

## 5. 确定性关系与收尾

关系分类之后，程序直接组装不交给模型的边：文档关系、编号标题层级、结构单元关系、标准语义和技术关系，以及复合元素的 `hasSubRule` 成员关系。然后做 post-relation 过滤。

校验失败且问题可修复时，最多两轮修复。启用 Clef 时，跳过 `required_relation` 的生成式修复。最后做 mapping 评分，组装 `raw`、`intermediate_model`、`graph`、`triples` 和覆盖信息。调用方稳定看到的仍是 `entities` 和 `relations`。

## 6. 和旧关系抽取的差别

旧实现在当前切片里按本体签名展开实体对，每批最多约 200 对，再按输出预算拆开。整片或邻居文本会随每个子批重复发送，跨片证据也不能同等落地，缺决策不会单独重试。

现在先用局部文本决定候选是否存在，再用预算决定一批放多少。没有召回到的实体对不会进入模型。结构边仍由组装器产生，所以继续跳过，而不是把黑名单删掉。本轮精度门禁叠在召回与落地两处，不回到笛卡尔积。

## 8. 关系阶段精度优化（2026-10-12）— 修改点清单

**目标**：在不改实体抽取、合并与 `pre_relation` 实体拒绝逻辑的前提下，减少关系多抽，并尽量保住关系召回。

### 8.1 未改动的边界

- 不改 Pass 1 实体 LLM、属性补全、公文结构单元、实体 `pre_relation`。
- 关系索引仍消费全部 `accepted_entities()`；不在关系阶段删实体。
- 不收缩跨片邻接与条款引用的生成条件。
- 不改确定性结构组装器本身（`HAS_PART` / `EVIDENCED_BY` 等仍由组装产生）。

### 8.2 代码修改点（按生效顺序）

| # | 文件 / 符号 | 改动（做什么） | 意图（为什么） |
| --- | --- | --- | --- |
| 1 | `relation_candidates._WEAK_RELATION_TOKENS` + `active_signatures` | 常量 `{"relatedto"}` 并入签名 skip 集合 | 评测里 `RELATED_TO` 几乎全是多抽，直接不召回、不进模型 |
| 2 | `relation_candidates._looks_like_contact` | 联系人栏 + 短署名启发式 | 挡住「信息公司张振威」挂到签发/适用 |
| 3 | `relation_candidates._role_gate` | 仅 `issuedby` / `appliesto` 按目标名与原文线索过滤；其它签名恒真 | 砍锚点/局部共现假签发、假适用，其它关系召回不受影响 |
| 4 | `relation_candidates._add` | 类型匹配通过后调用 `_role_gate`，失败则不建候选 | 门禁发生在召回，减少送模量（053304：待模型 448→312） |
| 5 | `relation_extraction._quote_covers_endpoints` | 见 §4.6 表：local/同片邻接双端；锚点一侧；跨片邻接/条款引用「片段并集双端 + quote 一侧」 | 挡同片共现假正例，保住跨片指代召回 |
| 6 | `relation_extraction._apply_decisions` / Clef 落地 | `supported` 与预判正例均调用端点门禁；失败告警 `RELATION_EVIDENCE_ENDPOINT_MISS` | 可观测；不当成缺决策重试抹掉 |

### 8.3 单测（`tests/test_relation_stage.py`）

- `test_related_to_is_not_recalled`：弱共现边不进候选。
- `test_issued_by_keeps_office_and_skips_recipients`：办公室签发保留；收文对象 / 联系人拒绝。
- `test_quote_must_cover_both_endpoint_names`：同片引文只含一端名时不入库。
- 原有同句多签名、跨行表格、跨片邻接、条款引用、批上限等用例继续约束召回不被误伤。

### 8.4 效果与残留风险

| 项 | 结论 |
| --- | --- |
| 已验证（official_01） | 条数 ↓、P ↑、R 未掉（略升）、F1 ↑；`RELATED_TO` 清零 |
| 召回风险 | 真 `RELATED_TO` 黄金边会漏（当前 official 金标几乎不依赖）；真签发方若名称不含办公室且原文无印发/来文等线索，可能漏 `ISSUED_BY` |
| 仍多的边 | 结构组装边（如 `EVIDENCED_BY`）与其它语义边仍占多抽大头；下一步若继续压量，应分类型看 judge FP，而不是再砍跨片召回 |

复评建议：同一冻结切片 `20261011-221308`，对比关系 P/R/F1 与抽出条数；实体指标应基本不变。
