# 知识图谱驱动的问题求解

<Purpose>
理解用户请求，通过知识图谱检索业务语义与方案，调度原子工具执行并交付可审计的答案。Agent 自主导航与调度，但业务知识必须来自图谱证据——模型记忆只能用于导航决策，不能用于填充业务事实。
</Purpose>

<Use_When>
- 用户提出需要查询数据、分析指标或解决业务问题的请求
- 请求涉及知识图谱中的实体、指标、规则或方案
- 需要将自然语言转化为结构化查询并返回数据/图表/分析结果
- 请求可能跨越多个知识子空间或需要组合多个数据源
</Use_When>

<Do_Not_Use_When>
- 纯闲聊或与业务数据无关的对话 — 直接回复
- 用户明确要求使用特定工具且不需要图谱导航 — 直接调用工具
- 简单的单步查询（如"列出所有表"）— 评估是否需要完整的问题求解流程
</Do_Not_Use_When>

<Why_This_Exists>
LLM 容易在业务场景中"幻觉"——用训练数据中的常识补全业务规则、指标口径或方案步骤。本 skill 通过强制图谱证据溯源，确保：
1. 业务概念和指标口径来自图谱，而非模型记忆
2. 解决方案来自图谱中的 SolutionClass，而非 Agent 自行设计
3. 每个关键结论都能追溯到图谱节点和工具返回
4. 知识缺口被显式记录，而非被静默填补
</Why_This_Exists>

<Integration>
本 skill 是三层流水线的编排层，内部调度以下两个子 skill：

```
用户请求
  → [阶段一] ProblemFrame（自行理解）
  → [阶段二] semantic-align（语义对齐与图谱检索）
  → [阶段三] 证据门检查（刚性门控）
  → [阶段四] plan-execute（方案实例化与执行）
  → [阶段五] 交付答案
```

**契约**：
- 阶段二产出 `GraphContext`（包含 knowledge_space、aligned_entities、solution_class、resource_nodes、evidence_ledger、gaps）
- 阶段四消费 `GraphContext`，产出 `ExecutionReport`
- 本 skill 负责门控判断和最终交付，不直接操作图谱工具

**何时跳过子 skill**：
- semantic-align 可跳过：当前会话已有缓存的 GraphContext 且用户未改变问题域
- plan-execute 可跳过：用户仅要求解释方案而不需要执行
</Integration>

<Execution_Policy>
- 按五阶段推进，但允许根据证据回退和迭代
- 每个阶段的输出是下一阶段的输入，禁止跳过阶段
- 证据门是刚性检查点：未通过不得进入执行阶段
- 遇到知识缺口时显式记录，不要静默填补
- 歧义只在会改变知识空间选择或指标口径时才询问用户；其他情况带假设前进并在结果中披露
- 工具返回 envelope 必须检查 `code == 0`；失败信息必须保留
</Execution_Policy>

## 核心约束

你可以自主理解用户意图、决定探索顺序和选择工具，但不得把模型记忆或常识当成业务知识。以下内容必须来自知识图谱：

- 业务概念及其定义、别名和边界；
- 实体、属性、关系、指标口径和业务规则；
- ProblemClass、SolutionClass、方案步骤及资源要求；
- 数据源、表、字段、SQL 模板和可视化要求。

用户输入可作为目标与约束；工具返回可作为运行证据。你的推断只能用于选择下一步动作，不能替代图谱证据。图谱没有给出的内容必须标记为"知识缺口"，不得补写成事实。

<Steps>

### 阶段一：建立 ProblemFrame

Agent 自行理解请求，不调用独立意图识别工具。生成内部结构：

```json
{
  "raw_request": "用户原始请求",
  "goal": "要解决的问题",
  "target_objects": ["对象或指标"],
  "constraints": {"时间": "", "范围": "", "其他": []},
  "expected_output": "答案、数据、图表或文件",
  "search_terms": ["用于图谱链接的最小关键词"],
  "ambiguities": []
}
```

**歧义处理规则**：
- 仅在歧义会导致不同知识空间、不同指标口径或不可逆操作时询问用户
- 例如："销售额"有两个不同口径的指标 → 消歧；"最近"可以是7天或30天但不改变方案选择 → 带假设前进
- 带着明确假设继续时，在 `ambiguities` 中记录并在结果中披露

**自检**：
- [ ] search_terms 是否精炼（2-5个高信息密度词）？
- [ ] 歧义是否已正确分类（需消歧 vs 带假设前进）？

### 阶段二：图谱语义与方案获取

执行 `semantic-align` 的流程。必须至少尝试：

- `qasystem-tools__locate_knowledge_space`
- `qasystem-tools__link_entities`
- `qasystem-tools__query_entity_properties`
- `qasystem-tools__search_graph`

目标不是机械走固定关系名，而是从图谱实际返回的节点、关系和属性中找到：

- 与请求对应的标准实体或术语；
- 适用的 ProblemClass；
- 与 ProblemClass 相连的 SolutionClass；
- SolutionClass 的步骤、输入、输出、约束和资源要求；
- 执行所需的数据、规则、模板或组件节点。

**回退策略**：
- 知识空间定位失败 → 调用 `get_all_subspaces`，列出候选让用户选择
- 实体链接无高置信度结果（全部 score < 0.5）→ 向用户确认关键词含义
- 3 跳探索后仍未找到 SolutionClass → 记录缺口，不继续无限探索

### 阶段三：证据门检查

进入执行前必须确认以下五项（刚性门控，缺一不可）：

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 1 | 知识空间 | 已定位可回答的空间，或定位失败已明确记录 |
| 2 | 实体链接 | 关键术语至少有一个可信图谱实体（score ≥ 0.5 或有合理选择理由）|
| 3 | 方案来源 | 业务方案来自可追溯的 SolutionClass 或等价方案节点 |
| 4 | 资源完备 | 方案所需资源已找到，缺失项已在 gaps 中列出 |
| 5 | 无伪造 | 没有把模型自行设计的步骤伪装成图谱方案 |

若缺少 SolutionClass，不得自行设计一个业务方案。可以继续探索图谱、请求用户补充，或输出"知识图谱尚未沉淀该方案"。

**证据门自检**：
- [ ] 每个通过项能否指出具体的图谱节点 ID 或证据路径？
- [ ] 如果有任何项标记为"缺失"，是否已在 gaps 中记录？

### 阶段四：方案执行与验证

执行 `plan-execute` 流程。Agent 可以决定并行或串行、重试方式和具体原子工具，但必须保持图谱方案的目标、约束和依赖关系。任何调整都要记录原因。

**执行中的回退**：
- 工具连续失败 3 次 → 停止重试该步骤，标记为 failed，执行其他独立步骤
- 前序输出不满足下一步要求 → 回退到参数绑定或回到阶段二补充图谱信息
- 关键资源在 gaps 中且影响执行 → 标记步骤为 blocked

### 阶段五：交付答案

优先直接回答用户问题，同时保留可审计性：

```text
[结论或交付物]

依据：关键实体/关系/方案节点与必要的数据结果
执行：实际采用的图谱方案及完成情况
假设：仅列出确实使用的假设
知识缺口：图谱缺失、工具失败或证据不足之处
置信度：高/中/低，并说明依据
```

**置信度判定**：
- **高**：知识空间、实体、SolutionClass、资源全部有图谱证据，所有步骤执行成功
- **中**：关键要素有图谱证据，但有次要资源缺失或部分步骤失败
- **低**：SolutionClass 缺失（自行设计替代路径并已声明）、关键工具失败、或主要证据来自推断

禁止静默回退、伪造图谱命中、用常识填补业务字段，或在证据不足时给出确定性结论。

</Steps>

<Anti_Patterns>
以下是必须避免的常见错误模式：

1. **跳过证据门直接执行**
   - 错误：图谱探索未找到 SolutionClass，Agent 自行设计 SQL 方案并声称"根据知识图谱方案执行"
   - 正确：报告"知识图谱尚未沉淀该方案"，询问用户是否接受手动指定的查询路径

2. **用模型记忆填充业务字段**
   - 错误：resource_nodes 中没有表的字段信息，Agent 从训练数据中补出字段名
   - 正确：调用 describe_table 获取真实字段，或记录为知识缺口

3. **图谱空结果解释为"不存在"**
   - 错误：search_graph 返回空 → "该实体没有关联指标"
   - 正确：search_graph 返回空 → "本次未检索到关联指标"，可尝试不同关系类型或更大深度

4. **静默回退**
   - 错误：方案执行失败后，Agent 用一段笼统的文字回复代替实际数据
   - 正确：报告执行失败，说明失败原因和已尝试的参数，列出可用的替代路径

5. **无限探索**
   - 错误：3 跳后仍无 SolutionClass，继续扩展搜索
   - 正确：3 跳后仍未找到 → 记录缺口，报告当前已知信息，询问用户是否缩小范围
</Anti_Patterns>

<Examples>
<Good>
用户："上周华东区销售额是多少？"
Agent:
  1. ProblemFrame: goal="查询华东区上周销售额", search_terms=["华东区", "销售额"]
  2. locate_knowledge_space → 定位到"销售统计"子空间
  3. link_entities → "华东区" → 实体 ID 123, "销售额" → 指标 ID 456
  4. search_graph → 找到 SalesQuerySolution，含 SQL 模板和所需字段
  5. 证据门：SolutionClass、数据源、指标口径均有图谱来源 ✓
  6. plan-execute → execute_sql → 返回 1,234,567 元
  7. 交付："华东区上周销售额为 1,234,567 元。依据：实体[华东区#123]、指标[销售额#456]、方案[SalesQuerySolution#789]"
</Good>

<Good>
用户："分析一下华北区的库存周转情况"
Agent:
  1. ProblemFrame: goal="分析华北区库存周转"
  2. locate_knowledge_space → "库存分析"子空间
  3. 发现两个候选指标："库存周转率"和"库存周转天数"，口径不同
  4. 向用户确认需要哪个指标（因为会影响后续查询方案选择）
  5. 用户选择"库存周转率"→ 继续执行
</Good>

<Good>
Agent 在证据门阶段发现图谱中没有对应的 SolutionClass。
Agent: "当前知识图谱中尚未沉淀「库存周转分析」的标准方案。我可以：
  1. 基于已找到的指标[库存周转率#789]和实体[华北区#456]，尝试直接查询原始数据供您参考
  2. 或者由您指定需要的具体分析维度
  请问您倾向哪种方式？"
</Good>

<Bad>
用户："今年的利润增长怎么样？"
Agent: "今年利润增长15%，表现良好。"
Why bad: 没有通过图谱验证指标口径和数据源。15% 是模型编造的。
</Bad>

<Bad>
Agent 在证据门阶段发现图谱中没有对应的 SolutionClass，于是自行设计了 SQL 查询方案，声称"根据知识图谱方案执行"。
Why bad: 不得自行设计一个业务方案冒充 SolutionClass。应报告知识缺口。
</Bad>
</Examples>

<Escalation_And_Stop_Conditions>
- **知识空间定位失败**: 调用 `get_all_subspaces` 列出候选让用户选择；仍无法定位时报告"无法确定知识领域"
- **实体链接无高置信度结果（全部 score < 0.5）**: 向用户确认关键词含义或提供候选实体列表
- **图谱中无 SolutionClass**: 报告"知识图谱尚未沉淀该方案"，不自行设计；可提供基于已找到实体的替代路径供用户选择
- **方案所需资源缺失**（如表不存在、字段找不到）: 记录缺口并报告，不猜测替代方案
- **同一工具连续失败 3 次**: 停止重试该步骤，报告失败原因和已尝试的参数，继续执行其他独立步骤
- **用户请求存在歧义且会影响结果正确性**: 向用户消歧后再继续
- **证据门 3 次迭代仍未通过**: 报告当前已知信息和缺口，请求用户指导
</Escalation_And_Stop_Conditions>

<Final_Checklist>
- [ ] ProblemFrame 已建立，search_terms 精炼，歧义已记录或已消歧
- [ ] 知识空间已定位（或定位失败已如实记录）
- [ ] 关键术语有至少一个可信图谱实体链接
- [ ] 证据门五项全部通过（或未通过项已明确记录）
- [ ] 方案执行完成（或受阻原因已记录在 ExecutionReport 中）
- [ ] 最终输出区分了图谱事实、运行结果、推断和知识缺口
- [ ] 置信度有明确依据
- [ ] 没有用模型记忆填充任何业务字段、指标口径或方案步骤
- [ ] 没有把自行设计的方案伪装成图谱方案
</Final_Checklist>
