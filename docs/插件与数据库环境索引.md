## 插件与知识沉淀的关系

本地 VSIX 中，`knowledge-editor` 发起 `previewIngestion`，由 `knowledge-resource` 组装并向应用服务发送 `POST /knowledge-map/ingestions/preview`。请求包含 `resource_ids`、`resource_types`、解析器与切片配置；其中 `resource_types` 是所选**元类 UID** 列表，插件并未在该请求中发送 PlantUML 本体全文或已经切好的 `chunks`。预览后，插件以 `POST /knowledge-map/ingestions/confirm` 确认入库。应用服务是否以及如何把元类 UID 编译为抽取本体，需要按其实际服务实现和联调结果核验，不能仅由 VSIX 推断。

插件的 `chunk_type=0` 表示语义切分；本仓库 `algorithm/knowledge_pipeline/chunking.py` 中的 `chunk_type=0` 表示递归切分，`4` 才表示语义切分。跨服务对接应使用明确的参数映射与切片结果校验，不能直接复用整数值。详见 [应用服务 API 索引](应用服务API索引.md#知识沉淀接口契约) 和 [算法 API 迁移说明](算法API迁移说明.md)。

## 数据访问边界

Attu 和 Neo4j Browser 用于人工查看，不构成 QASystem 的应用连接配置。QASystem 通过 `APPLICATION_SERVICE_URL` 调用应用团队服务；`FILE_SERVICE_URL` 只作旧配置回退。除已保留的 SQL 兼容通道外，不在算法或 MCP 中新增直连 Neo4j、Milvus 或 Elasticsearch 的调用。外部服务端点统一登记在 [`external_services/application.py`](../external_services/application.py)；能力未开通时按现有错误协议显式失败。详见 [外部应用服务与鉴权说明](外部应用服务与鉴权说明.md)。

## 核验方式

1. 在 VSIX 交付目录确认插件版本；插件状态以实际安装版本为准。
2. 在应用服务 [在线接口文档](https://zhongche.zhouhao.work/docs) 查看当前请求模型和鉴权要求；文档可能随服务更新。
3. 使用获授权的账号在 Attu、Neo4j Browser 中核对预览、确认入库后的数据。不要把登录密码或令牌粘贴到工单、测试产物或提交记录。
