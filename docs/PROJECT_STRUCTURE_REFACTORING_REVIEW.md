# QASystem 项目结构重构审查计划

> 状态更新：当前实现已取消单文本向量化 HTTP 接口，保留知识沉淀、批量向量化和置信度更新三个业务接口；知识沉淀编排已迁移到 `backend/app/services/`。下文保留为历史审查记录。

## 1. 文档目的

本文档用于在 QASystem 项目结构重构前，向历史维护者、服务负责人、部署负责人和调用方确认影响范围。

本文档不描述具体执行命令、开发排期或文件迁移步骤，重点回答以下问题：

1. 项目未来保留哪些对外能力。
2. 现有目录和服务分别计划保留、合并、重构还是删除。
3. 哪些外部系统、脚本或部署可能受到影响。
4. 各历史维护者需要确认什么。
5. 满足哪些条件后，代码才可以被安全删除。

任何被标记为“待确认”或“条件删除”的资产，在责任人完成确认前均不得删除。

---

## 2. 重构背景

当前仓库同时包含以下多种形态：

- 面向旧前端的完整 FastAPI 后端。
- 四个知识沉淀 HTTP 接口。
- 多组可独立启动的算法应用。
- 多套 MCP Server 实现。
- `agentcode` Agent 与 MCP 客户端运行时。
- 训练、实验、演示、初始化和临时运维脚本。
- 多份依赖、配置和部署说明。

这些能力在不同阶段由不同维护者加入，当前缺少统一的服务边界。主要风险包括：

- 同一路径存在多个 HTTP 实现。
- MCP 同时使用多种 SDK 和启动方式。
- 算法模块通过修改 `sys.path` 相互导入。
- 配置默认值分散，外部服务地址可能互相覆盖。
- 无法仅通过目录名称判断代码是否仍被生产调用。
- 删除历史目录时容易破坏隐式依赖。

本次重构目标是明确产品边界，并将代码结构调整为可验证、可维护、可安全裁剪的形态。

## 3. 拟定产品边界

### 3.1 保留的 HTTP 业务接口

拟仅保留以下四个对外业务接口：

| 能力 | 方法 | 路径 | 认证 | 目标状态 |
| --- | --- | --- | --- | --- |
| 统一知识沉淀 | POST | `/api/knowledge/precipitation` | 无 | 保留 |
| 单文本向量化 | POST | `/api/component/nl2cypher/text-to-vector` | 无 | 保留 |
| 多文本向量化 | POST | `/api/component/nl2cypher/text-to-vectors` | 无 | 保留 |
| 图谱置信度更新 | POST | `/api/component/kg-update/calculate-confidence` | 无 | 保留 |

基础设施健康检查 `/health` 继续保留，但不计入业务接口数量。

四个接口的请求与响应契约以接口协议和自动化契约测试为准。未经接口变更评审，不应改变路径、字段名称、默认值和成功响应结构。

### 3.2 保留的 Agent 能力

`agent/` 保留，定位为：

- Agent 运行时。
- MCP 客户端。
- 工具发现与调用管理器。
- 技能加载与执行环境。

`agentcode` 不再承担重复业务实现。业务能力应由统一服务层或统一 MCP Server 提供。

### 3.3 保留的 MCP 能力

现有 MCP 能力原则上保留，但不再允许每个业务目录自行实现一套 MCP Server。

拟保留并统一评审的工具域包括：

| 业务域 | 当前能力 | 目标归属 | 是否确认仍有调用方 |
| --- | --- | --- | --- |
| 知识 | 知识抽取、知识空间定位 | `mcp_services/domains/knowledge/` | 待确认 |
| 推理 | 意图识别、问题规划、答案生成 | `mcp_services/domains/reasoning/` | 待确认 |
| 数据 | SQL 查询 | `mcp_services/domains/data/` | 待确认 |
| 可视化 | 绘图 | `mcp_services/domains/visualization/` | 待确认 |

所有 MCP 工具统一由一个 Server 注册和启动，`agentcode` 仅连接该统一入口。

## 4. 目标项目结构

目标结构用于说明长期责任边界，不代表所有目录必须一次性迁移完成。

```text
qasystem/
├── backend/
│   ├── app/
│   │   ├── main.py
│   │   ├── api/
│   │   │   ├── precipitation.py
│   │   │   ├── vectorization.py
│   │   │   └── confidence.py
│   │   ├── services/
│   │   │   ├── precipitation.py
│   │   │   ├── document_parser.py
│   │   │   ├── knowledge_extractor.py
│   │   │   ├── vectorizer.py
│   │   │   └── confidence.py
│   │   ├── schemas/
│   │   └── config.py
│   └── tests/
├── algorithm/
│   ├── document_processing/
│   ├── knowledge_extraction/
│   ├── vectorization/
│   ├── confidence/
│   └── common/
├── mcp_services/
│   ├── server.py
│   ├── registry.py
│   ├── config.py
│   ├── domains/
│   │   ├── knowledge/
│   │   ├── reasoning/
│   │   ├── data/
│   │   └── visualization/
│   └── tests/
├── agent/
├── docker/
├── docs/
├── models/                 # 不纳入 Git
└── deploy/                 # 本地交付目录，不纳入 Git
```

目标边界要求：

- HTTP、MCP 和 Agent 调用同一业务服务层，不复制算法实现。
- 算法目录只提供可导入的 Python 包和纯业务函数。
- MCP 工具文件只负责协议适配、参数校验和结果转换。
- 外部服务配置统一进入配置模块，不在算法文件中设置环境变量。
- 业务模块导入时不得创建目录、写文件、连接外部服务或修改 `sys.path`。

## 6. 统一 MCP 目标约束

### 6.1 统一实现

- 使用官方 `mcp.server.fastmcp.FastMCP`。
- 仅保留一个 Server 启动入口。
- 不再混用 `fastmcp.server.FastMCP`、底层 `Server` 和多套自定义启动器。
- 每个业务域可以拥有独立工具文件夹，但不得自行启动 Server。
- 工具注册由中央 `registry.py` 完成。

### 6.2 工具兼容性

每个旧 MCP 工具迁移前必须记录：

- 当前工具名称。
- 描述文本。
- 输入 JSON Schema。
- 输出结构。
- 是否访问模型、数据库、文件系统或网络。
- 当前调用方。
- 超时和错误行为。

如果修改工具名称或参数，必须确认所有 `agentcode` 配置、Prompt、Skill 和外部 MCP 客户端均已同步。

### 6.3 业务层复用

MCP 工具不得直接复制 HTTP 接口实现。目标调用关系为：

```text
HTTP API ─┐
          ├─> 统一业务服务 ─> 算法包 / 外部服务
MCP Tool ─┘
```

## 7. 外部依赖影响

历史维护者需要确认以下外部依赖是否仍由其服务使用：

| 外部依赖 | 当前用途 | 拟定状态 | 待确认事项 |
| --- | --- | --- | --- |
| 文件服务 | 存储原始、抽取和向量 Markdown | 保留 | `/third/files/upload` 契约和鉴权 |
| LLM API | 本体驱动知识抽取、部分 MCP | 保留 | 模型、Base URL、超时和限流 |
| Neo4j | 置信度路径证据、知识空间、可选入库 | 待明确 | `save_to_db` 是否必须实现 |
| Elasticsearch | 置信度文本证据 | 保留或替换 | 索引名称和查询契约 |
| 模型目录 | 向量、MinerU、意图等模型 | 保留、外置 | 哪些模型仍为生产必需 |
| Milvus | 历史意图与向量能力 | 待确认 | 四接口向量化是否真正依赖 Milvus |

外部依赖不得仅因 Compose 中没有对应服务而判定为无用。必须同时检查环境变量、调用日志、服务器进程和外部调用方。

## 8. 配置与部署影响

### 8.1 配置收敛

拟统一以下配置类别：

- HTTP 服务配置。
- 文件服务配置。
- LLM 配置。
- Neo4j、Elasticsearch、Milvus、MySQL 配置。
- 本地模型目录配置。
- MCP Server 配置。
- `agentcode` MCP 客户端配置。

重构后不再允许：

- 在模块导入时覆盖环境变量。
- 在业务代码中硬编码生产密码。
- 同一个配置项存在多个不一致默认值。
- 算法模块自行读取不同位置的 `.env`。

### 8.2 部署形态

部署原则保持：

- 镜像只提供运行环境和依赖。
- 业务代码挂载到 `/app`。
- 模型单独挂载到 `/models`。
- `deploy/` 作为不纳入 Git 的交付目录。

需要由部署负责人确认：

- 统一 MCP Server 与 HTTP 服务运行在同一容器还是独立进程。
- 如果同容器运行，进程管理和健康检查如何定义。
- 如果独立运行，是否需要新增端口、stdio 配置或进程守护。
- 服务器是否仍存在直接进入容器修改代码的操作流程。

## 9. 删除判定标准

一个目录或服务只有同时满足以下条件，才可以判定为安全删除：

1. 不在四个 HTTP 接口的静态和动态依赖链中。
2. 不在统一 MCP 工具的依赖链中。
3. 不被 `agentcode` 的配置、Prompt、Skill 或工具注册引用。
4. 不被部署脚本、计划任务、初始化脚本或运维脚本调用。
5. 不存在外部 HTTP、MCP、命令行或 Python 导入调用方。
6. 不包含需要迁移的数据、模型、配置或业务规则。
7. 原维护者或业务负责人已确认停用。
8. 删除后契约测试、MCP 工具测试和本地启动验证全部通过。
9. 已具备可回退的版本标签或提交记录。

不能仅凭以下理由删除：

- 当前主入口没有显式导入。
- 最近没有 Git 提交。
- 目录名称看起来像测试或临时目录。
- 当前开发机没有启动对应服务。
- Docker Compose 中没有对应服务。

## 11. 风险分级

### 高风险

- 删除仍有外部调用方的 HTTP 或 MCP 接口。
- 修改 MCP 工具名称和输入 Schema。
- 删除 Neo4j、ES、MySQL 或模型相关代码前未确认业务用途。
- 将多套实现合并时改变知识抽取或置信度算法结果。
- 删除历史目录中的初始化、迁移或恢复脚本。

### 中风险

- 合并配置后默认值变化。
- 改变模型路径或部署挂载路径。
- 将 MCP Server 合并后改变进程生命周期和超时行为。
- 精简依赖清单时遗漏延迟导入依赖。

### 低风险

- 删除已确认无调用的旧文档。
- 删除缓存、生成物和本地测试产物。
- 修正目录名称和纯内部导入路径，且测试完整覆盖。

## 12. 审查通过条件

项目结构重构可以进入实际变更阶段，需要至少满足：

- 产品负责人确认四个 HTTP 业务接口为最终范围。
- Agent 负责人确认 `agentcode` 必须保留及其兼容要求。
- MCP 负责人确认需要保留的工具清单。
- 历史模块维护者完成影响确认，或明确记录无法联系及替代验证依据。
- 部署负责人确认新部署和进程边界。
- 数据负责人确认数据库、索引、模型和生成文件的保留策略。
- 四接口契约测试已建立并持续通过。
- MCP 工具列表、Schema 和最小调用测试已建立。
- 候选删除目录均满足删除判定标准。
