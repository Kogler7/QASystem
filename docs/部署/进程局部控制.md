# Backend CPU 进程局部控制

`ops runtime` 管理 Backend 中处理普通任务的 CPU worker。调整数量、排空或重启这些 worker 不会重启 Backend 容器，也不会重启 API 网关。GPU worker、MinerU 引擎、Agent 和独立模型容器尚未纳入这套局部控制。

首次安装这版代码仍需按部署流程更新源码和有效配置版本。容器端口、挂载、GPU 设备授权发生变化时，仍需重新创建对应容器；普通 CPU 进程数量调整不需要重建环境镜像。

## 配置与应用

用 `ops config` 修改“CPU 执行进程数”，可填 `auto` 或 `1–32`。界面用 `[进程]` 标记，实际数量保存在 `runtime-config/config.json` 的 `settings.EXECUTION_CPU_WORKERS`。根 `.env.example` 继续维护版本默认值，旧 `.env` 值只用于迁移，运行时不会回退到容器旧环境变量。

也可以通过受控配置事务修改。创建私有 JSON patch：

```json
{"settings":{"EXECUTION_CPU_WORKERS":"4"}}
```

先查看差异，再以计划的基准版本提交：

```bash
ops config plan --patch cpu-plan.json
ops config apply --patch cpu-plan.json --base-revision 12 --reason "CPU任务积压，增加执行进程" --actor agent
ops runtime apply
```

`12` 必须替换为计划显示的当前版本。配置事务与进程应用分开：保存只更新计划；`runtime apply` 才把 CPU worker 数量调整到该计划。首次启动也读取同一份有效计划，不存在另一套 CPU 数量默认配置。

## 操作命令

```bash
ops runtime status
ops runtime drain
ops runtime restart
ops runtime apply
```

| 命令 | 行为 |
| --- | --- |
| `status` | 查看实际 CPU 进程、排空状态、最近操作及应用版本 |
| `drain` | 停止领取新任务，等待当前任务完成，然后退出全部 CPU worker；网关保留 |
| `restart` | 逐个等待旧 worker 退出后启动替代进程，再按当前计划补齐数量 |
| `apply` | 增加缺少的 worker，或排空多余的 worker；也可补回意外退出的进程 |

命令返回 JSON。`accepted`、`running` 表示仍在处理；`applied` 表示该次 CPU 进程操作完成，不能把它当成模型、Agent 或整个系统的健康确认。`running` 进程状态仅代表进程尚未退出，实际任务消费能力还应结合 worker 心跳和队列观测。

每次变更输出操作编号。断线后需要重试同一次操作时，使用原编号：

```bash
ops runtime restart --request-id 原操作编号
```

同一有效配置版本和同一编号不会重复启动进程。配置版本变更后，旧编号不能用于新的操作；`status` 可查看原操作状态。

## 长任务与故障

排空不会取消当前任务，任务的心跳、资源续期和完成确认继续执行。等待超过内部排空预算时，操作报告失败，并保留仍在执行的进程；不会强杀任务，也不会同时启动一个替代进程。待任务完成后，重新执行 `apply` 或 `restart`。

CPU worker 意外退出会显示失败并记录日志，不再导致网关和其他角色一起退出。先查看任务状态和日志，再执行 `apply` 恢复；已有消费者实例恢复和终态防重复逻辑继续生效。API 或解析引擎的严重故障仍沿用原监督策略，当前不承诺它们的零中断重启。

控制通道是 Backend 容器内的私有 Unix socket，文件权限限制为同一运行用户；ops 通过 `docker exec` 调用，只允许登记的 `cpu` 角色，不接受任意命令、PID 或进程数量。变更数量必须先经过配置事务，不能通过控制命令绕过配置版本。

进程配置读取记录与实际应用事件分开保存。启动以及控制的 `running`、`applied`、`failed` 事件写入现有 `runtime-config/observed/events`，`ops history --json` 可以关联配置版本、操作编号与实际进程。记录只包含操作信息，不包含凭据。
