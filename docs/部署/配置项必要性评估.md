# 配置项必要性评估（2026-10-12）

目前的问题不只是数量多。配置界面直接收录了 `.env.example` 的变量，没有充分区分当前部署需要的参数、旧流程参数和没有接入代码的参数。因此用户会看到一些改了也不起作用的选项，还有一些内部开关被呈现为需要用户决定的配置。

本次检查基于当前源码和 Compose，模板共有 221 个赋值项。检查了消费代码、部署脚本和动态前缀读取。本次没有连接 88 核对运行实例，没有删除配置或改变服务行为。下文是整理建议，不表示迁移已经完成。

## 用户指出的两项

| 配置 | 实际用途 | 建议 |
| --- | --- | --- |
| `QASYSTEM_LOAD_DOTENV` | `backend/app/environment.py` 决定后端是否再次读取仓库根 `.env`。部署环境已经注入变量时，应避免再读另一份文件。 | 保留这一保护机制，但从普通配置页移走。托管启动应自动确定，本地开发才需要覆盖。不能直接删掉 `false`：未注入 `ENVIRONMENT` 时会恢复自动读取。 |

远程推理功能与旧镜像是两回事。`ALGORITHM_RUNTIME_PROFILE=remote-only` 仍有实际消费者；调用远程解析、Embedding 等能力可以沿用统一环境镜像，不需要保留第二种镜像。

`QASYSTEM_LOAD_DOTENV` 的说明也要改：“HTTP 注入环境”不准确，注入环境的是启动进程或 Compose。修改 Compose 注入的 `.env` 值一般需要重新创建容器；单纯重启不能重新读取这份配置。

## 第一批：没有对应功能消费者的项

下面 21 项，在当前受版本控制的生产代码中没有找到对应功能消费者。搜索排除了配置目录、UI、文档和测试中的单纯登记；也检查了已知动态读取方式。这些应先下架，或者在确实需要该能力时补齐消费代码和测试，不能继续作为有效旋钮展示。

| 类别 | 参数 | 问题 |
| --- | --- | --- |
| 抽取思考轮次 | `KG_EXTRACT_THINKING_PASSES`、`KG_EXTRACT_THINKING_MAX_TOKENS` | 模板有说明，实际抽取没有读取这两项。 |
| JEV 服务选择 | `KG_EXTRACT_JEV_PROVIDER`、`KG_EXTRACT_JEV_BASE_URL`、`KG_EXTRACT_JEV_TIMEOUT_SECONDS` | 当前 JEV 配置函数没有接入这些服务选择参数。不能靠修改它们切换常驻服务。 |
| 旧 v3.1 参数 | `KG_EXTRACT_V31_DISABLE_THINKING`、`KG_EXTRACT_V31_CLEF_TIMEOUT`、`KG_EXTRACT_V31_CLEF_MAX_CALLS`、`KG_EXTRACT_V31_SUPPORT_THRESHOLD`、`KG_EXTRACT_V31_ALTERNATE_THRESHOLD`、`KG_EXTRACT_V31_DECISION_MARGIN`、`KG_EXTRACT_V31_RELATION_RETRIES`、`KG_EXTRACT_V31_STRICT_COVERAGE` | 当前实现没有读取。注意 v3.1 的请求、文档超时仍有效，不应一起删除。 |
| Router 开关 | `KG_EXTRACT_USE_ROUTER` | 抽取函数有 `use_router` 参数，但没有读取这个环境变量，修改它不能关闭 Router。 |
| 远程模型限制 | `EMBEDDING_MAX_CONCURRENCY`、`DOCUMENT_PARSE_MAX_CONCURRENCY`、`DOCUMENT_PARSE_MAX_FILE_MB` | 当前远程客户端没有用这些值实施限制。 |
| 资源等待 | `EXECUTION_RESOURCE_WAIT_TIMEOUT_SECONDS` | 当前资源执行代码没有读取该项。 |
| 模型描述 | `VLLM_MODEL_VERSION`、`EMBEDDING_MODEL_NAME`、`EMBEDDING_MODEL_VERSION` | 当前生产功能没有消费这些模板变量。不要与实际使用的远程 `EMBEDDING_MODEL` 混淆。 |

另外，`CONFIDENCE_SBERT_MODEL_PATH` 只被健康检查当作可选目录检查，没有接入模型加载。当前置信度能力调用会明确报未开放。它不应给用户造成“填路径就能启用”的印象。因此这一批共 22 项：21 项无功能消费者，1 项只有目录检查。

## 第二批：旧流程和重复配置

这些项有消费者，但不属于当前推荐流程。建议退出普通配置页，按兼容计划逐步清理。

| 项目 | 建议 |
| --- | --- |
| `QASYSTEM_REMOTE_ENV_IMAGE` 以及 `BACKEND_MEMORY_LIMIT`、`AGENT_MEMORY_LIMIT`、`REDIS_MEMORY_LIMIT` | 当前只在旧 remote-only Compose 使用。清理旧链时一起处理；若统一部署确实需要内存限制，再接入主 Compose。 |
| `CLEF_SOURCE_DIR`、`CLEF_PYTHON` | 旧宿主机 systemd 服务使用，容器部署不需要。兼容说明独立保留，普通容器配置不展示。 |
| `LLM_MODEL_DIR`、`LLM_SERVED_MODEL_NAME`、`LLM_GPU_DEVICE_IDS`、`LLM_BIND`、`LLM_HOST_PORT`、`LLM_GPU_MEMORY_UTILIZATION`、`LLM_MAX_MODEL_LEN` | 旧单模型启动流程使用。当前按模型勾选的界面应把这些值放在对应模型下，不再维护第二份全局单模型配置。 |
| `FILE_SERVICE_URL` | 由 UI 迁移旧值，业务代码只读 `APPLICATION_SERVICE_URL`，普通界面不要展示两个同义入口。 |

本轮已按最新要求删除上述旧入口和同义回退，迁移规则见本文顶部链接。

历史评估：上一轮清理了持久化评测 YAML，但当时应用配置里的 `QASYSTEM_JUDGE_BASE_URL`、`QASYSTEM_JUDGE_MODEL`、`QASYSTEM_JUDGE_ADAPTER`、`QASYSTEM_JUDGE_MAX_TOKENS` 仍在。按“每次评测通过命令行临时配置”的要求，这四个默认项应退出应用配置体系。模板的 judge token 默认值为 1024，评测程序的命令行默认值又不同，留下两处来源容易造成误解。`QASYSTEM_JUDGE_API_KEY` 可以作为可选凭据保留，由评测命令选择凭据变量，界面不显示明文。

## 第三批：保留机制，但不要让用户逐项填写

- Python 导入路径、日志缓冲开关、容器内部运行目录、运行就绪文件路径，是启动约定或内部参数。需要保留，但普通页面不必展示；只有支持自定义布局时才进入高级配置。
- `CLEF_DEVICE`、`NANOJEV_DEVICE` 是容器可见 GPU 编号。用户选择宿主机 GPU 后，程序应推导容器内设备，避免用户同时维护两种编号。
- 内部服务地址、内部端口等能由部署拓扑确定的值，应由程序生成。外部服务模式才要求输入地址。
- LibreOffice 路径等工具位置，先自动发现，确实需要覆盖时再显示高级项。

不能把“搜索不到完整变量名”直接当作无用。Clef/NanoJev 的请求大小、题数、选项数、队列长度等是按前缀动态读取；GPU 显存请求也有动态读取；`COMPOSE_PROFILES`、Python 启动变量和 MinerU 参数可能由 Compose、Python 或依赖库读取。这些不是无效项。

## 真正应保留的配置

普通页面集中在服务端口、源码和权重目录、模型启用、宿主机 GPU 分配、模型上下文和显存预算、应用服务地址、抽取算法及抽取模型。保留 `GPU_DEVICE_IDS`，不能破坏生产机器常用的 `4,5,6,7` 分配。

队列、并发、超时、租约、显存请求等有实际作用，应留在高级配置；Clef/NanoJev 的保护限制只在启用对应模型时展示。特定算法参数也只在选择对应算法时展示，不能把所有算法的参数混在一起。

同时存在“该登记却没登记”的情况：`KG_EXTRACT_LLM_TIMEOUT_SECONDS` 和 `VLLM_ENABLED` 有实际消费者，却不在根模板中。v2.2 当前读取 `KG_EXTRACT_V22_CLEF_*` 的启用、阈值、题数、超时、调用次数、状态长度和并发参数，模板却还保留了一批无效的旧 v3.1 Clef 参数。需逐项决定哪些是正式可配置项，登记其消费者、适用版本和默认值，其余作为代码内部参数管理。

## 配置界面和维护机制如何改

每项配置需要记录：谁读取、适用于什么模式或算法、默认值由谁提供、修改后怎样生效。普通页面只展示当前模式需要的项，高级参数折叠，兼容项单独列出，无消费者的项不能作为有效配置展示。

“实际值”必须按消费者核对：模型进程查对应服务，Compose 参数查实际容器部署配置，热配置查已加载版本。不能拿后端进程环境代替所有服务的状态。拿不到证据时显示“未核实”；当前链路不用时显示“不适用”；不应一律写“未显式配置，使用程序默认值”。

后续删减仍走配置版本维护机制：源码提交记录参数新增、删除、替代关系；CLI 明确展示迁移差异和受影响服务；用户手动确认后生成新配置；部署 guard 校验该版本。自动迁移可以提出计划，不能代替用户批准。

优先处理顺序是：下架无效项，清理旧镜像链，移走评测默认项，再把内部参数和条件参数从普通页面拆出去。这些整理本身不需要重建环境镜像；涉及进程环境变化时按相应服务重新创建容器。
