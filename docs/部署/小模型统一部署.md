# 小模型统一部署

模型统一放在 `${HOST_MODELS_DIR}/llm/`，容器只读挂载到 `/models`。
88 的 `HOST_MODELS_DIR=./models` 相对 `/mnt/data3/qasys`，因此实际目录是
`/mnt/data3/qasys/models/llm`。模型、下载缓存和测试结果都不进入镜像。

| 模型 | 模型目录（相对 HOST_MODELS_DIR） | 精度 |
|---|---|---|
| Qwen3.5-4B | llm/Qwen--Qwen3.5-4B | BF16 |
| Qwen3.5-9B | llm/Qwen--Qwen3.5-9B | BF16 |

| Qwen3.8-27B | llm/cyankiwi--Qwen3.8-27B-AWQ-INT4 | 第三方 INT4 检查点 |

下载版本、文件大小和权重 SHA256 固定在 `docker/llm-models.json`。
联网准备机器可运行 `python docker/download_llm_models.py --models-dir <模型根目录>`；
离线部署前加 `--verify-only` 复核，不访问外网。

## 统一环境

所有服务继续使用 `qasystem-env-v1`，共用一个 Python 环境。
依赖组合为 vLLM 0.31.0、Torch 2.13.0、TorchVision 0.28.0、
Transformers 5.17.0、MCP 2.0.0、OpenCV 4.13.0.92。
Backend 与 Clef 的重叠依赖保持一致；MCP 服务端及 Agent 客户端兼容 SDK 1/2。
Dockerfile 对 `pip check` 不再豁免冲突，指标组件初始化失败会挡住构建。

这是环境依赖变更，需要重新构建和分发环境镜像；源码仍单独只读挂载。
88 的 3090 测试不替代生产 A40 的驱动、内核和实际模型加载验收。
构建和验证状态以本次测试报告为准，不能只凭依赖安装成功宣布可发布。

## 启动

### 键盘配置界面（推荐）

在 88 登录后运行：

```sh
cd /mnt/data3/qasys
python3 qasystem/docker/configure.py --project-dir /mnt/data3/qasys
```

仓库中用 `python3 docker/configure.py`，交付包中用 `python3 runtime/docker/configure.py --project-dir .`。原 `setup_llm.py` 命令也默认打开这个界面；逐项提问的旧流程仅在显式加 `--legacy` 时运行。

进入界面只备份并读取配置，不运行 Docker、不读取整个权重文件、不启动模型。界面携带当前发布版本的 `.env.example`，所有配置项都展示当前值、默认值、现有模板注释和生效方式。已有未知配置及未修改的凭据原样保留，凭据不回显。↑↓ 或 j/k 移动，空格勾选模型或切换布尔开关，回车编辑，`/` 搜索，`d` 恢复选中项的默认值，`q` 退出且不保存未保存的编辑。

勾选模型后出现 GPU 编号、宿主端口、上下文长度及显存比例，可同时配置多个模型。权重目录只检查是否存在，不自动下载。三个动作相互独立：

- `s` 保存：检查端口重复、允许/预留 GPU、同卡多模型、参数格式、模型目录及模型宿主端口占用；检查其他进程是否改过文件，然后生成 `.env`、`runtime-config/settings.json`、`models.json` 和 `models.compose.json`。**不会启动、停止或重建任何容器，也不会提前预留计划中的 GPU。**
- `v` 校验权重：必须再输入 `verify`；这时才完整读取已勾选模型的文件，显示模型、文件序号、大小和文件名。较大的分片仍需时间计算 SHA256。
- `a` 部署：必须再输入 `deploy`；检查现有统一镜像/vLLM、GPU 实际占用与权重显存预算。重建现有 Backend/Agent 来应用启动配置及 GPU 预留，启动已勾选的本地模型；取消勾选并部署会停止本界面之前启动的对应模型。它不接管外部模型服务，不重新构建环境镜像，不创建另一个 Backend。**启动命令成功只表示已提交启动，实际模型就绪需看健康状态和日志。**

备份在运行时目录的 `backups/<时间>/`，保存原 `.env` 与已有 JSON 配置，目录权限 700、备份文件权限 600。备份含凭据，不要提交或分享。发现并发修改会拒绝覆盖。GPU 预留采用保守策略，停用模型后不会自动释放旧预留，确认服务完全停止后才能自行移除。

### 可变配置的生效方式

根 `.env.example` 是默认值和说明的唯一来源；可变配置目录由 `QASYSTEM_RUNTIME_CONFIG_DIR` 指定，默认 `./runtime-config`，只读挂载到 Backend/Agent 的 `/app/runtime-config`。必须挂载**目录**，不能只挂载 `settings.json`，否则原子替换文件后容器可能仍读到旧文件。第一次增加目录挂载需要重建容器一次，以后修改已支持的热配置只需保存。

当前热配置支持：抽取算法版本、抽取模型地址/名称、输入输出 token 上限、并发、QPS/QPM、请求超时、thinking 开关、quota group、v3.1 请求/文档预算，以及 judge 地址/名称/adapter/token 上限。Backend 在有本体的抽取/沉淀请求入队时读取并冻结抽取配置；修改影响新请求，在途任务和重试继续使用原快照。热配置 JSON 不接受凭据或任意环境变量。其他算法内部开关、API 密钥、队列/进程参数仍是启动配置，不能宣称都支持热更新。

评测在启动 judge 时读取同一个文件；容器内自动用 `/app/runtime-config/settings.json`。宿主机评测应在部署目录运行，或通过 `QASYSTEM_RUNTIME_SETTINGS_FILE` 指定实际文件，CLI 显式 judge 参数仍优先。本地模型在 Backend 容器内使用 `http://llm_<模型名转为小写下划线>:8000/v1`，如 `http://llm_qwen_qwen3_5_4b:8000/v1`；宿主机使用对应的回环端口。两种运行位置需要相应的地址，界面不会猜测调用位置。

GPU、权重路径、模型监听端口、vLLM 上下文和缓存容量是服务启动参数，修改后必须重启对应模型进程；宿主端口映射、目录挂载和容器环境修改需要重建对应容器。界面标注“启动配置”的项只保存不立即生效，`a` 是维护窗口动作，会重建 Backend/Agent，已有任务应先结束。Clef/NanoJev 自身的启动配置需按现有部署流程重启相应服务，不由这个本地 vLLM 部署动作管理。

当前支持已登记模型的单 GPU 部署，多卡张量并行尚未提供。启用/停用计划、启动命令提交和实际模型健康是三个不同状态，不能把勾选或保存视为服务已就绪。

### 手动启动

把根 `.env.example` 的 `LLM_*` 项加入部署 `.env`，选定模型目录、服务名和专用 GPU。
`LLM_GPU_DEVICE_IDS` 必须显式填写，并同时加入 Backend 的
`EXECUTION_GPU_RESERVED_DEVICE_IDS`；保留 `GPU_DEVICE_IDS` 原有配置。
默认绑定回环地址，其他容器可通过 Compose 服务名 `llm:8000` 调用。

仓库目录中执行：

```sh
docker compose -f docker-compose.yml -f docker/docker-compose.llm.yml --profile llm up -d llm
```

交付包把补充 Compose 放在根目录，第二个 `-f` 改为 `docker-compose.llm.yml`。
同一服务切换模型时修改 `.env` 并 recreate；多模型常驻时按实际 GPU 预算增加实例。
最大上下文是输入与输出的合计预算；`auto` 用于容量探索，日常部署应显式设定业务长度。
压测需分别记录 prefill、首 token 等待、decode token/s、总耗时和实际完成 token 数。
仅请求被接受、随后取消的输出上限，不等于已经完整生成过该长度。
