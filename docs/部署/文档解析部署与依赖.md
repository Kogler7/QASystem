# 文档解析部署与依赖

本文记录文档解析组件的格式转换、镜像依赖、模型挂载、GPU 配置和运行检查。解析参数与引擎选择行为见[文档解析行为规范](../算法/文档解析行为规范.md)。

## 1. 格式转换

| 输入与引擎 | 前置处理 |
|---|---|
| OFD | ofdrw 转 PDF，再按 PDF 的自动引擎选择进入解析流程；转换失败且环境为 MinerU 4.x 时回退 4.x 原生 OFD 解析（flash 档） |
| DOCX/DOC/PPTX/PPT 使用 `vlm` 或 `mineru` | LibreOffice 转 PDF，再进入解析流程（MinerU 4.x 环境由 mineru4 适配层承接） |
| PNG/JPG/JPEG 使用 `vlm` 或 `mineru` | Pillow 封装为单页 PDF，再进入解析流程（同上） |
| PPT 使用 `docling` | LibreOffice 转 PPTX，再由 Docling 解析 |
| PPTX、图片使用 `docling` | Docling 原生解析 |
| DOC/DOCX、PPT/PPTX、XLS/XLSX、CSV/TSV、HTML、EPUB、RTF、ODF、OFD、PDF、图片使用 `mineru4` | MinerU 4.x 原生解析，无需预转换；非 PDF/图片格式自动降 `flash` 档 |
| Markdown、TXT | 按 UTF-8 BOM/UTF-8 或 GB18030 直接解码 |

## 2. 镜像依赖

| 依赖 | 安装来源 | 用途 |
|---|---|---|
| LibreOffice Core | Dockerfile 系统包 | Office 格式转换基础能力 |
| LibreOffice Writer | Dockerfile 系统包 | DOC/DOCX 转换 |
| LibreOffice Impress | Dockerfile 系统包 | PPT/PPTX 转换 |
| Noto CJK | Dockerfile 系统包 | 中文字体渲染 |
| Pillow | `backend/requirements.txt` | 图片转 PDF |
| Docling | `backend/requirements.txt` | `docling` 引擎；模型外置于 `models/docling-models` |
| MinerU | `backend/requirements.txt` 和 `backend/requirements.mineru-extras.txt`（`mineru[torch]==4.0.4`） | `mineru4` 引擎及由它承接的 `mineru`/`vlm` 引擎；MinerU 2.x 已退役，模型外置于 `models/mineru4` |
| OpenCV full/headless 4.11.0.86 | `backend/requirements.mineru-extras.txt` | MinerU、vLLM 和图像预处理；兼容目标机 Linux 3.10 内核 |
| OpenJDK 17 Runtime | Dockerfile 系统包 | 执行 OFD 转换器 |
| ofdrw 2.3.9 | Dockerfile Maven 构建阶段 | OFD 转 PDF |

镜像构建会执行 `pip check`，检查 LibreOffice、FFmpeg、Poppler、中文字体、完整 Python 模块、Backend/Agent 入口以及 Docling 的 PPTX/IMAGE 输入能力。运行时校验还要求 `opencv-python` 和 `opencv-python-headless` 均为 `4.11.0.86`。OpenCV 5.0 自带 Qt5 的 ELF ABI 下限为 Linux 3.17，无法在目标机 3.10 内核加载；禁止通过修改容器内 `libQt5Core` 的 `.note.ABI-tag` 临时绕过。模型不打入镜像，运行期固定从 `/models` 读取；必须在联网机器使用独立下载脚本准备好模型目录后再交付，部署服务器无需访问 Hugging Face、ModelScope 或互联网。

容器内 LibreOffice 路径：

```text
/usr/bin/soffice
```

容器默认通过以下命令调用镜像内置的 OFD 转换器：

```text
java -jar /opt/qasystem/ofdrw/ofd-to-pdf.jar <input.ofd> <output.pdf>
```

如需使用经验证的外部或自定义转换器，可通过 `OFD_CONVERTER_COMMAND` 覆盖命令；命令需要依次接收输入 OFD 路径和输出 PDF 路径。

## 3. 模型挂载

模型目录通过 Compose 挂载到容器 `/models`：

```env
HOST_MODELS_DIR=./deploy/models
MINERU_HOME=/app/backend/data/mineru4
MINERU_MODEL_BASE_DIR=/models/mineru4
MINERU_MODEL_SMALL_BACKEND=onnx
MINERU_MODEL_VLM_ENGINE=llama-cpp
MINERU4_TIER=standard
```

MinerU 2.x 已退役：`mineru.json`、`MINERU_MODEL_PIPELINE_PATH`、`MINERU_MODEL_VLM_PATH` 不再使用。MinerU 4.x 模型放在 `${HOST_MODELS_DIR}/mineru4`（容器内 `/models/mineru4`）：`MinerU-4_models_onnx`（basic 档小模型，约 819MB）与 `MinerU2.5-Pro-2605-1.2B-GGUF`（standard/advanced 档 VLM，llama.cpp，约 1.2GB）。4.0 会在模型根目录写 `.locks`，模型本体只读挂载时需把该目录单独叠成可写挂载（Compose 已内置 `${MINERU4_LOCK_DIR}:/models/mineru4/.locks`，宿主需先创建该目录）。

在联网机器执行以下命令下载 Docling、BGE-small-zh 等基础模型：

```powershell
.\download-models.ps1
```

脚本默认使用 ModelScope，可通过 `-Source huggingface` 切换 MinerU 下载源。它会下载 Docling 默认模型到 `models/docling-models`、512 维 BGE-small-zh 到 `models/bge-small-zh-v1.5`（向量模型从 Hugging Face 下载），并继续下载 MinerU 2.5 权重（`OpenDataLab/PDF-Extract-Kit-1.0` → `models/mineru/pipeline`、`OpenDataLab/MinerU2.5-2509-1.2B` → `models/mineru/vlm`），因为现行 `GET /health?full=true` 仍要求这两个目录存在；MinerU 4.x 模型用 4.x 自带的 `mineru-models-download --tier basic|standard --small-backend onnx|torch --vlm-engine llama-cpp|vllm` 下载到 `models/mineru4`。需要 NanoJev 关系判别时追加 `--jev`（`C-Tianyu/NanoJev` → `models/nanojev`，可选，不进基础包）。置信度能力等待应用团队接口开通，不再加载本地图谱或文本证据模型。下载完成后将整个 `models/` 目录复制到离线部署包。

自动引擎选择依据运行时可用性：`vlm` 路线需要可用的 VLM 端点（本地 vLLM 或外部 `MINERU_VLM_SERVER_URL`），端点不可用时自动回退本地 MinerU 路线；`mineru4` 路线需要 `/models/mineru4` 模型齐备。

## 4. GPU 部署

默认 Compose 为 Backend 申请全部 GPU（`gpus: all`），supervisor 读取 `GPU_DEVICE_IDS` 并为每个子进程单独设置 `CUDA_VISIBLE_DEVICES`，把模型进程限制在宿主机后四张卡：

```yaml
services:
  backend:
    gpus: all
```

旧独立部署入口已移除，使用 `ops config` 审核配置后执行 `ops deploy`。

容器内检查：

```bash
docker compose exec backend python -c "import torch; print(torch.cuda.is_available(), torch.cuda.device_count())"
docker compose exec backend nvidia-smi
curl 'http://127.0.0.1:8006/health?full=true'
```

`GET /health` 默认只检查服务存活。添加 `full=true` 后会校验 Docling、MinerU 和已配置向量模型的外部目录，Python 模块、LibreOffice、Java、OFD 转换器，以及 SQL、知识抽取 LLM 和应用团队统一服务的 TCP 连通性；任一项缺失时返回 `503` 与 `failed` 列表。服务不再直连 Neo4j 或 Elasticsearch。该检查不会下载模型、初始化 GPU 模型或修改外部服务。为兼容已有调用，`validate_models=true` 也会触发同一套完整检查。

## 5. 构建与验证

```bash
.\build-image.ps1
docker run --rm qasystem-env-v1 libreoffice --headless --version
# 完整应用校验由 build-image.ps1 挂载仓库源码后执行
```

Compose 使用本地镜像并配置 `pull_policy: never`。Dockerfile 或依赖变更后需要重新构建镜像。

## 6. 运行错误

依赖或转换能力不可用时，解析错误会返回具体原因，包括：

- 未找到 LibreOffice/soffice
- LibreOffice Writer 或 Impress 转换失败及命令输出
- LibreOffice 转换超时
- 缺少 Pillow
- 图片损坏或格式不正确
- 缺少 Docling、MinerU 等 Python 模块
- MinerU 所选路线的模型目录缺失
- 缺少 Java 或镜像内置 ofdrw 转换器
- OFD 转 PDF 失败、超时或未生成目标文件
