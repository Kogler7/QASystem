# 执行任务恢复与GPU预约

任务队列使用 Redis Streams，恢复不是按运行时长强制重做任务。超出 `EXECUTION_REAPER_MIN_IDLE_SECONDS` 后，还必须核对实际取走该消息的消费者实例是否失联，才能原子地转移消息。正常长任务持续报告心跳，因此即使运行超过十分钟也不会被抢走。

## 名称与实例分开

调度worker名称保持稳定，便于向指定GPU/解析worker派发；每次进程启动生成独立consumer实例ID。重启后不会把旧消息误认为新进程正在处理。消费者心跳单独保存，避免为同一worker登记两份调度容量。旧版本的心跳记录仍可用于保护尚在执行的旧worker；迁移后失联旧实例可正常恢复。

共享与定向队列都在原stream中确认消息。已经成功、失败或取消的任务不再执行；运行中任务才增加attempt并重新排队，最多次数仍由 `EXECUTION_MAX_ATTEMPTS` 决定。旧进程退出时只能删除自己的worker登记，不能注销新进程。

## 资源预约不是运行超时

内部心跳每5秒更新，心跳记录保留30秒。GPU预约的900秒TTL只是异常退出后的兜底回收时间，执行中每隔至多5秒续期。不能据此限制文档处理时长；算法调用/文档预算仍按对应算法协议维护。

完成、失败和协作式取消都释放资源。预约已经过期则不允许复活；续期失效或Redis异常时记录本地错误，结果不写入成功记录、不自动重试。已发出的同步调用可能需要等其返回才能丢弃结果，这不是强制中断CUDA或外部HTTP请求。发生网络分区或进程冻结时，队列仍是至少一次恢复机制，不能宣称对外部副作用提供全局恰好一次执行；已持久化终态的任务不会再被恢复执行。

## 验证

`tests/backend/test_execution_liveness.py` 覆盖正常长任务、完成/失败/取消释放、预约失效不发布、真实Redis活/死消费者、重启同名worker、定向ACK与终态不重做。测试Redis使用独立本地16389端口，不访问业务Redis；未运行测试Redis时集成用例明确跳过。

这批代码没有批准部署配置，也没有更新88服务。此前已审议的其它队列内部化、Agent/MCP、解析和模型配置清理分批实施，不因本次安全修复宣称全部完成。
