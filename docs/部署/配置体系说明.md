# 配置架构与维护流程

当前声明版本：`2026.10.14.1`。声明随代码版本提交；部署上的实际配置必须另经用户审核。代码已提交或合并，不代表 88 已部署，也不代表运行进程已使用新值。

## 配置在哪里维护

| 文件/模块 | 保存内容 | 谁维护 |
| --- | --- | --- |
| 根 `.env.example` | 当前版本部署参数的名称、默认值和说明 | 开发者随代码维护；不保存真实密钥 |
| `docker/config-declarations.json` | 当前声明版本、消费者、默认回退、热更属性、迁移规则、模型默认值及说明 | 开发者明确登记；门禁校验 |
| `docker/config-releases/<版本>.json` | 不可变的历史声明 | 每次声明升级新增文件，禁止覆盖旧版本 |
| 部署 `.env` | 密钥、源码/权重/数据目录、端口、GPU、队列和进程启动参数 | 用户通过 `ops config` 审核后生成 |
| `runtime-config/config.json.settings` | 已支持热更新的业务参数 | 同一 UI 审核后生成 |
| `runtime-config/config.json.models` | 每个 vLLM 模型的启用计划与启动参数 | 同一 UI 审核后生成 |
| `docker.configuration` | 应用统一读取、声明校验、热值读取和实际读取记录 | 业务代码统一调用，不直接读环境 |
| 本轮评测命令行 | case 范围、抽取覆盖、judge、并发和门禁 | 每轮临时指定，不保存默认评测计划 |

`.env.example` 是清单，不是另一份实际配置。JSON 声明中的部署默认值是该发布的记录，门禁要求与模板一致。内部参数的代码回退也登记在声明中；不同功能确实需要的默认值，不会仅因数值相同就合并。

## Docker Compose 的职责

根 `docker-compose.yml` 定义基础服务、依赖、命令、GPU 可见性、挂载、端口、健康检查和重启策略。它读取已生成的部署值，不另设一套可调参数默认值。缺少必需的插值参数时，Compose 报错并提示运行 `ops config`。

`.env` 在这里承担两个作用：Compose 用它替换镜像、宿主路径和端口等变量；`env_file` 将启动参数注入容器进程。修改 `.env` 后，已有容器的进程环境不会自动改变。

`models.compose.json` 由 `config.json.models` 自动生成，与基础 Compose 合并来部署勾选的 vLLM 模型。`applied.compose.json` 和 `applied-models.json` 记录已提交部署的计划，用来判断哪些模型应停用或重新创建。它们都不是人工配置入口；部署记录也不代表服务健康。

唯一应用环境镜像系列是 `qasystem-env-v1`，保留 `QASYSTEM_ENV_IMAGE` 供选择该镜像的版本标签。源码从 `QASYSTEM_SOURCE_DIR` 只读挂载，模型从 `HOST_MODELS_DIR` 只读挂载。数据和配置读取日志使用可写卷。Dockerfile 只维护环境依赖，不打入应用源码、模型或实际配置。

## 什么修改需要重启

| 修改 | 生效方式 |
| --- | --- |
| 已支持的业务热参数 | 审核保存后，新请求/新客户端读取；在途请求沿用原快照 |
| 模型 GPU、权重、上下文、显存预算和推理参数 | 部署后重建对应模型容器 |
| `.env` 启动环境、宿主端口、挂载、进程数量 | 重新创建受影响容器，`restart` 不会更新这些值 |
| 已挂载的业务源码 | 按现有源码同步与服务重启流程生效 |
| CUDA、Torch、vLLM 或其他环境依赖 | 才需要重建和分发环境镜像 |

热参数以 `docker/runtime_config.py` 的 `HOT_KEYS` 与声明共同校验。目前覆盖抽取版本、模型地址/名称、输入输出预算、并发/配额、请求超时、thinking、v3.1 时间预算，以及已登记的解析、Embedding 和决策服务参数。密钥、Agent 自身的模型与 worker 数仍是启动参数。

共享进程配额池会保守收紧并发/QPS/QPM。提高或解除已有配额限制不能仅靠热更新，需要重启对应进程。模型启动参数和本轮 judge 参数不属于业务热参数。

## ops 命令

```sh
# 命令尚未安装时，在部署目录用交付的 Python 入口安装：
python3 runtime/ops.py --project-dir . install

ops config
ops check
ops reload
ops deploy
ops status
ops history
ops history --json
ops logs backend agent
```

源码目录可使用 `python3 ops.py --project-dir . <操作>`；Windows 可使用 `python ops.py` 或 `ops.ps1`。安装器创建用户级命令并登记 PATH，不需要管理员权限；当前终端尚未刷新 PATH 时，继续使用 Python 入口或新开终端。

`config` 打开 UI，先备份并读取实际状态，不启动服务。`check` 核对批准版本和配置冲突。`reload` 在 Backend/Agent 内验证配置可读和抽取配置有效，不重启、不加载模型、不验证下游服务连通性。`deploy` 应用已经审核的启动配置和本地 vLLM 计划；模型计划未部署时，`reload` 会拒绝把它当成已生效。

当前 `ops deploy` 管理 Backend、Agent 和 UI 登记的 vLLM 模型。Clef/NanoJev 属于基础 Compose 的决策服务，改其启动参数仍需按决策服务部署文档重新创建对应服务，不能把一次 Backend/Agent 部署当作决策模型已重载。

## 人工审核与 guard

UI 展示运行服务的实际值、编辑计划、默认值和生效方式。保存前逐页展示新增、删除、改值、声明说明/默认值/消费者变化以及迁移规则；用户填写原因并输入指定版本确认词后才写文件。凭据只显示变更，不回显内容。取消审核不写配置，不批准版本。

guard 在部署动作之前和容器业务进程启动之前执行。它检查声明与消费者、当前文件指纹、批准记录及对应历史记录。手改实际文件、声明升级未审核或批准记录不一致都会拒绝使用；没有自动确认或跳过选项。Agent 不能代替用户批准，单元测试临时目录除外。

热配置读取同样检查批准版本，删除新文件不能绕回旧文件。首次启用 guard、配置目录或 observed 可写挂载时，需要用户审核并重新创建容器一次。这里只约束本项目维护的入口，不是对主机管理员的权限隔离。

## 配置历史与实际使用记录

```text
runtime-config/
  config.json                   当前热配置和模型计划
  models.compose.json           自动生成的模型部署结构
  approved-config.json          当前批准版本指针
  history/                      不可变审核记录
  versions/r000001/             每次批准的独立配置归档
  events/                       批准、部署、可读验证等事件
  observed/events/              应用/探针实际读取的配置记录
  database.json                 ops history 重建的脱敏汇总视图
  backups/                      UI 入场备份
```

归档 `.env` 含真实凭据，仅保存在权限受限的本地目录；不得提交、分享或进入交付包。JSON 视图只显示脱敏值或指纹。批准、已提交部署、容器验证可读、应用实际读取和下游调用成功是不同证据，不能混为“已生效”。旧历史缺少读取证据时不会补造记录。

## 迁移与开发门禁

旧 `settings.json`、`models.json` 只在尚无 canonical 文件时作为迁移输入；已有 `config.json` 时不叠加它们。UI 审核保存后删除旧文件，并把 `.env` 的热参数迁入 `settings`。同义名称统一迁入标准名称，值冲突必须编辑确认。旧 `LLM_*` 参数迁入每个模型，迁移不会自动启用模型。

详见 [配置清理与标准名称迁移](配置清理与标准名称迁移.md)。未知、尚不能确认消费者的用户自有项不会被猜测删除。已确认退役的项目不能重新写入当前实际配置；历史声明与迁移墓碑仍保留。

新增/删除配置、修改消费者、回退或热更属性，必须同步代码、测试、模板、当前声明和新版本文件。模块被删而配置还留着，或应用绕过集中模块直接读环境，门禁报错。不得重新自动扫描声明来消除失败。

```sh
python3 -m docker.config_contract
python3 -m pytest -q
```

测试与发布门禁另见根 `AGENTS.md`；88 用现有 `qasystem_backend`，不新建评测 Backend。配置审核是用户动作，代码合并不会自动修改部署实际文件。

用户保留 `QASYSTEM_ENV_IMAGE`、`QASYSTEM_SOURCE_DIR`、`HOST_MODELS_DIR`。删除 `QASYSTEM_LOAD_DOTENV`、`QASYSTEM_RUNTIME_CONFIG_DIR`、`PYTHONPATH`、`PYTHONUNBUFFERED` 的用户配置入口，当前部署模板由 183 项减为 179 项；声明由 274 项减为 270 项。这里统计的是声明项，不是实际进程读取数量。

配置目录固定为部署根目录下的 `runtime-config/`，在容器内只读挂载到 `/app/runtime-config`；实际读取记录使用子目录可写挂载。`ops`、guard、应用和模型部署都遵守同一目录约定。容器固定注入 `ENVIRONMENT=production`、`PYTHONPATH=/app:/app/agent`、`PYTHONUNBUFFERED=1`，这些是内部启动约定，旧 `.env` 同名值不能覆盖。

后端自动识别容器或已设置 `ENVIRONMENT` 的托管启动，仅未托管的本地启动加载仓库根 dotenv。旧 `QASYSTEM_LOAD_DOTENV` 不再读取，也不能强制容器加载另一份配置。

旧自定义配置目录由 `ops config` 读取用于提出迁移计划。打开、预览和取消不搬迁实际配置或批准记录；人工审核保存时，将历史版本、批准记录、读取记录和已应用模型状态复制到固定目录，保留原目录。新旧目录同时存在实际配置或历史时拒绝覆盖；并发修改或写入失败会阻止迁移、回滚本次新写内容。此次变更需要用户重新审核，不能由 Agent 代批，也尚未修改 88。

本次同时移除 11 条指向已删除旧 Compose/systemd 文件的消费者记录。门禁逐项检查消费者路径，其他消费者仍存在也不能掩盖失效路径；交付源码故意排除的外部评测工具仍遵守外部消费契约例外。固定启动约定纳入声明版本校验，历史声明保持不可变。
