# 配置放在哪里，什么时候生效

应用保留两个需要维护的文件。评测每轮使用命令行，不再维护独立的默认配置文件。

| 配置入口 | 保存什么 | 修改后如何生效 |
|---|---|---|
| 部署目录 `.env` | 镜像、源码/权重目录、端口、GPU、队列、进程参数和密钥 | 重新创建受影响容器；无需重建镜像 |
| `runtime-config/config.json` 的 `settings` | 已支持热更新的抽取参数、共享模型服务参数 | 已挂载该目录的服务，在新请求中读取；在途请求沿用快照 |
| 同一 `config.json` 的 `models` | 各模型是否启用、GPU、端口、上下文和显存比例 | 保存只改变计划；明确执行部署后才改变模型服务 |
| 本轮评测命令行 | 数据范围、抽取覆盖、judge、并发、超时、门禁等 | 只对这一轮有效 |

`.env.example` 是当前版本的配置清单和说明，不是额外的运行配置。`Dockerfile` 只维护环境依赖；修改业务参数不需要构建 `qasystem-env-v1`。

## 为什么改 `.env` 后 restart 不够

Compose 创建容器时把 `.env` 对应的值写入容器环境。`docker compose restart` 只重启原容器，不重新读取这些值。需要按部署流程重新创建受影响服务，例如：

```sh
docker compose up -d --force-recreate backend agent
```

这不是重新构建镜像。只更新已经挂载的外置应用源码，仍可按现有流程 restart；改端口、挂载或容器环境则需要 recreate。

## 旧文件怎么处理

打开应用配置界面会先备份，不会立即迁移或部署。明确保存时：

1. 将旧 `settings.json`、`models.json` 合并到 `config.json`，随后删除旧文件。
2. 将 `.env` 中已支持热更新的业务参数迁入 `config.json.settings`，去掉 `.env` 的重复项。
3. 保留凭据、未知配置及未修改凭据的原始引用方式。保存前检查文件是否被其他进程修改。

已有 `config.json` 时，以它为准，不再叠加旧 JSON 文件。没有新文件时仍可读取旧文件，便于升级前后兼容。首次使用热配置必须确认 Backend/Agent 已挂载整个 `runtime-config` 目录；如果没有，需要重新创建一次容器。

`models.compose.json`、`applied.compose.json`、`applied-models.json` 是程序生成的部署文件或状态记录，不作为人工配置入口。备份目录包含凭据，不提交到 Git。

## 评测不保存默认计划

删除 `eval/params.yaml` 和 `eval/quick_params.yaml`。评测不自动加载 `eval/.env`、参数 YAML 或历史 profile。评测界面每次从本轮临时计划开始，将选项转换为命令行供预览和执行；退出后不自动保存计划。

结果目录内的参数快照只用于解释这一轮结果，不作为后续评测的输入。各命令参数见 `eval/README.md`；可直接运行 `python3 eval/run.py --help` 查看当前版本支持的选项。

应用配置界面继续展示运行服务的实际值与待保存配置。保存计划、提交部署、服务健康是三个不同状态，不能把保存成功当作已生效。

## 配置版本、人工审核和部署 guard

每个部署目录维护自己的批准版本。`runtime-config/approved-config.json` 记录当前批准版本，`runtime-config/history/` 追加各次版本：时间、审核账号、必填原因、与前一版本的差异和文件指纹。凭据仅保留变更指纹和隐藏提示，不把内容写进审核页面或记录。目录权限为 700，记录文件为 600。

按 `s` 保存时，界面先展示与上次批准版本的差异，包括参数新增/删除/改值、默认值/说明/热更属性的变化。首次审核展示完整清单。需要逐页浏览，填写原因，再输入界面显示的 `confirm r<版本号>` 才写文件并记录批准。取消不写配置，也不改变热参数。`a` 部署时，程序先把所需 GPU 预留变化加入计划，再走同一人工审核过程；不能部署后偷偷修改 `.env`。

guard 在部署动作前检查批准版本，Backend、Agent、Clef、NanoJev 和本地 vLLM 的 Compose 启动入口也执行 guard，校验通过才启动业务进程。手改 `.env`、`config.json`、生成的模型 Compose 或版本清单，即使直接执行 Compose，仍会因指纹不一致被阻止。批准记录本身修改或丢失对应历史记录也会被阻止。重新打开 UI 审核才能纳入新版本，没有 `--approve`、`--yes` 或跳过选项。

新格式热配置在读取时也验证批准记录；手改后不会被新请求采用。删除新文件不能绕回旧 `settings.json`。旧部署在尚未迁移时保留旧文件兼容读取，一旦建立新格式的批准版本便执行审核校验。版本清单同时核对部署模板和外置源码中的发布模板，避免源码升级后一直沿用旧部署清单。

可以只执行校验，不启动服务：

```sh
python3 qasystem/docker/config_guard.py --project-dir /mnt/data3/qasys
```

第一次启用 guard 时，旧部署没有批准记录，需要用户在 UI 建立首次批准版本。不得由 AI 或部署脚本代替确认。启用入口和只读挂载需要 recreate，不能只替换源码然后直接 restart。此机制约束受维护的部署入口；拥有主机管理权限的人仍可另写 Compose、删除入口或修改程序，它不是对主机管理员的权限隔离。

开发时修改环境变量必须在 `.env.example` 登记，提交消费者、相关测试和下表记录。清单变更由 Git 留存，部署时由 UI 展示给实际维护人员审核。服务读取未经支持的热变量仍会报错，不能以任意 JSON 键替代登记。

## 统一操作入口：ops

入口随源码和交付包一起放在根目录。Linux 首次运行 `sh ./ops install`，Windows 运行 `.\ops.ps1 install`。安装到用户目录，登记用户 PATH，不要求 root 或管理员权限；检测到已有其他 `ops` 命令会拒绝覆盖。Linux 会给 Bash/Zsh 的启动文件追加 PATH，并备份已有文件。重新登录 SSH 或重新打开终端后用 `ops --help` 核对；Linux 当前终端也可执行 `export PATH="$HOME/.local/bin:$PATH"`。

安装的命令绑定当前交付目录，目录移动后需要重新安装。未安装时始终可以用 `sh ./ops`、`.\ops.ps1` 或 `python ops.py`。Fish 等其他 shell 请自行加入 `~/.local/bin`，不能承诺所有 shell 自动发现。

| 命令 | 用途 |
| --- | --- |
| `ops config` | 打开现有配置 UI，备份、编辑、人工审核和保存 |
| `ops check` | 检查批准版本、配置结构和冲突，不部署 |
| `ops status` | 查看批准状态及实际容器状态 |
| `ops reload` | 检查 Backend/Agent 能读取批准配置，不重启 |
| `ops reload --services backend` | 只检查指定的 Backend |
| `ops deploy` | 沿用现有部署流程，重新创建应用容器并应用模型计划；必须已经人工批准 |
| `ops restart backend agent` | 重启指定服务，适合只更新挂载源码；不能刷新 Compose 注入的环境变量 |
| `ops logs backend` | 查看最近 100 行服务日志 |

`reload` 不改进程的 `os.environ`，不重新加载 Python 源码，也不声称刷新所有缓存。受支持的消费者本来就动态读取 `config.json`；保存并批准后即可供下一次读取使用，reload 是明确的容器内校验步骤，不是第二次批准。它会校验挂载文件、批准版本和抽取配置，遇到启动环境未同步、未部署的模型计划或任一服务检查失败会返回非零退出码。此步骤不执行真实模型推理，成功不等于下游地址可达。安装和查看状态也不产生配置批准记录。

目前动态参数包括抽取算法、模型地址/名称、token 预算、并发与限速、抽取超时，以及远程 Embedding/解析/Clef/NanoJev 的地址、已登记路径和超时，Embedding 的模型名及批大小。显式请求或客户端参数优先于默认热配置。客户端新建时读取，已经创建的实例保留原值；抽取任务在提交时快照，执行和重试保留旧配置。公共切片使用的 Clef 客户端走同一读取路径，但不承诺整个沉淀流水线的所有阶段共享一个配置快照。

并发和限速有额外边界：现有共享配额池只允许实时收紧，防止模型别名绕过同一账号的限制。提高并发、提高 QPS/QPM，或把已有非零限制改回 0，需要重启相应进程才能放宽；reload 读取到新值不代表池已放宽。收紧属于共享调度规则，会影响进行中任务后续发出的请求，任务的模型、算法及输入快照仍保持原值。

密钥仍留在启动环境中，不写入非秘密热配置。端口、挂载、GPU 可见范围、进程数量、运行模式，以及模型权重、上下文和显存启动预算没有改成热参数。更换模型服务的地址可动态生效，启停模型或加载新权重仍走 deploy。当前 Agent 自身的模型、密钥和 worker 数量也仍属于启动参数，不能因为支持 ops reload 就称其已支持热切换。

本轮代码尚未部署到 88。首次上线新消费者仍需重启相应服务；配置清单与热更属性变化必须先由用户在 UI 审核。以后只修改已支持的动态值，才无需重启容器。

## 声明版本、配置版本和实际读取历史

声明版本属于代码发布，当前为 `2026.10.12.1`。`docker/config-declarations.json` 登记参数说明、默认值、适用范围、消费者和热更新属性；`docker/config-releases/<版本>.json` 保留不可变的版本副本。根 `.env.example` 继续作为部署默认值来源，JSON 中的默认值是该发布的记录，门禁要求两者一致，不能分别维护两套不同默认值。

内部和兼容参数不全部放进普通 UI，但同样登记在声明中。迁移保留了已有调用者的默认回退，并记录其表达式；原先各模块不同的回退没有在本轮强行改成一个值。修改读取调用、回退、Settings 模型服务默认值，都会触发声明门禁，要求更新版本。今后新增参数应优先由集中管理模块提供一致默认值。

机器上的配置版本是独立的 `r1`、`r2` 等。记录同时绑定软件源码提交（交付包的 `SOURCE_COMMIT`，源码仓库的 Git HEAD）和声明版本。软件版本更新即使参数没有变化，也会在审核差异中显示源码版本变化，批准后生成新的配置版本。用户审核后自动生成：

```text
runtime-config/
  config.json                    当前热配置和模型计划
  approved-config.json           当前批准记录
  history/                       不可变的审核记录
  versions/r000001/
    .env                         该版本原始启动环境，含凭据，私有保存
    config.json                  该版本热配置和模型计划
    models.compose.json          该版本生成的模型部署文件
    environment.json             脱敏版本记录，含声明版本和文件指纹
  events/                        审核、容器可读验证事件
  observed/events/               进程实际读取事件
  database.json                  ops history 生成的可重建 JSON 视图
```

`database.json` 相当于小数据库的查询结果，权威数据是不可变的版本及事件文件。每次事件写独立文件并原子替换，避免多个 worker 同时改一个大 JSON 导致丢记录。旧版本不会被新版本覆盖。整个运行配置目录禁止提交到 Git；原始 `.env` 版本归档和密钥备份必须由部署人员控制访问权限。Windows 的 POSIX chmod 不等于 ACL，需要用宿主目录 ACL 限制访问；Linux 私有目录为 700，原始配置文件为 600。

升级前已有的审核 JSON 也会纳入历史视图；没有原始版本归档的记录会标记 `archive_available=false`。不凭空还原旧密钥、默认值或进程实际读取情况。生成视图时核对审核记录指纹，以及已有版本文件与审核快照的一致性。

状态不能合并为一个“已生效”：`approved` 表示用户批准；`verified-readable` 表示 ops 已在容器检查读取；`read` 表示某个进程确实取得该值。实际读取事件记录时间、进程、当时批准版本、参数名、实际值或凭据指纹、来源。记录中的 `approved_revision` 是读取时的批准版本，不是对整台机器已全部切换的断言；旧进程读到旧启动环境时，仍保留真实旧值。在途抽取任务沿用提交时的快照，历史读取不代表模型推理或任务成功。

事件的 `actor` 区分 `ops-probe` 检查进程和 `application` 应用进程，`service_instance` 标识容器实例。不能用 reload 的短进程读取记录证明常驻 worker 已采用新配置。

集中模块仅在受管容器中自动写实际读取历史；本地开发和单测不会自动生成生产读取记录。批准目录仍以只读方式挂载，只有 `observed` 子目录额外挂载为可写，所有应用服务共享这一历史位置，不新增配置变量或队列。审核时创建宿主私有目录；事件 JSON 已脱敏，为保证 Docker root 写出的文件也能被宿主目录所有者读取，事件文件为 644，宿主父目录为 700。拥有 Docker 管理权限的人不属于这个权限隔离边界。

```sh
ops history        # 查看版本及事件数量，生成数据库视图
ops history --json # 查看脱敏 JSON，不输出原始 .env
```

## 配置逻辑门禁

```sh
python -m docker.config_contract
```

检查直接环境读取、未声明的字面量配置名、失去消费者的声明、模板默认值与声明不一致、热更新属性不一致，以及读取调用和兼容回退变化未登记。受版本控制的旧声明副本禁止就地改写。打包前执行全源码检查；部署 guard 再检查交付源码。评测工具和外部部署文件按仓库约定不进入运行源码包，其消费契约由打包前检查，运行时只检查已交付的应用消费者和冻结声明版本。

静态检查不能证明第三方库在每次请求里是否读取某变量。Compose、Python、MinerU 等自行读取的项需要显式登记外部消费者；资源类型显存参数、供应商凭据名采用明确的动态命名空间，不允许任意普通参数绕过声明。业务应用当前通过 `docker.configuration.getenv/required` 取值，`algorithm.runtime_settings` 仅保留兼容导出。配置存储、guard 和 ops 的环境适配不属于业务读取模块。
