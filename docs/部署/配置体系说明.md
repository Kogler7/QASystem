# 配置架构与维护流程

当前声明版本：`2026.10.14.11`。声明随代码版本提交；部署实际配置通过 ops 的 GUI 或受控自动事务提交，保留版本、原因和变更清单。代码已提交或合并，不代表 88 已部署，也不代表运行进程已使用新值。

## 配置在哪里维护

| 文件/模块 | 保存内容 | 谁维护 |
| --- | --- | --- |
| 根 `.env.example` | 当前版本部署参数的名称、默认值和说明 | 开发者随代码维护；不保存真实密钥 |
| `qasystem_config/config-declarations.json` | 当前声明版本、消费者、默认回退、热更属性、迁移规则、模型默认值及说明 | 开发者明确登记；门禁校验 |
| `qasystem_config/config-releases/<版本>.json` | 不可变的历史声明 | 每次声明升级新增文件，禁止覆盖旧版本 |
| 部署 `.env` | 凭据、源码/权重/数据目录、端口、GPU 和需创建容器的启动参数 | ops GUI 或受控自动事务生成 |
| `runtime-config/config.json.settings` | 业务热参数与明确标记的进程计划 | 同一配置事务生成；CPU 数量保存后需进程 apply |
| `runtime-config/config.json.models` | 独立 vLLM、Clef、NanoJev 和 Backend 管理的解析模型记录 | 同一事务生成，模型记录区分唯一启动管理者 |
| `runtime-config/config.json.services/accounts/routes` | 服务连接、能力、账号额度与功能服务引用 | 同一事务生成，不重复填写模型地址和凭据 |
| `qasystem_config.configuration` | 应用统一读取、声明校验、热值读取和实际读取记录 | 业务代码统一调用，不直接读环境 |
| 本轮评测命令行 | case 范围、抽取覆盖、judge、并发和门禁 | 每轮临时指定，不保存默认评测计划 |

`.env.example` 是清单，不是另一份实际配置。JSON 声明中的部署默认值是该发布的记录，门禁要求与模板一致。内部参数的代码回退也登记在声明中；不同功能确实需要的默认值，不会仅因数值相同就合并。

公共配置核心是 `qasystem_config/`，负责读取、声明、迁移、校验、事务、归档和纯文件 I/O，不依赖 Docker 或交互界面。业务通过 `qasystem_config.configuration` 获取值；运维 UI 和 Docker 操作只是它的调用方。旧 `docker.configuration` 等兼容入口已移除，不保留第二套读取模块。

`docker/` 保留容器启动命令、模型交付工具和 ops 界面。配置事务的核心接受明确的配置对象，宿主 CLI 的编辑器工厂在 `docker.configure.run_transaction`；公共核心不反向导入这个工厂。原生模型进程的共享启动逻辑在 `model_runtime/`，与 Docker 命令生成分开。

迁移前的 `docker/config-releases/` 原样保留用于历史验证，新版本只新增到 `qasystem_config/config-releases/`。历史文档中的旧模块名记录当时实现，不是继续可调用的兼容接口。

## Docker Compose 的职责

根 `docker-compose.yml` 定义基础服务、依赖、命令、GPU 可见性、挂载、端口、健康检查和重启策略。它读取已生成的部署值，不另设一套可调参数默认值。缺少必需的插值参数时，Compose 报错并提示运行 `ops config`。

`.env` 在这里承担两个作用：Compose 用它替换镜像、宿主路径和端口等变量；`env_file` 将启动参数注入容器进程。修改 `.env` 后，已有容器的进程环境不会自动改变。

`models.compose.json` 由 `config.json.models` 自动生成，与基础 Compose 合并部署由 ops 管理的勾选模型。Backend 管理的解析引擎不会重复生成独立模型容器。`applied.compose.json` 和 `applied-models.json` 记录已提交部署的计划，用来判断哪些模型应停用或重新创建。它们都不是人工配置入口；部署记录也不代表服务健康。

唯一应用环境镜像系列是 `qasystem-env-v1`，保留 `QASYSTEM_ENV_IMAGE` 供选择该镜像的版本标签。源码从 `QASYSTEM_SOURCE_DIR` 只读挂载，模型从 `HOST_MODELS_DIR` 只读挂载。数据和配置读取日志使用可写卷。Dockerfile 只维护环境依赖，不打入应用源码、模型或实际配置。

## 什么修改需要重启

| 修改 | 生效方式 |
| --- | --- |
| 已支持的业务热参数、服务路由与账号额度 | 提交后，新请求/新客户端读取；在途请求沿用原快照 |
| CPU 执行进程数量 `[进程]` | 提交进程计划后执行 `ops runtime apply`；不重启网关或容器 |
| 模型 GPU、权重、上下文、显存预算和推理参数 | 部署后重建对应模型容器 |
| `.env` 启动环境、宿主端口、挂载、设备授权及尚未支持局部控制的进程参数 | 重新创建受影响容器，`restart` 不会更新这些值 |
| 已挂载的业务源码 | 按现有源码同步与服务重启流程生效 |
| CUDA、Torch、vLLM 或其他环境依赖 | 才需要重建和分发环境镜像 |

具体参数以当前 `qasystem_config/config-declarations.json`、根 `.env.example` 和 `qasystem_config/runtime_config.py` 的读取集合为准，不再另列一份容易过期的旧名称。`HOT_KEYS` 表示新请求读取的参数，`PROCESS_KEYS` 表示保存后仍需明确应用到进程的计划。服务/账号/用途记录通过同一有效配置快照读取。

已登记 LLM 服务及共享账号采用 Redis 跨进程调度，不由各算法分别计算额度。模型启动参数和本轮评测 judge 选择不属于业务热参数；算法调度策略随算法代码维护。

## ops 命令

```sh
# 命令尚未安装时，在部署目录用交付的 Python 入口安装：
python3 ops.py install

ops config
ops check
ops reload
ops deploy
ops status
ops history
ops history --json
ops logs backend agent
ops runtime status
ops runtime apply
```

单独验证公共配置源码使用 `python3 -m qasystem_config.config_contract`。交付包将公共核心放在 `runtime/qasystem_config/`，宿主 `ops.py` 根据自己的文件位置加载该源码，因此从其他工作目录执行绝对路径入口仍能使用。公共配置读取、schema 和纯 I/O 不需要 Docker daemon；部署、容器状态和 GPU 模型启动才调用 Docker。

源码目录可使用 `python3 ops.py --project-dir . <操作>`；Windows 可使用 `python ops.py` 或 `ops.ps1`。安装器创建用户级命令并登记 PATH，不需要管理员权限；当前终端尚未刷新 PATH 时，继续使用 Python 入口或新开终端。

`config` 打开 UI，先备份并读取实际状态，不启动服务。`check` 核对批准版本和配置冲突。`reload` 在 Backend/Agent 内验证配置可读和抽取配置有效，不重启、不加载模型、不验证下游服务连通性。`deploy` 应用已经审核的启动配置和本地 vLLM 计划；模型计划未部署时，`reload` 会拒绝把它当成已生效。

当前 `ops deploy` 管理 Backend、Agent 及登记为 ops 管理的独立模型，包括 vLLM、Clef、NanoJev。解析引擎由 Backend supervisor 管理，避免重复加载。CPU 局部控制使用 `ops runtime`，不能把一次 CPU apply 当作决策模型或 Agent 已重载。

## 配置事务审核与 guard

UI 展示运行服务的实际值、编辑计划、默认值和生效方式。保存前逐页展示新增、删除、改值、声明说明/默认值/消费者变化以及迁移规则；用户填写原因并输入指定版本确认词后才写文件。凭据只显示变更，不回显内容。取消审核不写配置，不批准版本。

guard 在部署动作之前和容器业务进程启动之前执行。它检查声明与消费者、当前文件指纹、批准记录及对应历史记录。手改实际文件、声明升级未审核或批准记录不一致都会拒绝使用；没有跳过 guard 或未经校验的自动确认选项。用户授权的 Agent 可以使用受控非交互配置事务，仍需原因、基准版本、全部校验及脱敏变更清单；GUI 与自动入口使用相同保存事务。

热配置读取同样检查批准版本，删除新文件不能绕回旧文件。首次启用 guard、配置目录或 observed 可写挂载时，需要用户审核并重新创建容器一次。这里只约束本项目维护的入口，不是对主机管理员的权限隔离。

## 迁移与开发门禁

旧 `settings.json`、`models.json` 只在尚无 canonical 文件时作为迁移输入；已有 `config.json` 时不叠加它们。UI 审核保存后删除旧文件，并把 `.env` 的热参数迁入 `settings`。同义名称统一迁入标准名称，值冲突必须编辑确认。旧 `LLM_*` 参数迁入每个模型，迁移不会自动启用模型。

详见 [配置清理与标准名称迁移](配置清理与标准名称迁移.md)。未知、尚不能确认消费者的用户自有项不会被猜测删除。已确认退役的项目不能重新写入当前实际配置；历史声明与迁移墓碑仍保留。

新增/删除配置、修改消费者、回退或热更属性，必须同步代码、测试、模板、当前声明和新版本文件。模块被删而配置还留着，或应用绕过集中模块直接读环境，门禁报错。不得重新自动扫描声明来消除失败。

```sh
python3 -m qasystem_config.config_contract
python3 -m pytest -q
```

测试与发布门禁另见根 `AGENTS.md`；88 用现有 `qasystem_backend`，不新建评测 Backend。用户已允许 Agent 通过受控事务操作配置并生成变更清单；代码合并本身不会自动修改部署实际文件。

## 2026-10-14：独立模型与调用路由统一

独立聊天 vLLM、Clef、NanoJev 都由 `ops` 管理；基础 Compose 不再包含重复的 Clef/NanoJev 启动定义。该批 .3 声明 237 项，其中部署模板 150 项、内部项 87 项；这些数量不包含 `config.json` 的逐模型记录字段，也不是实际进程读取项数。旧原生模型启动变量与 MinerU 的重复 vLLM 启动变量仅用于 UI 提出迁移，不再覆盖已登记模型。

`config.json.models` 按 `engine`（vllm/native）和 `adapter`（chat/clef/nanojev）登记，记录相对 `HOST_MODELS_DIR` 的权重路径、设备、端口、预算和引擎参数。`device` 使用 `cpu` 或 `gpu:<物理编号/UUID>`，内部 `cuda:0` 从隔离后的设备推导；GPU 不可用明确失败，不回退到 CPU。新增同类模型按 n 添加关闭的记录，不新增模型专属环境变量。扫描到目录只显示存在，不代表文件完整，更不会自动勾选。

`services` 登记本地模型或远程 API；本地地址由稳定服务名和固定内部端口 8000 推导，不重复配置目录、GPU或地址。`routes` 指定真实用途选择的 service ID，Backend 从同一批准快照解析，新请求使用新路由，在途请求保持原快照。当前实际覆盖抽取和实体数量选择；评测仍按每轮 CLI 临时选择，不恢复默认 judge 计划。远程 API 登记不启动容器，凭据只引用已有环境变量。账号共额度保留明确的 quota_group，不根据服务ID推断独立账号；当前限流池仍是进程内机制，不能宣称跨进程总额度已实现。

MinerU 解析引擎仍由 Backend worker/supervisor 管理：`mineru-vlm` 的 `manager=backend-worker`、`device=worker` 使用现有任务GPU，或显式选择一个可用GPU。`ops` 只登记参数，不生成额外常驻实例；重复启动会报错。既有解析、队列和本地算法能力没有删除。
