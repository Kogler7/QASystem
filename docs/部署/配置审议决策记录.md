## 2026-10-14 · 抽取算法策略与 LLM 服务能力分开维护

用户否决下面原先保留公共抽取高级项的建议，要求外部 LLM API 能力限制单独配置，算法调度参数由各版本代码维护。理由：抽取算法不共享同一套需求，KG_EXTRACT_LLM_* 很少手动调整，已成为维护负担。下表仅保留作为被替代方案的记录，不作为实现指令。

| 配置项 | 当前默认 | 建议 | 说明 |
| --- | --- | --- | --- |
| KG_EXTRACT_LLM_MAX_INPUT_TOKENS | 65536 | 保留高级项 | 一次调用的输入预算，不能超出实际服务上下文允许的剩余空间 |
| KG_EXTRACT_LLM_MAX_OUTPUT_TOKENS | 空，回退到16384 | 保留为唯一标准输出预算，默认16384 | 一次调用最多生成多少token |
| KG_EXTRACT_LLM_MAX_TOKENS | 16384 | 迁入 MAX_OUTPUT_TOKENS 后删除重复配置 | 当前已是输出预算旧名；冲突经UI审核 |
| KG_EXTRACT_LLM_TIMEOUT_SECONDS | 300秒 | 保留高级项 | 一次模型调用的超时，不是整份文档耗时上限 |
| KG_EXTRACT_LLM_DISABLE_THINKING | 1 | 保留，以“启用模型思考”友好展示并正确反向映射 | 模型适配器按实际能力发对应参数；不支持时不发送不兼容参数 |

环境配置迁移不能自动删除仍需兼容的请求协议 max_tokens 字段；公共读取、各版本消费者与旧请求兼容须一起验证。

最终决定：

- 外部服务记录维护服务能力和账号配额：上下文上限、服务输出上限、实际并发与 QPS/QPM 等；地址、模型、凭据引用继续登记在同一服务来源。共享账号配额按账号/配额组协调，不能按不同算法各算一份。
- 各算法版本在代码中维护自己的输入/输出预算、是否思考、恢复与重试策略、任务时间预算，不要求用户维护公共抽取环境旋钮，也不改放到另一份用户可编辑大 JSON。
- 本组五项 KG_EXTRACT_LLM_MAX_INPUT_TOKENS / MAX_OUTPUT_TOKENS / MAX_TOKENS / TIMEOUT_SECONDS / DISABLE_THINKING 的用户入口退役，按上述两层职责拆分消费者；旧自定义值与行为变化由 UI 明示审核。
- 算法请求不能突破实际服务能力；超出时按算法策略拆分或明确报错，不静默丢弃正文。未知 API 能力不能猜测；服务硬上限与算法默认预算不是一回事。
- 公共 HTTP 传输超时与算法整份文档/单次生成预算需要明确区分。服务参数是否支持思考的能力描述也不能等同于算法是否选择思考。
- 请求协议中的 max_tokens 等兼容字段、本轮显式评测覆盖不因环境配置清理直接删除。其余 KG_EXTRACT_LLM_* 项逐项归类，不能将地址、密钥或共享账号限流与算法参数一起盲删。

- 服务先登记，再被用途选择；服务ID是调度身份，不按调用算法创建独立额度。

- 同账号的不同服务另共同受账号总额度约束；服务级并发和账号级限额同时满足。
- 统一调度复用现有内部Redis与集中外部服务入口，不新添队列地址或外置Redis用户配置，不让算法各实现一套router/限流器。

- 队列仅保存凭据引用或auth_context_id，不携带Authorization/真实密钥；日志不可输出凭据。

此组在模型路由提交与远端合并后独立实现，不把已登记路由或进程内限流冒充完整统一排队功能。
