# 88 小模型容量与性能测试记录（2026-10-11）

## 结论与使用边界

本次测试机器为 88（tangshan88），单张 RTX 3090 24 GiB，不能将结果直接当作生产 A40 的性能。所有长度均为 token，输入与输出共用上下文预算，不能同时取各自最大值。吞吐为单请求生成速度，不是并发总吞吐。

上述新模型“已完成最大输入”是已测试下界，不是逐 token 找出的精确物理极限。输出申请测试只收到 16 个非空文本事件便取消，不能据此声称几十万 token 输出完整跑通。现有 8B 的 32688 输出则确实完整完成。

Qwen3.5-4B 在这批模型中兼具较快 prefill 和较大输入容量；9B 在中文抽取小样本中格式遵循更好。Gemma 短输入生成快，但长输入 prefill 明显较慢。27B INT4 在本次统一 90% 显存预算下无可用 KV 容量，启动失败；不代表提高预算或多卡也无法运行。

## 测量方法与异常

使用 `/v1/completions`，随机种子取用例标签，输入为 1000–9000 范围内的 token ID，精确控制长度；`temperature=0`、`ignore_eos=true`。这是容量负载，不代表自然语言质量。短输入重复 2 次，长输入 1 次；预热行单列，不纳入速度比较。

Prefill 为 Prometheus `request_prefill_time_seconds_sum` 前后差；仅请求计数差恰为 1 时采信。TTFT 是客户端首个非空文本到达时间，包含排队、网络、调度等，不能代替 prefill。生成速度优先采用 `(completion_tokens-1)/server_decode_s`，避免 SSE 文本合并和 UTF-8 空片段造成偏差；全程耗时从发请求到结束。

Gemma 的 65536 输入用例虽完成，但对应指标计数差为 10，不能把混合指标当作该请求 prefill，因此该行 prefill/服务端生成速度留空，保留 TTFT 与总耗时。131072 输入完成，prefill 149.554 秒。261120 输入用例 HTTP 200 后 300.155 秒仍无首个文本，记录为超时；之后的近上限长输入测试被主动取消以节省时间，未获得完整结果，不能说 262144 上限已验证。

Qwen3.5-9B 接近上下文上限时发生 KV cache 抢占重算，原始累计指标记录 6 次 preemption，prefill 从 65536 输入的 19.495 秒升至 70784 输入的 42.506 秒。部署不宜直接把临界长度视为稳定服务容量。

Qwen3.8-27B INT4：权重占约 18.37 GiB，90% 预算下剩余 KV 空间约 0.15 GiB，报 `Cannot auto-fit max_model_len: not enough GPU memory available to serve even a single token`。未产生有效请求数据。

旧版 8B 扩容时 KV 容量为 32704 tokens，但保留块等开销使实测输入 32688+1 完成、32689+1 在 40 秒内无输出。新版对比还改变了 max_num_seqs 等配置，容量差异不能全部归因于 vLLM 版本。

## 统一镜像补测结论

Gemma 在统一镜像内直接使用全局 `vllm`，未挂载临时 venv。512 输入 + 512 输出：prefill 0.181 秒、生成 81.41 token/s；4096 输入 + 512 输出：prefill 1.537 秒、生成 77.38 token/s，与首轮结果接近。完整 4096 输出耗时约 51.1 秒。申请 262143 输出被接受并开始生成后主动取消，超出上下文总长的输入/输出请求均返回 400。12 个中文抽取样例严格事实及对象 schema 均通过。

## 中文抽取质量小样本

共 12 个中文事实抽取用例，温度 0、最多输出 1024 token、请求关闭 thinking；不使用受约束 JSON 解码，不修复模型输出。要求单个 `{"facts":[["主体","关系","客体"]]}` 对象。它不是标准榜单，也未经过生产抽取流水线全量门禁，不能据此宣称某模型整体能力更强。
