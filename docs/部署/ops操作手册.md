# ops 操作手册

本文说明当前已经提交的操作入口。独立 vLLM、Clef、NanoJev 已由 ops 模型记录管理；API 服务、共享账号和用途选择已接入表单与跨进程调度。88 尚未部署本轮配置改动；更新源码不等于已经审核服务器配置。后续清理尚未全部完成，旧兼容入口的边界见[LLM 服务与统一调度](LLM服务与统一调度.md)。

## 首次使用

在宿主机操作，不在 Backend 容器里操作。需要 Python、Docker 和 Compose；启动 GPU 模型还需要 NVIDIA 驱动及容器 GPU 支持。权重需事先下载到宿主机，ops 不会因勾选自动下载权重。

交付包的部署根目录包含 `ops.py`、`docker-compose.yml`、`.env.example` 和 `runtime/`。进入这个目录：

```bash
python3 ops.py --help
python3 ops.py install
```

安装器把命令绑定到这份部署目录，在用户目录创建启动器并登记 PATH，无需管理员权限。Linux 重新登录 SSH 后使用 `ops`；当前终端也可执行 `export PATH="$HOME/.local/bin:$PATH"`。Windows 使用 `python ops.py install`，然后重新打开终端。目录移动后需要重新安装；发现同名其他命令时会拒绝覆盖。

不安装也能使用：将下文的 `ops` 换成 `python3 ops.py`。Windows 换成 `python ops.py`。这些 Python 命令均在包含入口文件的目录执行。

如果源码目录与部署目录分开，尚未放置部署根入口，可显式指定根目录。例如 88 现有目录布局在同步新版源码后，可使用：

```bash
python3 /mnt/data3/qasys/qasystem/ops.py --project-dir /mnt/data3/qasys config
```

后续把 `config` 换成 `check`、`deploy`、`status`。这种布局要安装短命令，先按交付布局放好部署根 `ops.py` 及其依赖，不能直接绑定不存在的入口。不要在旧源码上执行示例并假定新版功能已经存在。

## 配置并部署独立模型

```bash
ops config
ops check
ops deploy
ops status
```

1. 设置 `QASYSTEM_ENV_IMAGE`、`QASYSTEM_SOURCE_DIR` 和 `HOST_MODELS_DIR`。源码、权重分别只读挂载，镜像沿用 `qasystem-env-v1`。
2. 在“模型”分区勾选模型，选择适用的推理方式和设备，设置宿主端口、权重相对路径及引擎参数。vLLM 可设置上下文和显存比例；Clef/NanoJev 使用原生适配器参数。GPU 编号需要在允许范围内；不要直接照搬生产默认的 `4,5,6,7` 到卡数不同的测试机。MinerU 的解析引擎仍由 Backend worker 管理，不能再登记一个由 ops 重复启动的实例。
3. 按 `s`，逐页审核差异，填写变更原因并输入界面要求的确认词。取消不批准、不写入实际配置。Agent 不能替用户确认。
4. 退出后执行 `ops check`，再执行 `ops deploy`。部署检查已批准版本、模型启动条件、GPU 与端口冲突，并应用启用计划；当前还会重新创建 Backend、Agent。
5. 用 `ops status` 查看配置批准版本及容器状态，再做一次实际推理请求验证。配置批准、容器运行、模型能完成请求是不同状态。

打开界面不会启动服务；扫描到权重不会自动启用；保存只记录配置。完整权重校验需要在界面按 `v` 并输入 `verify`，会读取大文件，可能耗时数分钟。`ops check` 不执行这项完整校验，也不验证下游连通性。

修改启动参数后执行 `ops deploy`，不能仅用 `restart`：已有容器的环境、GPU、挂载与端口不会随 `.env` 改动而更新。普通源码修改无需重建环境镜像。

## 界面按键

| 按键 | 操作 |
| --- | --- |
| ↑ / ↓ | 选择项目 |
| ← / →、Tab | 切换分区 |
| Space | 勾选模型或切换布尔项 |
| Enter | 编辑当前项目 |
| d | 恢复当前项默认值 |
| / | 按名称、说明搜索 |
| PgUp / PgDn | 翻页 |
| r | 重新查询实际运行状态 |
| s | 审核并保存 |
| v | 显式启动完整权重校验 |
| a | 审核并部署，按界面提示确认 |
| q | 退出 |

`[启动]` 表示修改后需要重新创建相应服务；`[热更]` 表示已支持的新请求动态读取。实际状态行用于查看，编辑计划在相应配置项中修改。“未核实”不能当作当前默认值；实际值与计划值不一致时先查是否部署过。

## 常用命令

| 命令 | 用途与边界 |
| --- | --- |
| `ops config` | 查询状态、编辑、人工审核；入口时备份原配置 |
| `ops check` | 检查批准版本、结构和配置冲突，不部署 |
| `ops deploy` | 应用已批准的启动配置和独立模型计划 |
| `ops reload` | 检查 Backend / Agent 内热配置可读，不加载模型、不重启、不验证下游请求 |
| `ops status` | 查看配置批准状态和容器状态 |
| `ops history` | 查看本地版本和读取记录 |
| `ops history --json` | 查看脱敏 JSON 汇总 |
| `ops logs backend agent` | 查看 Backend / Agent 最近日志 |
| `ops restart backend agent` | 重启现有容器，不更新容器启动环境 |

热参数审核保存后由新请求读取，在途请求保留已有快照。提高进程配额池已有并发上限等情况仍需重启，边界见[配置体系说明](配置体系说明.md)。不要把 `reload` 当作万能生效命令。

## 注册 API 服务并选择用途

在 `ops config` 中先登记账号及其额度，再登记 API 服务的名称、地址、模型、凭据变量引用和实际能力上限，最后为知识抽取、图谱检索或 Agent 选择已登记的服务。字段逐项编辑，不需要手写供应商 JSON。共用账号的服务关联同一账号记录，不复制真实密钥。

审核保存后，新请求使用新的服务快照；在途任务继续使用原快照。已登记服务共用 Redis 请求排队与服务/账号并发、QPS、QPM。这里不管理供应商 TPM，网络分区下已发出的 HTTP 请求也不能保证立即停止。完整能力与验证边界见[LLM 服务与统一调度](LLM服务与统一调度.md)。

## 常见问题

| 现象 | 处理 |
| --- | --- |
| 找不到 `ops` | 新开终端检查 PATH，或直接使用 `python3 ops.py` |
| UI 提示需要交互终端 | 交互 SSH 登录，远程单命令使用 `ssh -t` |
| guard 拒绝部署 | 用 `ops config` 查看版本和差异，人工审核；不要手改批准文件绕过 |
| 修改 `.env` 后仍是旧值 | 手改会使批准指纹失效；通过 UI 审核后部署，启动参数需要重新创建容器 |
| 权重已找到但没有模型服务 | 检查是否勾选、审核并执行部署；目录存在只证明目录检查通过 |
| `reload` 提示模型计划未部署 | 模型启动参数需要 `ops deploy` |
| 检查通过但请求失败 | 查看容器状态及日志，单独验证实际服务请求；结构检查不证明连通性 |

配置历史位于部署根 `runtime-config/`。历史归档可能含凭据，只留本机，不提交 Git、不放交付包。更多维护规则见[配置体系说明](配置体系说明.md)和[配置清理与标准名称迁移](配置清理与标准名称迁移.md)。

## 执行任务恢复的边界

执行层现在自动维持长任务心跳和GPU资源预约，用户无需设置心跳间隔或预约TTL。`EXECUTION_REAPER_MIN_IDLE_SECONDS`仍是滞留消息进入恢复检查的等待时间；它不是模型调用或任务超时。只有取走消息的消费者实例失联后，消息才能被回收。任务已完成但进程没来得及确认消息时，只补确认，不重做任务。

资源续期失败会记录本地错误，丢弃本次结果并停止自动重试；在`ops status`和执行日志中排查Redis与worker后，再人工重试。不能把配置已批准、容器可读或心跳正常当作任务完成证据。常驻模型的启停和账号服务限流继续由原有ops服务登记管理，本批没有改动模型地址、密钥或GPU选择。详见[执行任务恢复与GPU预约](执行任务恢复与GPU预约.md)。
