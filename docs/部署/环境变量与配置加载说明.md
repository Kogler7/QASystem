# 环境变量与配置加载说明

本文说明 QASystem 在本地开发、Docker Compose 和其他托管环境中的配置来源、加载顺序及生效方式。

## 基本原则

- `.env.example` 是可提交的配置模板，不存放真实密钥。
- 仓库根 `.env` 是本地配置文件，也是当前 Docker Compose 的 `env_file`。
- Docker、Kubernetes、systemd 和 CI/CD 等托管环境应把配置注入进程环境。
- Server 仅在未检测到托管环境时加载仓库根 `.env`。
- 配置读取统一遵循“进程环境优先”，dotenv 不覆盖已经存在的变量。

## 配置来源与优先级

优先级从高到低为：

```text
Docker/Kubernetes/操作系统注入的进程环境变量
    ↓
本地开发使用的仓库根 .env
    ↓
代码默认值
```

后端使用 `load_dotenv(..., override=False)`，因此 `.env` 不会覆盖同名进程环境变量。

## Server 的加载判断

启动入口调用 `backend.app.environment.configure_runtime_environment()`，判断规则如下：

| 条件 | 是否读取根 `.env` |
| --- | --- |
| `QASYSTEM_LOAD_DOTENV=true` | 是，显式强制加载 |
| `QASYSTEM_LOAD_DOTENV=false` | 否，只使用进程环境 |
| 未设置开关，但进程已有 `ENVIRONMENT` | 否，视为托管环境 |
| 开关和 `ENVIRONMENT` 都未设置 | 是，视为本地直接启动 |

`QASYSTEM_LOAD_DOTENV` 支持 `true/false`、`1/0`、`yes/no` 和 `on/off`；其他值会使启动快速失败，避免误用模糊配置。

需要注意：本地直接启动时，加载判断发生在读取 `.env` 之前。因此即使根 `.env` 中写有
`QASYSTEM_LOAD_DOTENV=false`，只要启动进程此前没有注入该变量，本地启动仍会自动读取根 `.env`；
Docker Compose 则会先通过 `env_file` 注入该变量，所以 Server 不会再次加载文件。

## Docker Compose

`docker-compose.yml` 使用：

```yaml
env_file:
  - .env
```

Compose 在创建容器时读取根 `.env` 并注入 backend 进程。推荐配置：

```env
QASYSTEM_LOAD_DOTENV=false
ENVIRONMENT=production
```

宿主映射端口由 Compose 层变量控制：`BACKEND_HOST_PORT`（默认 `8006`，已列入 `.env.example`）和 `AGENT_HOST_PORT`（默认 `9180`，已列入 `.env.example`）。二者只影响宿主机发布端口，不改变容器内端口（Backend 8000、Agent 9180）。

修改 `.env` 后，`docker compose restart` 不会重新创建容器环境。应执行：

```powershell
docker compose up -d --force-recreate backend
```

只修改环境变量不需要重建镜像；修改 Python 代码或依赖后才需要重新构建镜像。

## 本地启动

本地 PowerShell 直接运行时，如果没有预先设置 `ENVIRONMENT` 或 `QASYSTEM_LOAD_DOTENV`，后端会自动加载仓库根 `.env`：

```powershell
$env:PYTHONPATH="$PWD;$PWD\agent"
Set-Location backend
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

如需完全忽略 `.env` 并只使用当前终端变量：

```powershell
$env:QASYSTEM_LOAD_DOTENV="false"
$env:ENVIRONMENT="development"
```

本地修改 `.env` 后需要重启 Uvicorn。业务配置在模块导入时读取，不支持运行中热更新。

## LLM 配置分组

| 模块 | 环境变量前缀 |
| --- | --- |
| 知识抽取 | `KG_EXTRACT_LLM_*`、`KG_EXTRACT_ALGO_VERSION` |
| 图谱定位与实体链接 | `GRAPH_LLM_*` |
| Agent 运行时 | `AGENT_LLM_*` |

知识沉淀逐切片调用 LLM 时，可配置：

```env
KG_EXTRACT_LLM_MAX_CONCURRENCY=4
KG_EXTRACT_LLM_QPS=2
KG_EXTRACT_LLM_QPM=60
KG_EXTRACT_LLM_DISABLE_THINKING=1
KG_EXTRACT_THINKING_PASSES=relation,repair_relation
KG_EXTRACT_THINKING_MAX_TOKENS=32768
KG_EXTRACT_JEV_ENABLED=0
KG_EXTRACT_JEV_MODEL_PATH=/models/nanojev
KG_EXTRACT_JEV_ACCEPT=0.9
KG_EXTRACT_JEV_REJECT=0.9
```

- `MAX_CONCURRENCY`：同时在途的请求数，至少为 `1`。
- `QPS`：一秒滑动窗口允许的最大请求数，`0` 表示不限制。
- `QPM`：一分钟滑动窗口允许的最大请求数，`0` 表示不限制。
- 首次 LLM 请求和 JSON 格式重试都会占用配额。
- `DISABLE_THINKING=1` 时所有抽取 pass 关闭思考；设 `0` 后仅 `THINKING_PASSES` 列出的步骤（默认关系/关系修复）使用 `THINKING_MAX_TOKENS`。
- `JEV_ENABLED` 默认关闭。打开后在已绑定 GPU 的 worker 中加载 `/models/nanojev`（`C-Tianyu/NanoJev`）；模型不存在、checkpoint 不完整或处于 `remote-only` 则抽取显式失败。权重通过 `docker/download_models.py --jev` 写入 `HOST_MODELS_DIR`，不进环境镜像。只有关系 choice 概率达到 `JEV_ACCEPT` / `JEV_REJECT`（默认均为 0.9）才跳过关系 LLM；其余 pair 与无法确定性锚定的证据仍走抽取 LLM。实体模糊合并同样只在 `JEV_CHOICE_CONFIDENCE` 以上才合并。
- `KG_EXTRACT_ALGO_VERSION`：选择知识抽取算法版本，`latest`（默认，使用独立的 `latest` 包）或显式 `v2` / `v3`；Backend 抽取接口与 MCP `kg_extract_v2` 共用。做版本对比评测时显式设为 `v2` 或 `v3`。

## 排查配置是否生效

容器内只检查非敏感配置：

```powershell
docker compose exec backend python -c "import os; print({k: os.getenv(k) for k in ['ENVIRONMENT','QASYSTEM_LOAD_DOTENV','KG_EXTRACT_LLM_MAX_CONCURRENCY','KG_EXTRACT_LLM_QPS','KG_EXTRACT_LLM_QPM']})"
```

不要在日志或排障命令中输出 `*_API_KEY`、数据库密码或其他密钥。

知识沉淀成功响应的 `data.stats.extraction.scheduler` 也会返回实际生效的并发、QPS 和 QPM，但不会返回密钥或 LLM 地址。

## 统一执行层

生产和本地完整联调默认使用以下配置：

```env
EXECUTION_MODE=async
EXECUTION_REDIS_URL=redis://redis:6379/1
MCP_EXECUTION_MODE=sync
```

`EXECUTION_MODE=inline` 仅用于显式单元测试和算法断点调试。`EXECUTION_MODE=async` 描述内部计算通过队列和 Worker 执行，不改变现有业务 HTTP API 默认同步返回的协议；只有 `Prefer: respond-async` 或新增 Jobs API 才默认立即返回 `202`。显式异步调用可从 `execution.result_url` 获取最终 envelope。`MCP_EXECUTION_MODE=sync` 是生产默认：重工具进入同一队列，但调用方等待并获得原工具结果；设为 `async` 才返回持久任务句柄。异步执行层找不到 Redis 或无法入队时必须失败关闭并返回 `503`，禁止自动回退到入口进程。GPU Worker 使用 `EXECUTION_GPU_*` 配置记录显存预算和 Lease；目标 8 卡 A40 设置 `GPU_DEVICE_IDS=4,5,6,7`，单容器 supervisor 仅为选中的后四卡派生 vLLM 和 Worker 子进程，并自动设置各子进程的 `CUDA_VISIBLE_DEVICES`。

执行失败重试尊重错误码协议（见[错误码协议](../接口/错误码协议.md)），非 retryable 错误码不再白重试。Worker 另内置 PEL 滞留消息重投做崩溃恢复：`EXECUTION_REAPER_ENABLED`（默认 `true`）、`EXECUTION_REAPER_MIN_IDLE_SECONDS`（默认 `600`）、`EXECUTION_REAPER_INTERVAL_SECONDS`（默认 `60`）。

## 可观测性与告警

```env
QASYSTEM_ALERT_WEBHOOK=
QASYSTEM_ALERT_STAGE_SLOW_PARSE_SECONDS=
QASYSTEM_ALERT_STAGE_SLOW_CHUNK_SECONDS=
QASYSTEM_ALERT_STAGE_SLOW_EXTRACT_SECONDS=
```

- `QASYSTEM_ALERT_WEBHOOK`：钉钉/企业微信机器人 webhook（text 消息格式）。留空则不发送任何告警；同 event+request_id 60 秒内去重；发送失败只记日志，不影响主流程。
- 三个慢阶段预算变量（秒）：知识沉淀流水线对应阶段超过预算即发送 `slow_stage` 告警，只告警、不中断任务；留空或 0 表示不告警。
- 指标端点 `GET /api/v1/observability/metrics`（不鉴权，与 `/health` 一致）输出队列深度、job 状态计数、告警/空抽取计数与各阶段耗时分位数；request_id 经 contextvars 贯穿服务日志，空抽取会写入 `stats.extraction.empty_reason` 并计数 `empty_extraction_total`。

## 流水线解析页分片

```env
KNOWLEDGE_PIPELINE_PARSE_SHARDING=false
```

知识沉淀流水线（`POST /api/v1/pipelines/knowledge-ingestion`）内 PDF 解析默认整篇编排；设为 `true` 后走页分片编排加速（复用 `EXECUTION_VLM_SHARD_MIN_PAGES` / `EXECUTION_VLM_SHARD_COUNT`，按存活 VLM Worker 并行）。非 PDF 文件、`options` 显式 `page_sharding=off`、inline 执行环境（无队列）自动回退整篇解析。
