# 环境变量与配置加载说明

应用通过 `qasystem_config.configuration` 读取配置。业务模块不得直接读取或修改环境变量；公共核心和声明门禁约束读取来源、消费者、默认回退及生效方式。完整架构与迭代记录见 [配置体系说明](配置体系说明.md)，操作命令见 [ops 操作手册](ops操作手册.md)。

## 配置来源

| 来源 | 用途 | 修改后的操作 |
| --- | --- | --- |
| 根 `.env.example` | 唯一部署环境默认值模板，无真实凭据 | 随声明版本、消费者和测试提交 |
| 部署 `.env` | 容器环境、挂载路径、端口和部署参数 | 通过 ops 事务保存，再执行 `ops deploy` |
| `runtime-config/config.json` | 已提交的热参数、CPU 进程计划、模型记录、API 服务与功能路由 | 根据声明的生效方式使用新请求、进程应用或部署 |
| 声明与私有版本记录 | 校验配置版本、消费者和生效记录 | 自动维护，不能直接改写历史 |

当前声明在 `qasystem_config/config-declarations.json`，新声明历史在 `qasystem_config/config-releases/`。迁移前的 `docker/config-releases/` 仅保留不可改写的历史证据，不是读取入口。实际配置历史位于部署私有运行时目录；原始凭据不进入 Git 或脱敏 JSON 视图。

## 生效顺序

中央模块先确认配置项已登记，再按其声明读取。已提交的热参数从挂载的运行时配置中获取，影响后续请求；进程参数从有效的运行时计划读取，不回退到旧容器环境。其余启动参数读取创建容器时注入的环境，并使用声明登记的回退。不要把“已保存”“已应用”“服务健康”当成同一个状态。

CPU worker 数量标记为 `[进程]`：保存计划后执行 `ops runtime apply`。该操作停止旧 worker 领取新任务，等待在途任务完成，再调整进程数量，Backend API 保持运行。排空超时会报告实际状态，不自动强杀。GPU worker、Agent 及模型容器不属于这一批 CPU 局部控制范围。

独立模型和外部 LLM API 通过注册记录管理。功能选择服务，同一服务使用统一队列与能力限制；不要重新加入已退役的全局模型地址、GPU 或算法生成参数。最新可用字段以 ops 界面及声明为准，本文不重复维护一套参数默认值。

## 容器与本地开发

Compose 负责拓扑、挂载、入口、端口和健康检查。它在创建容器时通过 `.env` 注入环境，并固定内部启动约定；入口先执行 `python -m qasystem_config.config_guard`，校验当前文件、已提交版本与历史，再启动应用。

修改 `.env` 后，单纯 `restart` 不会改变既有容器环境。使用 `ops deploy` 应用容器属性。修改已挂载的热配置无需重新创建容器；端口、挂载、GPU 可见范围变化仍需 recreate。只有环境依赖变化才重建 `qasystem-env-v1`，普通源码更新替换外置源码。

本地开发仍通过中央启动模块判断 dotenv：容器内或已有 `ENVIRONMENT` 时不加载；非容器且没有 `ENVIRONMENT` 时加载仓库根 `.env`，只补充未注入值。已删除 `QASYSTEM_LOAD_DOTENV`，不能用旧开关改变加载行为。开发入口的显式参数受专属启动合同约束，受管部署不能借 CLI 覆盖登记参数。

## 运维与检查

```bash
ops config plan
ops config
ops check
ops deploy
ops status
ops history
```

自动配置可使用同一受控 `plan/apply` 事务，必须带原因、来源与基准版本；具体参数见操作手册。禁止手写实际配置绕过 guard。发布和打包使用 `python -m qasystem_config.config_contract` 校验声明、消费者和历史，容器启动另外验证部署实际配置。

`ops --help` 和公共配置读取不依赖 Docker daemon。部署、容器状态与容器重启需要 Docker。公共核心不导入界面和 Docker 工具，不保留旧 `docker.configuration` 兼容副本。
