# Clef-flash 与 NanoJev 部署

两套模型共用 `qasystem-env-v1`，权重仍由 `HOST_MODELS_DIR` 只读挂载到 `/models`，
源码由 `QASYSTEM_SOURCE_DIR` 只读挂载到 `/app`。交付脚本包含 `clef_service/` 与 `nanojev_service/`。
两套服务单进程常驻，启动时加载权重并预热后才报告 ready。

## 环境与模型准备

执行 `./build-image.ps1` 构建并验证环境镜像。移除旧 Clef 独立环境需要重建镜像；
以后只改应用源码时不重建。Clef、NanoJev 与 Backend 共用 Python 环境，
`clef_service/requirements.txt` 的重叠依赖与 Backend 保持一致，不重复安装 Torch/CUDA。
已在 88 的 RTX 3090 上验证 Torch 2.9.0、Transformers 5.17.0 的真实模型加载、预热、
中英文文本/JSON 输入，以及 choice、noul、score 三类推理；两套模型均可使用此组合。
不把源码、模型或宿主虚拟环境复制进镜像。

联网准备机可执行：

```powershell
./download-models.ps1 -Jev -Clef -SkipDocling -SkipMineruPipeline -SkipMineruVlm -SkipEmbedding
```

NanoJev 下载到 `models/nanojev`，Clef 下载到 `models/clef-flash`。
已有 88 权重可直接使用，无需重复下载。下载源和固定版本见 `docker/download_models.py`。
离线交付分别传输镜像、源码包和模型目录。

## ops 管理的常驻服务与 GPU 分配

从配置版本 `2026.10.14.3` 起，基础 Compose 不再定义 clef/nanojev 两个服务。部署根运行 `ops config`，在模型分区勾选 `clef-flash`、`nanojev`，分别设置 `engine=native`、适配器、`device=cpu` 或 `gpu:编号/UUID`、权重相对路径、宿主监听/端口和原生引擎参数。两者均使用共同的 `HOST_MODELS_DIR`，内部GPU设备自动为 `cuda:0`。

目录存在不代表权重完整，不触发启用。人工审核保存后通过 `ops deploy` 启动，生成的服务名为 `model_clef_flash`、`model_nanojev`，容器内固定端口8000。服务仅在模型加载和预热成功后健康；`ops status`/`ops logs`查看实际状态。宿主默认监听127.0.0.1，Backend通过Compose内网访问，不需要将推理口公开。

服务分区的 `services` 登记本地/API服务，`routes.entity_count` 选择默认实体数服务；显式请求模型仍须有唯一已启用登记，不能被默认路由覆盖。独立服务密钥使用已有 `CLEF_API_KEY`/`CLEF_SERVICE_API_KEY`、NanoJev对应引用，不复用用户 Authorization，不把认证头写入队列产物。

保留生产 `GPU_DEVICE_IDS=4,5,6,7`。ops把独立模型GPU预留放入审核，Backend既有调度排除这些设备。两模型共卡须配置预算总和不超过100%并验证真实峰值；GPU不可用不会回退CPU。旧native目录/GPU/device/端口变量由UI可见迁移，旧内部bind需重新确认宿主发布地址。

旧基础Compose或宿主服务仍属于外部实例，ops不会自动停止或接管。用户需在迁移验证成功后处理旧实例；端口/GPU冲突会阻止新部署。历史测试与质量结论仍以原报告为准，本次模型管理重构尚未在88迁移部署。参见[配置体系说明](配置体系说明.md)和[模型服务路由](../接口/模型服务路由.md)。

## NanoJev

配置 `NANOJEV_SERVICE_URL` 时，Backend 的所有队列 worker 共用常驻 HTTP 模型，
无需在 worker 中加载 Torch 或权重，也不启动另一套 Backend。
保持 `KG_EXTRACT_JEV_ENABLED=0`，服务可用与业务启用分开验证。
只有服务地址为空时才使用原有本地 GPU 加载兼容路径。显式本地探针为：

```sh
docker compose exec -e PYTHONPATH=/app -e CUDA_VISIBLE_DEVICES=空闲卡UUID \
  -e HF_HUB_OFFLINE=1 -e TRANSFORMERS_OFFLINE=1 \
  backend python -m algorithm.knowledge_extract.v2.jev_probe
```

客户端只在 Torch 提供可选 native Triton API 时关闭该扩展，兼容没有 `torch._native` 的发布版。
探针通过只代表可以加载和执行，不代表知识抽取质量通过。
NanoJev 的通用 checkpoint 不等于领域 JEV checkpoint；不得因部署成功直接打开领域决策开关。
抽取启用与质量门禁按 [JEV 决策层](../算法/JEV决策层.md) 和仓库 `AGENTS.md` 执行。

## 88 常驻延迟验证（2026-10-11）

3090 上短文本、每题 3 个选项、每组连续 12 次 HTTP 请求。剔除首个请求后：

| 模型 | 1 题中位数 | 8 题中位数 |
| --- | --- | --- |
| NanoJev | 30 ms | 65 ms |
| Clef-flash | 148 ms | 368 ms |

NanoJev 单独加载约 8 秒，属于启动成本；以上不是长文档或并发吞吐基准。
正式镜像部署后仍需复测健康、稳定延迟和显存占用。

## 共享 Python 环境验证（2026-10-11）

88 上使用临时验证容器、只读源码/权重挂载和 `--network none`，未修改常驻服务。
Clef 与 NanoJev 按顺序加载，比较原独立环境与主环境的英文文本、中文 JSON 两组输入；
每组覆盖 choice、noul、score，重复请求 6 次，并验证请求体超限返回 413、完整上下文超限返回 422。
两环境均通过，choice 选择、noul 二值判定及 token 计数一致，最大概率绝对差为 0.00173。
这是依赖兼容性冒烟验证，不代表领域抽取质量门禁；共用 GPU 上的延迟有波动，不据此作性能结论。
原始记录与对比结果保存在本次工作目录的 `tmp/image-size-validation/`。

主环境使用 Torch 2.9.0+cu129、Torchvision 0.24.0+cu129、Transformers 5.17.0、
Accelerate 1.11.0、Safetensors 0.8.0。Pydantic 清单对齐实际运行版本 2.14.0，
避免旧 2.12.3 固定版本覆盖 MinerU/DocVortex 所要求的 >=2.12.5。
镜像构建仍执行依赖冲突检查和挂载源码的完整运行时检查，只放行已有的三项声明冲突。
