# 知识图谱科研项目质量管理文档撰写计划（交大算法团队）

> 版本：V0.1（研究版）  
> 编制方：交大算法团队  
> 维护方式：先以 Markdown 维护内容基线，待甲方确认后按原模板回填 Excel/DOCX。  
> 研究范围：`docs/质量管理/质量管理要求文件模板`、`质量管理要求文件说明.docx`、仓库现有算法/接口/架构文档及 Git 提交记录。

## 1. 研究结论与执行原则

1. 甲方模板是版式和字段的最终依据；Markdown 只作为内容单一事实源（Single Source of Truth），不得另起一套章节体系。
2. 交大重点负责两类算法：知识沉淀（文档解析至知识落库）和问题求解（Agent loop 驱动标准 MCP 与 Skill 集合）；雪浪负责系统架构、工程实现和主测试执行；信息公司/甲方负责项目管理、业务需求和最终审批。
3. 所有需求、设计、代码、测试、缺陷和迭代成果必须建立可追溯编号：`BR-*`（业务需求）、`SR-*`（软件需求）、`AR-*`（算法设计）、`API-*`（接口）、`TC-*`（测试用例）、`BUG-*`（缺陷）、`RISK-*`/`OPP-*`（风险/机会）。
4. 未在当前仓库或甲方材料中确认的业务事实，不在文档中臆造；统一标记为“待甲方确认”或“知识缺口”。
5. 本项目当前未发现正式迭代数量和日期基线。计划先按 **4 个迭代、每迭代 2–4 周** 建立内容骨架，实际数量以项目经理确认结果为准；一旦变更，周报 Sheet、Sprint Excel、总体计划交付计划和测试排期必须同步调整。

## 3. 建议的迭代基线（待确认）

| 迭代 | 目标 | 交大算法主要内容 | 必须形成的证据 |
|---|---|---|---|
| Sprint 1 | 知识沉淀能力基线 | 文档解析/切片、知识抽取 Graph JSON、基础 `/api/v1` 契约 | SR/AR 初版、API 示例、TC 基线、代码评审、阶段演示 |
| Sprint 2 | 知识沉淀落库与质量控制 | Graph merge 去重、实体/关系校验、向量化、知识落库/外部持久化 | 数据模型、质量规则、TC 扩展、风险复盘、Git 提交 |
| Sprint 3 | Agent loop 问题求解 | 标准 MCP 与 Skill 集合、实体链接、关系/实体剪枝、3 跳探索、GraphContext | 求解设计、性能/异常用例、演示材料、Bug 闭环 |
| Sprint 4 | 集成、稳定性与交付 | Backend/Agent/MCP 联调、取消/队列/错误码、不可用能力显式失败、发布验收 | 集成测试证据、DoD 检查、最终评审、代码版本和交付说明 |

若最终采用其他迭代数量，保留上述“能力分层”原则，重新拆分目标，并同步更新所有迭代型文件。

## 4. 内容编写顺序与依赖关系

### 阶段 A：建立项目事实基线

- 确认项目名称、合同范围、甲方/信息公司/雪浪/交大人员、项目起止日期、迭代数量与周期。
- 从现有仓库提取可作为事实依据的两类算法模块：知识沉淀流水线（文档解析、切片、抽取、合并、向量化、落库）和问题求解运行时（Agent loop、标准 MCP、Skill、图谱导航与执行）。
- 建立术语表、编号规则、责任矩阵和文档版本历史。

### 阶段 B：先写需求，再写计划与设计

1. `05-业务需求.md`：明确业务目标、流程、边界和假设依赖。
2. `04-软件需求.md`：将业务需求拆成可验证的最小软件需求章节，补充输入/输出、异常、性能和安全要求。
3. `01-总体计划书内容.md`、`02-过程裁剪清单.md`、`03-风险机会.md`：以需求范围为基础确定排期、裁剪和风险措施。
4. `06-07-整体设计.md`：把每条 `SR-*` 映射到算法/系统/数据/接口设计。
5. 生成迭代任务、测试用例、代码评审和 Sprint 评审材料。

### 阶段 C：每个迭代的执行闭环

`迭代计划 → 风险/机会识别 → 需求交底 → 设计更新 → 开发与自测 → 代码评审 → 集成/系统测试 → Bug 跟踪 → Sprint 成果评审 → 回顾与下迭代计划`。

## 5. 各文档内容要点

### 5.1 总体计划书（Sheet 2–8）

- 项目概述：项目目标、算法范围、迭代周期/次数、合同范围、术语缩略语。
- 组织结构：明确交大算法负责人、算法开发、算法测试/质量接口人及与雪浪、信息公司的协作关系。
- 资源及培训：GPU/模型/数据/测试环境等作为外部或挂载资源记录；模型不写入镜像交付。
- 外部干系人：列出甲方业务接口人、信息公司项目经理、雪浪架构/测试接口人。
- 评审计划：需求、架构/整体设计、测试用例、核心代码、迭代评审、回顾和里程碑评审。
- 交付计划：每迭代明确源代码、算法说明、接口协议、测试用例/报告、演示材料和发布说明。
- 项目依赖：`APPLICATION_SERVICE_URL`、模型挂载、GPU、外部应用服务、图数据库/搜索能力开通状态等。
- 集成和测试：记录每日/按需集成策略、环境、功能/接口/集成/性能测试工具和方法；对尚未开通的图写入、置信度、文档证据能力明确写“调用时显式失败”。

### 5.2 需求与设计文档

软件需求最小章节建议至少覆盖：文档解析、Markdown 切片、Graph 抽取、Graph 合并、文本/图向量化、实体链接、图谱检索与剪枝、GraphContext 输出、错误码/超时/重试、权限与审计、性能与资源约束。

整体设计文档建议包含：逻辑架构、部署边界、算法组件职责、数据模型（实体/关系/证据/向量）、API 请求响应、幂等/异步/队列、超时与取消、可观测性、质量属性、第三方依赖与降级策略。

### 5.3 迭代型表格

- 周报 Sheet：只记录该迭代已完成情况和下迭代计划；状态、预估工时、实际工时必须可由任务记录或 Git/测试证据核对。
- Sprint 评审 Excel：每次迭代单独复制模板，填入待评审成果、参与人、评审关注点、结论和问题列表。
- 测试用例：`模块` 使用完整层级路径；`关联工作项` 填 `SR-*`，多个用 `|` 分隔；步骤和预期结果编号一一对应；P0/P1 用例优先覆盖核心链路和边界。
- Bug 记录：每条缺陷有唯一 `BUG-*` 编号，并关联 `TC-*`、`SR-*`、迭代、Git 修复提交和回归结果。

## 6. 统一追溯矩阵（维护重点）

| 链路 | 最低要求 |
|---|---|
| 业务需求 → 软件需求 | 每个 `BR-*` 至少映射一个 `SR-*`，未映射项说明裁剪原因 |
| 软件需求 → 设计 | 每个 `SR-*` 映射到设计章节、API 或数据结构 |
| 软件需求 → 测试 | 每个软件需求最小章节至少一个 `TC-*`；核心需求至少含正常、边界、异常用例 |
| 测试 → 缺陷 | 失败用例关联 `BUG-*`；缺陷关闭需有修复版本/提交和回归结果 |
| 迭代 → 评审/代码 | 每个 Sprint 有周报 Sheet、成果评审 Excel、代码评审记录和 Git 提交范围 |
| 风险/机会 → 行动 | 每个高优先级项必须有责任人、措施、跟踪日期、状态和关闭/转移结论 |

## 7. 质量门禁（DoD 对齐模板）

每个迭代在进入成果评审前检查：需求/设计/测试用例已评审；代码已提交配置库；核心代码已评审；算法自测和集成测试有证据；P0/P1 缺陷关闭或有批准的例外；无未说明的接口/数据变更；测试覆盖率、缺陷修复率和性能指标按甲方最终口径填写。发布前另行确认甲方统一验收测试结论。

## 9. 待确认输入（开始正式撰写前必须补齐）
