# 知识图谱科研项目系统架构与整体设计说明书（交大算法团队内容基线）

> 6、7 号模板合并维护；系统架构主责雪浪，交大负责算法、数据和接口设计。本文件依据当前仓库实现，未实现能力明确列为不可用。

## 1. 设计原则与逻辑架构

```text
应用/前端 → Backend FastAPI → 统一执行层/队列 → algorithm 业务函数
                                      ↘ MCP Server（knowledge/graph/data/visualization）
AgentCode API → Agent Runtime → MCP Client ────────────────────────────────┘
外部应用服务 ← external_services/application.py（APPLICATION_SERVICE_URL）
模型/GPU ← /models 只读挂载；源码 ← QASYSTEM_SOURCE_DIR 只读挂载
```

- HTTP 与 MCP 复用同一算法业务实现；算法模块不创建 FastAPI/MCP Server。
- Agent 负责会话决策，Skill 约束流程，知识图谱提供业务事实和 SolutionClass，MCP 仅提供原子能力。
- 不恢复 Neo4j/Elasticsearch 直连；应用团队服务是文件/向量等外部能力入口。

## 2. 组件职责

| 组件 | 主要职责 |
|---|---|
| Backend | API 路由、请求模型、统一响应、任务队列、Worker、SSE、取消和健康检查 |
| algorithm | 文档解析/切片、知识抽取、Graph merge、向量化、数据访问和可视化实现 |
| MCP domains | knowledge 抽取、graph 定位/实体链接/属性/一跳检索、data SQL、visualization |
| AgentCode | LLM↔Tool 执行循环、预算、取消检查、MCP 客户端和异步 Agent API |
| external_services | 应用团队 URL 注册、鉴权上下文和统一 HTTP 客户端 |

## 3. 两类算法设计

### 3.1 知识沉淀算法

知识沉淀由数据处理流水线驱动，负责把外部文档加工为可追溯知识资产：解析、切片、分片抽取、Graph 合并、文本/图向量化，并按配置调用外部知识服务落库。每个阶段保留输入输出、来源切片和失败信息。

### 3.2 问题求解算法

问题求解由 Agent loop 驱动，不把业务流程固化为单一意图识别器或方案规划器。Agent 通过 Skill 约束步骤和证据门，通过标准 MCP 调用知识、图谱、数据和可视化原子工具；多跳探索由多次一跳 MCP 调用组成。

### 3.3 文档与切片

解析产物包含 `file_name/file_type/markdown/content_length/parser`；切片项包含 `text` 和可选 `[start,end] ranges`。semantic 策略采用 Max-Min 算法和 512 维嵌入（实现说明见 `docs/文档切片算法说明.md`）。

### 3.4 Graph JSON

抽取和合并接口以 `graph` 对象承载 `nodes` 与 `relationships`；节点至少保留 id/name/labels/properties，关系保留 head/tail/relation 及关系属性。流水线 merge 后节点可带 `chunk_indices`，用于回溯原文切片。

### 3.5 向量与外部存储

文本向量按输入顺序返回；图 JSON 向量同样按输入顺序返回。配置 `APPLICATION_SERVICE_URL` 后，Markdown 和原始文本切片向量写入应用团队接口；未配置时 `artifacts=null`，不执行伪存储。

## 4. 接口设计

### 4.1 HTTP API

主要接口：`/api/v1/documents/parse`、`/documents/chunk`、`/graphs/extract`、`/graphs/merge`、`/embeddings/texts`、`/embeddings/graphs`、`/pipelines/knowledge-ingestion`、`/jobs` 及 `/health`。统一 envelope 为 `code/info/data/error/execution`。

### 4.2 MCP 原子工具

`locate_knowledge_space`、`get_all_subspaces`、`link_entities`、`query_entity_properties`、`search_graph(depth=1)`、`kg_extract_v2` 等注册在统一 MCP runtime。search_graph 只做一跳，Agent 通过多次调用构造路径；工具不得隐含整套意图识别或方案规划。

## 5. 执行、并发与资源

业务请求可同步等待、显式异步或有界等待；统一队列记录 `auth_context_id`，Worker 维护原子执行和 attempt。PDF VLM 路线达到阈值时按页段投递 `gpu.vlm`，容量不足排队，失败仅重试失败页段并按页序合并。具体队列容量、超时、并发和 SLA 待确认。

## 6. Agent loop 问题求解链路

`ProblemFrame → locate space → link entities → query properties → search_graph(depth=1) → GraphContext/证据门 → SolutionClass 实例化 → MCP/SQL 执行 → 带证据答案`。关键参数保存 `value_source`；无图谱证据时输出知识缺口，不得凭模型记忆补写。

## 7. 错误处理、降级和不可用边界

错误码遵循 `docs/错误码协议.md`，可重试错误保留 attempt；任务终态通过状态或 SSE 判断。图谱写入、置信度、维度刻度、文档证据等接口目前返回 `EXTERNAL_CAPABILITY_UNAVAILABLE`，调用方应展示明确失败原因并保留审计记录。OFD 仅转换为 PDF，不做签名验签。

## 8. 安全、配置与部署

源码、模型、密钥和运行时数据不进入环境镜像；源码只读挂载，模型只读挂载至 `/models`。配置集中于根 `.env.example`；生产保留 `GPU_DEVICE_IDS`（常见 4,5,6,7）。Authorization 仅通过 auth context 使用，不进入 payload、日志、SSE、execution 或结果。

## 9. 可观测性与质量属性

每个任务提供 `job_id`、events/executions/result URL；记录状态、原子任务、资源、重试和错误。目标可用性、RTO/RPO、吞吐、延迟、抽取 F1、检索命中率、覆盖率均待甲方确认。设计追溯：SR-001～SR-015 → 本文第 3～8 节 → 测试用例 TC-*。

## 10. 待确认项
