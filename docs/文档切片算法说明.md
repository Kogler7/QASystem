# 文档切片算法说明

本文说明当前代码实际实现的 Markdown 切片行为。接口字段和请求响应格式见[算法接口协议](算法接口协议.md)。

## 1. 处理流程

文档先由解析器转换为 Markdown，再执行切片：

```text
原始文件 → Markdown → 规则切片 → 定位原文字符范围 → text + range
```

切片长度使用 Python `len(text)` 计算，是 Unicode 字符数量，不是 UTF-8 字节数或模型 token 数。所有策略当前均设置 `chunk_overlap=0`，相邻切片没有人为重叠。

## 2. 策略总览

| `strategy` | 底层实现 | 自定义 `separators` | 长度控制 |
| --- | --- | :---: | --- |
| `recursive` | LangChain `RecursiveCharacterTextSplitter` | 否 | 内置字符回退，通常不超过 `size` |
| `symbols` | 项目实现的多符号拆分与顺序装箱 | 是 | 超长片段按字符硬切 |
| `custom_recursive` | LangChain `RecursiveCharacterTextSplitter` | 是 | 是否严格限制取决于是否配置字符回退 |
| `markdown` | LangChain `MarkdownTextSplitter` | 否 | 最终按字符回退，通常不超过 `size` |

## 3. recursive

默认策略，使用以下分隔符优先级递归切分：

```python
[
    "\n\n",
    "\n",
    "。",
    "！",
    "？",
    ".",
    "!",
    "?",
    " ",
    "",
]
```

算法先尝试保留段落；段落超过 `size` 时继续按换行、句末标点和空格切分，最后使用 `""` 按字符硬切。它适合普通中文或中英文混合正文。

此策略固定使用内置分隔符，请求中的 `separators` 不生效。

## 4. symbols

`symbols` 是项目自行实现的多符号切分算法。未配置 `separators` 时使用：

```python
["。", "！", "？", ".", "!", "?", "\n\n", "\n"]
```

执行步骤：

1. 按配置的每一种符号依次拆分文本，并尽量保留分隔符。
2. 按原文顺序遍历拆出的片段。
3. 相邻片段合并后不超过 `size` 时，装入同一个切片。
4. 单个片段本身超过 `size` 时，直接按字符硬切。

它适合句末标点比较稳定、希望明确控制切分符号的文本。该策略不会计算句子含义或向量相似度。

## 5. custom_recursive

该策略与 `recursive` 使用同一个递归切分器，但分隔符及其优先级由调用方提供。例如：

```json
{
  "strategy": "custom_recursive",
  "size": 500,
  "separators": ["\n## ", "\n\n", "。", ""]
}
```

以上配置表示依次尝试二级标题、段落、中文句号，最后按字符切分。分隔符数组的顺序表示从高层结构到低层结构的回退顺序。

注意事项：

- `separators` 为 `null` 或空数组时，会退回 `recursive` 的内置分隔符。
- 建议把 `""` 放在最后，保证其他分隔符均无法命中时仍可按字符硬切。
- 如果没有配置 `""`，长文本又不包含任何指定分隔符，结果可能超过 `size`。

## 6. markdown

该策略使用 LangChain `MarkdownTextSplitter`。当前依次考虑：

1. Markdown 一至六级标题。
2. 三反引号代码围栏。
3. `***`、`---`、`___` 等分隔线。
4. 段落空行。
5. 换行、空格和字符。

它会优先在 Markdown 结构边界切分，结构块仍然超过 `size` 时继续向更细粒度拆分。

这不是完整的 Markdown AST 解析：接口不会返回标题层级等结构化 metadata，也不保证一个完整章节始终位于同一切片。请求中的 `separators` 不参与该策略。

## 7. 参数行为

### size

`size` 是目标字符长度。切片不会严格等长，算法会优先选择自然边界。`recursive`、`symbols` 和 `markdown` 均具有最终字符回退；`custom_recursive` 是否具有这一保证取决于自定义分隔符是否包含 `""`。

Markdown 标记、链接地址和标题符号等都计入长度，因为切片作用于解析后的 Markdown 原文，而不是去除格式后的纯文本。

### separators

| `strategy` | 是否生效 |
| --- | :---: |
| `recursive` | 否 |
| `symbols` | 是 |
| `custom_recursive` | 是 |
| `markdown` | 否 |

### similarity

当前实现只校验 `0 <= similarity <= 1`，没有把它用于切片计算。不同的 `similarity` 值目前不会改变结果。该字段是预留的语义切片阈值，不代表当前已经实现基于向量相似度的语义切片。

## 8. range 定位规则

切片完成后，服务按顺序在输入 Markdown 中查找切片文本并返回：

```json
{
  "text": "第一段。",
  "range": [0, 4]
}
```

`range[0]` 是开始位置，`range[1]` 是结束位置且不包含该位置字符。偏移基于输入 Markdown 的 Python Unicode 字符索引，不是原始上传文件的二进制偏移。

定位优先从上一切片的结束位置继续查找；找不到时再从全文查找。递归切分器可能清理切片首尾空白，因此相邻 ranges 之间可能存在未包含的空白字符，不能假设所有 ranges 一定无缝覆盖全文。

## 9. 当前实现边界

- 没有基于 embedding 或 LLM 的语义切片。
- 没有 token-aware 长度控制。
- 没有切片重叠。
- 没有 Markdown AST 或章节层级 metadata。
- `similarity` 暂未参与计算。
- `range` 定位依赖切片文本仍能在原始 Markdown 中找到；无法定位时接口返回切片偏移错误。
