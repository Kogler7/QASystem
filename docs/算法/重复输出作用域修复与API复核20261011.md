# 重复输出：repair 作用域实际修复与有限 API 复核

继 41 次隔离研究和 25 次配对消融后，本轮完成可执行的 repair 请求一致性修复及 10 次追加 API 复核。**已修复的是不可能完成的 repair 请求和目录/schema 不一致，尚未证明这个缺陷是长循环的根因，也没有宣布循环彻底治愈。** 少量重复不作为主要失败，本轮没有上线流式取消。

## 实际代码变化

共享 `algorithm/knowledge_extract/repair_scope.py` 接入 v2、v2.2、v3、v3.1、latest 的 `split_extractor.py` 与 `prompt_router.py`。五个版本都依据实际实体目录和当前 schema enum 筛选合法关系签名、可执行 verifier issues，并将 from_id/to_id enum 限定到该目录中的 ID。没有为了满足 issue 扩大 rel_type enum，也不创建替代端点。

required issue 的 expected_relations 有必需项不可执行、target_type 缺失，或目录无合法签名时，保留该问题及原因到 `REPAIR_ISSUE_OUT_OF_SCOPE` 告警。有其他可执行 issue 时继续处理；全不可执行时直接返回空提议，**不向 API 发送空任务**。原 verifier 仍保留缺口，orchestrator 的 `repair_no_new_facts` 不会被改写为修复成功。不同批次使用同一个目录派生契约，避免 prompt 内再次收窄 schema 而与调用方校验器不同步。

v2/v2.2/v3.1 的 prompt renderer 原先又截目录到前 25 个，此预算隐藏在 schema 构造之后。现已删除该重复截断，目录预算交由调用方控制；v3/latest 的调用层 80 目录预算保留。第 26 个正确端点现在能被模型看见。现有实体 repair 路径保留；没有修改公共 table_jsonl、chunking、Judge、队列或凭据。schema 只验证 ID 和合法关系集合，具体 source/rel/target 签名仍须通过候选池校验。

主代理已将修复分批提交为 `e13d8cd`。研究代理没有自行提交、push 或重启服务；Backend 的部署与完整评测由主代理协调。

## 测试证据

`tests/algorithm/test_relation_repair_scope.py` 的 17 项测试覆盖五版本，包含：缺 Constraint 的任务跳过且不扩大 enum；混合问题保留可执行项；第 26 个端点显示、可执行；输入/plan 不变；必需关系集合不静默拆掉一部分；builtin repair 实际不调用 repair LLM、保留未修复 verifier 缺口。同步更新了 v3.1 旧目录截断测试。

五版本算法目录、作用域测试与上一轮消融测试共 **1207 passed、7 skipped**；7 个跳过均来自已有缺失评测 fixture，不是新增豁免。随后修正测试的 prompt 检查，使其直接检查消息内容而非转义后的字符串；最近作用域和 v3.1 prompt 测试 50 项通过。新评测工具测试与作用域共 18 项通过。工具测试校验冻结数据 SHA256、skip arm 不进入 API 计划、正确 Constraint 端点的存在及源文引用。

## API 复核设计

冻结集 `test_data/repetition/repair-fix-v1/`，构建工具 `eval/tools/repair_fix_study.py`。所有参考标签为 **agent-reviewed / provisional，无独立人类 gold**。调用沿用现有统一 Backend 的 SiliconFlow DeepSeek-V4-Flash，温度 0、thinking disabled、16384 输出 token、300 秒超时、无重试、最多两请求并发。两轮顺序反转，共 10 次；没有无限扩展矩阵。

1. 历史异常 repair 清理 JSONL 协议后的冲突请求，两次。其 fixed 侧用当前生产 helper 生成作用域，4 个 issue 全不可执行，因此生产直接 skip，零 API 调用。冻结集保存 skip 请求诊断，但不将它塞入模型要求返回 null。
2. 正向控制：在相同历史原文/目录中，补入代理归纳的 OperationalConstraint 端点 entity-23，只保留对“各事业部” entity-14 的一个问题；schema 根据完整合法端点类型重新生成。它不是只放宽 enum。原样和当前 helper 作用域修复各两次，比较修复是否保留有效任务。
3. 上轮完整覆盖原文的 A/B 语义片各两次，用逐字相同冻结输入再核对小任务是否循环。没有添加“最多输出 20 条”。这些实体任务不经过 relation repair helper，**不能将其表现变化归因于 repair 修复**。

“原样”是冻结历史调用经前轮协议清理的请求，不是重新运行最新合并版本全链路；本轮隔离 helper 贡献，全链路 source/chunks 对照由主代理另跑。第一次启动研究 runner 时错误覆盖了容器 PYTHONPATH，import 失败，没有发出 API 请求；恢复容器已有 PYTHONPATH 后运行了下面 10 次。完整 raw 在 `/app/backend/tmp/repetition-repair-fix-20261011/run`，主机备份 `/tmp/repetition-repair-fix-final-20261011`，本地 `tmp/repetition-repair-fix-20261011/repetition-repair-fix-final-20261011/run`，汇总 `tmp/repetition-repair-fix-20261011/report.json`。凭据未写入工件。

| 条件 | API 次数 | stop / length / 普通超时 | 完整记录/精确唯一 | schema、端点签名 |
| --- | ---: | --- | --- | --- |
| 原冲突 repair | 2 | 2 / 0 / 0 | 各 4 / 4 | 两次均无效，共 8 条 |
| 当前修复、原缺失端点 | 0 | 不适用，运行时直接 skip | 不生成 | 4 issue 保留 unresolved |
| 有 Constraint 端点，原样控制 | 2 | 2 / 0 / 0 | 各 1 / 1 | 均通过 |
| 有 Constraint 端点，修复控制 | 2 | 2 / 0 / 0 | 各 1 / 1 | 均通过 |
| A 语义片 | 2 | 2 / 0 / 0 | 17 / 16；22 / 21 | 均通过，各仅重复 1 条 |
| B 语义片 | 2 | 2 / 0 / 0 | 13 / 13；11 / 11 | 均通过，无重复 |

全部 10 次 stop，0 length，0 普通超时，可见 completion_tokens 总计 **4287**。不能用本轮零循环证明治愈，因为关系原样也未循环；修复贡献是确定性避免不可能任务和其非法输出。

正向控制四次都输出 `entity-23 CONSTRAINS_AGENT entity-14`，证明可执行候选路径保留，但**不代表上线可接受事实或全质量通过**：模型把原文 OCR 兼容汉字及内部空格规范化，quote 无法逐字定位。用当前 v2 `locate_quote` 检查，四次全部无法绑定。请求源文中的 Constraint 归纳本身也是代理暂定标签。这暴露了独立的 evidence 格式/绑定问题；本轮没有擅自修改已提交算法的 evidence 逻辑。若未来做归一化定位，必须回填真实原文 span，并在多处匹配时明确拒绝歧义，不能仅认为“看起来等价”就接受关系。

A 第 2 次为 21 个唯一候选，超过目标 20；因此“上轮返回片段均 ≤20”仅适用于那 25 次观察。按章节的小任务是负载估计，无法保证模型生成的候选条数，更不能靠输出 cap 截掉剩余事实。两轮拆分均完整返回，合并身份键唯一数 29、32；各有通知与附件名称两种 OfficialDocument mention，需要别名/类型审阅。正常合并不等于全部事实正确，没有独立 gold，也没有测试跨片关系覆盖。两轮 A/B completion_tokens 合计 1707、1891，两请求耗时求和 19.60、39.59 秒，队列与服务状态影响时延，不能说本轮更快。

## 根因定位进度与后续实施边界

已证实的触发条件是：repair issue 请求某关系时，本地目录无合法源类型，prompt 仍展示全签名。scope 修复可以直接消除这个请求缺陷。**尚未证实它触发重复长循环**；上一轮实体原样在温度 0 重现一次长循环、又正常完成一次，说明不能把任务矛盾、短输入、温度、信息密度任一个单因果当结论。

另一个历史上下文特征是表格里相同“领导批示”在多个单元格完整重复，known entities 又使用了规范化名称。重复源文、本体宽泛、开放式候选归纳、枚举例子被续写均可能扩大输出空间；它们只是待验证的触发假说。长循环的可观察放大机制仍是产生重复后长期没有新增记录，而持续耗尽输出预算。服务端路由、解码或模型权重的贡献缺少 logits/后端日志，不能区分。

建议上线顺序：先发布本轮 scope 修复并观察 `REPAIR_ISSUE_OUT_OF_SCOPE` 和最终 unresolved；对来源缺端点的任务，应明确实体补全/上下文检索的合法入口，而不是换类型造关系。然后验证小语义任务与跨片事实归并，少量重复直接去重。若要强保证实体负载，需可解释的输入估计与超负载再拆分，保留完整输入并集；候选数、独立事实数和记录数应分开计量。

流式连续零新增止损尚未上线。上一轮离线至少完成 40 条后检查最近 20 条全部无新增，可保留异常调用全部唯一候选、避免大段重复尾部；但实际取消、计费、未知后续事实以及长正常引用误杀需要端到端验证。当前修复不是零新增检测，不把离线模拟当生产效果。普通非流式 timeout 没有 partial，仍不能判为循环。

## 复现

```powershell
.venv/Scripts/python.exe -m eval.tools.repair_fix_study
.venv/Scripts/python.exe -m pytest -q tests/algorithm/test_relation_repair_scope.py tests/eval/test_repair_fix_study.py
.venv/Scripts/python.exe -m eval.tools.repetition_causal --out test_data/repetition/repair-fix-v1 --results tmp/repetition-repair-fix-20261011/repetition-repair-fix-final-20261011/run --report tmp/repetition-repair-fix-20261011/report.json
```

在已有 Backend 环境中运行 `repetition_study.py --dataset <冻结集> --plan <冻结集>/plan.json --out <新的tmp路径> --max-tokens 16384 --timeout 300` 可复放 10 次 API 计划；沿用容器原 PYTHONPATH。不要为此新建 Backend 或修改运行配置。冻结集中的 `repair-fixed-skip` 是可审计生产 skip 诊断，不进入调用计划。
