# 标准文件知识图谱更新算法设计

本文是标准文件入库时**知识图谱更新流程的目标设计**：本次抽取融合结果如何经暂存、候选检索、联合证据判断（JEV）、自动/人工处置、实体与关系对齐、证据与置信度更新，最终事务化落库。

相关已实现能力的位置：

- 抽取主流程（得到 `E_new` / `R_new` 之前的部分）见 [知识抽取算法逻辑说明](知识抽取算法逻辑说明.md)；
- `POST /api/v1/graphs/merge` 提供多图确定性去重合并（见 [算法接口协议](../接口/算法接口协议.md)）；
- JEV 环节的局部决策模型为 NanoJev，由 `KG_EXTRACT_JEV_*` 环境变量控制、默认关闭（见 [环境变量与配置加载说明](../部署/环境变量与配置加载说明.md)）。

## 一、算法流程

```
┌──────────────────────────────────────────────────────────────────┐
│  本次抽取融合结果                                                   │
│             E_new（实体集合）, R_new（关系集合）                     │
└───────────────────────────┬──────────────────────────────────────┘
                            ↓
              ╔════════════════════════════════╗
              ║  ① 知识更新暂存区 · Staging       ║
              ║  ├ 分配 TEMP_ID / UUID           ║
              ║  ├ 计算 Semantic ID 向量          ║
              ║  ├ 批次内自相似消重                ║
              ╚════════════════╤═════════════════╝
                               ↓
            ╔══════════════════════════════════════════════╗
            ║  ② 全量图谱候选知识检索（实体 + 关系 Embedding）   ║
            ║      A. 向量相似召回                          ║
            ║                                              ║
            ╚════════════════════════╤═════════════════════╝
                                     ↓
              ╔══════════════════════════════════╗
              ║  ③ 联合证据判断 · JEV                ║
              ║   Joint Evidence Vote              ║
              ║   判断更新实体候选对                  ║
              ╚════════════════════╤═══════════════╝
                                   ↓
            ┌──────────────┬──────────────┬──────────────┐
            ↓              ↓              ↓
      ╔══════════╗  ╔═════════════╗  ╔══════════╗
      ║  MATCH   ║  ║  POSSIBLE   ║  ║   NEW    ║
      ║ 同一实体  ║  ║ 疑似同一实体  ║  ║  新实体   ║
      ╚════╤═════╝  ╚══════╤══════╝  ╚════╤═════╝
           └──────────────┬───────────────┘
                          ↓
              ╔════════════════════════════════════╗
              ║  ④ 自动更新处理 · Proposal           ║
              ║  ┌ 动作类型：CREATE(新建) / MERGE（合并）║
              ║  / UPDATE（覆盖）/ VERSION（版本管理） ║
              ║  / LINK（都保留并连接指定关系）          ║
              ║  ├ 主实体建议（以谁为主）              ║
              ║  ├ 属性融合方案（含冲突清单）           ║
              ║  ├ 关系对齐方案                       ║
              ║  ├ Evidence 对比                     ║
              ║                                      ║
              ╚══════════════════════════════╤═══════╝
                                            or
                          ╔════════════════════════════════╗
                          ║  ⑤ 人工审核更新                   ║
                          ║  ┌ 哪些实体融合？                 ║
                          ║  ├ 怎么融合？                    ║
                          ║  ├ 以谁为主？                    ║
                          ║  └ 属性冲突怎么办？               ║
                          ╚══════════════════════════╤═══════╝
                                                     ↓
                            ╔═══════════════════════════════╗
                            ║  ⑥ 实体对齐                     ║
                            ╚════════════════════════╤══════╝
                                                     ↓
                            ╔═══════════════════════════════╗
                            ║  ⑦ Stable UID 对齐             ║
                            ╚════════════════════════╤══════╝
                                                     ↓
                            ╔═══════════════════════════════╗
                            ║  ⑧ 关系对齐                     ║
                            ║  ┌ R_new 映射到已对齐的实体端点   ║
                            ╚════════════════════════╤══════╝
                                                     ↓
                            ╔═══════════════════════════════════╗
                            ║  ⑨ Evidence / 置信度更新计算         ║
                            ║     多源证据聚合                     ║
                            ║     置信度更新                       ║
                            ╚═══════════════════════════════╤════╝
                                                            ↓
                          ╔════════════════════════════════════╗
                          ║  ⑩ 人工审核待更新操作                 ║
```

## 二、十一环节职责一览

|    # | 环节                     | 核心职责                | 关键产出                                                      |
| ---: | ---------------------- | ------------------- | --------------------------------------------------------- |
|    ① | **Staging**            | 规范化抽取结果、赋予临时身份、生成向量 | `E_staged` / `R_staged` 携带 `TEMP_ID / UUID / Semantic ID` |
|    ② | **候选检索**               | 三层召回构造精准候选池         | 候选池 = 向量近邻 ∪ 精确匹配 ∪ 关系邻域                                  |
|    ③ | **JEV 判断**             | 五维一致度打分并三档分流        | `MATCH` / `POSSIBLE` / `NEW`                              |
| ④or⑤ | **自动处理更新**             | 模型自主判断融合意图与冲突处置     | 动作类型、主实体建议、属性融合方案、Evidence 清单                             |
| ④or⑤ | **人工审核**               | 人工裁定融合意图与冲突处置       | 审核确认指令                                                    |
|    ⑥ | **Entity Linking**     | 建立临时身份到稳定身份的映射      | `TEMP_ID → Stable UID`                                    |
|    ⑦ | **Stable UID 对齐**      | 按稳定身份归并，确定落点        | 全图实体归并结果                                                  |
|    ⑧ | **关系对齐**               | 端点在先，关系去重与冲突检测      | 合法化后的关系集合                                                 |
|    ⑨ | **Evidence 更新**        | 多源证据聚合与置信度重算        | provenance + valid_from 标注                                |
|    ⑩ | **人工审核**               | 落库前复核实际写入操作         | 二次确认                                                      |
|    ⑪ | **Transaction Commit** | 多库更新                | 录入更新结果                                                    |
