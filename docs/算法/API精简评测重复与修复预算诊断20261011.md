# API 精简评测：重复与修复预算诊断

本报告只读分析 77adfd6 冻结版本的 JSON/API 五样本，不追加模型请求、不修改冻结运行源码。这里的 API 是 `matrix-deepseek / deepseek-flash`，输出预算 8192；不能与此前 SiliconFlow V4-Flash、16384 输出预算的隔离实验合并计算失败率。Qwen4B 的属性长循环是另一组证据，也不能归到这五个 API 样本。

原始结果位于 88 的 `/app/backend/tmp/final-mini-20261011-77adfd6/evaluation/json/api_deepseek/api_deepseek/runs/20261011-044618/`。完整调用和最终算法结果位于 `/app/backend/tmp/extraction-traces/20261011/<trace_id>/`。本地审计输出为 `tmp/repetition-mini-analysis-20261011/api-json-audit.json`，原始 trace 副本为同目录的 `api-json-traces/`。该输出不进入源码交付包。

总计 627 个生成入口、599 次实际 HTTP，599 次 `finish_reason=stop`。3117 个完整对象中只有 rule01 的实体生成响应 `000004-call-response.json` 有一个精确重复（20 行、19 唯一，最高重复次数 2）。没有观察到持续重复膨胀。797 条属性输出全部满足冻结 schema，其中 795 条能够通过当前 v3 的 `locate_quote` 绑定原文；这只是协议和引用位置有效，不能据此称为正确属性或独立人工真值。

这些正常结束不代表最终图谱质量合格。五个样本均为 partial，主评测报告实体 micro F1 0.452026、关系 micro F1 0.158301。当前证据说明这一组的主要质量损失不能归因于长度截断或长循环。

## official01 的“不完整响应”来自未调度的工作

official01 最终 `result.json` 的两个 terminal attempts 是：

| pass / chunk | message | pending_items |
|---|---|---:|
| repair_relation / repair-1.part-63 | Output split call budget exhausted | 89 |
| repair_relation / repair-2.part-63 | Output split call budget exhausted | 68 |

这两轮实际 repair_relation 请求共 126 次，恰好各 63 次，全部 stop。`algorithm/output_batching.py::generate_batched` 默认 `max_calls=63`；当还有初始批次或拆分子批次未处理时，在发起下一次请求之前人工增加 `type=incomplete` 的 terminal attempt。随后 `v3/run_state.py::primary_failure` 把它映射为 `LLM_RESPONSE_INCOMPLETE`，其优先级还高于后续的 `REPAIR_INCOMPLETE`。因此错误码混淆了“模型响应 length”和“程序还有工作但停止调度”。此例实际 API 耗时是 611.859 秒；4B official01 的 900 秒失败属于不同请求。

新增离线回归演示 `tests/eval/test_repair_budget_semantics.py`：64 个初始单项批次，前 63 次模拟正常 stop，返回 63 项；最后 1 项完全没有调用，仍产生人工 incomplete 并映射上述错误码。另一测试单独验证真实 length 的响应元数据路径。命令：

```powershell
.venv/Scripts/python.exe -m pytest -q tests/eval/test_repair_budget_semantics.py
```

结果为 2 passed。演示保留当前行为以揭示区别，没有放宽预算或修改运行算法。

## 修复作用域与剩余质量问题

official01 有 252 条 `REPAIR_ISSUE_OUT_OF_SCOPE` 诊断，official02 有 25 条；其他三个样本没有该诊断。被跳过的问题不具备当前实体目录支持的可执行端点/签名，跳过不代表覆盖成功。作用域修复防止要求模型执行非法任务，却无法凭空补齐缺失端点或事实。

| 样本 | 最终错误码 | 验证及剩余缺口 |
|---|---|---|
| official01 | LLM_RESPONSE_INCOMPLETE | hard=0，coverage 不完整；feature 86、relation 324、structural 1 |
| official02 | REPAIR_INCOMPLETE | hard=0，coverage 不完整；feature 10、relation 49 |
| rule01 | LLM_SCHEMA_INVALID | hard=4，四个最终 RuleType 实体重复；feature 11 |
| simple | REPAIR_INCOMPLETE | hard=0，coverage 不完整；feature 34、relation 4 |
| trouble | REPAIR_INCOMPLETE | hard=0，coverage 不完整；feature 71、relation 43 |

终态 verifier 使用 `repairable_types=()` 作只读验证，因此其 `repairable_issue_count=0` 并不表示没有未解决问题。覆盖标志、coverage_gaps 和最终 issues 必须一起读取。rule01 的四个重复最终实体属于身份归一/最终图谱合并问题，不能只凭它推断原始模型长循环；原始响应仅有一条轻微精确重复。

## 建议及证据边界

1. 将调度预算耗尽设为明确的工作预算状态，例如 `REPAIR_WORK_BUDGET_EXHAUSTED`，分别报告已调用次数、未处理项目数和真实 finish_reason。保留 partial 与覆盖缺口，避免下游把它当作 length 触发同请求重试。
2. 在 repair 调度前，对同一实体、同一关系义务及端点集合做确定性任务去重，按必需关系和有证据可执行端点排序；采用与 schema 作用域一致的批量请求，记录每个 issue 已完成/跳过/未处理。不能只增大 63 来掩盖大量任务。
3. 不执行缺失端点的非法 issue，但保留缺口并回到候选/端点补全阶段；不能通过放宽 enum 或将跳过计为解决来提高完成率。
4. 对轻微重复先用确定性去重；在线零新增止损只针对持续长循环，并需要验证流式取消、配额生命周期和费用边界。此组 API 没有长循环，无需由轻微重复引入激进截断。

已证实的是错误码的具体混用路径、未处理任务数量，以及这一组实际没有 length/HTTP timeout/长循环。任务去重和批量调度是否改善 F1、耗时尚未实验；这些建议不能作为已验证的生产修复。属性协议通过不等于语义正确，缺少独立人工 gold。Qwen4B 单实体/单属性配对复放仍等待主矩阵结束，未把未执行实验计入结果。
