# 评测方案审计与改进

调研日期：2026-10-08。范围为 `eval/` 的在线评测编排、实体与关系评分、报告、发布门禁和基线可复现性。本文说明本轮修订的依据与目标，不代表生产评测已经通过；测试与在线验证结果见文末记录。

## 结论与适用范围

现有方案适合继续作为知识沉淀流水线的统一评测入口：通过 HTTP / MCP 测真实调用链，golden 与算法源码分离，支持冻结切片比较抽取版本，保存逐条命中、漏抽、多抽明细，并控制耗时。无需为了更换框架引入整套 Ragas、nervaluate 或 lm-evaluation-harness 运行依赖。

本轮优先修复会改变分数或产生错误放行的实现问题，再补齐统计解释和可复现性。实体识别、关系抽取、属性完整性、原文依据、解析与切片质量是不同评价维度；本轮分数不能代表全部维度已经合格。

保留以下边界：

- `eval/run.py` 继续调用运行中的 Backend，不导入在线算法或后端包替代生产链路。
- 评测输入与 golden 保持在 `test_data/`；评测输出写入 `tmp/eval/runs/`。
- 不修改生产算法、运行镜像、鉴权队列或外部服务访问方式。
- judge 配置、诊断与 manifest 不保存 API key、Authorization 或其他密钥。

## 评分正确性修订

### 窗口索引必须通过原索引列表还原

本地自动匹配移除部分条目后，剩余索引可能是 `[0, 2, 5]`。judge 返回窗口内下标 `1` 时，它对应原集合下标 `2`，不能用窗口起点加 `1` 得到原下标 `1`。

本轮要求先校验窗口内索引为合法整数且未越界，再分别通过 golden 与 predicted 的索引列表映射回原集合。非法索引按 judge 失败处理，不能过滤掉错误结果后继续宣称该批评分有效。

### 本地确定项也是候选边，不提前锁死顶点

现有“同名且属性不冲突”的关系不具备传递性。两个同名 golden 的属性分别为 `{}` 和 `{"阈值": 5}`，两个预测的属性分别为 `{"阈值": 5}` 和 `{"阈值": 10}`：

- 先贪心配对第一个 golden 与第一个预测，剩余两项冲突，只得到 1 对。
- 配对第一个 golden 与第二个预测、第二个 golden 与第一个预测，可以得到 2 对。

因此本地匹配应收集所有确定候选边，而不是采用先到先得并移除相关顶点。judge 也应提供所有认可的候选边，不在每个窗口内提前做一对一裁剪；最后由评分器统一计算最大基数匹配。

只有本地候选已达到 `min(golden_count, predicted_count)` 时，实体或关系集合的命中数量才不可能再增加，此时可跳过该集合的 judge。否则保留可能参与增广路径的顶点，并收齐剩余候选。这里“饱和可跳过”只保证命中数量，不保证得到唯一实体映射；后文的关系映射诊断仍受此限制。

`pairs_presented` 只能证明候选出现在裁判输入中，不能证明模型逐对认真判断、没有遗漏，或判断正确。报告应将它作为调用覆盖诊断，不作为语义正确性的证明。

### 保留关系属性，明确指标名称

关系在 `entities/relations` 与 `nodes/relationships` 形式之间转换时应保留 `properties`，避免评分使用的字段随接口返回形态变化而丢失。新增往返转换回归用例，验证数值冲突等属性仍能到达评分器。

实体与关系继续使用 TP/FP/FN 计算 Precision、Recall、F1。原来的 `accuracy = TP / (TP + FP + FN)` 没有真负例项，其数学含义为 Jaccard/IoU。本轮新增明确的 `jaccard` 字段，保留 `accuracy` 作为历史 JSON 兼容别名；报告应优先显示 Jaccard，不能将其解释为普通分类准确率。

### 88 机初评暴露的类型误判与端点信息缺失

88 机 `official_01` 初评中，judge 将“部门 / 信息公司技术中心”与“活动 / 组织开源智能体风险排查工作”匹配，也将“部门 / 集团科信部”与“交互 / 填报反馈表并报集团”匹配。相关内容描述的是主体及其活动或交互，并不是同一实体。这说明只在提示词中要求语义相同不足以保证本体类型约束。

修订后的实体 `type` 以及关系 `rel_type`、`from_type`、`to_type` 分别要求经过 NFKC、casefold、去空白与下划线后完全一致。类型同义词、单复数变化不再交给 judge 自行推断。程序在合并候选前硬过滤跨类型结果，并在 `judge_coverage` 对应实体或关系集合的 `rejected_type_pairs` 中记录被拒绝的原集合索引；名称别名仍可在类型约束内由 judge 判断。

初评的关系 judge 未获得端点实体属性，8 个关系窗口均返回空数组。golden 使用短标签而预测使用正文表述时，仅提供关系五元组不足以确认端点指代。修订后，关系 prompt 分别提供 golden 与 predicted 的端点实体 `properties`，按当前窗口内的 `(type, name)` 去重，供裁判结合标题、原文内容、顺序号等确认身份。同一键下有多个属性候选时分别保留，不将其拼成一个不存在的实体；空上下文也不代表自动匹配或自动拒绝。上下文不包含先前实体匹配判决，不据实体映射自动增加关系 TP。

本地属性值归一化进一步收紧为保留全部标点，仅作 NFKC、casefold 与去空白等处理。原有名称归一化已保留 `+`、`-`、`.`、`/`、`%` 等数字语义符号；本轮新增 `-5` 与 `5`、`1.0` 与 `10`、`5%` 与 `5` 的回归保护，防止后续修改破坏这一约束，不将这些例子描述为已复现的旧故障。如 `100` 与 `100.0` 这样的语义等价写法仍交给 judge 判断。

关系本地自动匹配也检查端点上下文：即使五元组完全相同，只要双方端点候选的共享属性存在冲突，就转交 judge；有多个候选时要求所有跨侧组合兼容，避免同名短标签绕过上下文验证。缺少上下文仍沿用缺失属性不冲突的规则。

上述初评结果混有裁判误匹配和上下文缺失，不能把初评 F1 直接归因于算法效果。类型硬约束、属性归一化与关系上下文改变了评分器口径，必须重新评分并建立基线；修复后的分数与初评分数不能直接解释为算法提升或退化。

## 关系评测的边界

正式关系指标采用本体类型硬约束下的关系语义匹配，结合两侧端点属性判断指代，并增加独立 F1 阈值。阈值需结合重新建立的全量基线设置，不能因为实体阈值为某个数就假定关系必须相同。

另提供 `aligned_relations` 诊断：依据实体的一对一映射，检查关系两端点是否对应、方向是否一致以及关系类型是否符合要求。它用于发现“实体匹配和关系匹配各自看似正确，但相互矛盾”的问题。

本轮 `aligned_relations` **只作诊断，不作为新的发布门禁**。实体最大匹配可能存在多个同样大的解，某个稳定选出的实体映射未必使关系匹配最多；本地候选饱和时也可能未发现所有语义等价边。因此该指标不是联合优化实体和关系的完整图对齐分数。将来如需升级为正式指标，应先确定消歧、类型别名、关系方向和多解选择规则，并重新建立基线。

## 门禁与统计口径

### 评分失败必须显式挡住发布

judge 调用、响应结构、索引校验或结果解析失败时，仍保存 identity 对照和安全诊断，便于排查；但 `identity_fallback` 必须使正式 LLM 评测的质量门禁失败。报告需要展示降级数，不能用一个混合汇总 F1 掩盖有效语义评分与降级评分的差别。

`--min-relation-f1` 默认 `0`，待新基线确定阈值后启用；golden 与预测都没有关系的 case 不参与该关系阈值检查，预测出多余关系仍参与。`--require-scored` / `--no-require-scored` 可显式设置评分覆盖要求；未指定时，LLM 模式、任一 F1 阈值大于 0 或指定基线都会自动启用。缺失 golden、没有有效评分或应评模块未产生评分不能被解释为通过。探索性预测仍可允许未评分 case，但要明确标记，不能用该批结果证明发布门禁已过。关闭覆盖要求不会放行 LLM 裁判降级。

### 同时展示总体质量与样本覆盖

- **micro**：累加各 case 的 TP/FP/FN 后计算指标，反映全部实体或关系的整体质量；大文档占更大权重。
- **case_macro**：对参与评分的 case 指标等权平均，防止大型标准文档掩盖小文档的退化。
- **分组汇总**：按 official、standard、rule、simple 等文档类型展示相同口径及样本数量，避免只看一个总分。
- **group_macro**：先计算各组的 case_macro，再对有信息的组等权平均。
- **覆盖率**：同时记录目标、完成、失败、已评分、未评分和 judge 降级数量。声明平均值的参与范围，不能让失败或未评分样本在读者不知情的情况下消失。

golden 与预测均为空的维度不参加宏平均，以 `empty_cases` 单列；汇总没有可评条目时为 `null`。保留单案历史数值兼容时，仍应展示支持数，不能仅凭该维度的 0 或 1 推断算法优劣。失败 case 如果已有有效评分仍保留实际分数；缺评分不会被伪造为 0，均值必须结合覆盖率阅读。属性仅比较双方都填写的键意味着“无冲突”，不意味着“属性完整”。

## 可复现记录与基线迁移

每个批次保存 manifest，至少区分：

- **输入身份**：精确 case 列表、原文件、golden、本体的内容哈希；使用冻结切片时记录复用来源和输入指纹。
- **评测口径**：评测实现版本或哈希、匹配模式、提示词版本或哈希、judge 模型与相关参数。
- **运行配置**：解析、切片、抽取选项、服务端回报的算法版本及必要运行元信息。

比较不同抽取版本时，算法版本允许不同；数据、golden、本体、评分器及 judge 口径需要满足兼容条件。流水线配置是否允许变化取决于比较目的：抽取消融需要冻结上游输入，端到端比较则应记录上游变化，不能把两者解释为同一个实验。

显式指定基线后，如果基线缺失、manifest 缺失或相关口径不兼容，应阻止基线门禁通过并给出差异，不能跳过检查继续报告成功。旧批次因索引与匹配修复可能改变分数，也可能没有可验证的 manifest，必须建立新的正式基线。不能把旧分数与新评分器分数直接比较并宣布提升或退化。

`--baseline` 接受运行目录或 `summary.json` 路径。文件缺失或不是有效 summary 对象按配置错误退出 1；可读取但不兼容则使质量门禁失败。`--max-f1-drop` 默认 `0.02`，比较每个 case、每个应评模块的实体与关系 F1 绝对下降；`--max-latency-increase` 默认 `0.2`，比较 API 阶段耗时的相对增幅，不把 judge 评分耗时纳入性能比较。两侧都复用的 parse/chunk 没有新的服务耗时，跳过该阶段比较。

第一次生成切片的 `chunk-extract` 批次不能直接作为 `extract` 模式的基线。抽取版本比较应先冻结一次切片，再让两个版本都以 `extract --from-run <同一冻结批次>` 运行。`--dry-run` 不清理历史；实际评测清理过期记录时保护 `--from-run`、`--reuse-extract-from` 与 `--baseline` 引用的批次。

第一次建立新基线时，先不执行不存在的基线比较，完成全量单测、正式 LLM 评测、质量与耗时门禁，再将经过审核的批次作为后续参考。补评冻结预测有助于区分评分器修复与算法变化，但补评耗时不能代替真实服务执行耗时。

## 尚未覆盖的质量维度

本轮修复评分器不等于补齐标注。以下能力仍需后续建设：

1. **解析与切片语义质量**：当前接口成功、输出非空属于可用性检查。尚未建立覆盖关键文本保留、表格结构、公式、跨页内容、切片语义完整性的完整标注集。已有 `__source_range` 等生产契约测试仍须保留。
2. **证据质量**：当前 evidence 不参与实体、关系匹配。需要原文证据位置或可核验片段，才能独立检查引用有效性、支持性和遗漏情况。
3. **属性完备率**：当前共享属性无冲突并不惩罚单侧缺失。要增加完备率，应先定义各类型的必需字段、可选字段与标注缺省语义。
4. **裁判人工校准**：建立小型人工判定集，覆盖别名、同名异物、类型错误、关系反向、数值或日期冲突、缺失属性、重复实体和长文窗口。
5. **裁判稳定性**：对固定预测重复抽样、交换条目顺序，比较逐对判断与最终分数；先估计波动，再设置回归容差。固定 seed 或低 temperature 不能单独证明结果可重复。

生产失败 case 应沉淀为 `test_data/eval/` 的回归 case 或对应层单测。解析、切片、抽取或沉淀行为后续发生变化时，仍按仓库规定执行全量测试、在线正式评测、基线比较与生产观测，不能用 mini 评测代替发布门禁。
