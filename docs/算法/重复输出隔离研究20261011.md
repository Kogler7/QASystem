# 重复输出隔离研究（2026-10-11）

本轮建立了独立的冻结调用测试集，并完成 41 次隔离 API 调用。结论是：**输入信息量影响需要生成的记录数量，但不能单独解释重复循环。当前最有证据的工程改进是生成时止损和修复任务约束一致性；缩小输入、收紧候选粒度属于需要继续验证的负载控制手段。** 没有修改运行时算法或 Backend 默认配置。

## 测试集与实验条件

`test_data/repetition/v1/` 包含 8 个 case：历史实体循环、关系修复循环、属性字符串循环，各配一个正常对照；另有同为 402 字的低/高信息密度合成样本。每个 case 冻结原始消息、内部 schema、任务上下文、来源 trace、来源调用规范化 JSON 的 SHA256、历史输出指标和代理审阅的暂定参考标签。`manifest.json` 校验 UTF-8/LF 文件内容，避免 Windows/Git 换行差异。

自然样本仅由本研究代理设置和检查稀疏锚点，标签均为 **agent-reviewed / provisional，没有独立人类真值或复核**；历史去重后的记录也只是候选。正常实体样本的 2 个 Device 和 2 个 Fault 由代理逐项比对原文，不能当作独立人工 golden。合成样本由代理指定了 1/10 个业务部门锚点；低密度填充文本本身有重复，因此它是诊断对照，不能代表所有自然文档。

调用使用 88 已有配置中的 `siliconflow / deepseek-ai/DeepSeek-V4-Flash`。基线温度 0，`thinking.type=disabled`，无重试，最多 2 并发，单次 180 秒超时。筛选 21 次使用 8192 输出 token 上限；确认 20 次恢复 16384 上限。两组分别统计，不能混成同条件复现率。没有启用 `json_schema`。

实体原始消息加上当前公共 JSONL 注入后，基线请求的 `prompt_tokens=2748`，与历史循环请求一致。历史关系调用采用较早的 JSONL 注入，当前适配后是 9746 token，历史为 9765，因此关系复放包含协议变化。历史属性调用记录为 `json_schema` 上下文，本轮保留原提示做普通文本 API 复放；虽然输入 token 都为 5608，也不能证明旧服务端结构化输出路径被原样复现。

所有原始返回及安全请求参数保存在 `tmp/repetition-research-20261011/repetition-final-20261011/{screen,confirm}/`；历史原始日志副本在同目录上级的 `repetition-frozen/`。凭据从容器配置内存读取，没有写入测试集、请求文件或日志。测试集含内部文档摘录，不宜作为公开数据集发布。

## 主要结果

41 次调用有 38 次返回、3 次超时、1 次 `finish_reason=length`。已返回 usage 的调用合计 35616 输出 token；流式调用没有保存 usage，超时也可能在服务端产生费用，因此这个数字不是完整账单。

实体循环样本的方法对比如下。`返回数` 不含超时；身份重复按 `type + mention` 精确判断，完全重复按整个记录精确判断，不包含同义词归并。

| 方法 | 上限 | 尝试／返回 | 截断 | 发现重复的返回数 | 完整记录数 | 判断 |
|---|---:|---:|---:|---|---:|---|
| 原始基线 | 8192 | 2／2 | 0 | 完全 0，身份 0 | 26–32 | 本次正常，不代表风险已消失 |
| 原始基线 | 16384 | 3／2 | 0 | 完全 0，身份 0 | 26–27 | 另 1 次超时；循环有间歇性 |
| 最多 40 条记录 | 8192 | 2／2 | 0 | 完全 0，身份 0 | 20–40 | 可约束规模，尚不能证明降低循环概率 |
| 逐字 mention／收紧泛化候选 | 8192 | 2／2 | 0 | 完全 0，身份 2 | 25–27 | 仍重复同一身份，只是证据或位置不同 |
| 逐字 mention／收紧泛化候选 | 16384 | 2／2 | 0 | 完全 0，身份 2 | 24–29 | 提示词无法替代确定性去重 |
| 正文 734 → 498 字 | 8192 | 2／1 | 0 | 完全 1，身份 1 | 16 | 6.25% 完全重复，另 1 次超时 |
| 正文 734 → 498 字 | 16384 | 2／2 | 0 | 完全 1，身份 1 | 15–19 | 其中一次 5.26% 完全重复 |
| temperature=0.3 | 8192 | 2／2 | 1 | 完全 1，身份 1 | 26–145 | 循环返回 145 条，仅 42 唯一，71.03% 重复 |
| frequency_penalty=0.5 | 8192 | 2／1 | 0 | 完全 0，身份 0 | 11 | 返回末行 JSON 损坏、13 项 schema 错误、3 锚点仅 1 命中 |
| 流式重复检测 | 8192 | 2／2 | 0 | 完全 0，身份 0 | 32–34 | 两次都正常，未触发在线止损 |

基线、记录数上限、收紧候选、流式返回的自然实体样本均覆盖 3 个稀疏锚点。缩正文后只有 1 个锚点仍属于输入范围，另外 2 个是因为范围缩小而排除，不能拿它的输出量减少当召回提升。`frequency_penalty` 唯一返回的逐字 mention 比例也降至 72.7%，不建议据此修改默认解码参数。

正常短实体对照在基线以及记录上限、收紧候选、温度 0.3、频率罚、流式检测五种方法下，都保留了全部 4 个明确实体，格式和 schema 正常。这只能证明这些方法没有破坏这个极小对照。正常属性对照本次输出 3 项更新，历史是 4 项，缺少历史的 `tags` 更新；该字段没有完整人工 golden，不能声称所有正常属性的质量保持不变。

同为 402 字的合成输入，低密度生成 5/6 条记录（242/318 token），高密度生成 30/50 条（1460/2420 token），四次都没有重复并保留全部部门锚点。**字符数不是输出负载的充分指标；高密度会增加输出，但本轮没有观察到高密度必然触发循环。**

属性原始提示与“分类只选一个有证据类别、语义属性最多 80 字”各复放 3 次，全部正常，约 167/170 token。原始基线自身没有再循环，不能认定限制字符串已经治好问题。关系两种提示各 1 次也不循环，但每次输出的 4 条关系全部不符合 schema，详见下文。

## 可以定位到的原因与不能证实的原因

1. **重复发生在同一次模型响应内部。** 历史实体循环输入只有 734 字，输出 40351 字、268 条完整记录、108 条完全唯一，第一条重复在第 100 条；关系循环有 369 条完整记录、51 条唯一，最多同一记录重复 54 次。它们不是程序重试合并重复，也不只是文本长到解析器读不完。
2. **属性循环是另一种失败。** 一个尚未闭合的 `约束类型` 字符串反复枚举“流程约束、合规约束、质量约束、权限约束……”；重复片段覆盖 27150/27392 字。即使任务仅补一个实体，也可能循环，完整记录去重无法覆盖它。
3. **存在明确的不可满足修复任务。** `repair_relation-loop` 的 4 个 repair issues 都要求 `CONSTRAINS_AGENT`，relation signatures 也声明该关系，但输出记录的 `rel_type` enum 完全不允许它。两次复放均顺着 repair issues 输出该关系，4 条全部 schema-invalid。这个矛盾是可确定性审计的任务构造缺陷；本轮没有做消融证明它直接导致历史循环，不能把二者画等号。
4. **“尽量抽全”与宽泛概念给了较大的候选空间。** 循环实体输出中包含大量细碎或泛化对象；但正常基线也能以 26–32 条结束，而且多数 mention 已逐字来自原文。收紧归纳权限仍有身份重复，因此单独一句“禁止重复”或“逐字抽取”不足以保证结果。
5. **温度 0 不等于稳定输出或硬性去重。** 相同消息与匹配的输入 token 数，本轮能正常，历史能循环；温度 0.3 又实际出现循环。模型看得到先前生成的内容，但没有程序集合那样的唯一性约束。“模型失忆”没有被证实。模型内部概率、服务端采样／批处理／量化、版本路由均无法从这些 API 日志分离。

一般生成研究已报告最大似然解码和重复退化的联系，并提出训练级反重复目标；这支持“自回归重复退化”作为机制候选，不能当作此 provider 的内部实现证据：[Holtzman 等，ICLR 2020](https://arxiv.org/abs/1904.09751)，[Welleck 等，Unlikelihood Training](https://arxiv.org/abs/1908.04319)。[硅基 API 文档](https://docs.siliconflow.cn/docs/api/chat-completions-post)列有 `frequency_penalty`，本轮也有请求被接受，但接受参数和两次不同输出都不能证明该模型确实实现了预期惩罚。

## 流式止损的离线回放

每收到约 256 字检查一次：完全相同记录第三次出现，或短片段连续重复累计至少 400 字时停止。这是使用已保存输出的确定性模拟；在线三次流式调用都正常，未实测到异常取消。服务端是否立即停止计算以及如何计费也未经确认。

| 已保存的循环轨迹 | 触发字数／全部字数 | 减少后续字符 | 保留可恢复唯一候选 |
|---|---:|---:|---:|
| 历史实体 | 21760／40351 | 46.07% | 108／108 |
| 历史关系 | 6656／41170 | 83.83% | 51／51 |
| 历史属性字符串 | 768／27392 | 97.20% | 0；字符串未闭合 |
| 本轮 temperature=0.3 实体 | 10496／21253 | 50.61% | 42／42 |

保留下来的唯一候选仍需本体、证据和业务质量校验。属性循环不能通过补引号补括号变成可信事实，应标记该字段失败并以更窄任务重抽。对于合法长引文、重复表格和列表，短语检测可能误停；真正接入时应识别所在字段，对原文引用字段采用不同策略，并保留明确的部分结果／失败状态。

## 推荐次序与后续缺口

后续按用户指定的实体负载标准验证：单次目标约 20 个正文支持的独立实体，预计超过 30 个时触发进一步拆分。这个阈值是实验目标，尚未验证为最优值；不能通过丢弃第 21 条后的记录来满足目标。需要区分实体密度、业务记录数和模型过度泛化的候选数，拆分时保留上下文并检验完整覆盖与跨句关系召回。

先给关系修复增加调用前一致性审计：待修复关系、签名、端点类型与实际记录 schema 必须一致；不可生成的任务在调用前明确拒绝或重新分配，不能让模型猜一个有效别名。这个建议需要定位运行时代码并补消费者测试，本轮仅加入冻结样本的审计，不自动扩展线上 schema。

再接流式重复止损，同时分别检测完整记录／身份重复和未闭合属性字符串。止损与最终确定性去重承担不同职责：前者限制浪费和挂起，后者使已完成结果可用；两者均不能承诺事实质量。优先保持温度 0，不默认启用本轮损坏格式和锚点覆盖的频率罚。

切片可以按独立事项、表格记录和预估候选数量控制任务规模，保留局部标题与跨句上下文。固定字符数和固定 40 条记录不能适配所有输入：402 字高密度对照已能正确生成 50 条。语义属性长度限制可作为额外保护，但完整原文字段需要例外；更细切片和更窄候选粒度也可能损失跨句关系或合法归纳实体。

本轮已覆盖主要故障形态和七类方法，未完成大样本失败率估计、完整人工质量/F1、同请求跨 provider 对照以及服务端解码参数生效核验。特别是基线复放循环事件稀少，不能用方法组的零事件报告“显著改善”。88 同时运行其他研究，且相同短输出耗时可相差很大，耗时不用于判断模型速度提升。

## 复现与验证

在具有同 provider 环境变量、`openai` 和仓库 Python 路径的环境运行（88 用现有 `qasystem_backend` 执行即可，不另建 Backend）：

```sh
python -m eval.tools.repetition_study --dataset test_data/repetition/v1 --plan test_data/repetition/v1/plans/screen.json --out tmp/repetition/screen --max-tokens 8192
python -m eval.tools.repetition_study --dataset test_data/repetition/v1 --plan test_data/repetition/v1/plans/confirm.json --out tmp/repetition/confirm --max-tokens 16384
python -m eval.tools.repetition_report --dataset test_data/repetition/v1 --replays tmp/repetition-research-20261011/repetition-final-20261011 --historical tmp/repetition-research-20261011/repetition-frozen --out tmp/repetition-research-20261011/report.json
python -m pytest -q tests/eval/test_repetition_study.py
```

本轮工具测试 8 项通过，覆盖截断 legacy array 完整前缀、属性字符串循环、正常数组属性、schema wrapper／JSONL、停止模拟及不误停短正常输出、测试集 hash、不可满足关系修复。工具使用当前工作目录解析 repo 文件，实验结果写到 `tmp/`。模型调用按 case/method/repeat 文件跳过已完成任务，因此重新跑新实验必须选择新的输出目录；不应覆盖已有试验。
