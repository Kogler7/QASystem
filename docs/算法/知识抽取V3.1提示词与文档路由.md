# 知识抽取 V3.1：固定 System、领域 Skill 与统一 User

更新时间：2026-10-11。依据当前工作区的 [`prompt_router.py`](../../algorithm/knowledge_extract/v3_1/prompt_router.py) 整理；描述的是源码行为，不代表测试或生产服务器已部署此版本。历史文档中指向 `prompts.py`、声称“没有文档类型路由”的描述不适用于当前实现。

## 1. 提示词如何组成

抽取调用固定使用两条 chat message：

1. **system**：固定的 `BASE_SYSTEM_PROMPT`（`KNOWLEDGE_EXTRACT_V3_1_BASE_SYSTEM_PROMPT v1`），位于 [`prompt_templates.py`](../../algorithm/knowledge_extract/v3_1/prompt_templates.py)。沿用原 v3.1 的证据、实体、关系、属性规则，补充任务、策略、契约与原文的职责边界；不再追加领域提示词。
2. **user**：`build_chat_messages()` 按统一 JSON 外壳装配，顶层固定为 `task`、`output_contract`、`domain_policy`、`ontology`、`documents`。使用 JSON 序列化，原文中的标题、引号、伪造指令只作为字段值进入消息。

```text
首个 chunk 正文 → 确定文档类型 → 对应类型的 skill（不存在则为空）
                                          ↓
固定 System + 统一 User(task, output_contract, domain_policy, ontology, documents)
                                          ↓
                          模型 → 原有 JSON Schema 校验 → 后处理
```

| User 字段 | 内容及来源 |
| --- | --- |
| `task` | 当前 `operation`、任务纪律、`provided_segments` 范围、阶段允许的已知实体/关系 pair、修复问题；重试反馈也写入此字段。 |
| `output_contract` | 独立模块 [`output_contracts.py`](../../algorithm/knowledge_extract/v3_1/output_contracts.py) 统一维护阶段约束，以及实体、旧式关系、属性更新和 pair 分类的 schema 构造函数；调用方只提供本体、已知实体和候选 pair。`success_schema` 与传给模型结构化输出及本地校验的 schema 保持一致，附带正确的 `empty_result`。 |
| `domain_policy` | [`domain_skills.py`](../../algorithm/knowledge_extract/v3_1/domain_skills.py) 按已解析路由选择应用内的领域 skill，包含策略正文、已选策略 ID 和路由原因；只影响证据理解与候选粒度。这里不是 Codex 可安装的 SKILL.md。 |
| `ontology` | `compiled_task_catalog`：按阶段裁剪的编译本体目录，保留当前 v3.1 的上下文控制，不改成每轮灌入完整 PlantUML。 |
| `documents` | 当前 `current_chunk` 和允许的 `local_context`，只声明处理已提供分段，不声明完整文档覆盖。 |

默认仅提供公文、规则和 trouble 三类技能；simple 保持空技能，标准暂不提供技能。证据核验仍使用独立的核验 System。

## 2. 通用系统提示词

`BASE_SYSTEM_PROMPT` 将模型定位为**受已编译本体约束的知识图谱抽取器**。只依据当前上游 chunk 和允许的局部上下文，只使用本体声明的类型、属性、关系；输出必须是符合本轮 schema 的 JSON object。

| 方面 | 主要要求 |
| --- | --- |
| 证据 | 事实必须有原文依据，`evidence.quote` 优先逐字引用；无法逐字对应时引用最相关的真实片段。允许对多条记录作忠实归纳；禁止编造。 |
| 完整性 | 尽量抽全本体允许的事实，并列的单位、附件、对象等逐一提取。 |
| 实体 | 优先显式命名对象；本体允许时保留集合名词。数值、单位、字段标签、修饰词和标量属性值不单独成实体；同一 chunk 内同类型同 mention 去重。 |
| 关系 | 只提取原文明确表达且符合本体签名的关系，不虚构端点；本体允许时包含结构和证据关系。 |
| 属性 | 字面属性取原文或本体规范化值；语义属性可忠实概括。ICS/CCS 等公认标准编码表支持的规范值可补全，但不得猜测编码、缺失字段或常识事实。枚举多值尽量取全。 |

## 3. 按任务生成的通用用户提示词

| 任务 | 输入范围与目录 | 输出纪律 |
| --- | --- | --- |
| `entity` | 仅当前 chunk；只展示本体类型目录，不展示属性、关系和已知实体目录，也禁止从 `local_context` 抽实体。 | 只提议实体，不输出关系。每项仅含 `type`、`mention`、`start_char`、`end_char`、`evidence.quote`；位置为 chunk 内左闭右开区间，不能定位时填 0 并靠引用兜底。 |
| `property` | 展示本体类型及属性、intrinsic feature、已知实体及缺失属性；关系目录关闭。 | 只给已接受实体补缺失属性，不能改实体集合或类型。字面值应可在当前 chunk 定位；语义值可以归纳。字符串确实缺失时可填 `""`，不可用 `null` 代替。每个属性只更新一次，引用须支持更新。 |
| `relation` | 若提供候选 `relation_pairs`，只展示这些 pair，不开放其他关系目录或属性目录；端点已固定。 | 对每个候选选其 `relation_id` 或 `NONE`，输出 `pair_id`、`label`、`evidence.quote`；无原文证据选 `NONE`。没有候选 pair 的旧式分支使用 `relations` 输出结构。 |
| `repair` | 给出 verifier issues；已知实体最多展示前 25 个，当前 chunk 只保留 `chunk_id` 和最多 8000 字原文。 | 只修复列出的问题，不重复已接受事实；输出遵循本轮 schema。 |

实际 `output_schema` 由调用方传入，在 `output_contract.success_schema` 中完整呈现；未显式提供 schema 的实体调用使用本体编译所得的实体契约。修复任务若 schema 含 `entities`，采用实体输出契约，同时保留“只修复列出问题”的任务纪律。空结果由本轮 schema 决定，分别使用 `{"entities": []}`、`{"updates": []}`、`{"decisions": []}` 等，不再因输入是记录表而向属性/关系阶段错误提示 `entities` 空结果。

### 类型专属规则

公文表单规则归入 `official_document/SKILL.md`，仅在当前片段为表单时适用；规则表的归并、前件/后件及模板规则归入 `rule/SKILL.md`。检修表使用 `trouble/SKILL.md`，区分部件、故障、实验、结果和维修，禁止将正常结果当故障或混合不同记录的结果。JSON/表格形态本身不触发额外 skill。

## 4. 文档路由如何选择领域扩展

`resolve_document_route()` 只读取传入的 **第一个 chunk 的完整 text**，不使用本体、文件名、元数据、后续 chunk，也不跳过空的首片。一次请求确定一个类型，各 chunk、各阶段复用。

当前采用确定性的正文特征判定：公文标题/收文处理单；标准号及标准词汇；simple 对象声明或术语/关注点标题；规则表的故障分类与状况/原因、前件/后件；检修表的故障内容与处理方法、行修/互换记录等。信号不足或得分接近时为 generic。首片缺少类型线索时会走空策略，不会借本体猜测类型。

注册器只提供名称或 `route_hints` 匹配的技能给规划模型。模型读取文件后引用适用阶段的规则段，不能跨类型装配。`simple` 和 `generic` 始终保持空策略；标准暂未配置 skill。目录不存在、为空或缺少对应阶段/类型技能时，不调用规划模型，使用固定 System 和包含原文、本体、任务、输出契约的 User 继续抽取。已存在但格式损坏的技能仍报配置错误。

路由写入 `domain_policy.route`，策略写入 `profiles`，选中 ID 写入 `default_profiles`。技能版本、内容哈希和规划审计仍保留。

## 5. 公文路由提示词

`OFFICIAL_DOCUMENT_PROMPT_EXTENSION v5` 提醒模型关注标题、文号、发文/来文单位、主送/抄送、正文条目、附件、办理动作、约束和交换对象，并强调这些只是**本体映射提示**，不能扩展 schema。

- 一份公文保留一个 `OfficialDocument`，mention 用文件标题；文号等作为属性或证据。
- 正文开头、编号条目、报送要求、附件列表优先映射 `DocumentUnit`；明确的附件/材料/反馈信息映射 `OperationalInformation`；通知、报送、反馈等传递行为映射 `OperationalExchange`。
- `OperationalActivity` 以完整动宾事项为粒度：一个事项的状语、否定和结果保留在一起，并列事项分别抽取。带“不得/必须/严禁”等的要求优先作 `OperationalConstraint`。
- 只把明确的治理、建设、约束或交换对象作 `OperationalObject`，避免将风险描述中的普通名词泛化为业务对象。
- 收文处理单和审批表单是同一公文的处理信息载体；字段及纯流转签名不建实体，明确责任主体和事项仍提取。

## 6. 规则与检修技能

规则技能按原文条件与结果映射本体；保留条件方向、否定、数值和业务限定，不将同一分类下不同规则强行合并。检修技能区分排查动作与维修动作，实验结果只绑定实际产生它的实验，未知原因、正常阈值、系统 ID 不凭空补齐。

simple 不撰写技能；标准待 benchmark 补充后再考虑专用技能。

## 8. 上下文管理与第一步契约

`ChunkContextManager` 消费上游 chunk，不重新切片；按显式前后邻接 ID 或输入顺序找有界邻居，`same_section` 开启时按 `section_id` 过滤。实体阶段只读取当前 chunk 和类型目录，不再计算或传递原本会被 User 装配丢弃的邻居与已知实体。装配入口仍会阻止外部传入这些内容，避免跨片补抽和提前抽属性。属性与关系阶段的邻居选择算法保持原样。

属性阶段保留已接受实体和缺失属性目录，邻居文本由现有属性模块截断（单片 800 字、累计预算 2000 字，按整片加入，因此边界可能略超预算）；关系阶段保留调用方选定的 pair 与局部上下文。修复阶段 User 的当前文本最多 8000 字，关系修复实体目录最多 25 项。

按用户最终确认，第一步仍是：

```json
{
  "entities": [
    {
      "type": "本体稳定类型标识",
      "mention": "原文称呼或忠实归纳名称",
      "start_char": 0,
      "end_char": 0,
      "evidence": {"quote": "来源原文片段"}
    }
  ]
}
```

位置为当前 chunk 内左闭右开区间；上面 0 只是不能逐字定位时的约定，正常输出应提供真实位置。实体项不允许 `name`、`properties`、关系或额外字段，业务实体的 `name` 仍由原有后处理从 `mention` 生成。本次不改变来源绑定、实体合并或属性/关系抽取顺序。

重试时 System 不变，五段 User 不变，仅增加 `task.retry_feedback`；不再在 JSON 后追加 Markdown 导致 User 不可解析。新增回归测试见 [`test_prompt_router.py`](../../algorithm/knowledge_extract/v3_1/tests/test_prompt_router.py)，覆盖固定 System、路由、上下文隔离、原文边界、实体契约、形态策略、pair 分类、修复与重试。

## 11. 如何使用与修改

调用方提供本体和已切片的文档即可，入口自动生成两条消息；不用手动拼接领域提示词：

```python
from algorithm.knowledge_extract.v3_1 import extract
from algorithm.knowledge_extract.v3_1.chunk_context import ExtractionChunk

result = extract(
    ontology=ontology_text,
    chunks=[ExtractionChunk(chunk_id="chunk-0", text=chunk_text)],
)
```

此 `extract()` 返回稳定的最终 `entities / relations` 结果；第一步的模型契约仍是 span candidate，并非最终图实体的 `name / properties` 契约。需要诊断字段时调用 `extract_harness()`。LLM 配置沿用 `KG_EXTRACT_LLM_*`，无需新增环境变量。服务的版本选择值仍是 `KG_EXTRACT_ALGO_VERSION=v3.1`；本轮只验证算法包，未验证旧 Backend 适配器与这批工作区改动的整链集成，不代表修改该变量就完成部署。

若只想查看第一步实际送给模型的 System / User：

```python
from algorithm.knowledge_extract.v3_1.ontology_compiler import compile_plan
from algorithm.knowledge_extract.v3_1.prompt_router import resolve_document_route, build_chat_messages

plan = compile_plan(ontology_text)
chunk = ExtractionChunk(chunk_id="chunk-0", text=chunk_text)
route = resolve_document_route(plan, [chunk])
messages = build_chat_messages(task="entity", plan=plan, route=route, chunk=chunk)
# messages[0] = {"role": "system", "content": 固定系统提示词}
# messages[1] = {"role": "user", "content": 五段 JSON 字符串}
```

维护入口：通用约束改 `prompt_templates.py`；领域抽取粒度改 `domain_skills.py`；路由条件改 `prompt_router.resolve_document_route()`；输出字段与校验 schema 改 `output_contracts.py`。更改输出字段时仍须同步解析、后处理与契约测试。这里的 skill 是应用内 Python 策略，不需要在 Codex 安装。

样例原文（换行计一个字符）：

```text
关于开展设备巡检的通知
设备部负责开展设备巡检。
```

本体声明 `OfficialDocument`、`OperationalAgent`、`OperationalActivity`，公文路由自动命中。模型原始返回中的一项为：

```json
{
  "type": "OperationalAgent",
  "mention": "设备部",
  "start_char": 13,
  "end_char": 18,
  "evidence": {"quote": "设备部负责开展设备巡检"}
}
```

**不能把 Schema 通过等同于位置正确**。本次三项 mention 与 quote 都可在原文定位，但原始 offset 都不准确。原有 `_normalize_span_entities()` 自动纠正并记录 `ENTITY_SPAN_OFFSET_CORRECTED`；本轮未新增或改变该纠正策略：

| 类型 | mention | 模型原始位置 | 归一化后的 mention 位置 |
| --- | --- | --- | --- |
| `OfficialDocument` | 关于开展设备巡检的通知 | `[0, 12)` | `[0, 11)` |
| `OperationalAgent` | 设备部 | `[13, 18)` | `[12, 15)` |
| `OperationalActivity` | 开展设备巡检 | `[18, 24)` | `[17, 23)` |

后续 `bind_entity_evidence()` 中 `evidence.start_char/end_char` 表示**quote 位置**：后两项均为 `[12, 23)`，而不是 mention 位置。最终公开图实体的名称由 mention 转为 `name`，这不改变模型第一步只输出 type、mention、位置和 evidence 的要求。
