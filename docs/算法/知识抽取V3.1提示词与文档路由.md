# 知识抽取 V3.1：公共 System + 阶段约束、领域 Skill 与统一 User

更新时间：2026-10-12。依据当前工作区的 [`prompt_router.py`](../../algorithm/knowledge_extract/v3_1/prompt_router.py) 整理；描述的是源码行为，不代表测试或生产服务器已部署此版本。历史文档中指向 `prompts.py`、声称“没有文档类型路由”的描述不适用于当前实现。

> 当前 v3.1 仅执行实体抽取、属性补全和实体修复。关系候选、分类、语义核验、确定性边组装及关系修复已删除。返回接口保留 `relations: []`，其他算法版本不变。2026-10-12 已同步到 88 的现有 `qasystem_backend` 做测试，验证范围和限制见 [修复与验证记录](知识抽取V3.1-P1P2修复与88验证-20261012.md)。

## 2026-10-12 当前流程：候选带属性、独立证据校验与有界补全

本节覆盖后文历史记录中的“候选不带属性”“每个键只进一个批次”“全部来源一次输入”“修复截断 8000 字”等旧行为。运行时参数及边界详见 [v3.1 README](../../algorithm/knowledge_extract/v3_1/README.md#长文本请求预算)。

1. 程序按 V2 逻辑确认领域，每请求加载固定 skill 快照；候选阶段同时装配实体和属性规则。User 仍仅发送 `domain_policy.extraction_rules`，不让 LLM 再判断领域。
2. 候选阶段读取本体类型、属性与字段说明，在当前请求窗口输出 JSONL。例如：`{"type":"Person","mention":"张三","properties":{"duty":"检查"},"evidence":{"quote":"张三负责检查","property_quotes":{"duty":["张三负责检查"]}}}`。输出 schema 显式列出属性标识与数据类型，显示名不能作为属性键；每行再按实际 type 校验。兼容省略 properties 的旧候选。
3. 属性证据独立检查：属性引文不能用实体名定位兜底。明确的肯定字面值可直接验证；归纳、否定、歧义和修改既有属性需 LLM 明确确认。拒绝无依据的新值并记录告警。程序按完全相同的 type + name 分组，仅复制已核验且不冲突的值，语义综合仍由模型完成。
4. 已完成局部属性检查且无冲突、无待处理邻片的键跳过补全；无属性类型也跳过。只有冲突的键重读各冲突值的支持引文及附近上下文，重复文本和相同属性值只提交一次。其他情况按单键、来源窗口流式补全，完整键集合和唯一性校验进入重试循环。邻片即使没有实体候选也可提供代词/续文信息，但不跨文档，默认不跨章节。
5. 全部出现及属性支持来源保留为 evidences/property_evidence，并透传中间对象与图投影。UID 使用原始键的稳定哈希，不再规范化大小写、全半角或内部空格。修复只涉及相关键，没有进展即停止并如实报告剩余缺口。
6. 请求同时受完整消息字节预算、来源窗口及输出容量限制；默认窗口 2000 字、100 字重叠、消息 48000 字节。单次超时/超限/截断继续拆分，所有类型都按预算调度，不做词面硬剪枝。单个超大切片的窗口也在固定 worker 池并发，待执行任务不超过 2 * max_workers。证据回映原始 chunk ID/偏移。累计状态自身超预算则明确失败并保留已有事实，不静默截断；文档总 deadline 耗尽后直接停止调用和递归拆分。

所有调用保持普通文本模式。单窗口可直接完成实体与属性，涉及语义核验或跨片冲突时仍会有额外调用，不能保证每个实体都只调用一次模型。算法结果 run_trace 的完整提示词默认只留前 32 次，其余保留调用计量；这不改变应用层独立追踪文件的保留策略。确定性回归覆盖了 100 个来源切片、单片 600 个实体尾部、大小写投影、邻片指代、缺键重试和截断拆分；88 已进行 100 万字符模拟压力测试和 10 万字符真实模型实验，数据及适用范围见验证记录。

## 1. 提示词如何组成

抽取调用固定使用两条 chat message：

1. **system**：`BASE_SYSTEM_PROMPT` 公共规则加当前阶段约束，位于 [`prompt_templates.py`](../../algorithm/knowledge_extract/v3_1/prompt_templates.py)。公共部分保留证据与输入边界；实体、属性阶段仅追加对应提取规则，实体修复额外限制为列出的 repair_issues。同一阶段不随领域改变，不追加领域提示词；重试保留完整阶段 System。
2. **user**：`build_chat_messages()` 按统一 JSON 外壳装配，顶层固定为 `task`、`output_contract`、`domain_policy`、`ontology`、`documents`。使用 JSON 序列化，原文中的标题、引号、伪造指令只作为字段值进入消息。

```text
本体 + 受限切片信号（V2 规则） → 确定文档类型 → 对应类型的 skill（不存在则为空）
                                          ↓
公共 System + 阶段约束 + 统一 User(task, output_contract, domain_policy, ontology, documents)
                                          ↓
                          模型 → 原有 JSON Schema 校验 → 后处理
```

| User 字段 | 内容及来源 |
| --- | --- |
| `task` | 当前 `operation`、任务纪律、阶段允许的已知实体、修复问题；重试反馈也写入此字段。 |
| `output_contract` | 独立模块 [`output_contracts.py`](../../algorithm/knowledge_extract/v3_1/output_contracts.py) 统一维护阶段约束，以及实体候选、完整实体的 schema 构造函数；调用方只提供本体和已知实体。`success_schema` 描述 JSONL 单行实体；程序解析后装入内部 entities 集合做校验。请求不发送 response_format，不使用 JSON mode。 |
| `domain_policy` | 公共入口通过 `SkillAssemblyPlanner` 按已解析路由一次性预编译各阶段 skill；单次预览路径由 [`domain_skills.py`](../../algorithm/knowledge_extract/v3_1/domain_skills.py) 确定性选择，仅包含本阶段 `extraction_rules`，路由原因留在审计记录；只影响证据理解与候选粒度。这里不是 Codex 可安装的 SKILL.md。 |
| `ontology` | `compiled_task_catalog`：按阶段裁剪的编译本体目录，保留当前 v3.1 的上下文控制，不改成每轮灌入完整 PlantUML。 |
| `documents` | 本阶段提供的 `text`，只声明处理已提供分段，不声明完整文档覆盖。 |

默认目录保留公文、规则和 trouble 三类技能；V2 路由只自动匹配公文，standard 暂无技能，generic 使用空策略。证据核验仍使用独立的核验 System。

## 1.1 User 原模板与字段字典

当前继续使用原来的五段 JSON User。`<ONTOLOGY>/<EXAMPLES>/<DATA>` 分区模板仅讨论过方案，未应用到源码或 88 的本次 sample；无需回滚渲染代码。此前已实现的“公共 System + 阶段约束”保持不变。

这里的 User 指 `messages` 中 `role="user"` 的 `content`：它是经过 `json.dumps` 序列化的字符串，解析后才是以下对象。顶层键按下面的固定顺序序列化，重试时也保持该顺序。

```json
{
  "documents": [],
  "ontology": {},
  "domain_policy": {},
  "output_contract": {},
  "task": {}
}
```

这五段分别回答：**本轮做什么、输出什么格式、遵循哪些领域规则、允许抽什么、从哪里抽**。空对象和空数组仅用于展示骨架，实际请求包含下面的字段。

### task：本轮任务与输入范围

| 字段 | 类型 | 含义与取值 |
| --- | --- | --- |
| `operation` | string | `entity` 实体候选、`property` 属性补全、`repair` 实体问题修复。日志里的 `repair_entity` 是调用阶段名，User 中仍为 `repair`。 |
| `discipline` | string | 本轮任务纪律，如禁止新增实体、只修复列出问题；由程序按阶段生成。 |
| `known_entities` | array | 本轮允许使用的已接受实体目录。实体及实体修复阶段为空；属性阶段按需提供。 |
| `repair_issues` | array | 校验器提供的待修复问题；通常仅修复阶段非空。 |
| `retry_feedback` | string，可选 | 失败重试时追加，包含错误类型、具体校验错误和纠正要求；首轮不包含。重试不改原文、本体或输出契约。 |

`known_entities[]` 仅保留调用方提供的下列字段；修复时最多保留 25 个实体，并移除 `missing_properties`：

| 字段 | 含义 |
| --- | --- |
| `type` | 本体允许的实体类型标识。 |
| `name` | 已接受实体的名称，不允许属性阶段重命名。 |
| `properties` | 目录占位 `{}`；程序不把跨切片属性预先归并。 |
| `occurrences` | 该 type + name 在各切片中的原始出现记录，含 chunk_id、properties、evidence，交给 LLM 综合。 |
| `missing_properties` | 本轮可补全的缺失属性及其约束；只在调用方提供时存在。 |

`repair_issues[]` 来自 `VerificationIssue.to_dict()`：

| 字段 | 含义 |
| --- | --- |
| `code` | 可识别的问题代码。 |
| `message` | 问题的文字说明。 |
| `path` | 出错字段或对象的定位路径。 |
| `severity` | 严重程度；`error` 表示硬错误。 |
| `repair_type` | 修复类别；决定实体修复处理。 |
| `context` | 与问题有关的对象、证据等上下文，结构随问题类别变化。 |

### output_contract：输出契约

| 字段 | 类型 | 含义与取值 |
| --- | --- | --- |
| `success_schema` | object | JSONL 单行实体的 JSON Schema，规定允许的字段、字段类型、必填项、枚举和数组约束等。它是模型返回值的契约。 |
| `empty_result` | object | 本轮合法的空集合外壳，使用 `{"entities":[]}`；候选非空的属性阶段不允许遗漏实体。 |
| `constraints` | string | 补充证据、定位、字段范围等语义要求；和 schema 一起生效。 |

`success_schema` 内部是标准 JSON Schema，并随本体和阶段生成，不是固定业务字段表。常见关键词包括 `type`（类型）、`properties`（对象字段）、`required`（必填项）、`additionalProperties`（是否允许额外字段）、`items`（数组元素）、`enum`（允许值）、`minItems`（最少元素数）和 `uniqueItems`（元素是否唯一）。空字符串、空数组和省略字段不可互换，须按实际 schema 判断。

### domain_policy：领域规则正文

仅发送 `extraction_rules`（程序确认领域并加载 skill 后按本阶段装配的执行规则）。不再发送 `profiles` 嵌套，不要求模型重新判断领域；公文规则直接以“公文领域抽取规则”开头。无适用 skill 时规则为空字符串：`{ "extraction_rules": "" }`。同领域多个 skill 的本阶段规则按加载顺序拼接。路由的 kind/source/scores/reasons、技能版本、哈希和章节选择保留在 `profile.prompt_assembly.plans` 审计记录，不发送给 LLM。

### ontology：本轮编译后的本体目录

仅保留 `catalog`：实体候选和修复阶段展示允许的类型；属性阶段展示本体属性及数据类型。`format`、`ontology_id`、`feature_catalog` 不进入 User，不再发送占位说明。

### documents：直接提供原文

`documents` 是数组，每项直接以 `text` 开始，不再包裹 `current_chunk`，也不发送 `chunk_id`。属性阶段仍提供本批实体的全部来源切片。

| 字段 | 含义 |
| --- | --- |
| `text` | 本轮实际可读取的原文；内部证据位置由程序计算。 |
| `metadata` | 非空的业务来源信息，例如 sheet、行号；不发送 `signal_source`。 |
| `section_title` / `clause_number` / `page_no` | 非空的章节标题、条款编号和页码。 |

片段/文档/章节 ID、父子与相邻片段 ID、字符偏移只在程序内部使用。修复阶段只发送最多 8000 字符的 `text`。空 metadata 不输出。

`task` 不发送空的 `known_entities`、`repair_issues` 等字段；有内容时保留。已知实体的 `occurrences` 只发送非空属性及证据引用，不发送内部片段 ID 和证据定位信息。schema、本体目录及有效业务值不做通用删空，避免改变输出约束。

### Skill 编译不调用 LLM

Skill 由 V2 同等路由判断确定性选择，并在每个抽取任务内预编译一次，不再发送读取/规划消息。每次独立的抽取请求仍包含一份适用阶段规则。`profile.prompt_assembly.plans` 记录一条请求级审计（route、read_skills、stages），mode 为 `deterministic_skill_compile`，calls/attempts 为空。当前抽取 User 没有 `EXAMPLES` 或 `golden` 字段。

源码入口：[User 序列化](../../algorithm/knowledge_extract/v3_1/prompt_templates.py)、[按阶段组装](../../algorithm/knowledge_extract/v3_1/prompt_router.py)、[输出契约](../../algorithm/knowledge_extract/v3_1/output_contracts.py)、[片段字段](../../algorithm/knowledge_extract/v3_1/chunk_context.py)。

## 2. 公共与阶段系统提示词

`BASE_SYSTEM_PROMPT` 将模型定位为**受已编译本体约束的知识图谱抽取器**。只依据当前上游 chunk 和允许的局部上下文，只使用本体声明的类型和属性；输出为 JSONL，每行一个符合本轮 schema 的实体 JSON 对象。

以下规则按职责分配到公共部分及对应阶段，不再将所有提取规则同时发给每个阶段。

| 方面 | 主要要求 |
| --- | --- |
| 证据 | 事实必须有原文依据，`evidence.quote` 优先逐字引用；无法逐字对应时引用最相关的真实片段。允许对多条记录作忠实归纳；禁止编造。 |
| 完整性 | 尽量抽全本体允许的事实，并列的单位、附件、对象等逐一提取。 |
| 实体 | 优先显式命名对象；本体允许时保留集合名词。数值、单位、字段标签、修饰词和标量属性值不单独成实体；同一 chunk 内同类型同 mention 去重。 |
| 属性 | 字面属性取原文或本体规范化值；语义属性可忠实概括。ICS/CCS 等公认标准编码表支持的规范值可补全，但不得猜测编码、缺失字段或常识事实。枚举多值尽量取全。 |

## 3. 按任务生成的通用用户提示词

| 任务 | 输入范围与目录 | 输出纪律 |
| --- | --- | --- |
| `entity` | 仅当前 chunk；只展示本体类型目录，不展示属性、关系和已知实体目录。 | 只提议实体，不输出关系。每项仅含 `type`、`mention`、`evidence.quote`；模型不输出字符位置，程序根据原文引用绑定证据。 |
| `property` | 展示本体类型及属性、intrinsic feature、已知实体及缺失属性；关系目录关闭。 | 只给已接受实体补缺失属性，不能改实体集合或类型。字面值应可在当前 chunk 定位；语义值可以归纳。字符串确实缺失时可填 `""`，不可用 `null` 代替。每个属性只更新一次，引用须支持更新。 |
| `repair` | 给出 verifier issues；已知实体最多展示前 25 个，当前 chunk 只保留 `chunk_id` 和最多 8000 字原文。 | 只修复列出的问题，不重复已接受事实；输出遵循本轮 schema。 |

实际内部 `output_schema` 由调用方传入，其 entities.items 作为单行契约在 `output_contract.success_schema` 中呈现；未显式提供 schema 的实体调用使用本体编译所得的实体契约。修复任务若 schema 含 `entities`，采用实体输出契约，同时保留“只修复列出问题”的任务纪律。实体候选无结果时返回单独一行 `{}`，属性阶段必须返回全部给定实体，不再因输入是记录表而向属性阶段错误提示 `entities` 空结果。

### 类型专属规则

公文表单规则归入 `official_document/SKILL.md`，仅在当前片段为表单时适用；规则表的归并、前件/后件及模板规则归入 `rule/SKILL.md`。检修规则资产保留在 `trouble/SKILL.md`，区分部件、故障、实验、结果和维修，禁止将正常结果当故障或混合不同记录的结果。JSON/表格形态本身不触发额外 skill。

## 4. 文档路由如何选择领域扩展

`resolve_document_route()` 使用原 V2 确定性规则。先匹配本体中的类、属性、关系特征，每个命中特征加 5 分。单领域本体得分达标时直接采用；本体不足或两个领域均强时，再叠加前 12 个切片的信号。每片正文最多读取前 1200 字符，同时读取 section_title、clause_number 和指定元数据字段（title、heading、section_title、unit、block_kind、document_number、standard_number）。

公文文本信号：标题 +4，文号 +3，公文词汇 +1；标准文本信号：标准号 +4，条款结构 +2，标准词汇 +1。同类信号在请求内只计一次。最高分至少 6 且领先另一类至少 3 才选中，否则 generic。只输出 official_document、standard、generic；rule/trouble 资产保留，但不会被此规则自动选中。一次请求确定一个类型，各 chunk、各阶段复用。路由元数据保留 kind、source、scores、reasons，便于审计。

注册器按名称或 `route_hints` 匹配技能，程序预编译 `all` 与适用阶段规则段，不能跨类型装配。`simple` 和 `generic` 始终保持空策略；标准暂未配置 skill。目录不存在、为空或缺少对应阶段/类型技能时，使用公共 System + 阶段约束 和包含原文、本体、任务、输出契约的 User 继续抽取。已存在但格式损坏的技能仍报配置错误。

内部装配时路由写入 `domain_policy.route`，策略写入 `profiles`，选中 ID 写入 `default_profiles`。技能版本、内容哈希和请求级编译审计仍保留。

## 5. 公文路由提示词

`OFFICIAL_DOCUMENT_PROMPT_EXTENSION v5` 提醒模型关注标题、文号、发文/来文单位、主送/抄送、正文条目、附件、办理动作、约束和交换对象，并强调这些只是**本体映射提示**，不能扩展 schema。

- 一份公文保留一个 `OfficialDocument`，mention 用文件标题；文号等作为属性或证据。
- 正文开头、编号条目、报送要求、附件列表优先映射 `DocumentUnit`；明确的附件/材料/反馈信息映射 `OperationalInformation`；通知、报送、反馈等传递行为映射 `OperationalExchange`。
- `OperationalActivity` 以完整动宾事项为粒度：一个事项的状语、否定和结果保留在一起，并列事项分别抽取。带“不得/必须/严禁”等的要求优先作 `OperationalConstraint`。
- 只把明确的治理、建设、约束或交换对象作 `OperationalObject`，避免将风险描述中的普通名词泛化为业务对象。
- 收文处理单和审批表单是同一公文的处理信息载体；字段及纯流转签名不建实体，明确责任主体和事项仍提取。

## 6. 规则与检修技能

规则技能按原文条件与结果映射本体；保留条件方向、否定、数值和业务限定，不将同一分类下不同规则强行合并。检修技能区分排查动作与维修动作，实验结果只绑定实际产生它的实验，未知原因、正常阈值、系统 ID 不凭空补齐。

simple 不撰写技能；标准待 benchmark 补充后再考虑专用技能。

## 8. 上下文管理与第一步契约

`ChunkContextManager` 消费上游 chunk，不重新切片；按显式前后邻接 ID 或输入顺序找有界邻居，`same_section` 开启时按 `section_id` 过滤。实体阶段只读取当前 chunk 和类型目录，不再计算或传递原本会被 User 装配丢弃的邻居与已知实体。装配入口仍会阻止外部传入这些内容，避免跨片补抽和提前抽属性。属性阶段的邻居选择算法保持原样。

属性阶段保留已接受实体和缺失属性目录，邻居文本由现有属性模块截断（单片 800 字、累计预算 2000 字，按整片加入，因此边界可能略超预算）。修复阶段 User 的当前文本最多 8000 字。

按用户最终确认，第一步仍是：

```json
{
  "entities": [
    {
      "type": "本体稳定类型标识",
      "mention": "原文称呼或忠实归纳名称",
      "evidence": {"quote": "来源原文片段"}
    }
  ]
}
```

位置为当前 chunk 内左闭右开区间；上面 0 只是不能逐字定位时的约定，正常输出应提供真实位置。实体项不允许 `name`、`properties`、关系或额外字段，业务实体的 `name` 仍由原有后处理从 `mention` 生成。本次保留来源绑定与实体合并，删除关系抽取阶段。

## 2026-10-11：跨切片同名实体与完整属性输出

属性阶段按完全相同的 `type + name` 集中所有出现记录，同一键不会拆入不同批次。每个批次的 `documents` 包含相关切片完整原文，`known_entities[].occurrences` 保留各来源属性和证据。LLM 负责综合属性，输出每个唯一键的一条完整实体；同名不同类型不能合并，冲突与不同适用条件不能互相覆盖。

输出示例：`{"entities":[{"type":"Person","name":"张三","properties":{"duty":"检查并记录"},"evidence":{"quote":"张三负责检查"}}]}`。抽取链路不再生成实体 ID 或应用 `entity_id + updates`，也不通过 CandidatePool、实体解析器或图组装器合并属性。公开业务结果去掉证据定位字段，保留 type、name、properties；图兼容接口的 uid 仅属于输出适配。

## 当前各阶段 success_schema

| 阶段 | JSONL 每行必填字段 | 范围与校验 |
| --- | --- | --- |
| entity | type、mention、evidence.quote | type 限当前允许的具体类型；无候选返回单独一行 `{}`；字符偏移与证据由定位校验处理。 |
| property | type、name、properties、evidence.quote | 每批仅一个 type，name 限本批名称；properties 仅包含该类型的本体属性。每个唯一 type + name 必须恰好返回一次，完整性及重复由本地语义校验处理。 |
| repair | type、mention、evidence.quote | 沿用实体候选结构，且只处理 repair_issues；候选经属性阶段后才成为最终实体。 |

模型输出不含 `entities` 包装和外层数组，每行实体禁止额外字段。程序内部仍使用 entities 集合进行校验与后续处理。属性值严格匹配本体数据类型（包括数值、布尔及类型化数组）；无证据属性可以省略，无属性类型仍返回 `properties: {}`。同名属性属于不同类型时，schema 不再互相覆盖。旧 `updates` 结构或错用其他阶段 schema 会在发送前报错。

保持简单 schema 以兼容现有模型适配器；非空名称、字符位置有效性、实体键完整性、来源真实性不能仅靠 schema 保证，仍需本地校验。尚未通过本次改动后的 88 实际模型调用验证。

## 2026-10-12：取消模型字符偏移

实体候选与修复的 success_schema 只要求 type、mention、evidence（内含 quote），禁止 start_char/end_char。属性阶段保持 type、name、properties、evidence。

内部证据仍由程序定位并包含字符区间，不要求模型计数；引用不能定位时尝试实体名称，仍不能定位则保留未定位状态，交给后续证据校验，不编造 0:0 区间。候选证据重复出现时记录 ENTITY_EVIDENCE_AMBIGUOUS，首个匹配位置不代表已唯一消歧。

## 原文名称优先（2026-10-12）

entity 与 repair 共用 ENTITY_NAME_RULES，同时写入 System 和 output_contract.constraints。存在明确原文名称时逐字保留完整名称及内部空格、标点和大小写；当前输入明确标注同一实体全称/简称时优先原文全称，不自行扩写。仅无明确名称时允许归纳。属性阶段 name.enum 固定候选名称，跨切片完全相同 type + name 合并后仍逐字保留，不做别名归并。该规则是候选选择约束，不是程序自动猜测、替换模型名称；最终抽取质量仍需真实模型评测。

## JSONL 文本输出（2026-10-12）

所有 v3.1 模型调用使用普通 chat 文本，不发送 response_format，也不在重试中切换 JSON mode。抽取、属性补全和修复输出 JSONL；独立证据核验仍按其专用对象契约解析，但同样不启用 JSON mode。

实体行示例：`{"type":"Person","mention":"张三","evidence":{"quote":"张三负责检查"}}`。
属性行示例：`{"type":"Person","name":"张三","properties":{"duty":"检查"},"evidence":{"quote":"张三负责检查"}}`。

每个实体占一个物理行；字符串内换行写为转义字符。不输出 Markdown、说明文字、外层数组或 entities 包装。候选为空时单独输出 `{}`，不能与实体行混合；真正空响应仍视为失败。任一行无法解析、字段校验失败或响应截断，整次调用进入有界重试，不静默丢弃坏行。
