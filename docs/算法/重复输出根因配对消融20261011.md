# API 重复输出：配对消融与止损建议（2026-10-11）

本轮追加 25 次冻结调用，未改生产算法。**完整输入再次出现大规模重复直到 length；按语义分为不超过约 20 个实体的片段后，返回的片段未出现长循环，但仍有普通超时。关系修复的任务/schema 不一致确定存在，并导致错误关系；本轮尚未证明它触发历史循环。** 少量重复不是主失败指标，可以确定性去重。

## 条件与可审计材料

沿用已有 88 `qasystem_backend` 的 SiliconFlow / `deepseek-ai/DeepSeek-V4-Flash` 配置，温度 0、thinking disabled、输出预算 16384、无自动重试、请求超时 300 秒、最多两请求并发。不使用服务端 json_schema。冻结集为 `test_data/repetition/causal-v1/`，工具为 `eval/tools/repetition_causal.py` 和 `repetition_study.py`，测试为 `tests/eval/test_repetition_causal.py`。配置凭据只在内存读取，不写请求工件。

先执行关系两轮 10 次和实体三轮 9 次，再针对异常追加实体两轮 6 次；轮内顺序交错反转。它是有限、顺序自适应的小样本探索，不是固定样本量随机试验。完整脱敏请求、原始输出、finish_reason、usage、耗时和失败记录保存在 `tmp/repetition-causal-20261011/repetition-causal-all25-20261011/{run,replication}/`，合并副本 `combined/`，汇总 `report-all25.json`。88 主机备份 `/tmp/repetition-causal-all25-20261011`。没有继续扩大矩阵。

实体 whole 消息与前轮确认基线逐字一致，prompt_tokens=2748，与历史异常一致。关系 legacy 原样恢复旧共享 JSONL 追加，prompt_tokens=9765，与历史异常一致；clean 条件有意去掉旧 JSON wrapper/JSONL 冲突，不能称逐字原样。没有复放旧属性调用的服务端结构化模式。本轮质量标签均是 **agent-reviewed / provisional，没有独立人类真值**，稀疏锚点只证明局部字符串覆盖，不能代替完整事实质量评分。

第 3 轮整段输出 43504 字符、16384 token、247.84 秒。345 条完整记录中只有 92 条精确唯一，73.33% 记录重复；第 93 条开始重复，第 92 条以后再没有新增，剩余 253 条全是重复。去重后无 schema 错误不代表 92 个候选都正确：312 条完整记录是 OperationalObject，泛化工作对象明显膨胀。精确重复记录重新序列化后占记录字符约 70.75%，这个是字符浪费代理指标，不能当作精确 token 或计费占比。原样第 5 轮又正常输出 32 条，同样温度 0 仍存在请求间变动。

## 将单次负载压到约 20 个实体以内

用历史异常 734 字原文按完整章节分割：A 为前 498 字，B 为后 236 字；二者拼接逐字等于原文，没有删掉后续信息。保留标题为背景，明确禁止从背景新增事实；本体和输出预算保持不变，没有“最多输出 20 条”的限制。代理根据独立事实短语暂定 A 约 16–19 个、B 约 11–13 个候选，B 低于 15 是为了不破坏完整语义单元，实际返回也均 ≤20。该数量是暂定候选负载，不是独立人工 gold。

拆分完整两片都正常返回的轮次为 1、2、5，共 3/5；整段正常返回 1/5。完整拆分轮合并后 type+mention 身份键唯一数为 26、30、26，completion_tokens 合计 1469、1691、1556；A片只重复单条，最大重复两次，B 无重复。第 5 轮有 1 个跨片相同身份，合并去重即可。第 3、4 轮 A 超时，只返回 B，不能宣称整篇覆盖完成。

结果支持把拆分作为降低长输出风险的手段；样本少、原样仅复现一次循环、超时原因未知，不能声称彻底解决或确定信息量为唯一根因。返回片段的弱锚点存在标题/附件名称歧义：第 2 轮出现通知与附件两种 OfficialDocument mention，部分 B 片会复制背景标题，应审阅别名或类型错误。没有独立事实 gold，没有测试跨片关系，所以不能确认所有事实质量无损或跨片关系保持。拆分重复发送本体，A/B 输入 token 分别 2616/2470，合计高于整段 2748。正常整段 7.25 秒；成功拆分轮两请求耗时求和约 6.84、7.97、15.49 秒，队列/网络状态与同时其他任务影响时延，不足以宣称模型速度改善。

## 关系修复冲突：已确认的错误与因果边界

冻结历史 v2 调用提供 23 个 known entities，其中没有 OperationalConstraint。4 个 repair issues 要求 CONSTRAINS_AGENT；全计划 signatures 显示该关系源类型必须是 OperationalConstraint，但按本地实体类型过滤后的 schema enum 不允许该关系。因此使用提供目录和 schema 无法完成这 4 个任务。

两轮严格配对保持原文、实体目录、schema 不变，只将无法执行的 issues 和相应 signatures 排除。旧协议两次都返回空集合，清理 JSONL 两次都返回 null，这是忠实放弃当前无法完成的修复，不是生成了正确缺失关系。保留冲突时，旧协议 1/2 响应有 schema/类型错误，另一次改用 APPLIES_TO，虽通过 schema 和端点签名，仍未完成要求的 CONSTRAINS_AGENT；还返回了带代码围栏的旧集合格式。清理协议两次均输出非法关系，共 11 条端点签名错误。仅向 enum 加入 CONSTRAINS_AGENT 后，两次都通过记录 schema，但 8 条关系源是 OfficialDocument 或 OperationalAgent，全部违反源类型签名。这证明“放宽 enum”会隐藏错误，不能用作生产修复。

历史运行元数据 source_commit 为 `65ee14f20199f52ec6ee9546c577a3027f5511a1`，含 `a5e1555` 的旧 JSONL 注入。记录 `code-provenance.json` 比对当前 v2 的 schema helper、signature rendering、known-entity rendering 与该历史版本：对应函数 AST 一致。单测用当前 helper 和冻结 23 实体类型重新生成完全相同的缺失关系 enum，说明这个不一致构造路径仍存在。当前 v3 另有先将目录截到 80 再建 schema、prompt 展示全计划与未过滤 issues 的风险；历史样本属于 v2 且只有 23 实体，不能拿 v3 的 80 截断解释它。没有运行当前线上全链路重现同一 repair，不能直接把历史调用当成当前新调用。

10 次关系条件均未循环，因此可确认的是任务矛盾导致错误/无法完成，**尚不能确认该矛盾触发历史重复循环**。清理格式也没有消除语义冲突。

## 触发、放大与止损

已证实：历史循环来自单次生成而非程序拼接；温度 0 和相同 prompt 仍可能循环；重复序列出现后可持续消耗整个预算；约 20 个候选的拆分返回中本轮未见长循环，但普通超时仍发生；修复任务约束不一致导致错误关系。

相关但未证实：实体候选泛化为宽泛“工作任务/工作对象”扩大输出空间，接着进入重复续写；属性历史日志在一个约束类型字符串里不断复用本体举例类别，可能与“枚举多项尽量全部提取”有关。它们是可疑触发点，不是因果定论。未证实模型“忘记已输出内容”、信息密度单因果、特定 provider 解码实现或权重故障；没有服务端 logits/路由日志，无法进一步区分。

建议按以下顺序实施并另做生产回归：

1. repair 的 issue、目录、可执行关系签名、schema 应共用同一作用域。需要的端点缺失时回到实体补全或报告明确未修复，不能允许错误源类型替代。记录并校验 source/rel/target 签名，schema enum 通过只是第一层。
2. 对候选容易泛化的阶段采用完整语义单元的小任务，约 15–20 个有证据实体为初步目标，保持跨片标识/必要关系背景。小重复交给共享 parser 的确定性去重，不为单条重复重跑长任务。
3. 流式观察持续零新增才止损。离线建议阈值：至少完成 40 条记录后，连续 20 条都没有新的规范化完整记录时取消；正常长列表持续新增不会触发，A片单条重复也不会触发。对尚未闭合的短枚举字段，可另检测超过约 1000 字符的周期重复；应排除 evidence.quote 和允许长原文的字段，防止误杀。

第三项仅是离线模拟。新整段循环在第 112 条可触发，保留当次全部 92 个精确唯一候选，避免后面 233 条完整记录；历史实体/关系分别有 155/318 条零新增尾部。保留唯一候选不代表保留全部正确事实。现有工具的阈值测试覆盖持续新增长列表和轻微重复；没有部署实际取消，也没有确认 API 取消后的计费行为。超时诊断需要流式 partial/阶段指标；本轮非流式五次超时无法证明循环。
