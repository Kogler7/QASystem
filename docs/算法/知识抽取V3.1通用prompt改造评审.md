# 知识抽取 V3.1：A→B / B→C 两段评审与「单通用 prompt」改造方案（2026-10-08）

> 状态：本文评审的旧 `v3.1`（`v2` 副本 + prompt router）与 `v3.2` 单通用 prompt 实现均已随版本清理从代码库移除。当前 `v3.1`（包 `v3_1`）指语义 harness，见 [知识抽取V3.1语义Harness与评测](知识抽取V3.1语义Harness与评测.md)。

## 0. 评审范围与方法

### 0.1 对象

本评审只覆盖《知识抽取V3.1基线评审.md》流程图里的**两条边**：

```mermaid
flowchart LR
    A[ontology + chunks] --> B["编译本体 ExtractionPlan<br/>lru_cache 缓存"]
    B --> C[ChunkContextManager + 文档路由]
    C --> D[Pass1 实体候选 LLM]
```

- **A→B**：`split_extractor._compile_runtime`（`split_extractor.py:95-111`）—— 本体文本 → `(ExtractionPlan, OntologySchema)`，带 `lru_cache(maxsize=32)`。
- **B→C**：`ChunkContextManager`（`chunk_context.py:80-209`）+ `resolve_document_route`（`prompt_router.py:300-351`）—— 把 plan 与 chunks 变成「抽取上下文」和「领域路由」。

**不在范围**：Pass1 之后的候选池、确定性补充、关系分类、校验、沉淀（基线 §3.1–§3.12 已覆盖的其它条目）。凡与既有基线评审重叠的结论，本文只写**新增证据或修正**，并显式标注「(承基线 §x.y)」。

> **引用约定**（两篇文档都有 §2/§3 分节，必须区分）：
> - 「**基线 §x.y**」「基线 §3.8 H1」「基线评审 §5 第 11 条」→ 指《知识抽取V3.1基线评审.md》。

### 0.2 前提（本次新需求）

> **不用路由 prompt，只用一个通用 prompt 进行抽取。**

这句话在实践中不是一个开关，而是要求把 `resolve_document_route` 现在承担的**三件事**解耦（详见本文 §3.1）。本评审据此对 A→B、B→C 两条边做 reviewer，并给出改造方案。

### 0.3 方法

代码直读 + 可复现探针 + 逐版本对照。本评审**亲自执行并落数**的实测项：

## 1. 结论摘要

**A→B（本体编译与缓存）**

| # | 结论 | 严重度 |
| --- | --- | --- |
| A-1 | `lru_cache` 用「跨请求共享可变对象」换到的收益只有 **≈10ms/请求**（15KB 本体实测），收益与风险严重不对等 | P1 |
| A-2 | 基线评审「`ExtractionPlan` 是 frozen → 安全」**不成立**：plan 有 **6 个可变 dict 字段**、`OntologySchema` 有 **7 个可变容器**，全部跨请求共享；污染可复现且对下一次调用可见 | P1（修正基线 §3.3） |
| A-3 | **类型空间三处不一致**：prompt 目录=全量 60 类，schema enum=按 chunk 收窄，候选池空集时=回退全量。这是「单通用 prompt」的第一前置障碍，也是 §3.8 H2 `enum: []` 静默零抽取的通道 | P0 |
| A-4 | 本体**只在注释里声明的枚举**，编译期只发一条告警、**从不物化取值**；prompt 只在记录表 chunk 才渲染注释；属性 schema 只按 `data_type` 定类型。→ 模型被要求填一个「合法取值从未告诉它、也从不校验」的属性 | P0 |
| A-5 | `entity_candidates` schema **没有 `properties` 键**，与 relation/property pass 共享的实体契约结构性不一致 | P2 |
| A-6 | 缓存键含完整本体文本，且 `prompt_version` 是硬编码常量 → 结果无法自证「用的哪版本体/哪版 prompt」 | P2 |

**B→C（chunk 上下文与文档路由）**

| # | 结论 | 严重度 |
| --- | --- | --- |
| B-1 | 路由的耦合面比想象的小：**prompt 扩展 + 1 段 user prompt + 3 个确定性门 + 观测与日志**，共 4 类 8 处 | — |
| B-2 | 「路由 prompt」不止 system 扩展：每个 user prompt 都带 `## resolved route kind=…; reasons=route.ontology.standard.class,…`（实测 386 字符，占 user prompt 4.7%）——**去掉扩展但留着这一段，等于没去路由** | P1 |
| B-3 | 3 个确定性标准门的 `route.kind=="standard"` **是冗余门**：实测 4 个本体家族常开跑，official/rule/simple **注入 0**，standard 注入 70 实体 / 17 关系 | P1 |
| B-4 | 多文件拼接时 `local_context` **跨文件取邻居**（已复现：B 文件首片的 previous 是 A 文件尾片）；`document_id` 在 `local_context` 里从未被使用，`same_section` 在 `section_id` 全为 None 时是空操作 | P1 |
| B-5 | `find_span` 只做空白归一，**不做全角/半角归一**：中文文档里 `5.1` 定位不到 `５．１`（已复现）→ 证据不可定位 → 触发额外 LLM 核验（基线 §3.4 的成本放大效应） | P1 |
| B-6 | `ChunkContextManager` 对重复 `chunk_id` **硬失败**（`ValueError`），`latest` 已改为「重命名 + 告警」保留内容 | P2 |
| B-7 | 实体 pass 的 `local_context` / `known_entities` 是**死参数**：算了再被 placeholder 覆盖 | P2 |
| B-8 | 想加 `use_router=False` 会**被静默吞掉**：`extract_aggregate(**_)` → `extract_harness`（无该参数）→ `extract_split`，三层签名都要改 | P1 |

**最重要的两条改造结论**

1. **「单通用 prompt」在本仓库已有参考实现**：`latest`/`v3` 的 `use_router=False` + `disabled_document_route()`（`latest/prompt_router.py:557-569`、`latest/split_extractor.py:695/743-784`）+ 把领域规则**通用化后并入 base prompt**（`GENERIC_STRUCTURE_RULES`/`GENERIC_SEMANTIC_RULES`，`latest/prompt_router.py:30-94`，base v4→v5）。V3.1 的改造应**移植这套**，而不是另起设计。
2. **领域专用规则里，真正不可通用化的只有「类型映射提示」**（如「发布机构 → Publishing Organization」）。通用 prompt 想保住这部分精度，只能把映射知识**搬进本体**（类注释/别名/枚举），这正是开源社区 schema-driven 抽取的共同做法（本文 §4.8：GraphRAG/LightRAG/Graphiti/fast-graphrag/KAG 的默认路径全是「单通用 prompt + 本体注入」，无一家按领域切 prompt）。只删扩展、不动本体，精度一定掉，且掉多少无法从历史实验推断（本文 §5.1）。

## 2. A→B：本体编译与 `lru_cache`

### 2.1 现状

```python
# split_extractor.py:95-111
@lru_cache(maxsize=32)
def _compile_runtime(
    ontology: str,
    target_types: tuple[str, ...] | None,
    include_subclasses: bool,
    mode: str,
    unknown_content_policy: str,
) -> tuple[ExtractionPlan, OntologySchema]:
    """Reuse immutable ontology artifacts across repeated harness runs."""
    plan = compile_plan(...)
    return plan, OntologySchema.parse(ontology or "")
```

调用点唯一：`split_extractor.py:486`（`extract_split` 入口，每请求一次）。返回的 `plan` 下游被 7 个模块消费（`prompt_router`、`candidate_generation`、`property_enrichment`、`entity_resolver`、`hierarchy`、`standard_semantics`、`composite`）。

### 2.2 A-1：缓存的收益只有 ≈10ms，风险却是跨请求共享状态

**P1 · 证据类型：实测（本机 15,180 字符本体）**

| 环节 | 耗时 |
| --- | --- |
| `compile_plan` 首次 | 7.3 ms |
| `compile_plan` 二次 | 4.3 ms |
| `OntologySchema.parse` | 2.4 ms |
| **合计（缓存省下的）** | **≈10 ms / 请求** |

对照一次真实抽取的量级：`standard_04` 单 case **8m25s**（基线 §3.4）。即缓存的收益是总耗时的 **约 0.002%**。

它换来的是：同一 ontology 的所有并发请求（`max_workers` 明确支持并发路径）共享**同一个 plan 对象与同一个 schema 对象**。

docstring 写的是 `Reuse immutable ontology artifacts` —— 下一节证明这个前提不成立。

> **建议**：直接删掉 `lru_cache`，或改成「返回深拷贝」。10ms 不值得引入跨请求共享可变状态。若确实要省这一次 parse，正确做法是在**上层**（适配器/调用方）编译一次并显式传入，让共享是显式的、有主的。

### 2.3 A-2：「frozen dataclass ⇒ 安全」不成立（修正基线评审 §3.3）

**P1 · 证据类型：实测（对象同一性 + 污染可见性）**

基线评审 §3.3 的论证是：

> `ExtractionPlan` 是 `@dataclass(frozen=True)`，`allowed_types` 是 `frozenset` → **安全**；`OntologySchema` 是普通 `@dataclass`（非 frozen）→ 隐患。

**前半句不成立。** `frozen=True` 只禁止**重新绑定属性**，不禁止**修改属性指向的容器**。实测 `ExtractionPlan` 的可变字段：

```
plan 可变字段: ['class_specs', 'relation_specs', 'identity_specs',
                'feature_specs', 'composite_specs', 'output_schemas']
```

`OntologySchema` 的可变容器更多：

```
classes: list      relations: list     parents: dict
unresolved: list   _symbols: dict      _relations: dict   classes_by_id: dict
```

实测污染可见性（两次调用拿到同一对象）：

```
plan 同一对象      : True
schema 同一对象    : True
plan.class_specs 共享: True
污染后二次读取可见 : True     ← a[0].class_specs['__POLLUTED__']='x' 后，b[0] 也能看到
```

**结论**：A→B 的缓存安全性完全建立在「目前没有任何代码原地改写」这一**约定**上——不是一个被类型系统或不可变结构保证的性质。基线评审 §5 第 11 条用「全量结构化指纹前后对比 MUTATED: False」证明了**今天**没触发，但触发点的数量与类型比原文描述的多得多（13 个可变容器 vs 原文点名的 1 个）。

**这条对本次改造的意义**：本文 §4 的改造会新增「把枚举物化进 `PropertySpec`」「按本体能力谓词替代 route 门」等**新增写路径**，正好是这类污染最容易发生的地方。所以**先解决 A-2 再做本文 §4**，顺序不要反。

### 2.4 A-3：类型空间三处不一致（P0，改造第一前置）

**P0 · 证据类型：代码直读 + 实测**

同一个「允许类型集合」，在同一次抽取里有三个不同口径：

| 位置 | 取什么 | 实测（`eval-v3/standard_01`，60 类本体） |
| --- | --- | --- |
| prompt 的 ontology catalog（`prompt_router.py:584` → `_type_catalog_text`） | `plan.allowed_types` **全量** | 60 类，2,024 字符 |
| 下发给 provider 的 schema enum（`candidate_generation.py:998-1001` → `output_schema_for_types(plan, "entity_candidates", plan.relevant_types(chunk.text))`） | `schema_partitions` 命中的**连通分量**（`ontology_compiler.py:183-196`） | 本样例 60 类（无收窄） |
| 候选池（`entity_resolver.py:283-285`） | 空集时**回退全量** | — |

三个后果：

1. **模型看到 60 类，却只被允许输出其中一个子集**（该子集由子串匹配决定，§3.8 M1）。这是「说 A 做 B」的口径矛盾——改造后如果只留一个通用 prompt，这个矛盾会直接变成精度损失，必须先统一。
2. **收窄到空集即静默零抽取**（§3.8 H2-B）：`"enum": []` 通过本地校验，chunk 判 0 实体且无告警。
3. `schema_partitions` 这套机制（定义 `ontology_compiler.py:125-135`、编译 `:714`、plan 字段 `:172`、序列化 `:207`）**只服务 `relevant_types`**，而 `relevant_types` 只有 **2 个调用点**（`candidate_generation.py:1001`、`split_extractor.py:828`）。

**建议**：单通用 prompt 方案下，**类型空间必须唯一**——统一取 `plan.allowed_types`（全量），删除 `relevant_types` 收窄、连带删除 `SchemaPartition` 机制。收益三条：口径一致、`enum: []` 通道消失、plan 少一个字段。代价是 schema 变大（60 类 enum 约 1.6KB，实测 `output schema` 节 1,652 字符），在 `max_tokens=16384` 下可接受；若本体极大，正确做法是**按本体分区拆调用**而不是按 chunk 收窄 enum（后者已经证明是坏设计）。

顺带：`relevant_types` 实测 0.69 ms/chunk、`deepcopy` schema 0.016 ms/次，**都不构成性能理由**；删它们不需要性能评估。

### 2.5 A-4：本体声明的枚举从未进入 prompt，也从未进入 schema（P0）

**P0 · 证据类型：代码直读（三处独立核对）**

本体的「合法取值」通常写在类属性的注释里（中车/标准本体风格：`+ 条款类型 (clauseType): String // 要求型/推荐型/指示型/允许型/陈述型`）。这条信息在链路上被**三次丢弃**：

1. **编译期不物化**。`_enum_description_qa`（`ontology_compiler.py:288-317`）只做两件事：`data_type` 是 enum 但没注释 → `INVALID_ENUM_DESCRIPTION`；注释里有 `枚举/enum` 但 `data_type` 不是 enum → 再发一条 `INVALID_ENUM_DESCRIPTION`，文案是「**建议显式声明 enum 类型或数组值域**」。也就是说：编译期**已经识别**出「这个属性的取值域藏在注释里」，但**没有把取值解析出来**，只把它降级成一条告警。
2. **prompt 期不渲染**。`_catalog_text(plan, include_comments=record_table)`（`prompt_router.py:600`）——注释**只在 chunk 被判为结构化记录表时才下发**；而实体 pass 更彻底：`feature_section = "（实体任务不展示属性目录）"`（`prompt_router.py:585`，实测该节仅 42 字符）。
3. **schema 期无约束**。`_property_schema`（`property_enrichment.py:69-79`）只按 `data_type` 映射 JSON 类型（string/array/bool/int/number），**从不读 `prop.comment`**，所以即使本体声明了枚举，schema 里也没有 `enum`。

**后果对账**：§3.11 中-9 记录的「`:1108`/`:1118` 条款类型写 `"条款"`/`"要求"`，不在本体注释声明的枚举（要求型/推荐型/指示型/允许型/陈述型）内」——根因就在这里：**模型从来没有被告知那个枚举，也没有任何一层拦它**。这不是领域策略层的 bug，是 A→B 的信息丢失。

**这条对「单通用 prompt」是决定性的**：通用 prompt 不可能内嵌任何一个领域的合法取值。**枚举必须由本体携带、由 schema 强制**——这正是开源方案把领域知识放进 schema 而不是放进 prompt 的原因（本文 §4.8）。改造建议见本文 §4.6。

### 2.6 A-5：`entity_candidates` schema 缺 `properties` 键（P2）

**P2 · 证据类型：代码直读**

`ontology_compiler.py:675-686` 的 `entity_item` 只有 `type / mention / start_char / end_char / evidence`，`additionalProperties: False`，**没有 `properties`**。这与 §3.12 H2 的观察一致但更彻底：

- split pass 产出的实体 **`properties` 恒为 `{}`**（§3.12 H2 提到 `candidate_generation.py:887-890`）→ 所有 split 实体一律以 `name` 为身份；
- 而 `property_enrichment` / `relation` 两个 pass 用的是同一套实体概念、**带 properties**；
- 于是「实体」这个概念在同一条流水线上有两个形状，`_compat_properties`（§3.10 高-1）、`_declared_properties`、`feature_specs` 的口径差异都从这里长出来。

**建议**：这是有意的设计（span-first，注释 `prompt_router.py:579-582` 说明了理由：避免把标量值变成节点），**不建议在本次改造中改动**。但应在 docstring/契约上写明「split 实体 properties 恒空、身份一律取 name」，否则后面每一次读代码的人都会把它当 bug 再查一遍。

### 2.7 A-6：缓存键与溯源（P2）

**P2 · 证据类型：代码直读**

- 缓存键包含**完整本体文本**。同义不同空白/不同导出顺序的本体 = 不同 cache 条目；`maxsize=32` 意味着最多常驻 32 份「本体文本 + plan + schema」。32 个不同本体在批量场景下是现实的（benchmark 有 16+ 套本体），内存占用值得在改造时一并评估。
- `ExtractionRun.prompt_version` 硬编码为 `"knowledge-extract-v2-two-pass-v1"`（`split_extractor.py:538`），**与实际 system prompt 无关**（实际是 BASE v4 + 路由扩展 v5/v2）。后果有两个，第二个更重要：
  1. 结果无法自证用了哪版 prompt；
  2. **历史评测结论无法回溯核验**——包括本文 §5.1 那个决定本方案走向的 A/B 实验。
- 对照：`latest` 保留同一硬编码，但新增 `profile.prompt_versions`（`latest/split_extractor.py:835` → `PROMPT_VERSIONS`，`latest/prompt_router.py:134-138`）。**改造时直接照抄**：任何 prompt 版本 A/B 都必须先把真实版本写进 `profile`，否则下一轮改造又会陷入「结论不可核验」。

## 3. B→C：`ChunkContextManager` + 文档路由

### 3.1 现状：路由实际承担三件事，分布在 4 类 8 处

| 层 | 位置 | 内容 |
| --- | --- | --- |
| ① prompt 扩展 | `prompt_router.py:540-542`（拼接）、`:134-139`（`_route_extension`） | `OFFICIAL_DOCUMENT_PROMPT_EXTENSION v5`（1,606 字符/12 条）、`STANDARD_PROMPT_EXTENSION v2`（734 字符/6 条） |
| ② user prompt 的 route 段 | `prompt_router.py:643-644` | `## resolved route` + `kind=/source=/reasons=` |
| ③ 确定性门 | `split_extractor.py:630-634`、`:742-751`、`:752-756` | `enrich_standard_semantics`、`assemble_standard_semantic_relations`、`assemble_standard_technical_relations` |
| ④ 观测与日志 | `split_extractor.py:419`（`_empty_result`）、`:1145`（正常路径）、`:523-528`（日志） | `profile.document_route` |

下游契约影响**极小**（已全仓 grep）：

- `profile.document_route` 的消费者只有 `eval/tools/v2_scripts/verify_v2_wiring.py:38`（v2 接线自检，用的还是构造的假数据）；
- `eval/run.py` **不读任何路由字段**；
- backend 适配器只读 `profile.chunk_source_ids`、`profile.repair_stop_reason`，不读 route。

**即：删路由 prompt 没有外部契约阻力。** 真正的阻力只有 ③，见本文 §3.3（确定性门实测）。

### 3.2 B-2：「路由 prompt」不止 system 扩展，还有 user prompt 里的 route 段

**P1 · 证据类型：实测（真实本体 + 真实 chunk 构造 prompt）**

实测（`eval-v3/standard_01`，chunk 3,000 字符）：

| 组成 | 有路由 | 无扩展 | 占比 |
| --- | --- | --- | --- |
| system | 1,845 | 1,109 | 扩展 736 字符 |
| user | 8,174 | 7,846 | — |
| **合计** | **10,019** | **8,955** | **扩展 = 7.3%** |

（该案例路由为 `kind=standard, source=ontology, scores=(official=5, standard=40)`，与基线 §3.3 实测一致。）

而 `## resolved route` 这一节是 **386 字符**：

```
## resolved route
kind=standard; source=ontology; reasons=route.ontology.official.issue_relation,
route.ontology.standard.class, route.ontology.standard.clause, route.ontology.standard.clause_property,
route.ontology.standard.number_property, route.ontology.standard.section,
route.ontology.standard.section_property, route.ontology.standard.structure_relation,
route.selected.standard
```

**这一节是隐式路由 prompt**：它直接告诉模型「这是 standard 文档」，而且 `reasons` 里的 reason code **逐字就是本体类名**（`standard.class`、`standard.clause`…），等于把分类结论和证据一起喂给模型。它占 user prompt 的 4.7%，**比标准扩展本身（734 字符）的一半还多**。

> **改造要点**：只把 `prompt_extension` 置空、保留 `## resolved route`，等于「去掉了领域规则、留下了领域标签」——这是最坏的一种组合。两层必须同时处理（本文 §4.3）。

**三层路由面的总量**：扩展 736 + route 段 386 = **1,122 字符 ≈ 实体 pass prompt 的 11%**。补充实测（official_01，8 类本体）：system 3,376(开)/1,768(关)、user 3,489/3,135，合计 **6,865 vs 4,903 → 路由面占 28.6%**。即路由面的真实占比随「领域扩展长度 / 本体规模」在 **11%–29%** 之间浮动：本体越小、领域扩展越长的 case，占比越高。这进一步说明**这次改造不是为省 token**，而是为了去掉「换本体即静默失效」的域耦合（见本文 §4.2 与基线 §3.11 M7）。

### 3.3 B-3：3 个确定性门的 `route.kind=="standard"` 是冗余门（已实测）

**P1 · 证据类型：实测（4 个本体家族，常开跑确定性标准补全）**

`route.kind` 真正的硬依赖是三个确定性补全，它们决定「标准类的结构/语义实体与关系是否产出」：

```python
# split_extractor.py:630-634
standard_semantics = (
    enrich_standard_semantics(pool, manager, plan, warnings=warnings)
    if route.kind == "standard" else {}
)
# :742-751 / :752-756 同理
```

因此「删路由」的第一反应会担心：路由一删，标准确定性层就永远不跑。**实测表明这个门是冗余的**——`enrich_standard_semantics` 的 5 个子函数各自都有本体结构守卫（`_add_terminology` 守卫 `Terminology`；`_add_forms` 逐条守卫 `Annex` 等；`_add_metadata_semantics` 走 `_relation_targets`；`_add_technical_entities` 守卫 `ActionClass`/`Subject of Standardization`/`Property`/`ExternalResource`；`_add_content_entities` 在 `standard_semantics.py:1064-1069` 硬要求 `Normative Element`/`Informative Element`/`Clause` 三类都在，否则 `return {}`）。

把三个门**全部去掉、无条件常开**，在 4 个本体家族上跑（结构标题实体已预置，模拟真实时序）：

| 本体家族 | 结构标题实体 | `enrich_standard_semantics` 新增 | 两个标准关系组装器新增 |
| --- | --- | --- | --- |
| official（8 类） | 0 | **0** | **0** |
| rule（1 类） | 0 | **0** | **0** |
| simple（2 类） | 0 | **0** | **0** |
| standard（60 类） | 43 | **70**（Clause 17、ActionClass 11、Property 9、Constrain 7…） | **17**（`specifiesCharacteristic` 9、`imposesConstraint` 7、`referencesExternalResource` 1） |

**结论：在本体结构层面，非标准家族注入为 0，标准家族正常产出。** `route.kind=="standard"` 不是正确性门，只是「少跑一点代码」的优化。

> 探针的边界（诚实声明）：池内没有 LLM 候选实体（用确定性结构实体模拟）。这足以证明「非标准本体上常开不注入」；但**不能**证明「有 LLM 候选时也不注入」——`_add_metadata_semantics` / `_add_technical_entities` 会扫 `pool.accepted_entities()` 中的结构实体，注入仍需本体类存在，故判断为安全，但正式改造时应补一条带 LLM 候选（StubLLM）的回归测试。

**建议**：把门从「文档路由」换成**本体能力谓词**（plan 派生），例如：

```python
# 语义：本体是否声明了标准结构补全所需的类
def supports_standard_semantics(plan) -> bool:
    return all(cid in plan.class_specs for cid in ("Normative Element", "Informative Element", "Clause"))

standard_semantics = enrich_standard_semantics(...) if supports_standard_semantics(plan) else {}
```

这样同时解决三件事：(a) 与路由解耦；(b) 修掉基线 §3.6「批量沉淀 N 个文件只算一次路由」导致的「标准文件静默不跑标准补全」；(c) 把硬编码类名集中到一个谓词里，便于后续改成「按本体注释声明能力」（本文 §4.4）。

### 3.4 B-4：批量拼接时 `local_context` 跨文件取邻居（已复现）

**P1 · 证据类型：实测**

背景：批量沉淀把 N 个文件拼成一篇（`knowledge_precipitation.py:1125` 插 `## 文件: <name>`），后端适配器构造 chunk 时**从不设置** `previous_chunk_id`/`next_chunk_id`（`knowledge_extract_adapter.py:246-251` 只设 `section_id`/`section_title`/`clause_number`），所以 `_previous_id`/`_next_id`（`chunk_context.py:119-131`）**恒走位置相邻回退**。

复现（A/B 两文件各 2 片，`section_id` 全为 None——真实文档缺 section 元数据时的常态）：

```
B 文件首片 B-c1 的 local_context(previous=1): [('A-c2', 'A'), ('B-c1', 'B')]
```

**原因**：`local_context(..., same_section=True)` 的过滤是 `chunk.section_id == anchor.section_id`（`chunk_context.py:161-163`）。当两侧都是 `None` 时 `None == None` → True，**过滤退化为空操作**；而 `document_id` 在 `local_context`/`_previous_id`/`_next_id` 里**从未被比较过**（已核对 `co_methods` 使用的名字里没有 `document_id`）。

**后果**：每个文件的首片会把**上一个文件的尾片**文本塞进 relation / property pass 的 `local context`（实体 pass 的该段被 placeholder 覆盖，所以只影响后两个 pass）→ 跨界证据/属性污染（承基线 §3.6 第三条，本次给出可复现最小例）。

**建议**（按性价比排序）：

1. `ChunkContextManager` 增加**文档边界硬约束**：`_previous_id`/`_next_id` 在同 `document_id` 内查找，跨 `document_id` 返回 `None`；`document_id` 为空时退化为 `chunk_id` 前缀（批量路径的 `## 文件:` 段）。
2. `local_context` 的 `same_section` 语义修正：`section_id` 为 `None` 时应视为「未知」而**不是**「相等」——退化为「仅按位置」而不是「按位置且假装同节」。
3. 上游（沉淀/适配器）补齐 `previous_chunk_id`/`next_chunk_id`，让回退路径不再承重。

### 3.5 B-5：`find_span` 只归一空白，不归一全角/半角（已复现）

**P1 · 证据类型：实测**

`find_span`（`chunk_context.py:183-194`）把 quote 的连续空白折成单空格，再拼 `\s+` 正则 + `IGNORECASE` 搜索。**除此之外没有任何归一化**。实测：

```
chunk 文本: '5.1 范围\n本标准规定了５．１的要求。'      ← 全角
find_span('本标准规定了５．１的要求')  -> (7, 19)      ✅
find_span('本标准规定了5.1的要求')     -> None         ❌ ← 模型通常输出半角
```

中文 PDF/OCR 文档里全角数字与全角句点是**常态**，而 LLM 复述时通常输出半角。定位失败的代价不是「少一条 trace」，而是：

- 触发 `evidence_verification` 这个**非承重却被登记为 terminal** 的 pass（§3.2 H3）→ 可能把整篇判 failed；
- 在基线 §3.4 的成本结构里，`find_span` 失败正是「额外发起核验调用」的触发条件（模型越改写越贵）。

**建议**：`find_span` 增加 `unicodedata.normalize("NFKC", ...)` 双向归一 + 可选的全/半角等价类匹配；归一化必须**保留原始偏移映射**（在归一化串上定位后映射回原文区间），否则会破坏 `span_id`/`start_char`/`end_char` 的可回溯性——这是与后端 `source_block_ids → chunk 投影`（`knowledge_extract_adapter.py:334-345`）的直接契约，改错会静默错位。

顺带一条**未被修但成本可忽略**的项：实测 `find_span` 单次 0.006–0.007 ms（含未命中全篇扫描），**不是热点**。也就是说 §3.12 M6（`locate_quote` 无 `has_chunk` 守卫 → KeyError 崩整轮）是一个纯粹的**健壮性**问题，不是为了性能，修它的收益全在「不崩」。

### 3.6 B-6：`ChunkContextManager` 对重复 `chunk_id` 硬失败（P2，`latest` 已修）

**P2 · 证据类型：代码直读 + 实测 + 逐版本对照**

### 3.7 B-7：实体 pass 的 `local_context` / `known_entities` 是死参数（P2）

**P2 · 证据类型：代码直读**

`candidate_generation.py:985`（`manager.local_context`）与 `:993`（`relation_catalog_for_context`）在实体 pass 里**每次都算**，然后传给 `build_chat_messages`；而 `prompt_router.py:583-588` 的实体分支把两者都换成占位符：

实测这两节在最终 prompt 里分别是 **34 字符 / 62 字符**（即占位符本身）。

**建议**：`build_chat_messages` 与 `entity_pass` 的签名在实体任务下**不要接受**这两个参数，或显式标注「entity 任务忽略」。改造中如果引入通用 prompt，很容易顺手把「局部上下文」写进通用 prompt——**先决定它是死参数还是活的**，再改 prompt。

## 4. 改造方案：单通用 prompt

### 4.1 三层解耦总原则

「不用路由 prompt」= 断掉下面三条依赖，**不是**删掉 `resolve_document_route` 这个函数：

| 层 | 现状 | 改造后 |
| --- | --- | --- |
| ① prompt 扩展 | `route.prompt_extension` 拼进 system | **删除**领域扩展；把其中可通用化的规则并入 base prompt（本文 §4.2） |
| ② user prompt 的 route 段 | `## resolved route kind=…; reasons=…` | **删除**该节（或将 `route` 降级为不出现在 prompt 里的诊断字段） |
| ③ 确定性门 | `route.kind == "standard"` | 换成**本体能力谓词**（plan 派生，本文 §3.3） |

④ 观测字段（`profile.document_route`）保留，但语义从「路由结论」改为「路由是否启用 + 为何不启用」，见本文 §4.5。

### 4.2 层①：移植 `latest` 的 `GENERIC_*` 规则（本仓库已有的正解）

**关键事实：这个改造在 `latest`/`v3` 里已经做过一次。** `latest` 的 base prompt 从 v4 升到 v5，新增了两块**领域无关**的规则，正是把领域扩展里可通用化的部分抽出来：

```python
# latest/prompt_router.py:30-45
GENERIC_STRUCTURE_RULES = """[通用归类与粒度规则]
- 使用最具体的类型；不要用父类/抽象类型重复表达同一实体。
- 同一现实对象只保留一个实体：全称、简称、别名、编号不拆成多个；同一对象的不同表达应复用同一实体。
- 结构实体只按实际标题层级创建；一个标题只用一个最合适的结构类型；段落、列表、条目类内容优先抽为结构单元，不要拆成零散活动。
- 行为/工作事项以“一个动宾事项”为粒度：同一动宾短语连同其状语、否定词、结果短语聚合为一个；原文中并列出现的多个动宾事项必须分别抽取，不得只取其一或强行合并。
- 字段缺失保持缺失，不要用模板标题、编号或其他字段填充；不要把普通名词都抽成业务对象，只有作为管理/治理/建设/约束/交换/引用对象出现的才抽取。
"""

GENERIC_SEMANTIC_RULES = """[通用语义归类规则]
- 属性类实体是事实：…；约束类实体是规则：…
- 规则句归约束，事实句归属性；同一特性可分别以事实和规则出现，不要合并或改名。
- 义务/禁止性表述（应/不应/不得/严禁/禁止/未经……不得）优先归约束类实体…
- 同一范围内同一特性或同一规则的多个数值先合并为一条，再用属性记录最大值/最小值/范围/单位…
- 实体/属性名只写名词短语本身，不要带“要求/条件/方法/步骤/单位/计算/试验/计量”等结构词尾。
"""
```

**逐条映射（本次人工核对，`v3_1` 的两个扩展 → `latest` 的通用规则）**：

| `v3_1` 领域扩展规则 | 通用化后对应 | 是否已覆盖 |
| --- | --- | --- |
| 机构角色用最具体类型，不要建父类 Organization | 结构规则 1「使用最具体的类型」 | ✅ |
| 一个标准/一份公文只保留一个主实体 | 结构规则 2「同一现实对象只保留一个实体」 | ✅ |
| 同一对象的简称/别名复用，不要另建 Subject of Standardization | 结构规则 2 | ✅ |
| Clause/Subclause/Section/Annex 只按标题层级创建 | 结构规则 3 | ✅ |
| 正文条目优先抽 DocumentUnit，不要拆成零散活动 | 结构规则 3「段落、列表、条目类内容优先抽为结构单元，不要拆成零散活动」 | ✅ |
| OperationalActivity「一个动宾事项」粒度（含 3 个子条目示例） | 结构规则 4 | ✅ |
| 义务/禁止表述优先归约束，不拆活动 | 语义规则 3 | ✅ |
| 多个约束数值合并为一条 Constrain | 语义规则 4 | ✅ |
| 不要把风险描述里的普通名词都抽成 OperationalObject | 结构规则 5 | ✅ |
| 名称不带「要求/条件/方法/步骤/单位」等词尾 | 语义规则 5 | ✅ |
| 表单字段名/字段值不建实体；已阅/签名人名不建 Agent | base `[实体提取规则]`「字段标签…不是独立实体」+ 结构规则 5 | ⚠️ 部分 |
| **具体类型映射提示**：发布机构→`Publishing Organization`、提出机构→`Proposing Organization`、归口部门→`CompetentDepartment`、起草单位→`Drafting Organization`；附件→`OperationalInformation`；发布/报送→`OperationalExchange`；风险→`OperationalConstraint`… | **无通用对应** | ❌ **不可通用化** |

**结论**：18 条领域规则里，**约 15 条有通用对应**；剩下约 3 条的本质是「**中文业务词 → 本体类 id**」的映射表。这类知识**不应该写在 prompt 里**（§3.11 M7 已经证明「换本体即静默失效」，且这 1,606 字符里含 945 个中文字符）。

而 prompt 体积上：两个扩展合计 2,340 字符 / 18 条，`GENERIC_*` 合计 657 字符 / 10 条 —— **通用化是 3.5× 的压缩**，且压缩掉的部分恰好是最脆弱的硬编码。

> **第一优先级动作**：把 `latest/prompt_router.py:30-45` 的 `GENERIC_STRUCTURE_RULES` + `GENERIC_SEMANTIC_RULES` 原样移植进 `v3_1` 的 `BASE_SYSTEM_PROMPT`（v4→v5），并同步 `PROMPT_VERSIONS`（照抄 `latest/prompt_router.py:134-138` 与 `latest/split_extractor.py:835`）。这一步**与去路由解耦**：它先独立提升通用分支的质量，是后续 A/B 的对照组基础。
>
> 注意：`latest` 是「GENERIC 规则 **加上** 领域扩展」，不是「GENERIC 规则 **替代** 领域扩展」。所以移植 `GENERIC_*` 不等于完成改造，只是把通用分支补齐到与 `latest` 同一起跑线。

### 4.3 层②：删掉 user prompt 里的 route 段

`prompt_router.py:637-674` 的 user 模板里，`## resolved route` 是硬编码的一节。改造：

```diff
- ## resolved route
- kind={route.kind}; source={route.source}; reasons={', '.join(route.reasons)}
-
```
并同步：
- `route.reasons` 里那些 `route.ontology.standard.class` 之类的字符串**不得再进入任何 prompt**（它们逐字是本体类名，等于隐式标签）；
- `route` 仍可作为**诊断字段**返回（`profile`），但 `build_chat_messages` 的签名不再接受它，从源头保证 prompt 里不可能带出路由信息。这一步同时把本文 §3.1 的 4 类耦合压到 3 类，也让「改造是否彻底」变成一个可静态检查的命题（`build_chat_messages` 无 route 参数）。

### 4.5 层④：观测字段改造（`router_enabled` 而非 `document_route`）

### 4.6 类型空间统一 + 枚举入 schema（本次改造真正的精度补偿）

本文 §4.2/§4.3 是「减法」，减完必然掉精度（掉多少见本文 §5.1）。**补偿只能来自本体**，两条具体动作：

**(1) 类型空间唯一（对应 A-3）**
- 删除 `relevant_types` 收窄，schema enum 统一取 `plan.allowed_types` 中的具体类；
- 删除 `SchemaPartition` 机制（`ontology_compiler.py:125-135/172/207/714/798`）；
- 保留 `plan.output_schemas` 模板 + 每请求 `deepcopy`（实测 0.016 ms，不是问题）。

**(2) 枚举物化（对应 A-4）**

编译期新增物化步骤（`PropertySpec` 增字段）：

```python
@dataclass(frozen=True)
class PropertySpec:
    ...
    allowed_values: tuple[str, ...] | None = None   # 从注释/enum 类型解析而来
```

三条渲染路径同时接通：

| 路径 | 现状 | 改造 |
| --- | --- | --- |
| prompt 目录 | 注释只在记录表 chunk 下发（`prompt_router.py:600`） | 属性目录**恒定**下发 `allowed_values`（只渲染取值，不渲染整段注释，避免 5,526 vs 3,818 字符的膨胀）；实体 pass 是否需要看到属性目录需 A/B 决定 |
| 属性 pass schema | `_property_schema` 只看 `data_type` | `allowed_values` 存在时输出 `{"type":"string","enum":[...]}` |
| 编译告警 | `_enum_description_qa` 的 `INVALID_ENUM_DESCRIPTION` 只说「建议显式声明」 | 解析成功即消除告警（把「建议」变成「已物化」） |

这一条同时解决 §3.11 中-9 的枚举越域、§3.8 H2 的一部分、以及「换本体即静默失效」——因为取值域从此由本体携带，通用 prompt 不需要知道它是哪个领域。

**(3) 类型映射提示的归位（对应本文 §4.2 的 ❌ 行）**

把「中文业务词 → 本体类」的映射从 prompt 搬进本体注释，并让 prompt 无差别渲染。三种可选载体（按成本从低到高）：

- **类注释（最小改动）**：在 `.puml` 里给类写「适用场景/选择规则」；`_type_catalog_text` 目前**完全不渲染类注释**（`ontology_compiler.ClassSpec` 有 display_name/stereotypes，没有类级 comment 渲染路径），需要新增渲染。实测 `_catalog_text(include_comments=True)` 比不加注释多 1,708 字符（3,818→5,526，+45%）——类注释会再叠加，需纳入 prompt 预算（基线 §3.4「无统一长度预算」应同步补一条断言）。
- **别名/stereotype**：`OntologyClass.symbols` 已有解析（`ontology_schema.py` `_symbols`），可把业务词做成 alias 参与匹配与渲染。
- **枚举值**：见 (2)。

> 这一节的本质：**把「领域 prompt」的知识搬进「本体 + schema」**。这是本评审从开源社区调研中得到的最一致结论（本文 §4.8）：主流开源抽取框架全都是「单 prompt + schema 注入」，没有一个是「按领域切 prompt」的。

### 4.7 开关、灰度与回滚

1. **参数穿透三层**（本文 §3.8）：`extract_split(use_router=...)` → `extract_harness(use_router=...)` → `extract_aggregate(use_router=...)`，并把 `extract_aggregate` 的 `**_` 收紧。
2. **默认值**：建议 `use_router=True` 起步（与 `latest` 一致，`latest/split_extractor.py:695`），用一个环境变量（如 `KG_EXTRACT_ROUTER=0`）在生产灰度关闭，而不是改代码默认值——这样回滚是改 `.env` + `docker compose restart backend agent`，不需要重新发版。
   - **注意**：`.env` 开关这一层本身有前科——基线 §3.6 实测 `KG_EXTRACT_MAX_REPAIR_ROUNDS` 等三个变量对 V3.1 完全无效。所以新增开关**必须在 `config.py` 里显式读取并加一条「已生效」自检**（例如启动日志打印 `router_enabled`），否则会重演「改了没效果」的静默陷阱。
3. **回滚点**：`use_router=True` 时必须与今天的行为**逐字节一致**（包括保留 `## resolved route` 一节）——否则 A/B 的两臂差异不止一处，实验又不可解释。建议实现上让 `build_chat_messages` 接受一个 `route_hint: str = ""`，路由开启时传旧文本、关闭时传 `""`，这样两臂只有这一处差异。

**二、对「单 prompt 覆盖多域」最关键的五条工程经验**

1. **类型清单是变量，不是 prompt 正文**。GraphRAG 的 `entity_types` 是运行时配置，换领域 = 改配置（必要时换 prompt 文件），不改代码里的领域分支。→ 对应本项目：`plan.allowed_types` 已经是这个变量，**不该再在 prompt 里硬编码类型名**（§3.11 M7）。
2. **类型约束要「prompt + 代码」双保险**。fast-graphrag 在 `_extract_from_chunk` 里对实体做 `_clean_entity_types` 白名单后置过滤，类型不在列表就丢弃【源码】。→ 对应本项目：`CandidatePool.allowed_types` + `CandidateSelector` 已经是这个位置，但**类型漂移目前不产生任何 `empty_reason`/告警**（§3.2 M3），应补上；且能下沉到 provider enum 时优先用 enum 而不是 prompt 喊话。
3. **类型约束强度的三种做法**（都在避免模型自造类型名）：闭集枚举 + **恰好一个**逃生舱（LightRAG 的 `Other`）、**整数 ID 分类**（Graphiti 的 `entity_type_id: int`）、**解码期 JSON-Schema enum**（LangChain）。→ 本项目已有第三种（`_compile_output_schemas` 的 `enum`）；Graphiti 的整数 ID 对「enum 里 60 个长英文类名」这种场景更稳，值得作为 A-3 统一类型空间时的备选。
4. **粒度方向没有普适答案，必须由本体裁决**。GraphRAG 的**类型生成侧**明令 `Avoid general entity types such as "other" or "unknown"` + 禁止重叠类型【源码】；而 LangChain 的**抽取侧** system prompt 反过来要求只用基本类型（`always label it as 'person'. Avoid using more specific terms like 'mathematician' or 'scientist'`）【源码】。两者方向相反。→ 本项目本体的粒度已由本体作者决定（standard 60 类），**通用 prompt 的任务是「用最具体的类型」还是「用粗类型」必须由本体裁决**，不能照抄任何一家（这正是本文 §4.2 结构规则 1 的语义）。
5. **few-shot 跟着语料走，不跨域硬塞**。GraphRAG 的 `prompt-tune` 从**用户自己的输入**里选 chunk 造示例（`--selection-method`/`--min-examples-required`/`--max-tokens` 控预算）【文档】。→ 对应本项目：与其为公文/标准各写一段领域规则，不如用 `test_data/eval-v2|v3` 的 golden 离线生成/筛选 few-shot 示例，并把示例集纳入 benchmark 门禁。

**三、失败恢复：社区的三板斧，正好对着本项目已记录的三个缺陷**

| 社区做法 | 本项目对应位置 | 说明 |
| --- | --- | --- |
| gleaning 多轮补抽（GraphRAG `CONTINUE_PROMPT` + `LOOP_PROMPT` 的 `Y/N` 自问自答；LightRAG `entity_continue_extraction_user_prompt`） | `repair` 循环（§3.10 中-2 计数不可靠、§3.10 中-4 死代码） | 单 prompt 化之后，**补抽会成为召回的主要来源**，优先级应上调 |
| **补抽必须显式携带原文**（GraphRAG [issue #615](https://github.com/microsoft/graphrag/issues/615)：gleaning 未带原始输入） | §3.10 中-3（repair 上下文索引空间与 verifier 不一致）、基线 §3.4（repair 两次截断只剩 <56%） | **同一个 bug 类**。本项目比社区问题更严重：截断且无标记、索引还错位 |
| 解析失败重试（iText2KG `max_tries=5`）+ 分隔符容错解析（GraphRAG [issue #1183](https://github.com/microsoft/graphrag/issues/1183)） | §3.2 H1/H2（截断前缀被丢弃、schema 一处脏字段丢整批） | 社区把「解析容错」当第一等公民；本项目已实现 `_recover_array_prefix` 却不返回结果 |

**四、必须记录的反例与预期校准（避免把调研结论用过头）**

1. **极端文风域可能仍需要独立模板**：Youtu-GraphRAG 为小说单独建模板（`prompt_type_map`）【源码】。→ **改造建议**：不要物理删除领域扩展，而是**降级为可选覆盖层**，默认走通用 prompt。KAG 的做法就是标准答案（`init_prompt_with_fallback(prompt_name, biz_scene)`：先试 `{biz_scene}_{prompt_name}`，失败回落 `default_{prompt_name}`）【源码】——**领域 prompt 是可选覆盖，不是必需路径**。这同时满足「只用一个通用 prompt」与「保留极端域的回退手段」，也和本文 §4.7 的可回滚设计一致。
2. **通用/零样本 prompt 的绝对水平不高，要有心理预期**：InstructUIE（[arXiv:2304.08085](https://arxiv.org/abs/2304.08085)）摘要原文记录 `gpt-3.5-turbo achieved an F1 score of 18.22 on the Ontonotes dataset`；UniversalNER（[arXiv:2308.03279](https://arxiv.org/abs/2308.03279)）虽在 43 数据集/9 领域、上万类型上零监督超过 ChatGPT 平均 7–9 F1，但代价是**定向蒸馏训练**而不是纯 prompt。→ 单靠「一个通用 prompt + 本体注入」拿不到 UniversalNER 那种跨域水平；**如果去掉路由后精度不达标，正确解法是补 schema/示例/后处理，而不是退回路由**。
3. **社区没有公开的「路由 vs 单 prompt」受控消融**（调研明确结论）。→ 这恰好是本文 §5.1 那个 A/B 的价值：**同本体、同模型、同 golden 的双臂对照，产出即外部可引用的数据**，可直接支撑本项目的架构决策。引用相邻结论（如上面两条）时必须注明「不是路由消融」。
4. **未核实项（勿当事实引用）**：GraphRAG 选分隔符而非 JSON 的官方理由；Graphiti 用户侧 `entity_types` dict 的源码实现；KGGen 提示词正文；以及社区常说的「类型枚举爆炸 / 跨域 few-shot 干扰 / 长 prompt 中段失效」均无权威出处。本评审**不使用**这些未核实结论作为论据。

**五、可迁移到本项目的结论（收敛版）**

1. 「单通用 prompt + 本体注入」是社区事实标准，**本项目的改造方向不需要重新论证**；但有两点必须自己补：**类型空间唯一**（A-3）与**枚举进 schema**（A-4）——社区全都做到了，本项目现在是空白。
2. **别再加领域规则**：领域知识放 schema/本体，prompt 只留通用规则（本文 §4.2）；领域扩展降级为可选覆盖层（KAG 模式，本文 §4.8 四·1）。
3. **`entity_types` 必须唯一真源**：本项目已有真源（`plan.allowed_types`），问题是派生了三个口径（A-3）。统一到一处比调 prompt 有效得多。
4. **补抽与解析容错要优先于 prompt 调优**：单 prompt 化之后，召回瓶颈会从「领域规则」转移到「补抽（repair/gleaning）」与「解析容错（H1/H2）」——这两块的社区做法可以直接照抄，且都不需要领域知识。

### 4.9 不要做什么（反面清单）

| 反面动作 | 后果 |
| --- | --- |
| 只把 `OFFICIAL_DOCUMENT_PROMPT_EXTENSION`/`STANDARD_PROMPT_EXTENSION` 置空 | 保留 `## resolved route`（含 `kind=standard` 与本体类名 reasons）→ 领域标签仍在，领域规则没了，**最坏组合**（本文 §3.2） |
| 只删扩展，不移植 `GENERIC_*` | 通用分支丢掉「最具体类型/一对象一实体/动宾粒度/义务归约束/数值合并/命名不带词尾」等 15 条精度规则 → 精度下降无法归因到「去路由」还是「丢规则」（本文 §4.2） |
| 顺手删掉 `resolve_document_route` 函数 | 三个确定性门一起失效 → 标准链路的 Clause/Property/Constrain 与 17 类关系全丢（本文 §3.3 实测）；正确顺序是先换门、再停用路由 |
| 在 `extract_split` 加 `use_router` 就以为开关生效 | 被 `extract_aggregate(**_)` 静默吞掉，A/B 两臂实际相同 → 得出「无差异」假结论（本文 §3.8） |
| 为了「省 token」去路由 | 路由面只占实体 prompt 的 11%（本文 §3.2）；真正的收益是去掉域耦合与硬编码，不是省 token。用省 token 论证这个改造会得出错误结论 |
| 在没修基线 §3.8 H1（`rdfs_subClassOf`）之前做能力谓词 | `class_specs` 缺父子链 → 谓词判错 → 标准补全在 `rdfs_subClassOf` 本体上继续静默失效（本文 §4.4） |
| 物理删除两个领域扩展（而不是降级为可选覆盖层） | 丢掉唯一能救「极端文风域」的手段（Youtu-GraphRAG 反例，本文 §4.8 四·1）；建议照 KAG 的 `default + 可选覆盖` 形态保留 |
| 照抄 LangChain「强制粗粒度类型」的 system prompt | 与 GraphRAG 的类型生成规则相反；本项目本体是 60 类细粒度，套粗粒度提示会直接把精度打散（本文 §4.8 二·4） |
| 把「去路由」当成精度问题的解法 | 社区零样本通用 prompt 的绝对水平本就不高（InstructUIE 摘要记录 GPT-3.5 在 Ontonotes 上 F1 18.22，本文 §4.8 四·2）；精度不达标应补 schema/示例/后处理，而不是退回路由 |

## 5. 验证与门禁计划

### 5.1 必须先纠正的一个历史结论（否则会得出错误预期）

仓库里**已经做过一次「有无路由 prompt」的 A/B**（`docs/算法/知识抽取算法逻辑说明.md:605-612`）：

| 实验 | official 实体 P/R/F1 | official 关系 P/R/F1 | standard 实体 P/R/F1 | standard 关系 P/R/F1 |
| --- | --- | --- | --- | --- |
| 路由 prompt | 74.89 / 70.59 / **72.68** | 18.10 / 28.00 / **21.99** | 71.97 / 81.97 / **76.65** | 73.92 / 83.92 / **78.60** |
| 通用 prompt | 2.63 / 5.88 / **3.64** | 0.00 / 0.00 / **0.00** | 32.00 / 7.16 / **11.71** | 43.24 / 8.65 / **14.41** |

**这个结论不能直接用来判定本次改造**，三条理由（本次核对）：

1. **对照臂的 base prompt 是 v1，不是当前的 v4**。同文档 `:631-638` 记录的「通用 Prompt（基础 system prompt）」是 `KNOWLEDGE_EXTRACT_V2_BASE_SYSTEM_PROMPT v1`——只有 4 行，**连 `[实体提取规则]`/`[关系提取规则]`/`[属性提取规则]` 都没有**。而 `v3_1` 现在发的是 v4（1,109 字符、20 条规则，本次实测）。也就是说，那一轮实验里「通用」臂同时失去了**领域规则 + 全部基础抽取规则**，测出的是「弱 prompt vs 强 prompt」，**不是「去路由」的边际效应**。（此推断基于该文档同节记录的 prompt 原文——实验产物已删除，无法直接核验，故必须用当前 base 重测确认，即 §5.2 阶段 2。）
2. **`latest` 之后做了通用化**（`GENERIC_*`，本文 §4.2），正是为了消除这个混杂；在 v5 base 上重测才有意义。
3. **实验产物已不可核验**：文档引用的 `eval_results_official_standard_20260909_*` 目录在 `tmp/` 下已不存在；且 `run_trace.prompt_version` 是硬编码常量（A-6），**任何历史产物都无法证明自己用的是哪版 prompt**。

> **行动**：把「重测有无路由 prompt」列为改造的第一个交付物，且**必须在移植 `GENERIC_*` 之后**测（否则重测的还是同一个混杂）。重测前先修 A-6（真实 prompt 版本入 `profile`），否则下一轮又会陷入同样的不可解释。
>
> **附带价值**：本次调研确认，**开源社区没有公开的「路由 prompt vs 单通用 prompt」受控消融**（本文 §4.8 四·3）。所以这一组 A/B（同本体、同模型、同 golden、两臂只差路由）产出的是**可外部引用的数据**，能直接支撑 `algorithm/knowledge_extract` 的架构决策——这也是把实验做严格（本文 §4.7 第 3 条的「逐字节单变量」要求）的额外理由。

## 6. 残留未决（需要决策的问题）

1. **类型目录里的「类型映射知识」放哪里？** 类注释 / 别名 / stereotype / few-shot 示例，四条路的成本与效果差异未实测。建议先做「类注释渲染」+「few-shot 示例」两个小实验（本文 §4.6(3)、§4.8 二·3）。
2. **实体 pass 是否应该看到属性目录？** 现状是完全不给（42 字符占位符，A-5 的设计意图是避免把标量值变节点）。若要在单 prompt 下保住属性精度，可能需要给「属性名 + 取值域」但不给「值」（本文 §4.6(2)）。需要 A/B。
3. **`use_router=False` 时 `local_previous/local_next/same_section` 是否还保留？** 现状是实体 pass 死参数（B-7）。若通用 prompt 要显式声明「只用 current chunk」，这三个参数应彻底删掉；若要启用局部上下文，则必须先修 B-4。
4. **`KG_EXTRACT_ROUTER` 的语义边界**：只关 prompt，还是连确定性门一起关？`latest` 的实现是「一起关」（`official_roles`/`entity_admission`/`standard_skeleton` 全关，`latest/split_extractor.py:785-787/894-903/910`）。本评审建议 V3.1 **只关 prompt、保留确定性补全**（因为 V3.1 的确定性门已被本文 §3.3 证明是本体自守卫的），但这会让两版的同名开关语义不同——需要显式文档化，避免运维误用。
5. **本体的能力谓词是否需要「本体声明」而非「硬编码类名」？** 长期看应该让本体自己声明「支持标准结构补全」（如 stereotype 或专用注释），但这是一次本体格式变更，影响面在算法之外。建议本次只做「集中到一个谓词」，不改本体格式。
6. **两个领域扩展是「降级为可选覆盖层」还是「物理删除」？** 调研反例（Youtu-GraphRAG 为小说单独建模板，本文 §4.8 四·1）与 KAG 的 `default + 可选覆盖` 形态都指向「保留但默认不用」。建议：**保留常量、默认不拼接**，并把「是否存在覆盖层 / 实际用了哪一层」写进 `profile.prompt_versions`——这样既满足「只用一个通用 prompt」，又保留了极端域的退路，代价只是两个常量留在代码里。

### 8.6 运行时发现（与本次改动无关，但会挡住发布）

在 88 上做隔离验证时撞到两个**现网配置问题**，它们与本轮代码改动无关，但会让「按 AGENTS.md 跑门禁」直接失败，必须一并处理：

**(1) `KG_EXTRACT_LLM_DISABLE_THINKING=1` + 硅基流动模型名 → 每一次抽取 LLM 调用都 404（P0）**

判定链（`llm_client.py`，四份实现同源）：

```python
_is_deepseek_v4_flash(m) = m.casefold().startswith("deepseek-v4-flash")     # llm_client.py:68-70
skip_responses          = _is_deepseek_v4_flash(self.model) and not official_deepseek
```

- `KG_EXTRACT_LLM_DISABLE_THINKING=1` 时 `not self.disable_thinking=False` → `prefer_chat_json_schema=False`；

**同一份代码在 `KG_EXTRACT_LLM_DISABLE_THINKING=0` 下正常**（走 chat.completions + json_schema，1.5s 返回）——这也是本文 §8.3 那批 A/B 能跑通的原因（当时的容器 env 是 `0`）。

- **(a) 配置侧**：`.env` 设 `KG_EXTRACT_LLM_DISABLE_THINKING=0`，然后 `docker compose up -d backend`（**`restart` 不刷新 env**）。
- **(b) 代码侧**：把 `_is_deepseek_v4_flash` 放宽到能识别带厂商前缀的 id（如 `"deepseek-v4-flash" in model.casefold()`），`v2`/`v3`/`latest`/`v3_1` 四处同步——否则任何用网关别名（`deepseek-ai/…`、`Pro/deepseek-ai/…`）的部署都会踩同一个坑，而该守卫存在的**唯一目的**就是不进 Responses 路径。

   - `standard`：两口径基本持平 —— judge 实体 0.342→0.320、judge 关系 0.205→**0.222**；identity 实体 0.256→**0.257**、identity 关系 0.105→**0.117**（关臂关系更好）；差异在单跑噪声量级（±0.02）；
