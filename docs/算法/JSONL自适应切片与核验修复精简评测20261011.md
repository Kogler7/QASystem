# 抽取优化测试结果：哪些有用，哪些还没解决

这轮修掉了一个明确的提示词错误：4B 已经抽出的规则条件和结论，之前会被后面的核验步骤错误地删掉。表格也已经改成可以按行切分的 JSONL。但模型重复到超出输出限制的问题还在，切得更小也没有稳定提高抽取质量。目前建议保留这两项修复，实体数量自适应切片继续默认关闭，4B 暂时只用于实验。

## 最后一轮实际跑出了什么

用 v3 抽取算法，在同样的五份文档、同样的切片上，对比 DeepSeek API 和本地 Qwen3.5-4B。评分统一用 API Judge，也就是让模型比较抽取结果和标准答案，判断哪些实体和关系匹配。

| 模型 | 返回可评分结果的文档 | 完整完成抽取的文档 | 实体 F1 | 关系 F1 | 五份文档抽取耗时合计 |
|---|---:|---:|---:|---:|---:|
| DeepSeek API | 5/5 | 0/5 | 45.70% | 13.20% | 约 28 分钟 |
| Qwen3.5-4B | 4/5 | 0/5 | 28.51% | 13.27% | 约 56 分钟 |

F1 同时考虑错抽和漏抽，越高越好，不能直接读成“正确率”。4B 有一份文档到 900 秒上限仍没返回可评分结果；表里的分数把这份失败文档按没有交付结果计算，防止只统计成功样本把分数抬高。它内部已经生成了部分内容，不代表模型真的什么都没抽。

其余九份也都是部分结果，仍有步骤报错或任务没有做完。两模型并行运行，表里的时间是各自五次抽取时间相加，不是整轮等待时间，也不包括切片和评分。

**API 在这轮实体抽取和用时上更好。关系抽取两者都很差，还不能说这套流程已经可靠。** 评分模型本身也会有误判，这些数字主要用于发现问题，不能代替人工检查。

## 已经修好的问题：核验步骤误删了规则字段

原来抽取规则属性时，程序会给模型一段与当前实体有关的原文。到了核验步骤，却把完整文档位置换成占位文字，同时要求模型“只根据当前原文判断”。

4B 因此认为没有原文，拒绝了已经抽出的字段。修复后，提示词明确告诉它：当前实体附带的那段原文可以作为核验依据。

规则文档上的变化很直观：修复前有 39 个规则节点，但只有 9 个同时保留了条件和结论；修复后 39 个都保留了这两个字段。另做的同题对照也确认，旧提示下出现的 46 次“没有原文”拒绝，在新提示下没有再出现。

这项修复有用，已经部署到 88。但字段保住了，还要判断内容和规则身份是否正确。这 39 个节点中，评分模型只匹配到了 10 个标准答案，不能把“字段齐了”当成“规则全抽对了”。

## 长输出到底为什么出问题

日志里有两类问题，处理办法不同。

API 的主要问题是流程做不完。最终五份文档用了 754 次模型请求，没有一次因为输出长度上限被截断。但程序反复生成、核验、补抽，把时间或补抽次数用完了，仍留下未完成任务。因此，日志里写“输出不完整”，有时指整个抽取流程没完成，不能据此认定某次模型回答被截断。

4B 则确实会不停重复。最终五份文档里观察到 5 次严重循环。例如，一个属性请求输出了 121 条记录，实际只有 14 条不同的内容，末尾连续 107 条没有新增内容，最后碰到输出长度上限。这种重复既浪费生成时间，也挤占后续核验的时间。

这些结果说明，**减小输入不能保证解决重复问题**。缩短切片后仍会循环；只让模型处理少量目标实体的属性，也重现过循环。把任务进一步缩成“单个实体”或“单个属性”后，几次回放没有循环，但输出缺少必要的证据或格式不合要求，最后没有得到可接受的事实。这种拆法还不能直接启用。

目前只定位到了部分触发条件，尚未找到既能稳定止住循环、又能保住抽取质量的方案。核验提示词错误已经修复，生成阶段的重复还需要继续处理。

## 表格改成 JSONL 和切得更小，有没有用

原来的记录表会转成一个大 JSON，切片器为了避免切坏结构，会把整个表保留下来。现在每行转成一个 JSON 对象，模型仍能看到列名和单元格内容，切片器也能沿完整行分开。

| 文档 | 原来的 JSON | 改成 JSONL | JSONL 再按预测实体数切分 |
|---|---:|---:|---:|
| 公文 1 | 11 片 | 11 片 | 11 片 |
| 公文 2 | 3 片 | 3 片 | 4 片 |
| 规则文档 | 1 片 | 3 片 | 6 片 |
| Simple 故障诊断 | 2 片 | 2 片 | 3 片 |
| trouble 故障样本 | 1 片 | 2 片 | 3 片 |
| 合计 | 18 片 | 21 片 | 27 片 |

最长的一片从约 1.4 万字符降到约 4000 字符，再切分后约 2300 字符。检查没有发现非空白正文遗漏，JSONL 记录也没有被从行中间切断。

**JSONL 解决了大表难以切分的问题，但抽取分数没有普遍提高。** 更小的片也可能带来新问题。Simple 文档有 27 个标准实体，API 原先抽出 39 个，其中 27 个匹配；启用再切分后抽出 88 个，却只有 15 个匹配。检查发现，很多新节点来自已有术语的别名，还有些术语被换成了别的类型。

不同片段对同一术语的理解不一致，是需要继续查的方向。现有证据还不足以把所有退化都归因于切片。

Clef 这一轮预测了 21 个原始片，其中 6 个被再切分，最终得到 27 片。没有预测超过 40 个实体的样本，也没有人工逐片数实体，所以尚不能证明它能稳定把每片控制在 20 个实体以内。自适应功能继续默认关闭，测试请求显式开启即可。

## Judge 怎么选

拿同一批已经抽好的五份结果，不重新抽取，只比较评分方式：

| 评分方式 | 实际工作方式 | 评分用时 |
|---|---|---:|
| API Judge | 每次比较一批候选，共 55 次请求 | 约 28 秒 |
| Clef | 每次判断一对候选，共 5010 对 | 约 30 分钟 |

当前调度下，API 批量评分快得多。这个差距包含了批量与逐对判断的区别，不能直接归结为模型本身快慢。

两种评分的匹配结果也不一致。检查还发现，API 把多项候选放在一起时，周围候选会影响个别判断。Clef 多匹配出来的项，既可能纠正漏判，也可能引入误判；缺少独立的人工标签，暂时不能宣布谁更准。

因此，后续实验要固定评分方式；比较 Judge 时，要使用同一批抽取结果，并人工确认一部分有争议的匹配。这轮六组抽取方案都使用同一个 API Judge，Clef 对照单独做，没有混着算分。

## 接下来优先处理什么

最值得先做的是给关系核验留出时间。一个公文样本已经生成了 182 条待核验的关系，但走到核验时，900 秒预算已经耗尽，相关模型请求根本没发出去，最终没有交付关系。应尝试生成一批就及时核验，或限制前面的补抽开销。

4B 的循环需要加止损：连续输出重复内容时尽早停止，并保留已经生成且通过校验的部分。单实体、单属性拆分仍需验证证据质量，不能只看它不循环就认为修好了。

再切分导致的别名膨胀和类型变化，也需要单独做回归测试。在这些问题查清前，不建议把自适应切片设成默认开启。

## 88 的交付情况和实验限制

应用代码已提交并 push 到 develop，部署版本为 `9a749d1`。88 沿用原有 backend、agent 和环境镜像。2165 项单元测试通过，34 项跳过；真实请求也确认，默认不调用 Clef，显式开启后调用 3 次、3 片变成 4 片，决策日志正常落盘，正文范围完整。

这轮使用五份小规模文档，未通过全量生产评测要求。运行中还遇到其他部署重启，未完成样本是在保留原记录后另起批次恢复的。恢复时使用的 v3 抽取代码没有变化，但运行时间、服务负载和源码版本不同，所以目前的涨分或降分都不能当成严格的因果结论。
