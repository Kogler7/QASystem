# 文档解析行为规范

本文只规定解析器配置、引擎选择、识别开关、失败回退和解析元数据。文件上传及其他业务参数由对应接口规范定义。

## 1. 解析器配置

`parser_config` 的结构：

```json
{
  "engine": "auto",
  "force": false,
  "page_sharding": "auto",
  "page_shard_size": 0,
  "max_page_shards": 16,
  "mineru_options": {
    "language": "ch",
    "ocr_mode": "auto",
    "table_enable": true,
    "formula_enable": true
  },
  "keep_page_edges": "first_page",
  "page_edge_min_chars": 3
}
```

| JSON 路径 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `engine` | string | `auto` | 用户建议的解析引擎 |
| `force` | boolean | `false` | 是否强制使用 `engine`；为 `true` 时必须指定与文件类型兼容的引擎 |
| `page_sharding` | string | `auto` | VLM PDF 页段策略：`auto`、`on`、`off` |
| `page_shard_size` | integer | `0` | 目标页段大小；`0` 表示自动均衡，最大 `256` |
| `max_page_shards` | integer | `16` | 单请求最大页段数，范围 `1..32` |
| `mineru_options.language` | string | `ch` | 文档语言 |
| `mineru_options.ocr_mode` | string | `auto` | OCR 策略：`auto`、`on`、`off` |
| `mineru_options.table_enable` | boolean | `true` | 是否启用表格识别 |
| `mineru_options.formula_enable` | boolean | `true` | 是否启用公式识别 |
| `keep_page_edges` | string \| integer[] | `first_page` | 保留哪些页的页眉/页脚：`off`、`first_page`、`all`，或 1 基页码数组 |
| `page_edge_min_chars` | integer | `3` | 页边文本短于该长度时按水印/标志残片丢弃，最小 `1` |

`mineru_options` 会传给 MinerU 支撑的 `vlm` 和 `mineru` 两条路线；最终使用其他引擎时忽略。`mineru4` 走 MinerU 4.x 自己的 `tier` 档位（默认 `standard`，可用环境变量 `MINERU4_TIER` 覆盖）。注意 4.x 只对 **PDF/图片** 提供分档解析，DOC/DOCX/PPT/PPTX/XLS/XLSX/RTF/ODF/OFD/HTML/CSV/EPUB 运行时会**自动降到 `flash`**（元数据 `mineru4_options.tier` 与 `tier_reason` 会说明原因）；4.x 原生支持这些格式，因此不再需要先转 PDF。4.x 没有表格/公式开关与语言参数，这些入参会被忽略并记录在解析元数据 `mineru4_options.ignored_options` 中；输出格式（正文 Markdown、表格 JSON 代码块、页眉/页脚补回规则）与其它引擎完全一致。`keep_page_edges` 与 `page_edge_min_chars` 对 `docling`、`vlm`、`mineru`、`mineru4` 四条路线都生效。系统按 JSON 严格解析 `parser_config`，配置包含未定义字段、错误类型或不支持的枚举值时返回参数校验错误。

默认情况下，`engine` 只是首选或 fallback 候选。需要压测或明确指定解析路线时，在同一层设置 `"force": true`；系统会跳过自动分类和 fallback，仅使用指定引擎。`force=true` 配合 `engine=auto` 或不兼容的文件类型会返回参数错误。

页段并行是执行层的内部能力，只适用于实际规划为 VLM 的 PDF。调用方不传解析引擎或任何分片参数时，规划层仍会先解析实际执行路线；达到服务端阈值的 VLM 阶段自动展开为页段原子任务并进入 `gpu.vlm` 队列，由空闲 worker 动态领取。`page_sharding`、`page_shard_size` 和 `max_page_shards` 只用于显式调优、诊断或关闭自动行为，不是启用并发的必要条件。实际页段数仍受 worker 容量、服务端上限和资源调度策略约束。每个原子任务记录页范围、worker、GPU、尝试和时间线，容量不足时排队等待，失败时只重试失败页段，最终按 `shard_index` 合并 Markdown。

有明确页范围的 shard 可能只包含页眉、页脚、页码或空白页。MinerU 正常过滤这些非正文元素后，即使 Markdown 为空，该 shard 也按成功完成并返回 `empty=true`，不会触发重试。父任务合并时跳过空 Markdown，并在 `data.sharding.empty_shards` 和 `data.parser.sharding.empty_shards` 中记录对应 `shard_index`。只有整个文档未分片解析为空，或全部 shard 合并后仍为空，才返回 `DOCUMENT_CONTENT_EMPTY` 或页段合并失败。

## 2. 解析引擎名称

| 规范名称 | 解析方式 | 适用文件 |
|---|---|---|
| `auto` 或不传 | 由系统按本文规则选择 | 所有支持的文件 |
| `text` | 文本原文直读 | Markdown、TXT |
| `docling` | Docling 文档结构解析 | PDF、OFD、Word、PowerPoint、图片 |
| `vlm` | 视觉语言模型整页解析。**2.x 已退役**：4.x 环境下同样由 `mineru4` 适配层承接 | PDF、OFD、Word、PowerPoint、图片 |
| `mineru` | MinerU 专用模型流水线解析。**MinerU 2.x 已退役**：环境里装的是 4.x 时，该名称由 4.x 适配层承接（行为与输出格式不变） | PDF、OFD、Word、PowerPoint、图片 |
| `mineru4` | MinerU 4.x 本地推理（`tier` 档位：`flash`/`basic`/`standard`/`advanced`，本地模型，不调用远程 API） | PDF、图片、OFD、DOC/DOCX、PPT/PPTX、XLS/XLSX、CSV/TSV、HTML、EPUB、RTF |
| `pandas` | Pandas 表格读取 | XLSX、XLS、CSV |
| `beautifulsoup` | Beautiful Soup HTML 解析 | HTML、HTM |

兼容别名：

| 别名 | 规范名称 |
|---|---|
| `excel` | `pandas` |
| `bs4` | `beautifulsoup` |
| `html` | `beautifulsoup` |

## 3. 文件类型、默认引擎和用户指定行为

| 文件类型或场景 | 系统默认引擎 | 用户指定引擎如何处理 | 失败后的行为 |
|---|---|---|---|
| 文本型 `.pdf` | `docling` | 合适且不同的用户引擎作为一次性 fallback | 默认引擎失败后尝试一次用户引擎 |
| 扫描或复杂 `.pdf` | `vlm` | 合适且不同的用户引擎作为一次性 fallback | 默认引擎失败后尝试一次用户引擎 |
| `.ofd` | 转为 PDF 后按 PDF 自动分类 | 合适且不同的用户引擎作为一次性 fallback | OFD 转换失败时返回转换错误；PDF 解析失败后尝试一次用户引擎 |
| 简单 `.docx` | `docling` | 合适且不同的用户引擎作为一次性 fallback | 默认引擎失败后尝试一次用户引擎 |
| 复杂 `.docx` | 未指定时为 `vlm` | 合适的用户引擎直接作为主引擎 | 用户引擎已经被使用，不再自动切换 |
| `.doc` | `docling` | 合适且不同的用户引擎作为一次性 fallback | 默认引擎失败后尝试一次用户引擎 |
| `.pptx` | `docling` | 合适且不同的用户引擎作为一次性 fallback | 默认引擎失败后尝试一次用户引擎 |
| `.ppt` | `docling` | 合适且不同的用户引擎作为一次性 fallback | 默认引擎失败后尝试一次用户引擎 |
| `.png`、`.jpg`、`.jpeg` | `vlm` | 合适且不同的用户引擎作为一次性 fallback | 默认引擎失败后尝试一次用户引擎 |

以下格式只有一种合适的引擎，系统直接使用固定引擎并忽略用户指定的其他引擎，不进行 fallback：

| 文件类型 | 固定引擎 |
|---|---|
| `.md`、`.txt` | `text` |
| `.xlsx`、`.xls`、`.csv` | `pandas` |
| `.html`、`.htm` | `beautifulsoup` |

各类文件允许使用的引擎：

| 文件类型 | 合适的引擎 |
|---|---|
| PDF、OFD、DOCX、DOC、PPTX、PPT | `docling`、`vlm`、`mineru`、`mineru4` |
| PNG、JPG、JPEG | `vlm`、`mineru`、`mineru4`、`docling` |
| XLSX、XLS、CSV | `pandas`、`mineru4`（默认仍是 `pandas`） |
| HTML、HTM | `beautifulsoup` |
| MD、TXT | `text` |

用户指定不适合目标文件的引擎时，系统忽略该值并继续使用默认方案，不因此直接报错。例如：

```text
CSV + parser_config.engine=vlm
  → 忽略 vlm
  → 使用 pandas

HTML + parser_config.engine=docling
  → 忽略 docling
  → 使用 beautifulsoup
```

## 4. Fallback 原则

系统不在多个引擎之间无条件互相回退，只为用户指定的合适引擎兜底一次。

```text
系统默认引擎成功
  → 返回结果

系统默认引擎失败
  ├─ 用户指定了另一个适合该文件的引擎
  │    → 尝试该引擎一次
  └─ 未指定、指定值不合适或指定值与默认一致
       → 直接返回解析失败
```

复杂 DOCX 是特殊情况：合适的用户指定引擎会直接成为主引擎，因此失败后不会再自动尝试系统原本的默认引擎。

### VLM 端点未配置时的自动回退

自动选择（`force=false`）规划出的引擎为 `vlm`，而 `MINERU_VLM_SERVER_URL` / `MINERU_VL_SERVER` 均未配置、且 `MINERU_VLM_BACKEND` 为默认的 `vlm-http-client`、且本地 MinerU 4.x 可用时，系统改用 `mineru`（由 4.x 适配层承接）作为主引擎（覆盖场景：扫描或复杂 PDF、复杂 DOCX、图片与演示文稿的默认规划），并在 `engine_selection.auto_fallback_reason` 中记录原因。

- `force=true` 的强制 `vlm` 请求不受影响，仍严格按指定执行（缺少端点时失败）。
- VLM 服务端点（`server_url`）仅在 `vlm` 引擎实际启动执行计划时注入；本地 MinerU 4.x 推理不需要端点。
- 本地 4.x 是否可用按「主解释器里装了 4.x，或 `MINERU4_PYTHON`（默认 `/opt/mineru4/venv/bin/python`）存在」判定。
- MinerU 2.x 已退役，任何引擎名都不会再回退到 2.x 的 `OCRProcessor`。


## 5. PDF 自动分类

系统最多检查 PDF 前 5 页，统计文本层字符数和内容图片数：

```text
平均每页文本字符数 >= 200
并且
平均每页内容图片数 <= 1.5
  → 文本型 PDF，使用 docling

否则
  → 扫描或复杂 PDF，使用 vlm
```

内容图片数只统计显示面积占页面比例不低于 3% 的图片；水印、角标这类装饰图（例如标准文本每页右下角的 15pt 标记）不计入，否则纯文本 PDF 会被误判成扫描或复杂版面。返回元数据里的 `raw_images` 保留未过滤的原始对象数，`decorative_images_ignored` 记录被忽略的数量。

如果 PDF 特征分析失败，系统按扫描或复杂 PDF 处理，优先使用 `vlm`。

## 6. OFD 转换与解析

OFD 文件先使用镜像内置的 ofdrw 转换为临时 PDF，再完全复用 PDF 自动分类、引擎选择和一次性 fallback 规则。响应中的 `file_type` 保持为 `ofd`，`final_engine` 表示处理转换后 PDF 的最终解析引擎。

当 **OFD 转 PDF 失败**、且环境为 MinerU 4.x 时，系统改用 4.x 原生的 OFD 解析（`flash` 档）而不是直接报转换错误；此时 `engine_selection.request_role` 为 `ofd_conversion_fallback`、`converted_file_type` 为 `.ofd`。若环境仍是 2.x，保持原有转换失败错误。

```text
OFD 转 PDF 失败
  → 返回 DOCUMENT_CONVERT_FAILED

OFD 转 PDF 成功
  → 按 PDF 文本层和图片特征选择 docling 或 vlm
  → 如有兼容的用户指定引擎，按 PDF fallback 规则处理
```

该链路用于内容解析和 Markdown 生成，不读取或验证 OFD 电子签名、印章或证书的法律效力。

## 7. DOCX 自动分类

系统直接读取 DOCX 内部的 `word/document.xml`，精确统计实际表格、绘图和公式元素。满足任意条件即判为复杂 DOCX：

```text
表格数量 >= 4
或 绘图/图片数量 >= 5
或 公式数量 >= 3
```

| 分类 | 无用户指定时的默认引擎 |
|---|---|
| 简单 DOCX | `docling` |
| 复杂 DOCX | `vlm` |

如果 DOCX 特征分析失败，系统按普通文本型 DOCX 处理，优先使用 `docling`。

## 8. 识别开关

`mineru_options` 当最终实际引擎为 `vlm` 或 `mineru` 时传入解析后端。实际使用 `text`、`docling`、`pandas` 或 `beautifulsoup` 时，系统忽略整个配置对象。

### `mineru_options.ocr_mode`

| 配置值 | Pipeline 实际参数 | 行为 |
|---|---|---|
| `auto` | `method=auto` | MinerU 自动判断使用 PDF 文本层还是 OCR |
| `on` | `method=ocr` | 强制 OCR |
| `off` | `method=txt` | 使用文本层，不执行 Pipeline OCR |

`mineru_options.ocr_mode` 传入其他值会导致 `parser_config` 参数校验失败。

图片和扫描 PDF 通常需要视觉识别，不建议为它们设置 `mineru_options.ocr_mode=off`。

### `mineru_options.table_enable`

| 值 | Pipeline 行为 |
|---|---|
| `true` | 启用表格识别与结构还原 |
| `false` | 跳过 Pipeline 表格识别 |

### `mineru_options.formula_enable`

| 值 | Pipeline 行为 |
|---|---|
| `true` | 启用公式检测与识别 |
| `false` | 跳过 Pipeline 公式识别 |

### 常用组合及效果

OCR、表格识别和公式识别是相互独立的能力。开启 OCR 后，表格和公式开关仍然有效。

| `ocr_mode` | `table_enable` | `formula_enable` | 典型效果与适用场景 |
|---|---:|---:|---|
| `auto` | `true` | `true` | 自动判断文本层/OCR，同时完整识别表格和公式；通用默认方案 |
| `on` | `true` | `true` | 强制 OCR，并完整识别表格和公式；适合复杂扫描文档 |
| `on` | `true` | `false` | 强制 OCR并还原表格结构，不运行公式专用识别；适合扫描报表、清单和合同 |
| `on` | `false` | `true` | 强制 OCR并识别公式，不还原表格结构；适合扫描论文或技术资料 |
| `on` | `false` | `false` | 只关注页面文字和基础版面；资源消耗相对较低 |
| `off` | `true` | `true` | 使用 PDF 文本层，同时专项识别表格和公式；适合文本层可靠的复杂 PDF |
| `off` | `false` | `false` | 主要提取 PDF 原始文本层；适合结构简单且文本层可靠的 PDF |

关闭表格识别后，表格内文字仍可能作为普通文本被提取，但行列和单元格结构可能丢失。关闭公式识别后，公式可能被当作普通文字，出现字符缺失、乱码或顺序错误。

## 9. 页眉/页脚保留与文本层对账

`keep_page_edges` 与 `page_edge_min_chars` 对 `docling`、`vlm`、`mineru`、`mineru4` 四条路线都生效。

### `keep_page_edges`

解析引擎会把页面上下边缘的文字判成版面装饰并丢弃，标准封面的 `ICS 01.120`、`CCS A 00`、发布与实施日期正在其中：

* MinerU 用版面模型把它们判成 `abandon`（`discarded_blocks`），而 Markdown 只渲染 `para_blocks`；
* Docling 把它们放进 `FURNITURE` 内容层，`export_to_markdown()` 默认只导出 `BODY`。

`keep_page_edges` 打开后，系统按页从 PDF 文本层取回页面上下边缘带的文本行，**只补回该页 Markdown 中缺失的行**（已在正文出现的行会被跳过，避免重复），顶部行放在该页正文之前、底部行放在其后。

| 值 | 行为 |
|---|---|
| `off` | 不补回页边内容，与旧行为一致 |
| `first_page` | 只补回本次解析范围内的第一页（默认；分片解析时即该分片首页） |
| `all` | 每一页都补回 |
| `[1, 3]` | 只补回指定页（1 基、相对本次解析范围） |

`page_edge_min_chars` 默认 `3`：页边文本短于该长度时按水印、标志残片丢弃（例如封面右上角的 `GB` 标志）。取值必须是 `>= 1` 的整数。

没有文本层的扫描件取不到页边文本，此时 `mineru` 路线退回该页自己的 `discarded_blocks`，`docling` 路线保持引擎输出不变。

### 文本层对账（docling）

Docling 在拼接文本单元时会按字形间距补空格；宽字距的西文字体会被导出成 `GB / T1 . 1`、`4 . 1 概述`。Docling 路线在导出后会用同一页的 PDF 文本层做三步校正：

1. **合并被拆开的标题**：把 `## 6` + `## . 1 0 废止阶段` 这类被拆成两行的条款标题拼回去，仅当拼接结果去掉空白后确实出现在该页文本层时才合并。
2. **逐行对账**：只有某行去掉空白后与文本层某一行完全一致且唯一时，才替换为文本层的写法。
3. **收拢编号空格**：把 `4 . 5 . 1`、`2 0 2 6`、`A. 6`、`ISO / IEC` 这类导出伪影收拢为 `4.5.1`、`2026`、`A.6`、`ISO/IEC`；`Part 4`、`第 4 部分` 等正常空格不受影响。

三步都不引入文本层之外的内容，也不改动表格、图片和 Markdown 结构；扫描件无文本层时是空操作。返回元数据中的 `text_layer_reconcile` 记录页数、替换行数与合并的标题行数。

已知限制：当导出器把同一条款的多个 PDF 行合并成一个 Markdown 段落时，该段落无法与单行文本层精确对齐，其中残留的空格不会被收拢；导出器把编号与标题拆成两个独立块时，标题结构可能仍是分开的两行（文本本身不丢失）。

## 10. 表格输出为 JSON

解析结果中的**数据表**输出为 ```` ```json ```` 代码块，正文、标题、图片等其余结构仍是 Markdown——**只有数据表本身变成 JSON**。

| 文件类型 | 引擎 | 表格来源 | 输出位置 |
|---|---|---|---|
| `.xlsx`、`.xls`、`.csv` | `pandas` | 每个 sheet 的表头与数据行 | 每个 sheet 一个 `## sheet 名` 小节；行列式 sheet 出 `{"columns", "rows"}` JSON，稀疏 sheet（表单式）出键值对 JSON |
| `.pdf`、`.ofd` | `docling` | Markdown 管道表格 | 原表格位置替换为 JSON，表格标题行保留 |
| `.pdf`、`.ofd` | `mineru`、`vlm` | HTML `<table>` | 原表格位置替换为 JSON |
| `.docx`、`.doc`、`.pptx`、`.ppt`、图片 | `docling` | Markdown 管道表格 | 原表格位置替换为 JSON |
| `.md`、`.txt` | `text` | — | 原文直读，不做转换 |
| `.html`、`.htm` | `beautifulsoup` | — | 不做转换 |

JSON 结构固定为列名加记录数组：

```json
{
  "columns": ["相关方角色", "分阶段/提案登记", "分阶段/决定"],
  "rows": [
    {"相关方角色": "建议方", "分阶段/提案登记": "查看", "分阶段/决定": "查看、编辑"}
  ]
}
```

规则：

* 首行（或 Excel/CSV 的列名）作为表头；表头重名按 `值`、`值_2` 去重，空表头按 `列1`、`列2` 命名。
* 合并单元格按"分组/子列"展开成单层表头，例如 `分阶段` + `提案登记` → `分阶段/提案登记`；HTML 的 `rowspan`/`colspan` 与 Markdown 里重复的分组表头都会这样处理。
* 数据行按表头宽度补齐，短行补空字符串，长行补齐列名后仍保留数据，不丢单元格。
* 单元格内的换行折叠为空格，`\|` 还原为 `|`，保证 JSON 合法。

### 稀疏表：按形状判定，输出键值对 JSON

收文处理单、审批单、传阅签字栏这类**稀疏表**没有表头——首行就是数据，单元格又大量合并。它们不输出 `columns`/`rows`，而是输出**键值对 JSON**：

```json
{
  "doc_type": "form",
  "title": "收文处理单",
  "fields": {"收文号": "信息公司收(2026)209号", "来文单位": "中国中车集团有限公司"},
  "signatures": [{"signer": "白雪峰", "time": "2026-03-27 16:36", "status": "请刘总阅批。"}]
}
```

原因是硬套行列模型会把文档原意彻底打乱：首行会被当成表头（例如某个签名和"李明 2026-03-30 09:35"变成列名），`rowspan`/`colspan` 展开时同一个值会被复制进它覆盖的每一列（一行里重复出现四五次），"标签 → 值"的对应关系随之丢失。

判定**一张表一张表地做**，三个信号取"或"，任一命中即按稀疏表处理：

```text
合并密度（带 rowspan/colspan 的单元格占比）>= 0.6     # 仅 HTML 表；单元格数 < 8 时不采信
或 首列过半是 `标签:`（以冒号结尾的短文本）
或 首行不像表头（含完整日期/时间、句读，或本身是 `标签:`）
或 首行的值在数据行首列反复出现（首行本身是数据）
  → 稀疏表：输出键值对 JSON

否则
  → 行列式数据表：输出 {"columns", "rows"} JSON
```

合并密度只对 HTML 表可得（管道表格、Excel 没有 `rowspan`/`colspan` 信息，传 `None`）；阈值是 `table_json.py` 里的模块级常量，可按语料调整。

**只有表头、没有数据行的表一律按数据表处理**（列数不足 2 也同理）：全空的数据行会被规整步骤丢掉，剩下的一行就是表头本身。此时「首列是标签」之类的信号只是在描述表头——`项目号：/跟踪号：/成本对象：` 这类模板表头会把标签率顶到 1.0——并没有「标签 → 值」版式可还原，判成稀疏表只会得到字段全空的键值对 JSON。空表头加空数据的表不输出任何内容。

**刻意不用"填充率"**：实测真实记录表 `故障数据样例（规则抽取）.xlsx`（17 列×10 行）填充率只有 0.64，而多张表单反而在 0.69~0.94，两者完全重叠——用它会把故障记录表误判成表单。合并密度 + 标签率 + 表头可信度这三条在语料上分得开：GB/T 权限表合并密度 0.06、无标签列、表头可信；收文处理单标签率 0.75、合并密度 0.57；被切碎的传阅签字表则靠"首行其实是数据"命中。

键值对 JSON 的 `fields` 保序；同名标签重复出现时收成数组，不丢内容；`signatures` 从"人名 + 日期"片段里抽 `signer`/`time`/`status`/`raw`；都没归入的文本进 `notes`。`title` 依次取 Markdown 标题、表格首行横跨整行的短文本、文件名。

表格末尾的 `注:` 整行注释仍然拆成普通文本接在表格 JSON 之后。

> 注：按文件名判定"表单类文件（文件名含 `表单`）里的表不转 JSON、还原为阅读顺序文本"的旧行为**暂时停用**。代码保留在 `table_json.py` 的 `_render_table_block` 里（注释状态），工具函数 `is_form_source` / `render_form_text` 一并保留，取消注释即可恢复。

元数据中的 `tables_json.count` 记录行列式 JSON 表数量，`tables_json.forms` 记录键值对 JSON 表数量；`mineru_options.table_enable=false` 时 Pipeline 可能识别不到表格，自然也不会有 JSON。

## 11. 返回元数据

系统返回精简的解析元数据。元数据在具体接口响应中的位置由对应接口规范定义。

示例：

```json
{
  "preferred_engine": "docling",
  "requested_engine": "mineru",
  "request_handling": "fallback_candidate",
  "final_engine": "mineru",
  "fallback": {
    "from_engine": "docling",
    "reason": "Docling 解析失败"
  },
  "mineru_options": {
    "language": "ch",
    "ocr_mode": "on",
    "table_enable": true,
    "formula_enable": false
  }
}
```

### 引擎选择字段

| 字段 | 含义 |
|---|---|
| `preferred_engine` | 系统根据文件类型和初步分析选择的引擎 |
| `requested_engine` | 用户传入并规范化后的引擎名称 |
| `final_engine` | 最终实际使用的引擎 |
| `request_handling` | 系统如何处理用户指定的引擎；未指定引擎时不返回 |
| `fallback` | 发生 fallback 时记录原引擎和失败原因；未发生时不返回 |
| `mineru_options` | 最终引擎为 `mineru` 时返回其实际配置；`vlm` 虽接收相同开关，但当前不返回该字段 |
| `keep_page_edges` | 记录本次请求的页边保留配置与 `page_edge_min_chars` |
| `tables_json` | 表格处理结果：`count` 为转成行列式 `columns/rows` JSON 的表数量，`forms` 为转成键值对 JSON 的稀疏表数量 |
| `page_edges` | 页眉/页脚补回结果：`injected` 逐页列出补回的顶部/底部文本；占位符与页数不一致时给出 `skipped` 原因 |
| `text_layer_reconcile` | Docling 路线的文本层对账结果：`pages` 与 `replaced_lines` |
| `pdf_profile.images` | 计入版面复杂度的内容图片数（已忽略水印、角标等装饰图） |
| `pdf_profile.raw_images` | `images` 同源但未过滤的原始图片对象数 |
| `pdf_profile.decorative_images_ignored` | 被判定为装饰图而忽略的数量 |
| `encoding` | `text` 引擎识别到的文本编码；其他引擎不返回 |

### `request_handling` 取值

| 值 | 含义 |
|---|---|
| `matched_default` | 用户指定与系统偏好一致 |
| `fallback_candidate` | 用户引擎未作为主引擎，已保留为一次性 fallback |
| `selected_primary` | 用户引擎与系统偏好不同，用户引擎覆盖系统偏好并直接使用 |
| `ignored_incompatible` | 用户引擎不适合目标文件，系统忽略用户引擎并使用系统偏好 |
| `forced` | `force=true` 强制使用指定引擎 |
| `ofd_conversion_fallback` | OFD 转 PDF 失败后改用 MinerU 4.x 原生 OFD 解析 |

## 11. 配置示例

### 系统自动选择

```json
{}
```

### 指定 VLM 作为用户建议

```json
{
  "engine": "vlm"
}
```

对于 PDF，系统仍先按文本层和图片特征选择默认引擎；如果默认不是 VLM 且解析失败，才尝试一次用户指定的 VLM。

### 复杂 DOCX 直接使用 Pipeline 并关闭公式识别

```json
{
  "engine": "mineru",
  "mineru_options": {
    "language": "ch",
    "ocr_mode": "auto",
    "table_enable": true,
    "formula_enable": false
  }
}
```

只有当该 DOCX 被系统判定为复杂文档时，用户指定的 `mineru` 才直接成为主引擎；简单 DOCX 仍优先使用 Docling，并把 `mineru` 保留为一次性 fallback。
