# 知识抽取 V3.2：通用提示词联合抽取

> 状态：本文记录的 `v3_2` 实验实现已从代码库移除（历史归档）。文中配置项、环境变量与命令不再可运行，结论仅作对照记录。

## 目标和接口

V3.2 是独立的抽取实现，Python 包为 `algorithm.knowledge_extract.v3_2`，配置为 `KG_EXTRACT_ALGO_VERSION=v3.2`。默认 `latest` 保持原值。Backend、沉淀链路和 MCP 继续通过既有适配器选择版本。

输入沿用 V2：PlantUML `ontology` 和上游提供的 `Iterable[ExtractionChunk]`。V3.2 直接复用 V2 的 `ExtractionChunk` 类型，不重切片，不接受把完整文本或 dict 当作 chunk。`extract()` 的稳定输出同 V2：

```json
{
  "entities": [{"type": "Device", "name": "设备甲", "properties": {}}],
  "relations": [{"from_type": "Device", "from_name": "设备甲", "rel_type": "CONNECTS", "to_type": "Device", "to_name": "设备乙"}]
}
```

上例仅展示字段形状，实际关系的两端都必须出现在 entities 中。`extract_aggregate()` / `extract_harness()` 另外提供 V2 兼容的 `raw`、`graph`、`intermediate_model`、`attempts`、`warnings`、`verification`、`profile` 与状态信息，供后端按证据投影回每个原始切片。内部证据字段不进入 `extract()` 业务输出。

V2 的 `repairer`、`entity_adjudicator`、`max_repair_rounds` 关键字仍可传入，但在 V3.2 中作为显式无操作选项保留，不会增加修复、裁决或模型调用。`profile` 区分原始候选数、最终接受数和逐片过滤数；同身份去重不计为拒绝，以便后端正确区分“没有候选”和“候选被校验过滤”。

## 实现边界

每个非空原始 chunk 使用一份通用系统提示词及同一用户模板，**一次同时生成实体、属性和关系**。用户模板只注入本体、规范化标识目录、目标类型、当前 chunk 和输出 schema。每次运行只选定一个提示词变体。

不运行文档分类、领域路由、实体/关系分阶段抽取、属性补抽、结构实体补造、规则关系补造、LLM 修复或 JEV。共享 V2 的数据契约、本体解析、图 UID、图组装与调度等低层组件，不调用旧版抽取流水线。程序负责类型/属性规范化、identity 统一、同身份去重、证据定位、关系签名与端点校验，不增加模型没有输出的事实。

**接口兼容不代表校验行为相同**：V3.2 要求实体名称或身份能定位到原文，若使用独立身份属性，该身份也必须能定位。V2 候选阶段允许名称经过忠实归纳、只用可定位的 quote 承载证据。这项更严格的准入规则可能降低规则、事项等语义实体的召回；两份提示词使用相同校验器，评测期间保持冻结，不能把校验差异归因于提示词。

本实现不引入运行依赖，环境镜像无需重建。评测输出保存在 `tmp/`，不进入运行时源码包。

## 两个静态提示词

提示词保存在 `algorithm/knowledge_extract/v3_2/prompts.py`。通过 Python `prompt_variant` 参数或 `KG_EXTRACT_V32_PROMPT_VARIANT` 选择：

- `baseline`：先独立写下的简明通用提示词，包含本体限制、证据、identity、端点闭合、去重和 JSON 输出。
- `distilled`：默认候选，从当前 V1/V2 总结可跨领域使用的规则，强化最具体类型、并列完整性、结构作用域、表格语义归并、属性忠实归纳、条件/否定/单位和输出前自检。

二者共享输入、输出 schema 和后处理，不同时调用，便于将差异归因于提示词。保留 baseline 原文，不因观察评测结果而回改对照组。

| 来源 | 提炼内容 | 排除内容 |
| --- | --- | --- |
| `v1/extractor.py` 的 `_build_prompt` | 联合实体/关系 JSON、目标范围、identity、关系签名、数据边界 | 文档分类、专项类名/关系、人为数量限制 |
| `v2/prompt_router.py` 的基础系统规则 | 证据、本体、并列实体、属性归纳、关系方向 | 外部 ICS/CCS 编码补全 |
| V2 标准文档扩展 | 最具体类型、别名、实际结构层级、同条件范围 | 标准领域固定类型与关系名 |
| V2 表格规则 | 同对象记录归并、综合属性、条件和结果完整性 | 强制非空、固定业务模板 |
| V2 多阶段模板 | 不继承 | entity-only、span、property pass、pair/NONE、repair |

**来源限制**：当前 `v1/extractor.py` 的通用 system prompt 直接导入 `v3.prompt_router.BASE_SYSTEM_PROMPT`，不能将此次对照称为“独立历史 V1 prompt 对 V2 prompt”。本实验比较的是先写的 baseline 与基于当前 V1/V2 代码提炼的静态通用模板。

V1 的“同小节动作合并”和 V2 的“独立并列事项分别抽取”存在冲突，提炼版按独立事实决定粒度。名称、编码和数值保持原文，职责/定义等语义字段可忠实归纳；正文不支持的属性保持缺失。

## 评测方法

统一使用 `eval/run.py` 通过真实 Backend HTTP 抽取接口测试，不增加算法目录内的 benchmark 入口。模型、golden、冻结切片和抽取参数在两组间一致；实验服务与现有服务隔离。根据用户确认，两组的联合抽取均关闭 thinking，评测 judge 也关闭 thinking。运行期间工作区的评测器发生并行修改，原始两组的 judge 协议不同；最终对比必须使用下文记录的冻结评分口径，不能直接比较原始 LLM 分数。

冻结输入来自现有 `20260930-082952` 批次，原批次共 16 个 case、50 个 chunk、149,473 字，覆盖 official、rule、simple、standard。按用户要求，最终实验目录仅冻结 mini eval 的 5 个 case（12 个 chunk、30,706 字），不扩展全量。早期尝试中的其余冻结文件只作输入归档，不计入实测。只测试抽取阶段，复用解析与切片结果，不将这些阶段的质量归因于本次抽取改动。

评测采用 LLM 一对一语义匹配，同时记录 identity 指标。若 judge 降级或失败，必须披露，不把 identity 回退分数当正式语义分数。发布门禁使用实体 F1 ≥ 0.5、无空抽取/失败 case、单 case ≤ 1800 秒、抽取阶段 ≤ 900 秒；还需满足仓库 AGENTS.md 的基线与生产观测要求。

复现实验时应先用以下环境变量启动隔离 Backend，再运行 mini 入口；只给评测进程设置版本和提示词不会改变已运行的 Backend：

```bash
export KG_EXTRACT_ALGO_VERSION=v3.2
export KG_EXTRACT_V32_PROMPT_VARIANT=baseline  # 第二组改 distilled
export KG_EXTRACT_V32_DISABLE_THINKING=1       # 联合抽取默认关闭 thinking

.venv/bin/python eval/mini_eval.py \
  --params <临时参数文件> --stage backend --mode extract \
  --from-run <冻结切片目录> --match-mode llm \
  --fail-on-empty --min-f1 0.5 --max-case-seconds 1800 \
  --max-stage-seconds parse=300,chunk=120,extract=900 \
  --runs-retention-days 0
```

参数文件需固定实际可用的抽取和 judge 模型。本次既有服务器配置为 SiliconFlow 的 `deepseek-ai/DeepSeek-V4-Flash`，不能直接使用当前 `eval/params.yaml` 中的 `deepseek-chat` 请求覆盖。

上面展示标准 mini 入口。本次 900 秒对照通过实验目录中的 `eval_wrapper.py` 调用同一个 `eval.run.main()`，将 `MAX_ATTEMPTS` 固定为 1；直接运行标准入口仍会使用评测器默认的整例重试次数。两臂的精确命令、配置及源码哈希分别保存在实验目录 `mini/baseline/launch.json` 和 `mini/distilled/launch.json`。实体/关系 F1 不单独衡量属性完整性。

### 已定位的质量问题

- 公文正文不完整：`official_01` 的正文位于 `chunk-0003`，baseline 在该片超时，distilled 在该片返回不完整。两组保留的实体主要来自表单、签阅记录，实体数量增加不能证明正文召回提升。
- 规则身份过严：`rule/故障记录test` 两组均为空，分别记录 4、13 条 `UNGROUNDED_ENTITY_IDENTITY`。原文中存在 golden 的 6 个规则对象；V3.2 的严格身份定位与归纳型名称存在冲突。产物未保存原始候选值，不能将每条问题逐一对应到 golden。
- 简单样例关系仍缺失：提炼版恢复了 `Solution` 实体，但 golden 的 `Problem --需要方案--> Solution` 仍未进入输出。模型输出的其他关系不能替代这条目标关系；仅放宽实体别名匹配不能解决这一漏抽。
- 标准文档正文损失：baseline 的 24 实体、distilled 的 28 实体和 12 关系均来自 chunk-0002，前两片均失败。提炼版的“电池单体”预测为 `Object`，gold 为 `Subject of Standardization`；这也会使其相关边在 identity 口径下不匹配。该例没有完整成功的提炼版语义判分，不能把类型字符串差异直接当成语义裁定。
- 别名与数据标注影响精度：提炼版简单样例同时保留部分对象的 ID 名称和自然名称；公文中部分新增人名确有原文但未被 golden 标注。应分别核查重复实体、未标注事实与无依据事实，不能把所有 FP 统称为幻觉。

`verification.rejected_issue_count` 统计校验问题条数，可能包含属性问题或整个响应不完整，不能直接视为被丢弃的实体/关系数量。

本 mini 集 golden 共 456 个实体、517 条关系，标准文档分别占 80.3% 和 77.2%。总体 micro F1 受该样例强烈影响，结论应结合逐例结果；本次没有重新运行 V2，不能宣称优于 V2，也没有独立的属性完整性评分。
