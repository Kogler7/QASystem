## 阶段装配的确定性问题

[skill_planner.py](/Users/binzhou/bjtu/qasystem/tmp/skill-review-20261013/snapshot/algorithm/knowledge_extract/v3_1/skill_planner.py:11) 的 `semantic_only=True` 只保留 all、semantics；[prompt_router.py](/Users/binzhou/bjtu/qasystem/tmp/skill-review-20261013/snapshot/algorithm/knowledge_extract/v3_1/prompt_router.py:396) 在 entity 调用时只选 entity 阶段，在实体修复时组合 entity、repair。实际装配如下。

| 技能 | entity | property | repair_entity | verification |
| --- | --- | --- | --- | --- |
| official_document@7 | all + entity | all | all + entity | all |
| rule@4 | all + entity | all + property | all + entity + repair | all |
| trouble@3 | all + entity | all + property | all + entity + repair | all |

直接后果：

- 规则 skill 的“因果方向不反转”、RuleTypeBody 的类别解释、RuleTemplate 的语义、标识字段约束，只进入 property。首轮抽属性和实体修复不受这些专用规则约束，核验也没有同一份判据。
- 检修 skill 的“预防性更换不能证明部件故障”和五类边界在 entity；核验只看到一句很短的 all。调用方本体可能补足一部分，但 skill 所承诺的稳定约束并没有完整抵达核验器。
- 公文所有长篇生成规则几乎都放在 all，因此核验器同时接收“应抽取哪些实体”等生成指令。System 能限制输出，但无关指令增加负担，也掩盖真正需要核验的语义规则。

**首选修法不是把所有规则再次复制到所有阶段。** 当前注册器已经支持 `## rules:semantics`，应利用它：all 保留本体优先和证据边界；semantics 放类型、粒度、归属、派生与禁止推断；entity/property/repair 只保留各自操作。生成和核验共享语义，输出格式仍由 System 和 output_contract 控制。三个技能都更新版本，并验证最终消息，而非只检查 Markdown 文件包含某句话。

## 公文领域

总体判断：信息丰富，但最明显地依赖现有样本，且类型边界存在自相矛盾。需要重写判定顺序，比继续追加禁止句更重要。

### 活动与交互和约束的冲突

[公文 skill 第 43 行起](/Users/binzhou/bjtu/qasystem/tmp/skill-review-20261013/snapshot/algorithm/knowledge_extract/v3_1/skills/official_document/SKILL.md:43) 把“报送排查反馈表”列为独立活动，随后又要求同一报送行为优先作为 OperationalExchange，不再输出活动。又将“高等级网络系统部署管控”列为活动，同时要求包含“未经……不得”等表述时不拆活动。这两组规则在 official_01 上直接相撞。

golden 同时保留活动“报送排查反馈表”和交互“报送排查反馈”，也同时保留部署管控活动及约束；调用方本体并未声明这些类型全局互斥。因此，一刀切抑制跨类型表示既不通用，也不能稳定复现当前标注。

建议按三个独立问题判断：文本是否提出可执行工作；是否表达传递或协同；是否规定必须遵守的条件。各视角都满足本体时可同时表达，但每个都必须有自己的语义和证据，不能通过同义改写批量制造活动。**禁令中的动作不能被改写成“已经执行”或无条件的正向任务。** 若业务希望强制互斥，应在本体或明确标注规范中声明，不能由 skill 擅自规定。

### 粒度示例已经形成样本答案提示

skill 的六个活动示例几乎对应 official_01 golden 的六个活动；另一长串示例直接复用了 official_02 的正文。它们也不构成统一语言学规则：“安全监测与事件处置”合并了两个动作，“健全机制、加强投入”等又要求分开；“向集团报告”被称为状语或结果短语，实际上可能是独立传递行为。

建议删除这些运行时样本原句，迁入回归测试。通用判据改为：有独立交付物、执行对象、责任、时间或条件的事项分别表达；同一事项的目的、方式和结果限制作为属性保留。仅有连词、逗号或动词数量，不足以决定拆分。正反例使用跨领域的抽象对象，不能携带 benchmark 名称、实体数量或目标答案。

### 结构层与业务层不应互相排斥

“正文条目优先 DocumentUnit，而不是多个活动”会使模型以结构抽取替代业务抽取。[公文本体](/Users/binzhou/bjtu/qasystem/test_data/eval/official/ontology/Official_Ontology.puml) 明确提供两种视角。official_04 的章节、子条目、分年建设要求都应各按定义判断，不能完成 DocumentUnit 后就停止任务识别。

建议结构单元按真实标题、编号及段落边界划分；父标题和子条目可各有实体，父节点不能重复吞下所有子正文。未编号段落可以归纳标题，但缺少文档位置证据时不能猜全篇“第几段”。业务事实再独立判定。无名结构单元的身份必须保留所属文档及局部锚点，避免不同公文的“第一条”被精确名称归并。

### 表单规则应排除无语义值而非排除角色

现有“部门名无明确职责就不成为实体”比本体更窄。本体的 OperationalAgent 包括公文出现的组织、部门和角色；发文、主送、抄送、承办、联系人本身也可能构成文档角色，并不总要附带完整工作句。

建议保留纯签名、“已阅”个人和空字段不造实体的规则；明确区分“字段名不是实体”和“字段值可以指向本体实体”。是否抽主体由类定义及其文档角色决定，职责缺失就留空，不为证明主体存在而编造职责。纯签收个人也不得扩张成不存在的岗位。

必须保留对批示中业务事实的抽取。official_01 的“技术中心牵头、安全中心配合”、official_02 的技术中心与规划运营部、official_03 的技术中心和工业软件事业部，都在 chunk 中；golden 没有对应主体。这是标注覆盖问题，不能通过禁止抽取表单任务来提高 precision。

### 公文属性缺少来源角色与错位判断

official_04 的表单把“收文日期：2025-07-24”放在“缓急”值中，把拟办意见放在“抄送”中；批示又碎裂在乱序 notes 中。只按表头复制会错填，靠常识复原则可能造事实。

建议增加通用规则：按字段语义、明确标签、主体及来源角色共同绑定；带“收文日期”的文本不能因落在缓急字段就成为缓急。正文日期、印发日期、收文日期不能互换；联系人电话与登记联系电话不能任意覆盖。多片段可分别引用，不伪造连续引文。乱序文本只有存在可验证的连接依据时才恢复原有顺序，否则保留有证据部分及未解决状态。

同一公文在正文和表单中出现空格、括号差异时，当前精确 type+name 合并可能留下两个管理单元。例如 official_01 的正文标题含 `开展 OpenClaw（…）`，表单标题为 `开展OpenClaw(…)`。仅写“一份公文一个实体”不足以实现约束。应在程序中依据文件关联、文号和标题证据设计可审计的归并，保留原始名字与来源；不能让 property 阶段擅自改名。

## 规则领域

总体判断：已有“不按故障分类合并”和“不反转因果”的正确方向，但规则发现判据不完整，而且关键规则放错阶段。原文是记录，不应把每个事故叙述都提升为普遍成立的定律。

### 首先判断记录支持哪一种命题

建议在 semantics 定义以下类别，实际字段值仍取调用方本体：

| 证据形态 | 可以抽取 | 不能推出 |
| --- | --- | --- |
| 明确原因导致现象 | 原因或条件 → 现象 | 现象必然证明唯一原因 |
| 编码与含义有显式对应 | 编码 → 文中给出的含义 | 外部代码字典、跨设备复用编码解释 |
| 明确操作后恢复或未恢复 | 带原场景限制的操作 → 观测结果 | 操作必然治愈、被换部件必然损坏 |
| 假设、条件、阈值和组合 | 保留 AND、OR、先后、否定、比较符的条件命题 | 把假设写成已经发生，把 OR 写成 AND |
| 只有现象或做过某操作 | 保存为符合本体的已有事实；不满足规则类时不抽规则 | 填补原因、恢复结果或因果方向 |

rule_01 的第 14、46 条有市电条件和假设；第 31 条有“继电器板故障 → STEKOP 板死机 → 轨道红光带”的因果链。应保留直接陈述的两段关系语义，不自动扩展为所有传递闭包。第 35 条一行含多个不同代码及非设备故障，不能因同处一个单元格就拼成一条规则。

### 标识与概括边界需要收紧

“只有规则唯一对应单条记录标识时才填 ID”仍不够严格：记录序号标识事故记录，不因此成为规则 ID。应要求原文明确把该编号赋给该规则，或由调用方提供标识映射；否则不填。

当前规则要求保留所有地点，容易把同一规则按事故地点重复拆分。例如 CPU850 不稳定在不同站点重复出现，golden 抽为一条规则。建议区别规则适用条件与事件背景：影响结论成立的限定必须保留；记录日期、流水号、事故地点不能自动升级为规则成立条件。缺少泛化依据时保留限定，不擅自扩大适用范围；具体记录证据仍分别保存。

运行时目前只按精确名称合并。跨窗口生成两个语义相同、措辞不同的规则名，skill 的“可以归并”并不能保证去重。应先稳定无名规则的命名要素，再考虑独立的证据感知归并；不能把分类或代码单独当唯一键。

### 属性规则存在两处过度约束

“不得多个属性输出完全相同的值”应删除。RuleName 与实体名称相同是正常情况，不同属性也可能在简单语境下具有相同表达。正确要求是每个字段分别符合定义与证据，不能根据字符串相同就判错。

“语义属性不得直接复制实体名”也应改为“不得用实体名称冒充语义证据”。原文的短命题既可以作为名称，也可能完整表达某个属性；不能为了形式差异强制改写。

RuleTypeBody 与模板允许由本体定义的映射对有证据的命题分类。不能要求原文逐字出现 `ImplicationRuleType`，也不能从本体模板生成原文没有的事实。分类、模板与原文前后件之间的关系需同时进入生成和核验语义。

## 故障检修领域

总体判断：现有 skill 很少绑定特定样例，这一点好；但过于简略，不能稳定处理 50 条记录中的多步骤、预防性动作和相互矛盾的观察。

### 以操作和观察的归属控制拆分

一条记录可包含报出故障、现场复位、数据分析、正常检查、预防性更换和再次试验。建议使用“对象、动作、观察、时点或条件、是否实施”作为内部理解维度，分别映射到本体允许字段，不额外扩张输出 schema。

- 第 1 条“重新转93阀无效，大复位后正常”：两个实施动作与各自结果不能交换。
- 第 18 条“更换后仍排风不止”与后续“多次试验良好”：属于不同阶段，不能用后者抹掉前者。
- 第 30 条“多次重启无效，松电源板时得电正常，更换后编组正常”：三个条件下的结果不得合成“重启恢复”。
- 第 36 条数据分析与显示屏状态不一致：保留各自来源和冲突，不能多数表决成一个状态。

共同操作且共同结果可保留为一项；对象、步骤、数值或条件可独立区分时分别表达。不能固定“每个动词一实体”，也不能固定“一行一套五实体”。golden 本身存在同类情况有时拆开、有时合并，需统一标注粒度后再度量。

### 正常和预防性必须有明确语义

“更换”“互换”“预防性处理”不证明被处理部件有故障；正常检查不能消除此前报出的故障。现场异常与库内未复现可以同时成立。检修对象不必已经被证实损坏，当前本体允许被检测和被维修的对象。

只有明确做过的诊断、维修和验证动作才抽成相应实体。“处理后正常”可支持结果，但未明说试验、检查或观测行为时，不自动编造“某某功能验证实验”。“下载数据”是否包含分析要看原文，不能逢下载就补诊断结论。建议、请示和未来计划不能写成已实施。

预防性是单项操作的策略，不能从整行“预防”标签传播到先前重启、松动、恢复插头等所有动作。操作类型、更换动作和维修策略是不同属性。

### 数值与结果状态需要分开

第 8 条“环温32度、出风口14度”和第 42 条“环温31°、出风口21°”只能支持观测值，不能凭常识判断制冷合格。第 12 条明确写“升弓7秒，范围内”，可以支持文中给出的判定，但不能补一个正常范围。

应保留第 23 条的负温度、正负号、单位、阈值方向，以及同一状态的不同对象。ResultStatus 的“正常、通过、未判定”需依据本体映射和原文判断；同样的“未下降”“关闭”对不同对象不自动具有同一健康意义。

“A/B节、主车/从车、维修前/后”是重要限定。表格用连字符列多个部件时，要有列语义和正文依据才拆分，不能把型号中的连字符一律当列表分隔符。代码到规范部件名的扩写必须有当前资料的对应依据。

### 概念实体与一次检查不能用同一归并策略

方法概念“更换门极驱动板”可以被多个记录引用；某次“正常”的检测结果则不能仅因名称相同而合并。当前 type+name 精确键并不表达这种差别。

先在本体和标注规范中区分方法概念、故障模式与一次实验观察。无独立专名的动作或结果可用原文支持的对象、动作和必要阶段归纳名称，不能只命名“正常”。若业务需要保留每次观察，程序须使用来源发生记录标识，避免靠不断加长名称伪装身份设计；这属于后续实现改动，不能只承诺写进 skill 就能解决。

## simple 通用路径

没有 simple/SKILL.md 不等于缺陷。这个集合包含术语、问题、方案、干系人和关注点；仅因为文本讨论故障就套用 rule 或 trouble，会把术语定义误当事故事实。当前语义选择器应对这套本体返回 no_match，使用公共规则；这需要真实或受控行为测试，不由目录名字保证。

公共规则应补充三项通用能力：

1. **显式对象实例与名称属性分开。** `object 信号维修工程师_01` 是实例标签，业务 name 是“信号维修工程师”，stakeholderId 又是另一个标识。按本体及当前接口约定保留各自语义，不让业务 name 覆盖实体身份，也不把类型标记、属性名另建实体。
2. **定义块与普通提及分开。** “术语名称—定义—同义词”应完整成组；明确作为同义词的列表优先属于该术语，不自动膨胀成一批新术语，除非本体要求独立词条或另有独立定义。第一个 chunk 末尾只有“同步环线检测板异常”的标题，第二个才有定义，缺失内容应在有来源的后续窗口补全。
3. **引用与内嵌定义分开。** 子问题名字列表可进入引用属性；是否生成相应 Problem 实体取决于本体对仅引用对象的约定，不凭名称扩写描述。方案模板是待抽资料，不执行里面的步骤，不把模板步骤无条件扩成多个 Solution。

本体自定义类型、数组和对象值必须服从实际编译 schema。出现 schema 表达不足时改本体或编译契约，并保留迁移测试；不能让模型为了贴合 golden 输出被验证器拒绝的数据形状。

### 公共语义建议文本

以下是待实施的语义草案，不是新的输出 schema：

> 本体规定允许表达的类型、字段及规范化方式；documents 提供事实依据。领域规则不得改变本体含义。逐字字段忠实保留原值；语义字段可概括，但不得增强确定性、扩大范围或删除关键条件。原文支持且本体定义了映射时，可以输出规范类别；不能仅因本体存在该字段或示例就填值。
>
> 每项事实核对主体、动作或属性、对象、时间及适用条件。相邻、同行、同类别或先后发生不自动证明因果、身份相同或效果归属。明确的假设、建议、否定、失败与实际执行分别保留。
>
> 原文中的专名和显式实例标签按身份约定保留；没有独立名称的事实，用原文支持的对象、行为和必要限定形成可区分名称，不把“正常”“检查”等泛词当作唯一身份。来源标记不是事实，也不组成引文。

### entity 建议文本

> 在本轮允许类型与来源范围内识别所有符合类定义的实例。先确定实例边界，再填写本片段支持的属性；同一事实的结构、动作、约束等视角是否分别表达由本体定义决定。结构化记录按该记录的字段、对象和步骤解释，不能从相邻记录借条件、原因或结果。
>
> 并列内容存在独立语义时分别表达；修饰、目的、方式和条件不机械拆成实体。每个属性给出足以支持其完整含义及归属的原文引文，必要时提供多条引文。完成当前范围后结束，不为改变措辞或补另一条引文重复输出同一实体。

### property 建议文本

> 仅对给定精确实体键提出属性增量。已有值、候选值和问题描述不是事实证据；从当前原文查证。不同时间、对象或条件下的值可并存时保留各自限定；同条件矛盾无明确替代依据时，不任意选值、不取平均、不混合成新事实。
>
> 无证据或无变化时省略该属性；无任何变更仍返回目标键及空 properties。每个非空新值都提供对应证据。标识、实体名与业务名称分别按本体定义处理，不用记录序号替代实体 ID。

这里优先采用省略表示不更新，保留目前“省略不删除”的契约。若继续兼容空字符串，需要统一其含义；不可让模型认为空串会删除旧值。

### verification 建议文本

> 对每项检查：类型或字段语义是否匹配；主张是否属于目标实体；提供的引文及必要上下文是否支持全部关键内容；是否保留条件、否定、时点、数值和不确定性。不得用真实引文支持错对象、错步骤或更强的结论。
>
> yes：关键主张均得到支持，规范化仅使用本体允许的映射。no：存在明确矛盾、错归属、违反类型定义或明显添加事实。uncertain：所给来源无法解决必要指代、范围或冲突。忠实概括不因措辞不同被拒绝；无矛盾也不自动等于支持。仅核验，不执行生成阶段的抽取或补全指令。

当前 System 与 output_contract 对 no 的表述宽窄不同，应统一；对于局部资料中单纯缺证据的项，统一使用 uncertain，不在不同阶段来回改判。只有 yes 接收的规则保持不变。

### repair 与召回审计的边界

[覆盖审计](/Users/binzhou/bjtu/qasystem/tmp/skill-review-20261013/snapshot/algorithm/knowledge_extract/v3_1/coverage.py:144) 主要检查具有部分结构元数据的 chunk 是否至少绑定了实体；一片漏掉二十条记录，只要绑定一个实体就可能不会触发结构漏抽问题。它不是事实级 recall 检查。大量 benchmark 只有 range 或表格行范围，也不等于已具备所有结构触发字段。

建议在首轮之外维护“已扫描来源范围”和“候选覆盖状态”，按未充分覆盖的记录、定义块、列表或条目发起有界补漏。标记空范围是否审查过，不能要求每行必须产生实体。属性被拒绝且没有新证据时，不应无休止地重复请求。

当前修复契约不允许重命名、删除、拆分已接受实体。规则 skill 的“按各自原文纠正误合并”不能仅靠 repair 完成。短期先在候选准入防误合并；确需身份修复时另行设计受审计的拆分或替换操作，并验证引用、来源、隔离和发布状态。

## 建议的技能重组内容

| 文件 | semantics 中应统一的内容 | 阶段段保留的内容 |
| --- | --- | --- |
| official_document/SKILL.md | 结构与业务视角；工作与交互、约束边界；主体文档角色；表单与正文来源；重复引用身份；不从附件标题编正文 | entity：发现范围；property：字段绑定与冲突；repair：按问题重查 |
| rule/SKILL.md | 规则成立门槛；因果、指示、恢复；AND/OR、否定、阈值；规则与记录身份；事件背景与适用条件；类别与模板解释 | entity：枚举独立命题；property：逐字段增量；repair：不扩大规则范围 |
| trouble/SKILL.md | 五类语义；对象与步骤归属；实施与建议；预防性范围；观察与健康判断；概念与发生记录；编码与名称对应 | entity：保留多步骤；property：各字段查证；repair：不补造过程或效果 |

三份技能的 description 保留“典型类名可改名、本体优先、排除相邻领域”。正文使用语义角色解释典型类，不根据字段名包含某个字符串就强制映射。维护者参照路径可保留，但不进入运行消息；benchmark 案例留在测试。

不要新增按文件名、站名、设备编码或预设实体数量触发的规则；不增加“目标输出 40/543 个”的提示；不降低证据门槛迁就 golden；不通过放宽评测匹配来掩盖错误。通用性来自可迁移的判定条件，以及反例验证。

## 实施顺序与效果验收

### 第一批 统一判据与口径

1. 固定源码、三份 skill、本体、chunk、golden 和评分代码哈希，记录当前选中技能及实际规则段。明确本轮是 v3.1，不自动同步 latest。
2. 为上面的 golden 争议建立裁定清单；原标注和冻结输入保留。把业务需要的多视角、规则泛化和检修观察粒度写成标注规范，独立于样本名称。
3. 将共享语义移动并改写到 semantics；删除公文样本答案示例和硬性类型互斥；删除规则“属性不得相同”，统一补全与改值语义。
4. 同步更新契约测试和 README。测试应核对输入输出行为、证据归属和实际阶段消息，不依赖某个中文句子必须出现在 System 的固定位置。

### 第二批 验证召回与精度

先做相同冻结输入的受控消融：A 为当前快照；B 仅修规则段覆盖；C 为 B 加公文语义修正；D 为 B 加规则语义修正；E 为 B 加检修语义修正；F 为选定改动加公共 System。每一步保留完整产物及失败原因，不把路由变化、模型变化、golden 修订和 prompt 变化合成一个提升数字。

benchmark 以现有全部非重复 case 评估，mini 用于快速定位，不作为新增独立样本。参数固定模型、供应商配置、输入输出预算、窗口、并发、重试和 judge；所有版本使用同一个冻结批次执行 extract。评分失败、partial 和缺失样本单列，不能只比较成功案的平均 F1。

同时建立新的迁移集，按原始文档和记录来源分组留出，不能把同一行的改写分别放进开发集和留出集。必要测试包括：

| 组别 | 正向与反向测试 |
| --- | --- |
| 公文 | 只需报送与同时需形成材料；纯签阅与明确承办；工作目的与独立交付物；正文和批示重复；两份同编号条目；空表单与错位标签 |
| 规则 | 因果与共现；恢复与仅更换；代码有定义与无定义；AND/OR/先后；否定、±号和阈值；相同类别不同规则；同一规则重复；仅事故背景地点变化 |
| 检修 | 故障报出但检测正常；预防性更换；建议未实施；前后结果相反；同动作不同对象；同值不同步骤；正常范围缺失；部件型号含连字符 |
| 通用 | 本体类型和字段改名；主题相同但本体不同；显式实例标签和业务名；术语同义词；引用未定义；跨片定义；JSON/JSONL/普通段落等价表达 |
| 核验与修复 | 真实引文支持错对象；候选增加效果；无名实体忠实概括；冲突未解；截断恢复只补剩余项；无新证据时停止 |

### 第三批 补齐指标与按门禁发布

[当前实体 judge](/Users/binzhou/bjtu/qasystem/eval/run.py:1056) 只比较双方共同填写的属性；缺属性不算冲突。因此实体 F1 高，也可能几乎没有有效属性。必须额外报告：

- 各领域及各实体类型 precision、recall、F1，尤其规则、约束、实验和结果。
- 有来源的属性 precision、可抽取属性 recall；否定、数值、单位、条件、对象归属的关键错误数。
- 按实体对齐后统计缺失属性；数组按成员统计，长语义字段按关键命题统计，不仅看整段字符串相似度。
- 原文支持的额外实体与真正误抽分开人工裁定；不能把“没标”自动当“应当不存在”。
- 重复实体、误合并、错类型、规则方向错误、未知值填充、来源跨行污染。
- 选 skill 正确率，succeeded/partial/failed 比例，覆盖率，LLM 调用数、token、API 耗时与 judge 耗时。

建议把“高质量”的研发目标明确为：独立迁移集逐领域实体 precision ≥ 0.95、recall ≥ 0.90；有来源属性 precision ≥ 0.98、可抽取属性 recall ≥ 0.90；关键因果反转、否定丢失、跨对象拼接和无依据修复效果在专门反例集中为零。**这是待通过实验验证的目标，不是当前已达到的指标，也不替代既有生产阈值。** 小样本给出分母与不确定性，单 case 不足以证明领域泛化。

若长文本补全、身份归并或覆盖审计需要代码变更，另批实现并覆盖相应契约；不把它们伪装成纯提示词优化。发布仍按 AGENTS.md：单测、正式全量 LLM 评测、同口径基线比较、观测可用；保留原有 F1 与耗时门槛，不为放行降低标准。v3.1 的实体质量改进不能宣称关系抽取通过。
