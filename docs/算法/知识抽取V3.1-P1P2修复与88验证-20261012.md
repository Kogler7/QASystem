## 问题与改动

| 优先级 | 原问题 | 当前行为 |
| --- | --- | --- |
| P1 | 属性证据定位失败时，用实体名兜底，可能把无依据属性当成有效事实 | 属性证据独立核验；不可定位、只有短实体名、语义核验未确认的新属性均移除。属性值与支持来源保留对应记录 |
| P1 | 补全缺键、重复、重命名在重试外发现 | 精确实体键集合与唯一性校验进入生成重试循环；失败保留此前已验证的候选事实，明确返回 partial/failed |
| P1 | 分组使用原始名称，但图 UID 规范化大小写、全半角和空格，Backend 投影可能覆盖不同实体 | UID 对原始 type + name 编码求稳定哈希，Backend 优先保留对象 UID |
| P2 | 跨片合并仅保留一个引文，造成覆盖误报和重复修复 | 所有出现及属性支持来源保留到原始实体、中间对象和图节点；覆盖检查读取全部来源 |
| P2 | 一个批次携带全部来源，大文本或高频实体可撑爆请求 | 单键属性状态按有界来源窗口逐次补全；完整消息、窗口及输出容量共同限流，超限/截断/单次超时拆分 |
| P2 | 未抽到候选的相邻切片不会进入补全 | 接入同文档、默认同章节的候选为空邻片，覆盖代词、续文和表格说明 |
| P2 | 本体词面匹配会硬删除未命中类型 | 所有允许类型都参与抽取；大本体按预算分组调度 |

候选阶段现在同时返回 `type + mention + properties + evidence`，每行 JSONL。属性已核验、无冲突且无待处理邻片时跳过补全；无属性类型也跳过。程序只复制已验证且无冲突的值，跨片语义综合仍由 LLM 完成。核验及冲突补全仍可能增加调用，不能保证所有业务文档调用数都降低。

JSONL 逐行解析、原文完整名称、普通文本调用和空关系接口均保留。每请求按 V2 规则确认领域并加载一次 skill，User 中仅给出已确认领域的 `domain_policy.extraction_rules`。

88 真实规则样例进一步发现：候选阶段必须保留属性注释，并在输出 schema 显式列出属性标识。否则模型会把显示名 `RuleID` 当成实际字段 `规则ID`，连续触发重试。已补充 schema、提示与回归；跨类型同名属性仍按各行的实际 type 校验。

## 长文本边界

- 默认请求窗口 2000 字符、重叠 100 字符；原始 chunk ID 和证据偏移不变。
- 完整消息默认不超过 48000 UTF-8 字节，并结合客户端输入容量，预留重试反馈空间；本体、skill 和累计属性状态也计入预算。
- 单个超大切片也使用固定 worker 池；待执行窗口最多 `2 * max_workers`，避免整篇复制进任务队列。
- 冲突补全只重读支持引文和前后各 200 字上下文，相同文本及属性值去重；旧候选和候选为空邻片仍读取完整有界窗口。
- 累计状态本身超预算时明确失败，保留已验证事实；文档总 deadline 耗尽后不再调用模型或递归拆分。
- 算法 `run_trace` 默认只保存前 32 次完整消息，其他调用保留状态/耗时/token 计量；应用独立追踪文件的保留策略不在本次修改范围。

这些限制约束单次请求及工作队列，并不把整篇抽取变成恒定内存，也不能保证固定总耗时。实体、证据和总调用量仍随文档规模增长。
