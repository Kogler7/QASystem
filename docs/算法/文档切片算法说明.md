# 文档切片算法说明

本文说明当前代码实际实现的 Markdown 切片行为。接口字段和请求响应格式见[算法接口协议](../接口/算法接口协议.md)。

## 1. 处理流程

文档先由解析器转换为 Markdown，再执行切片：

```text
原始文件 → Markdown → JSON 块识别保护 → 规则切片 / 语义切片 → 定位原文字符范围 → text + range
```

所有策略在执行切分前都会先做 JSON 块识别保护：JSON 对象与含对象的数组（连同 ```` ```json ```` 围栏）作为独立片段不被切坏，标量数组（如 `[1]` 文献角标）不保护。超长 JSON 的处理按策略路径区分：`recursive` / `custom_recursive` 优先按顶层结构切分为合法 JSON，结构切不动再按宽度硬切；`symbols` 中超大 JSON 块独占一片；`markdown` / `semantic` 中 JSON 块整块保留。详见 2.1 节。

切片长度使用 Python `len(text)` 计算，是 Unicode 字符数量，不是 UTF-8 字节数或模型 token 数。`size_unit` 当前为接口预留字段，所有策略均按字符计数，`"token"` 模式尚未实现（见第 8 节）。

### 1.1 可选实体数量再切分

公共切片服务在完成上述切片、定位原文范围后，可再调用决策模型判断每个原始片的预计实体数量；随后才进入图谱抽取。此功能不绑定抽取算法版本，默认关闭。聚合流水线始终执行配置的切片策略，已删除按文档总字数跳过切片的 `chunk_threshold` 参数与分支。

启用时在请求中设置：

```json
"chunking": {
  "strategy": "recursive",
  "size": 4000,
  "chunk_overlap": 50,
  "adaptive_entity_count": true,
  "entity_count_model": "clef-flash"
}
```

`entity_count_model` 支持 `clef-flash`（默认）和 `nanojev`，复用现有模型服务地址、密钥、超时与服务端推理队列，不需要新增 Backend 连接配置，也不允许请求传入 URL 或密钥。使用固定英文三分类问法，不截断输入；未知模型参数被拒绝。Kev尚无常驻客户端，暂不支持请求选用。

预计0–20个实体保持原片，21–40个二分，41个以上三分。只判断原始片一次，不递归判断子片；普通文本按字符范围等分核心区，再扩展边界实现配置的 overlap。短片会降低分片数或有效 overlap，以保证每片推进。保留全局半开源范围 `[start,end)` 与原有 metadata。此计数是模型预测，不是已抽出的实体数量。

JSON、围栏和合法管道表保护块保持原片；服务不可用、超时、超长或响应无效时也保留原片。每次决策追加到 `backend/tmp/chunk_entity_decisions.jsonl`，可用现有可选 `CHUNK_ENTITY_LOG_PATH` 改路径；记录预测桶、计划与实际片数、源范围、子片大小、实际 overlap 和保护/回退原因，不记录原文或密钥。日志无法落盘时明确失败。

这是实验功能。当前Clef英文问法在21段历史抽取代理样本中一致19段、各3次零桶漂移；高桶准确率及端到端抽取收益尚未证明。测试源码未部署88 Backend；完整实验口径与限制见 [Jev自适应切片实验](Jev自适应切片实验.md)。

## 2. 策略总览

| `strategy` | 底层实现 | 自定义 `separators` | 长度控制 | 语义感知 |
| --- | --- | :---: | --- | :---: |
| `recursive` | 项目实现的递归切分 `split_recursively()`（内置分隔符） | 否 | 分隔符递归收敛 + 字符硬切兜底 | 否 |
| `symbols` | 项目实现的多符号拆分与顺序装箱 `split_by_characters()` | 是 | 超长片段按字符硬切 | 否 |
| `custom_recursive` | 同上 `split_recursively()`，传入自定义分隔符 | 是 | 同 `recursive` | 否 |
| `markdown` | 项目实现的标题预拆分 + 递归收敛 `split_by_markdown()` | 否 | section 超长递归收敛 + 字符硬切 | 结构级别 |
| `semantic` | 项目实现的嵌入向量语义切分 `split_semantically()` | 否 | 优先级：语义边界 > 字符硬切 | 是 |

五种策略均为项目自实现（不依赖 LangChain 文本切分器），切分前统一做 JSON 块识别保护（见 2.1）。

### 2.1 JSON 块保护（识别规则所有策略通用）

切分前统一执行 JSON 块识别（`_split_text_with_json_protection` / `_extract_json_blocks`）：用括号匹配 + `json.loads` 双重验证识别完整的顶层 JSON 块，并向前/向后检查相邻字符（避免把 `x{"a":1}`、`{"a":1}bc` 误判为独立块）：

- 只保护 JSON 对象和"含对象的数组"：`[1]`、`["参考文献"]` 这类标量数组视为正文片段，不保护。
- JSON 块连同紧贴的 ```` ```json ```` / ```` ``` ```` 围栏作为一个独立片段，不与文本互相切拼。
- 超过 `size` 的 JSON 块按策略路径区别处理：
  - `recursive` / `custom_recursive`：优先由 `_split_json_by_structure` 按顶层键值对（对象，`_split_json_object`）或顶层元素（数组，`_split_json_array`）结构切分，切出的每块用 `json.loads` 校验合法性并剔除空壳（`{}`、`[]`）；顶层是单个超大对象/数组、结构切不动或切完仍超长时，由 `_hard_split_json` 按固定宽度硬切（允许破坏结构）。
  - `symbols`：超大 JSON 块独占一片，不参与打包。
  - `markdown` / `semantic`：JSON 块整块保留，不做结构切分。
- 打包合并时 JSON 与文本类型隔离；碎片绝不并入 JSON 块，避免污染 JSON/围栏结构。
- `chunk_overlap` 只在相邻文本块之间施加，JSON 块不参与重叠。

## 3. recursive

默认策略，使用以下分隔符优先级递归切分：

```python
[
    "\n\n", "\n",
    "。", "！", "？",
    ". ", "! ", "? ",
    "；", ";",
    "，", ",",
    " ",
]
```

算法先尝试保留段落；段落超过 `size` 时继续按换行、句末标点和空格切分。所有分隔符都切不动（例如一个超长单词）时，按固定宽度硬切兜底，成品不超过 `size`；空字符串分隔符会被忽略。它适合普通中文或中英文混合正文。

此策略固定使用内置分隔符，请求中的 `separators` 不生效。

## 4. symbols

`symbols` 是项目自行实现的多符号切分算法。未配置 `separators` 时使用：

```python
["。", "！", "？", ".", "!", "?", "\n\n", "\n"]
```

执行步骤：

1. 按配置的每一种符号依次拆分文本，并尽量保留分隔符。
2. 按原文顺序遍历拆出的片段。
3. 相邻片段合并后不超过 `size` 时，装入同一个切片。
4. 单个片段本身超过 `size` 时，直接按字符硬切。

它适合句末标点比较稳定、希望明确控制切分符号的文本。该策略不会计算句子含义或向量相似度。

## 5. custom_recursive

该策略与 `recursive` 使用同一个递归切分器，但分隔符及其优先级由调用方提供。例如：

```json
{
  "strategy": "custom_recursive",
  "size": 500,
  "separators": ["\n## ", "\n\n", "。", ""]
}
```

以上配置表示依次尝试二级标题、段落、中文句号，最后按字符切分。分隔符数组的顺序表示从高层结构到低层结构的回退顺序。

注意事项：

- `separators` 为 `null` 或空数组时，会退回 `recursive` 的内置分隔符；数组中的空字符串会被忽略。
- 指定的分隔符在文本中都切不动时，按固定宽度硬切兜底，成品仍不超过 `size`，不依赖 `""` 作为最后防线。

## 6. markdown

该策略基于项目自实现的 Markdown 结构切分，依次执行：

1. （与其它策略一致）先识别 JSON 块并保护。
2. 按 Markdown 一至六级标题行预拆分 section（正则 `^(#{1,6}\s)`；文档开头仅含标题的 section 会并入下一个 section）。
3. 不超过 `size` 的 section 整体成片；超过的 section 按内置分隔符递归切分收敛。
4. 全部片段按原文顺序装箱合并（不产生过小碎片），最终仍超上限的按字符硬切。

它会优先在 Markdown 结构边界切分，结构块仍然超过 `size` 时继续向更细粒度拆分。

这不是完整的 Markdown AST 解析：接口不会返回标题层级等结构化 metadata，也不保证一个完整章节始终位于同一切片。请求中的 `separators` 不参与该策略。

## 7. semantic（语义切片）

`semantic` 是基于嵌入向量相似度的语义切片策略，采用 **Max-Min 算法**（Bhat et al., 2025）替代传统的 centroid 分组，解决了 centroid 漂移导致的弱语义边界问题。核心思路：**在语义边界处断开，让每个切片内保持内容连贯**。

### 7.1 执行步骤

1. **Markdown 结构预拆分**：按 `#` / `##` 等标题行将文档拆分为独立 section，每个 section 内部独立进行语义切片，避免跨章节的内容混合。无标题的文档作为一个整体处理。

2. **句子级拆分**：在每个 section 内将文本按自然语义边界拆分为原子片段。使用的分隔符及优先级：

   ```python
   [
       "\n\n",  # 段落空行（最高优先级，保留 Markdown 段落结构）
       "。", "！", "？", "；",  # 中文句末 / 分句标点
       ". ", "! ", "? ", "; ",  # 英文句末（含尾随空格，避免误切缩写）
   ]
   ```

   注意：**不使用** `\n`（单换行）和 `:` / `：`（冒号）。原因：
   - 单换行在结构化 Markdown（如术语库、表格）中不代表语义边界，使用会导致行级过度切分。
   - 冒号广泛存在于 `术语名称: xxx` 等结构化字段中，误切会拆分属性键值对。

3. **批量向量化**：将所有 section 的全部片段收集后，一次性使用 `bge-small-zh-v1.5`（SentenceTransformer）批量编码为 512 维向量，避免多次模型调用的开销。

4. **微小片段预处理**：长度 < 20 字符的片段（如 YAML frontmatter、空行、分隔线等）就近合并到相邻内容片段，避免噪声片段产生低质量 embedding。

5. **语义断点检测（breakpoint detection）**：计算相邻片段向量的余弦相似度，通过 `breakpoint_method` 配置的策略识别语义断点：
   - `"percentile"`（默认）：相似度低于第 15 百分位的相邻位置标记为硬断点。
   - `"stddev"`：相似度低于 `mean - 1.5 * std` 的位置标记为硬断点。
   - `"none"`：关闭断点检测，完全依赖 Max-Min 算法自主判断。
   
   硬断点是强制切分边界，Max-Min 分组不会跨越硬断点。

6. **Max-Min 语义分组**（核心改进）：不再使用 centroid 相似度，而是基于 pairwise 比较：

   - 分组过程中，加入新片段会使 chunk 超过 `size` 时直接切断（不执行相似度判断）。
   - **Chunk 内只有 1 个片段时**：`MaxSim` ≥ `similarity`（即 tau）且 ≥ `min_similarity` → 合并；否则 → 切断。
   - **Chunk 内 ≥ 2 个片段时**：
     - `MinSim` = chunk 内所有片段两两相似度的最小值（衡量"最弱连接"）
     - `MaxSim` = 新片段与 chunk 内任意片段的最大相似度（衡量"最强关联"）
     - 如果 `MaxSim >= MinSim` 且 `MaxSim >= min_similarity` → 合并；否则 → 切断。
   - **最小片段数保底**：上述条件不满足，但当前 chunk 内片段数 < `min_segments_per_chunk`（`split_semantically` 默认 2）且加入后不超过 `size` 时，仍强制合并。
   - 直观理解：新人加入团体，他最好的朋友必须至少和团体内最疏远的两人一样亲密。
   - 硬断点处强制切分，不受上述规则影响。
   - `min_similarity` 由 `similarity - 0.15`（下限 0.3）自动推导，防止 MinSim 过低时 chunk 语义发散。

7. **装箱与超长回退**：分组后的切片按原文顺序装箱合并（`size` 内的相邻切片合并，消除过小碎片）；仍超过 `size` 的切片按字符硬切为不超过 `size` 的片段。

8. **重叠窗口**：最终切片结果可通过 `chunk_overlap` 应用字符级滑动窗口重叠（对齐句子/段落边界，只在相邻文本块之间施加，JSON 块不参与）。

### 7.2 核心参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `similarity` | 0.6 | Max-Min 的 tau（初始阈值），控制前两个片段合并的敏感度 |
| `breakpoint_method` | `"percentile"` | 语义断点检测策略：`"percentile"` / `"stddev"` / `"none"` |

`similarity` 取值建议（与传统 centroid 方法兼容）：

| 阈值 | 行为 | 适用场景 |
| --- | --- | --- |
| **0.7 ~ 0.8** | 严格：对主题转换敏感，每个语义单元更小 | 结构化术语库、FAQ 文档，需要逐条目分离 |
| **0.5 ~ 0.6（默认 0.6）** | 适中：平衡语义连贯与切片密度 | 通用中文文档，混合主题的说明文档 |
| **0.3 ~ 0.4** | 宽松：仅在大主题跳跃处切分 | 主题连贯的长文、小说、技术手册 |

### 7.3 Max-Min vs Centroid 算法对比

旧版 centroid 算法存在 **centroid 漂移** 问题：随着 chunk 不断合并新片段，centroid 逐渐偏离初始语义，导致后续片段可能与 chunk 早期内容很相似、但与当前 centroid 已不相似，从而被错误切断。

Max-Min 通过 pairwise 比较消除 centroid 漂移：
- **不依赖聚合向量**：每次判断基于原始片段的 pairwise 相似度，而非不断变化的 centroid。
- **自适应阈值**：MinSim 随 chunk 增大而自然下降，自动变严格，无需手动调节。
- **保留最弱连接语义**：拒绝会让 chunk 内部最弱连接变得更弱的新片段。

### 7.4 性能与限制

- 本地模式需要加载 `bge-small-zh-v1.5` 模型（约 100MB 内存），按模型路径 LRU 缓存（最多 4 个实例）；remote-only 模式不加载本地模型，改走远程 embedding 服务。
- 模型加载失败或不可用时，`semantic` 自动回退为与 `recursive` 相同的规则递归切分。
- 向量编码为 CPU 计算，100 片段约需 <1s（Mac M 系列）到数秒（x86）。
- Markdown 标题预拆分使用正则匹配（`^(#{1,6}\s)`），不解析 code block 内的 `#`，极少数情况下可能误切代码块中的注释行。
- `breakpoint_method` 仅 `semantic` 策略下生效，其他策略忽略。
- 当前模型路径默认 `/models/bge-small-zh-v1.5`，请求级 `model_path` 优先，未传时使用 `VECTOR_MODEL_PATH` 环境变量覆盖。
- SentenceTransformer 不支持 `chunk_overlap` 的原生语义重叠，重叠通过字符级滑动窗口后处理实现。

### 7.5 与其他策略的对比

| 特性 | `recursive` 等 | `markdown` | `semantic` |
| --- | :---: | :---: | :---: |
| 识别语义主题边界 | 否 | 否 | 是（Max-Min + breakpoint） |
| 保留段落结构（`\n\n`） | 是（内置分隔符首项即 `\n\n`） | 是 | 是 |
| 保留 Markdown 标题结构（`#`） | 否 | 是 | 是（标题级预拆分） |
| 消除 centroid 漂移 | — | — | 是（pairwise 比较） |
| 自适应阈值 | 否 | 否 | 是（MinSim 动态调整） |
| 需要模型依赖 | 否 | 否 | 是（SentenceTransformer） |
| 适合场景 | 通用中文切片 | 结构化 Markdown | 多主题文档、内容连贯性要求高 |

## 8. 参数行为

### size

`size` 是目标字符长度。切片不会严格等长，算法会优先选择自然边界。`recursive`、`custom_recursive`、`symbols` 和 `markdown` 均具有最终字符硬切兜底（`custom_recursive` 不依赖 `""` 分隔符）；`semantic` 优先语义边界，但单句超过 `size` 时也会按字符硬切。

Markdown 标记、链接地址和标题符号等都计入长度，因为切片作用于解析后的 Markdown 原文，而不是去除格式后的纯文本。

### size_unit

`size` 的计量单位，当前为接口预留字段：

- `"char"`（默认）：Python `len(text)` 的 Unicode 字符数，所有策略均按此计数。
- `"token"`：尚未实现；接口契约中保留该枚举值，传入不会影响切片行为。

### separators

| `strategy` | 是否生效 |
| --- | :---: |
| `recursive` | 否 |
| `symbols` | 是 |
| `custom_recursive` | 是 |
| `markdown` | 否 |
| `semantic` | 否 |

### similarity

| `strategy` | 是否生效 | 说明 |
| --- | :---: | --- |
| `recursive` | 否 | — |
| `symbols` | 否 | — |
| `custom_recursive` | 否 | — |
| `markdown` | 否 | — |
| `semantic` | 是 | Max-Min 的 tau 参数，控制初始合并阈值 |

### breakpoint_method

| `strategy` | 是否生效 | 说明 |
| --- | :---: | --- |
| `recursive` | 否 | — |
| `symbols` | 否 | — |
| `custom_recursive` | 否 | — |
| `markdown` | 否 | — |
| `semantic` | 是 | 语义断点检测策略：`"percentile"`（默认）/ `"stddev"` / `"none"` |

### chunk_overlap

`chunk_overlap` 控制相邻切片之间的重叠字符数（默认 0，不重叠）：

- 必须小于 `size`。
- 所有策略均由项目实现的滑动窗口后处理施加：取前一块尾部（对齐句子/段落边界）作为当前块前缀。
- 重叠只在相邻文本块之间生效；JSON 块、类型切换处不加 overlap。
- `symbols` 策略打包时预留 overlap 预算（内部按 `size - overlap` 装箱），施加 overlap 后成品仍不超过 `size`。

设 `chunk_overlap=100, size=500` 时，相邻切片理论上共享 100 个字符（实际偏移受字符回退影响）。

## 9. range 定位规则

切片完成后，服务按顺序在输入 Markdown 中查找切片文本并返回：

```json
{
  "text": "第一段。",
  "range": [0, 4]
}
```

`range[0]` 是开始位置，`range[1]` 是结束位置且不包含该位置字符。偏移基于输入 Markdown 的 Python Unicode 字符索引，不是原始上传文件的二进制偏移。

定位优先从上一切片的结束位置继续查找；找不到时再从全文查找。递归切分器可能清理切片首尾空白，因此相邻 ranges 之间可能存在未包含的空白字符，不能假设所有 ranges 一定无缝覆盖全文。

## 10. 当前实现边界

**已实现：**
- `semantic` 策略：基于 `bge-small-zh-v1.5` embedding 的 Max-Min 语义切片（Bhat et al., 2025），消除 centroid 漂移。
- Markdown 标题预拆分：`#` / `##` 等标题行作为 section 硬边界，每个 section 内部独立语义切片。
- 语义断点检测（`breakpoint_method`）：在 consecutive similarity 谷值处识别硬断点，支持 `percentile` / `stddev` / `none`。
- `chunk_overlap`：所有策略（含 `semantic`）均支持相邻切片重叠。
- 微小片段预处理（`min_segment_len=20`）：噪声片段就近合并后再向量化。
- 超长切片字符回退：语义分组后超 `size` 的切片按字符硬切。
- JSON 块识别保护（所有策略）：JSON 对象 / 含对象数组连同 ```` ```json ```` 围栏独立成片；标量数组不保护；超长 JSON 仅在 `recursive` / `custom_recursive` 路径做结构切分（保持合法 JSON），失败按宽度硬切；JSON 与文本类型隔离打包，碎片不并入 JSON 块。

**待实现 / 边界：**
- `size_unit: "token"` 为预留字段，所有策略当前使用 `"char"` 模式（Python Unicode 字符计数）。
- Markdown 标题预拆分使用正则匹配，不解析 code block 内的 `#`，极少数情况下可能误切代码块中的注释行。
- `range` 定位依赖切片文本仍能在原始 Markdown 中被 `str.find()` 找到，无法定位时接口返回切片偏移错误。
- `semantic` 策略不支持自定义 `separators`。
