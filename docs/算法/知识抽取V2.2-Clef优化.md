# 知识抽取 v2.2 优化

更新时间：2026-10-11。改动只在 `algorithm/knowledge_extract/v2_2/`。版本仍称 v2.2，目录用下划线，和 `v3_1` / `v3.1` 一样，避免包名里出现点号。`v2`、版本路由和 Backend 适配器没有改。

目前有两项：用 Clef-flash 减少 Pass 1 之后的生成式调用；按 v3 的方式解析本体 `note`，把类定义和关系语义写进提示词。

## A. Clef 预判

v2.2 在 v2 两阶段流水线上加了一层 Clef-flash 预判。Clef 只回答封闭问题（关系标签或 `NONE`，证据是否被原文支持），不生成引文。服务不可用、超时、超长或置信度不够时，对应候选回到原来的生成式模型，不会被当成否定。

默认关闭。未设置开关时，抽取结果与 v2 相同。

## 1. 调用位置

```text
Pass 1 生成式抽实体
  └─ 证据对不上原文时：Clef noul；未判定的项仍走原证据核验
属性补全
  └─ 同样的 Clef noul，未判定的项仍走原核验
关系阶段
  └─ 按本体签名在句/行、相邻窗口和明确条款引用中召回候选
  └─ Clef choice 只看该候选的证据片段
       ├─ 高置信 NONE → 不再生成
       ├─ 高置信正例，且引文落在本次片段内 → 用该引文，不再生成
       └─ 其余候选 → 生成式小批分类（同一证据窗口为一组，受 max_concurrency 约束）
修复
  └─ 启用 Clef 时跳过 required_relation 的生成式修复（避免与 Clef 预判重复烧 token）
```

身份归一、规则补充、筛选、评分和组图仍是原来的代码。

## 2. 为什么先改这两处

关系阶段先按局部证据召回候选，再按证据窗口小批分类。单次最多 32 个候选，模型对每条返回 `supported`、`not_supported` 或 `insufficient_evidence`。正例必须给出本次片段中的逐字引文。

Clef 的 `choice` 一次前向给出选项概率，`output_tokens` 为 0。高置信负例不再送给生成模型。高置信正例只有在引文落在该候选片段内时才跳过生成；对不上仍交给生成模型写证据。

**保守增强（不降 `ACCEPT`）**：`cooccurrence_quote` 在无句号时按行切，并取两端名最近出现对；锚点候选（`preserve_on_none`）在双端共现引文不可得时，可用含局部端点的句/行落地。短名纯共现落地门禁与接受阈值不变。Clef 题面略强调「勿推测、仅共现不够」。

证据核验原来是另一次生成式调用。这里改成 `noul` 真伪题。判定阈值与关系相同：分数不低于接受阈值记 `yes`，不高于 `1 - 接受阈值` 记 `no`，中间记 `uncertain`。实体侧沿用原规则，`no` 只记告警、不删除实体。属性侧沿用原规则，`no` 拒绝这次属性更新。

## 3. 开关与配置

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `KG_EXTRACT_V22_CLEF_ENABLED` | `0` | `1` 才启用 |
| `CLEF_SERVICE_URL` | 空 | 启用时必填，例如 88 容器内 `http://host.docker.internal:8188` |
| `KG_EXTRACT_V22_CLEF_ACCEPT` | `0.9` | 接受阈值，须在 `(0.5, 1]` |
| `KG_EXTRACT_V22_CLEF_MAX_QUESTIONS` | `16` | 单次请求问题数，上限 16（与服务 `CLEF_MAX_QUESTIONS` 对齐；超长仍拆题） |
| `KG_EXTRACT_V22_CLEF_TIMEOUT` | `10` | 单次秒数 |
| `KG_EXTRACT_V22_CLEF_MAX_CALLS` | `512` | 单次抽取的 Clef 调用上限，用尽后剩余项回退生成模型 |
| `KG_EXTRACT_V22_CLEF_STATE_CHARS` | `800` | 每个问题附带的原文窗口字符数 |
| `KG_EXTRACT_V22_CLEF_MAX_INFLIGHT` | `2` | 进程内并发 Clef 请求数，上限 4（对齐服务队列）；`1` 完全串行 |
| `CLEF_SERVICE_API_KEY` / `CLEF_MODEL` / `CLEF_SERVICE_TIMEOUT_SECONDS` | 见 Clef 服务说明 | 由现有 `ClefFlashClient` 读取 |

启用了开关但没有 `CLEF_SERVICE_URL`，或客户端初始化失败时，本请求关闭 Clef，并写告警 `CLEF_DISABLED`。这不是抽取失败。

调用方也可以直接传入：

- `clef=False`：本次强制关闭
- `clef=ClefGate(client=...)` 或任意带 `systemone` 的客户端：本次强制使用该客户端

聚合结果 `profile.clef` 记录 `enabled`、`calls`、`relation_pruned_no_cooccurrence`、`relation_dropped`、`relation_grounded_without_llm`、`relation_sent_to_llm`、`verification_by_clef`、`verification_fallback_llm`、`repair_required_relation_skipped`、`unavailable`。

## 4. 如何运行 v2.2

包路径是 `algorithm.knowledge_extract.v2_2`。在仓库根目录：

```python
from algorithm.knowledge_extract.v2_2 import extract_harness
from algorithm.knowledge_extract.v2_2.chunk_context import ExtractionChunk

result = extract_harness(
    ontology=ontology,
    chunks=[ExtractionChunk(chunk_id="c0", text="张三就职于示例单位。")],
    validation_mode="permissive",
    best_effort=True,
)
print(result["profile"]["clef"])
```

这条导入会执行 `knowledge_extract/__init__.py`，从而加载 v1。本机没有 openai 时，改用 `algorithm/knowledge_extract/v2_2/bootstrap.py` 的 `install()`，它只注册 `v2_2`，不执行那个入口。线上评测/Backend：设 `KG_EXTRACT_ALGO_VERSION=v2.2`；要真正打到 Clef，另需 `KG_EXTRACT_V22_CLEF_ENABLED=1` 和 `CLEF_SERVICE_URL`（88 容器内常用 `http://qasystem_clef:8188` 或 `http://host.docker.internal:8188`）。

## 5. 接纳规则

| Clef 结果 | 关系 | 证据核验 |
| --- | --- | --- |
| 服务失败、超时、超长、预算用尽、响应不完整 | 该批 pair 交给生成模型 | 该项交给原核验 |
| 置信度低于接受阈值 | 交给生成模型 | 记 `uncertain`，沿用原核验后的接纳 |
| `NONE` 且两端名称都在窗口内，置信度达到阈值 | 不生成这条关系 | — |
| `NONE` 但窗口里看不到两端名称 | 不丢弃，交给生成模型 | — |
| 关系标签达到阈值，且同一句能定位两端名称 | 用该句作引文，不生成 | — |
| 关系标签达到阈值，但截不到短引文 | 只把这些 pair 交给生成模型写引文 | — |
| `noul` 达到阈值 / 低于 `1-阈值` | — | `yes` / `no`，之后仍走原来的实体保留、属性拒绝规则 |

没有在同一证据窗口、相邻窗口或明确条款引用里召回的实体对，不会进入 Clef，也不再单独记 `relation_pruned_no_cooccurrence`。文档锚点仍可与当前窗口里出现的另一端配对。

Clef 使用召回到的证据片段，不把整片 chunk 送进去。超长时按问题数对半拆开再请求，不靠截断原文来换一个否定结论。

Clef 调用默认最多 2 路并发（`KG_EXTRACT_V22_CLEF_MAX_INFLIGHT`），避免打满单卡推理队列（服务端 `CLEF_MAX_QUEUE_SIZE=4`）。可重试错误（429、503、超时、连接失败）再试一次。

## B. 本体 note 解析

v2 只解析类体里的属性行（`部件名称 (ComponentName) // ...`）。`note right of` 和 `note on link` 整段被丢掉，所以类定义、唯一性约束、非空约束进不了抽取提示词。v2.2 按 v3 的本体解析补上，解析发生在编译之前，不依赖 Clef 开关。

| 写法 | 落到哪里 | 提示词 |
| --- | --- | --- |
| `note right of "故障部件"` … `end note` | 该类的 `comment`。目标可以是显示名、别名或 stereotype，例如 `<<FaultComponent>>` | 实体类型目录和完整类目录，类名后追加 `//` 说明 |
| `note on link` … `end note` | 紧挨着的上一条关系的 `comment` | 关系签名后追加 `//` 说明 |
| 类体里不属于属性、也不是 `'` 注释的行 | 并进该类的 `comment` | 同上 |

`note left of`、`note top of`、`note bottom of` 仍不解析，与当前 v3 一致。

说明全文保存在 `OntologyClass.comment` / `OntologyRelation.comment`，并复制到编译计划的 `ClassSpec.comment`、`RelationSpec.comment`。写进提示词时每段最多 500 字，避免把整份约束书塞进每一次调用。500 字截断只影响提示词，编译结果里的 `comment` 仍是全文。

故障部件这类 note 因此会进入 Pass 1 的类型目录。其中「不要求从原始文本抽取」「不得填写故障状态或维修动作」是给模型看的约束文本，解析器不会据此改抽取规则或自动丢弃字段。

## 7. 性能优化（相对首版 Clef 接入）

针对 official 类文档「pair 爆炸 + 修复空转」，并在降本后补回召回：

1. **句级共现裁剪**：无共现的非锚点 pair 不再送 Clef/关系 LLM；文档锚点 pair 始终保留，且 Clef 高置信 `NONE` 不直接丢弃（回退生成式）。
2. **Clef 批更大、可少量并发**：`MAX_QUESTIONS` 默认 16；`MAX_INFLIGHT` 默认 2。
3. **同一切片关系多批并行**：证据窗口之间与同窗口内独立小批均可并行，受 `KG_EXTRACT_LLM_MAX_CONCURRENCY` / `max_workers` 与 QPM/TPM 档位约束。
4. **Clef 开启时跳过 `required_relation` 生成式修复**：告警码 `REPAIR_SKIPPED_REQUIRED_RELATION_AFTER_CLEF`。
5. **质量补丁**：公文锚点展示名用文件标题；`RELATED_TO` 正例不经 Clef 直接落地；称谓行确定性组装 `APPLIES_TO`。

## 8. 还没做的事

- 没有把 `v2.2` 注册进 `KG_EXTRACT_ALGO_VERSION`。要进生产路由，需要另改版本表和 Backend 的包名映射。
- 实体核验为 `no` 时仍然保留实体。这能少做一次生成，但不会减少后续关系 pair。审查里的 F06 仍在。
- 修复轮次没有改用 Clef 做定向补抽；仅在启用 Clef 时跳过 required_relation 生成式修复。
- 正式上线前应用同一批 staging 文档对比耗时与关系 F1（看 `profile.clef.relation_pruned_no_cooccurrence` / `relation_sent_to_llm` / `repair_required_relation_skipped`）。阈值 `0.9` 偏保守，召回下降时再调，不要先放宽到把低置信 `NONE` 直接丢掉。
