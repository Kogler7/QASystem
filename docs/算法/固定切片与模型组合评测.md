# 固定切片与模型组合评测

入口是 `eval/run.py`，小规模选集用 `eval/mini_eval.py`，批量模型组合用 `python -m eval.model_matrix`。三者调用同一评分实现。88 使用现有 `qasystem_backend`；不另建评测 Backend。数据在 `test_data/`，所有准备及评测输出放 `tmp/`，不放入运行时交付包。

## 可以独立变化的内容

| 实验变量 | 配置方式 | 复用规则 |
| --- | --- | --- |
| 输入文档和选集 | 位置路径、mini 选集，或方案 `cases` | 比较时保持 case、golden、本体相同 |
| 解析与切片 | 参数文件 `options.parser` / `options.chunking` | 先准备一次；更改切片参数须建立新的准备批次 |
| 抽取算法 | `--extract-version` 或方案 `version` | 请求级选择；无需为每组重启 Backend |
| 抽取模型 | `--extract-provider` / `--extract-model` | provider 须已注册在 Backend；更换模型必须重新抽取 |
| 抽取超时 | `--extract-request-timeout` / `--extract-document-timeout` | 对照尽量保持一致；输出 token 上限来自服务端 provider 配置 |
| judge | `--judge-model` / `--judge-base-url` / `--judge-adapter` | 可复用已有预测，仅重新评分 |

准备与执行有明确分界：`--prepare-only` 不调用抽取；执行组合时 `--mode extract --from-run` 读取冻结的 `chunks.json`，不重新解析或切片。准备阶段优先使用 case 中现成的 `document.md`；没有时才调用解析服务。解析部分失败、切片兜底或空切片会挡住组合实验。

## 分两步执行模型组合

以下方案保存到 `tmp/eval/plans/models.json`。模型名和 provider 名是示例，必须与部署配置相符。URL 使用运行脚本所在容器可访问的服务地址；`127.0.0.1` 指该容器自身。

```json
{
  "cases": ["official/official_01", "official/official_02", "rule/rule_01"],
  "extractors": [
    {"id": "qwen8b", "provider": "matrix-qwen8b", "model": "Qwen/Qwen3-8B", "version": "v3", "health_url": "http://qasystem-matrix-qwen8b:8000/health", "request_timeout": 180, "document_timeout": 900},
    {"id": "qwen35_4b", "provider": "matrix-qwen35", "model": "Qwen/Qwen3.5-4B", "version": "v3"},
    {"id": "siliconflow", "provider": "matrix-siliconflow", "model": "deepseek-ai/DeepSeek-V4-Flash", "version": "v3"},
    {"id": "deepseek", "provider": "matrix-deepseek", "model": "deepseek-flash", "version": "v3"}
  ],
  "judge": {"id": "clef", "adapter": "systemone", "model": "clef-flash", "base_url": "http://clef:8188"},
  "comparison": {
    "extractor": "siliconflow",
    "judge": {"id": "api", "adapter": "chat", "model": "deepseek-flash", "base_url": "https://api.deepseek.com/v1", "key_env": "DEEPSEEK_API_KEY"}
  }
}
```

从仓库根目录执行；Windows 可将 `python3` 替换为 `.venv/Scripts/python.exe`：

```sh
# 1. 只准备输入，一次解析/切片供全部模型使用。
python3 -m eval.model_matrix --workspace test_data/eval --plan tmp/eval/plans/models.json --output tmp/eval/matrix/prepare-01 --prepare-only

# 2. 复用准备批次，四个模型各自抽取、使用同一个 Clef 判分。
python3 -m eval.model_matrix --workspace test_data/eval --plan tmp/eval/plans/models.json --prepared tmp/eval/matrix/prepare-01/inputs --output tmp/eval/matrix/compare-01 --workers 4
```

`--output` 必须是尚不存在的 `tmp/` 下目录，重新实验另建批次；脚本不覆盖旧结果。`--workers` 控制同时运行的抽取模型组数，不等于模型服务内部请求并发；实际调用仍受 Backend 的 provider 配额和队列约束。可选 `health_url` 最多等待 900 秒，服务未就绪单独记录，不解释为模型质量差。

`cases` 省略时使用参数文件的 mini 选集；要严格复现应显式列出 case。各 extractor 的 `id` 须唯一且只含字母、数字、下划线、连字符。凭据仅从具名环境变量读取，不写进方案。

## 仅更换 judge，不重跑抽取

组合入口的 `comparison` 对选定 extractor 的已保存预测重新评分，缺失预测写入 `comparison.coverage.json` 并排除；不会为补评重新抽取。这是一个主 judge 加一组额外对照，尚非任意多个 judge 的全排列。

需要对任意一组结果增加第三个 judge 时，直接使用统一入口。以下两个目录各有不同职责：`--from-run` 指冻结输入，`--reuse-extract-from` 指原抽取批次。

```sh
python3 eval/run.py official/official_01 official/official_02 rule/rule_01 --workspace tmp/eval/matrix/prepare-01/inputs --stage backend --mode extract --from-run tmp/eval/matrix/prepare-01/inputs --reuse-extract-from tmp/eval/matrix/compare-01/siliconflow/clef/runs/<时间戳> --match-mode llm --judge-adapter chat --judge-model deepseek-flash --judge-base-url https://api.deepseek.com/v1 --judge-key-env DEEPSEEK_API_KEY --require-scored --case-attempts 1 --runs-retention-days 0
```

**单独使用 `run.py --reuse-extract-from` 时，缺少旧预测的 case 会重新抽取**；因此“只补评”必须只选择存在 `backend_extract.json` 的 case。组合入口已自动做这一筛选。损坏产物明确报错；严格评分还验证原预测的 manifest、切片和本体来源。不能用旧预测冒充另一个抽取模型的输出。

## 切片策略实验与实体负载实验的边界

比较切片策略时，复制参数文件、更改 `options.chunking`，对同一选集分别 `--prepare-only`，随后保持抽取模型和 judge 一致执行。这会得到两套不同切片，不能称为“固定切片的模型对照”。改变切片会改变输入 manifest，不能直接通过要求同输入的 `--baseline` 作为同一切片基线比较，应另行报告质量、覆盖及耗时。

主评测器目前没有“每次限制 15–20 个实体”的自动分片选项，也不靠截掉第 21 条结果实现该目标。重复研究的隔离复放入口 `eval/tools/repetition_study.py` 使用冻结请求进行原样与语义拆分对照，不能代替线上流水线评测。实体负载拆分是否降低重复风险、是否损失跨片关系，须由专项结果验证。

## 结果、判分限制和失败处理

准备目录 `inputs/prepared.json` 保存 case、切片数量、切片文件 SHA256 与准备阶段结果；本体复制到各 case 下。执行目录保存 `plan.resolved.json`、`params.json`、`results.json`；各 `<extractor>/<judge>/` 保存 `command.json`、`run.log`、`result.json` 和 `runs/<时间戳>/` 中的 manifest、summary、预测、耗时、逐条匹配明细。输入目录应保持不变，正式评分以每组 manifest 的哈希与可比性核验为准。

Clef/NanoJev 使用 SystemOne 逐候选对 yes/no 判定，候选边汇总后统一一对一匹配。SystemOne 每窗两侧最多各 4 项，即最多 16 个问题；明确的请求体或输入长度超限继续二分窗口，保持原条目、属性与端点上下文。单对仍超限、认证失败、无效选择和其他服务错误使评分失败，不当成正常无匹配；失败窗口保留诊断。Chat judge 使用参数文件的窗口配置，默认 golden 40 × predicted 20。`judge_coverage` 统计成功叶窗口的完整候选覆盖，超限后拆分尝试另在 `judge_batches.split_retry` 标记。

judge 失败时可能保存 `identity_fallback` 诊断，但这种分数不能作为正式语义质量结论；组合命令带 `--require-scored` 和 `--fail-on-empty`，任何失败组使组合退出 2。组合退出 0 只表示其配置门禁通过，不自动代表达到正式发布 F1/耗时阈值。完整发布门禁仍按 AGENTS.md 执行。

比较时分别报告抽取与判分耗时；补评沿用已保存的原抽取耗时，不能用补评时间宣称抽取提速。不同 judge 的分数分别建立基线，不能把换裁判导致的 F1 变化解释为抽取质量提升。API token 上限、模型上下文和 provider 配额来自服务端部署，评测脚本不自动扩大它们。

## 判分方案对照与模型能力对照

当前 Chat adapter 要求模型在窗口中找出全部匹配边，SystemOne adapter 对每个候选对作 yes/no 选择。虽然最后都得到候选边，两者任务组织、窗口大小、请求数和服务调度并不相同。因此这个组合入口的跨 adapter 结果属于**实际判分方案对照**，可以比较最终指标、失败率、总耗时和资源消耗，不能直接用耗时倍率判断模型本身更快、更慢或更准确。

要比较模型能力，需另建立同题试验，固定候选对、上下文、问题、选择项和覆盖范围，让 Chat API 也完成逐对选择；窗口自适应拆分也须同步到两组。当前组合入口尚未自动生成这种同题条件，不能将默认 `chat` 与 `systemone` 的运行冒充公平的模型能力对照。judge 结论还需对照预测与 golden 的抽样审阅，分数高不代表判得更准。
