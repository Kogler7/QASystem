# 知识抽取 V2.2-v31 抽取逻辑

更新时间：2026-10-14。包路径 `algorithm.knowledge_extract.v2_2_v31`，运行时 `KG_EXTRACT_ALGO_VERSION=v2.2-v31`。本文描述**当前代码**，不是待实施方案。

现行编排是显式两段：**Stage1 实体定稿并冻结 → Stage2 关系抽取**。Stage1 使用内嵌 `v2_2_v31/entity_stage/`（从 `v3_1` 同步的实体算法副本，运行时**不 import** `v3_1`）。关系阶段仍按 [长文档关系抽取方案](知识抽取V3.1长文档关系抽取方案-20261012.md) 做局部证据召回与小批分类，并保留压多抽门禁（弱共现跳过、签发/适用角色门禁、引文端点核对）。

---

## 入口与边界

```python
from algorithm.knowledge_extract.v2_2_v31 import extract
from algorithm.knowledge_extract.v2_2_v31.chunk_context import ExtractionChunk

result = extract(
    ontology=ontology,
    chunks=[ExtractionChunk(chunk_id="chunk-0", text=chunk_text)],
)
```

- 只消费上游已解析、切分好的 `ExtractionChunk`；不接收整篇 Markdown，不改 chunk 文本、ID 或 `__source_range`。
- 关系阶段里的句子 / 表格行是 chunk 内的临时证据视图，不是重新切片。
- 公开结果仍是 `entities` 与 `relations`。关系五字段：`from_type`、`from_name`、`rel_type`、`to_type`、`to_name`。`rel_type` 用本体原始标识（如 `hasSubRule`），不是提示词里的规范名 `hassubrule`。
- `profile.entity_extract_version` 为 `v3.1-aligned`；`profile.entity_stage_package` 为 `algorithm.knowledge_extract.v2_2_v31.entity_stage`；`profile.deterministic_enrichment` 为 `enabled`。
- 诊断参数 `relation_only=True` + 非空 `seed_entities`：跳过 Stage1、确定性实体补充与结构边组装，只跑 LLM 关系阶段；`profile.relation_only=true`、`deterministic_enrichment=disabled`、`entity_source=seed`。评测入口见下文「关系-only 离线评测」。

## 主流程

```text
ontology + chunks
  → Stage1：entity_stage（v3.1 对齐副本）实体发现 / 属性核验补全 / 实体修复
  → 精确 (type, name) 入 CandidatePool（source=v31_entity，禁止别名合并）
  → 冻结 LLM 实体身份：关系阶段不改 type / name
  → 确定性补充：文档锚点 / 结构标题 / 公文单元 / 标准语义（原 v2.2）
  → pre-relation（不拒绝 v31_entity）
  → 属性补全（覆盖补充实体）
  → Stage2：关系阶段（见第 4 节）
  → 关系入池；结构边组装（HAS_PART / EVIDENCED_BY 等）；CompositeElement
  → post-relation 过滤
  → 校验；仅关系侧可修复（v31 实体身份已冻结）
  → mapping 评分，组装 graph / triples
  → 输出 entities / relations
```

领域差异：实体阶段来自内嵌 entity_stage 的 Skill 选择与公共提示词；关系阶段仍可用外层文档路由。调用方不传文档类型。

## 1. 编译本体与文档路由

`ontology_compiler` 解析类、属性、继承、关系签名、identity 和复合元素，得到 `ExtractionPlan` 与 JSON Schema。严格模式下编译错误直接失败；宽松模式把告警留在结果里。

`resolve_document_route` 根据本体类和文本决定路由，并带上对应提示词扩展。后续实体、属性和关系调用都使用同一条路由。

## 2. 实体候选（内嵌 entity_stage）

Stage1 由 `entity_stage/` 完成（与 v3.1 实体主路径对齐的副本）：Skill 选择 → 逐窗/逐片发现 → 名称准入与属性核验 → 精确 `type+name` 属性补全 → 实体侧修复。身份键是精确 `type + name`，不做别名/指代合并。

桥接层 `v31_entity_bridge.seed_frozen_entities` 将定稿实体写入 `CandidatePool`：`source=v31_entity`，同精确键只并证据与非冲突属性。`CandidateSelector.pre_relation` 不拒绝此类实体。

**入池之后实体身份和类型冻结**：关系阶段不再改名、不合并、不删实体侧事实。端点一律来自 `accepted_entities()`。

## 3. 确定性补充与结构边（原 v2.2，已恢复）

Stage1 冻结后立刻跑原 v2.2 确定性补充，再进入关系 LLM 与结构边组装：

- `enrich_document_entities`：文档锚点 / 规范性引用
- `add_structural_heading_entities`：编号标题结构实体
- `add_official_document_units`：公文 `DocumentUnit`（路由为 official_document 时）
- `enrich_standard_semantics`：标准语义实体（路由为 standard 时）
- 关系 LLM 之后：`assemble_document_relations` / `assemble_numbered_hierarchy_relations` / `assemble_document_unit_relations`（`HAS_PART`、`EVIDENCED_BY`）以及标准语义/技术边

这些边不进入关系分类器，由程序按 span / source 组装。

### 关系-only 离线评测（诊断）

隔离 Stage2 关系能力时，用 case 的 `golden.entities` 作种子，不经 Backend extract：

```bash
python3 eval/run.py test_data/eval/trouble/trouble_mini \
  --mode extract --from-run tmp/eval/runs/<冻结切片> \
  --extract-version v2.2-v31 --relation-only-from-golden \
  --match-mode llm --min-relation-f1 0.5
```

- 跳过 Stage1、确定性实体补充、结构边组装（`HAS_PART` / `EVIDENCED_BY` 等）。
- 预测实体 = 种子实体；主门禁为 `--min-relation-f1`（此模式忽略 `--min-f1`）。
- official 等 golden 若含结构边，这些边会系统性记为 FN——这是「只测 LLM 关系」的预期代价，不能当作全链路回归基线。

## 4. 关系阶段：每一步在干什么

一句话：**实体先冻结 → 查它们在原文哪儿出现 → 按本体允许的边 + 局部共现生成候选 → 小批让模型判断「这组证据是否支持」→ 引文核对后入库 → 结构边由程序组装。**

入口：`candidate_generation.relation_pass` → `relation_extraction.run_relation_stage`。没有可判断的关系签名时不调用模型，记 `RELATION_NO_SCHEMA`。

精度优化只发生在三层：**签不签名进召回**、**候选建不建**、**正例引文收不收**。

### 4.0 总览与筛选顺序

```text
accepted_entities
  → ① 建关系索引          实体出现在哪句/哪行
  → ② 取活跃关系签名      本体允许哪些边（去掉结构边、RELATED_TO）
  → ③ 召回候选            局部共现 ∩ 类型匹配 ∩ 角色门禁
        local / anchor / adjacent / cross_reference
  → ④ Clef 预判（可选）    高置信否丢掉；高置信正例仍过引文门禁
  → ⑤ 小批 LLM 分类       每批 ≤32：supported / not_supported / insufficient
  → ⑥ 引文 + 端点门禁      通过才入库
  → 按 (from, rel, to, quote) 去重后入池
```

候选能不能进模型，按这个顺序筛：

```text
ontology 签名（两端类型合法）
  ∩ 同一证据窗口共现（或锚点 / 邻接 / 条款引用）
  ∩ 角色门禁（仅 ISSUED_BY / APPLIES_TO）
  → 才进模型做「是否支持」判断
```

**没有**「全文所有实体 × 所有实体 × 所有关系」再靠 ontology 砍。缩小规模的主因是局部共现；ontology 只约束「这对类型能不能有这条边」。

日志一行：`关系阶段: 候选=… 待模型=… 预判落地=… 未定位实体=…`。

### 4.1 关系索引是什么

**不是关系列表**，而是「实体在原文里出现在哪」的查找表，供后面召回用。

`build_relation_index` 只索引已接受实体，主要装：

| 字段 | 含义 |
| --- | --- |
| `entities` | 端点：id、类型、名字、文档范围、是否文档锚点 |
| `units` | 证据单元（句 / 表格行），带 chunk 内起止位置 |
| `unit_entities` | **哪个单元里出现了哪些实体** |
| `neighbor_chunks` | 哪些切片算邻居 |
| `coverage_gaps` | 原文找不到位置的实体 |

例子：实体「设备部」在第 3 句、第 7 行各出现一次 → 索引记下这两处。后面只在这些局部窗口里找可能的另一端。

具体规则：

- 表面形式取规范名、mention、证据引文（长度 2–180），在所属文档切片里查找，落到包含它的证据单元。
- 证据单元切分顺序：能解出至少两行的 JSONL → 管道表格行 → 句子 → 整段非空文本。
- 文档范围：全无 `document_id` 时整批算一份文档；有则按文档分开；明确文档与无归属切片混在一起时，无归属各自隔离并告警 `RELATION_DOCUMENT_SCOPE_UNSUPPORTED`。
- 找不到位置且非文档锚点 → 记缺口，只写日志，不中断。
- 文档锚点（`source=document_anchor`）即使当前句没有字面，也可与该句另一端配对。
- 相邻切片由 `local_previous` / `local_next` / `same_section` 决定；两边都有且不同的 `section_id` 则不是邻居，缺失时退化为按文档内距离。

### 4.2 关系签名是什么

一条**关系签名**来自本体编译，表示「哪类实体之间允许哪条边」：

```text
源类型 -[关系ID]-> 目标类型
```

例如 `Department -[issuedBy]-> Organization`。代码里 `RelationSpec.signature` 就是这个字符串。

`active_signatures` 取出本体签名后，去掉模型不该抽的边，再按「关系标识 + 两端类型」去重：

```text
skip = 结构边黑名单 ∪ {relatedto}
```

| 类别 | 行为 | 原因 |
| --- | --- | --- |
| 结构边（全路由） | 跳过，如 `hasPart`、`evidencedBy`、`hasClause` | 确定性组装器按位置/跨度建边，模型再抽会重复 |
| 标准路由封面/定义边 | 额外跳过，如 `issuedBy`、`defines`、`cites` | 标准组装会直接建 |
| 公文 / 通用路由的封面、定义边 | **仍交给**关系分类 | 组装器不负责这些语义边 |
| `RELATED_TO`（规范名 `relatedto`） | **一律跳过** | 评测中几乎全是共现多抽 |

提示词里用规范名（如 `hassubrule`）；入库 `rel_type` 用本体原始标识。

### 4.3 如何按 ontology 筛实体对并召回

有根据 ontology 筛实体对，发生在**建候选时**，不是事后再滤。

对每个证据窗口里实际出现的实体，对每条活跃签名：

1. 源实体类型必须能赋给签名的源类型（沿父类展开）
2. 目标实体类型必须能赋给签名的目标类型
3. 自环不生成；中间隔着一行/一句又没有条款号的对不生成
4. 通过后再过角色门禁（§4.4），才生成候选

每条候选是固定的「源实体 + 关系 + 尾实体 + 证据片段」，ID 为 `c-` + 内容哈希前 12 位。

四类召回（**不是**全文两两组合）：

| `scope_kind` | 何时生成 | 证据片段 |
| --- | --- | --- |
| `local` | 同一句或同一表格行两端都出现，类型符合，且过角色门禁 | 该证据单元 |
| `anchor` | 文档锚点 ↔ 当前单元另一端；过角色门禁 | 当前单元；带 `preserve_on_none` |
| `adjacent` | 相邻单元，两端落在边界两侧 | **同片**：两单元合成一条连续片段；**跨片**：邻居切片保留两个独立片段 |
| `cross_reference` | 当前单元写了「第 N 条」类明确条款号 | 引用单元 + 最多 3 个被引用片段（已在邻接窗口的不再补） |

**不收缩**跨片邻接与条款引用——这两类服务召回。精度主要靠角色门禁和引文门禁。

### 4.4 角色门禁是什么

`_role_gate`：**不是**通用本体规则，而是只对两类易混关系做的启发式过滤。在 `_add` 建候选前调用；不过关 → 候选根本不进模型。**不删实体**，只挡这条边。

**只作用于**规范名 `issuedby` / `appliesto`；其它签名一律放行，避免误伤召回。依据是「目标实体名 + 当前证据文本」。

#### `ISSUED_BY`（谁签发 / 印发）

| 步骤 | 规则 |
| --- | --- |
| 拒绝 | 目标像联系人栏短署名 |
| 接受 | 目标名含「办公室 / 办公厅 / 秘书处」 |
| 接受 | 原文含「签发 / 印发 / 来文单位 / 发文 / 发布」，且目标不是「各…公司/企业/单位」类收文对象 |
| 否则 | 拒绝（避免文档锚点与任意组织共现就建签发边） |

#### `APPLIES_TO`（适用对象）

| 步骤 | 规则 |
| --- | --- |
| 拒绝 | 目标像联系人栏短署名 |
| 拒绝 | 目标是办公室 / 办公厅 / 秘书处（签发主体不当适用对象） |
| 接受 | 目标名含「各 / 子公司 / 所属 / 单位 / 部门 / 企业」 |
| 接受 | 原文含「主送 / 抄送 / 报送 / 适用于 / 贯彻执行 / 落实」 |
| 否则 | 拒绝 |

#### 联系人噪声 `_looks_like_contact`

- 名称本身含「联系人 / 联系电话」→ 联系人。
- 否则：证据出现「联系人 / 联系电话 / 电话：」等，且名称长 2–16、又不含办公室/各/子公司/集团有限公司等组织线索 → 短署名（如「信息公司张振威」），拒绝挂到签发/适用边上。

### 4.5 Clef 预判（可选）

Clef 默认关闭。启用时按证据片段分组做封闭选择：

- 高置信否定 → 不再送给生成模型
- 高置信正例 → **仍须**引文落在片段内，并过 §4.6 端点门禁才落地
- 其余 → 进入生成模型

正例引文：优先双端共现最短句/行（无句号按行；多处出现取最近一对）；锚点候选若双端引文不可得，保守退化为含局部端点的句/行。不降低 `KG_EXTRACT_V22_CLEF_ACCEPT`。

看的是证据片段，不是整片 chunk。服务失败 / 超时 / 置信度不够时，候选回到生成模型，不当成否定。

### 4.6 小批分类与引文端点门禁

模型任务单位从「这一大段里实体两两可能有什么关系」改成「这组原文能否证明这几条候选」。

- 按证据片段 `(chunk_id, start, end)` 分组；同组按输出预算切成多批，单次最多 32 个候选；预算紧时再缩小。**32 是单次上限，不是一篇文档的关系总数。**
- 不同证据窗口并行；同窗口内独立子批也并行，受 `KG_EXTRACT_LLM_MAX_CONCURRENCY` / `max_workers` 与进程内 QPM/TPM（含输入档位收紧）约束。
- 单个证据窗口超过 8000 字符不发送，告警 `RELATION_INPUT_BUDGET`。

模型对每个 `candidate_id` 返回：

| status | 含义 |
| --- | --- |
| `supported` | 必须给出本次片段中的逐字引文，且能支持该关系，不能只因为两个名称共现 |
| `not_supported` | 本组证据不支持；不表示整篇没有该边，也不擦掉其它窗口的正例 |
| `insufficient_evidence` | 指代不清、引用目标不在本次片段，或条件无法确定 |

缺决策重试一次；仍缺则告警 `RELATION_DECISION_MISSING`，**不当成否定**。

#### 落地前：`_quote_acceptable`（端点 + 短名共现）

`supported` 与 Clef 预判正例在引文绑定成功后，还必须通过 `_quote_acceptable`；不通过则**不入库**。

先过 `_quote_covers_endpoints`：

| 候选类型 | 判定 | 失败告警 |
| --- | --- | --- |
| `local` | quote 必须同时包含源名和目标名 | `RELATION_EVIDENCE_ENDPOINT_MISS` |
| `anchor` | quote 至少包含一侧名称（文档标题常不在当前句重复） | 同上 |
| 同片 `adjacent`（一条连续片段） | 与 local 相同：quote 须含两端名 | 同上 |
| 跨片 `adjacent` / `cross_reference` | 两端名须在配对片段**并集**中；quote **至少点明一侧** | 同上 |
| 引文不在片段内 | — | `RELATION_EVIDENCE_INVALID` |

再过 `_quote_is_name_cooccurrence`（**通用、不绑文档类型**）：

- 仅检查同片双端候选（`local` / 同片合并 `adjacent`）。
- 两端名都出现在 quote 中，且**两端名长度均 &lt; 20**：去掉两端名与标点空白后若无任何剩余字 → 视为纯共现，告警 `RELATION_EVIDENCE_NAME_ONLY`，拒绝入库。
- 任一端名 ≥ 20 字（长标题、长名单等）→ **跳过**本检查，避免误伤「标题+收文对象」类合法引文。
- 跨片邻接 / 条款引用 / 锚点：不走本检查。

意图：挡短实体同片「只粘两个名字」的假边；长端点与跨片召回保持原口径。

#### 入池与去重

同一事实多个窗口：按 `(from_id, rel_type, to_id, quote)` 去重后分别保留。新证据 span 追加，不替换整份证据列表。`RelationResolver` 仍负责签名、端点类型、基数和最终去重。

## 5. 确定性关系与收尾

关系分类之后，程序直接组装不交给模型的边：文档关系、编号标题层级、结构单元关系、标准语义和技术关系，以及复合元素的 `hasSubRule` 成员关系。然后做 post-relation 过滤。

校验失败且可修复时，最多两轮修复。启用 Clef 时，跳过 `required_relation` 的生成式修复。最后做 mapping 评分，组装 `raw`、`intermediate_model`、`graph`、`triples` 和覆盖信息。调用方稳定看到的仍是 `entities` 和 `relations`。

## 6. 和旧关系抽取的差别

| | 旧实现 | 现在 |
| --- | --- | --- |
| 候选从哪来 | 切片内按签名展开实体对（最多约 200 对） | 局部共现 + 锚点/邻接/条款引用召回 |
| 原文怎么送 | 整片/邻居文本随每个子批重复发送 | 每个候选只带证明所需的证据片段 |
| 跨片 | 邻居可见，但跨片联合证据难同等落地 | 邻接双片段 + 条款引用最多 3 段 |
| 漏决策 | 不单独重试 | 缺项重试一次，不当成 NONE |
| 结构边 | 黑名单跳过，由组装器产生 | 同左（保留黑名单，不删） |

没有召回到的实体对不会进入模型。精度门禁叠在召回与落地两处，不回到笛卡尔积。

## 8. 关系阶段精度优化（2026-10-12）— 修改点清单

**目标**：在不改实体抽取、合并与 `pre_relation` 实体拒绝逻辑的前提下，减少关系多抽，并尽量保住关系召回。

### 8.1 未改动的边界

- 不改 Pass 1 实体 LLM、属性补全、公文结构单元、实体 `pre_relation`。
- 关系索引仍消费全部 `accepted_entities()`；不在关系阶段删实体。
- 不收缩跨片邻接与条款引用的生成条件。
- 不改确定性结构组装器本身（`HAS_PART` / `EVIDENCED_BY` 等仍由组装产生）。

### 8.2 代码修改点（按生效顺序）

| # | 文件 / 符号 | 改动（做什么） | 意图（为什么） |
| --- | --- | --- | --- |
| 1 | `relation_candidates._WEAK_RELATION_TOKENS` + `active_signatures` | 常量 `{"relatedto"}` 并入签名 skip 集合 | 评测里 `RELATED_TO` 几乎全是多抽，直接不召回、不进模型 |
| 2 | `relation_candidates._looks_like_contact` | 联系人栏 + 短署名启发式 | 挡住「信息公司张振威」挂到签发/适用 |
| 3 | `relation_candidates._role_gate` | 仅 `issuedby` / `appliesto` 按目标名与原文线索过滤；其它签名恒真 | 砍锚点/局部共现假签发、假适用，其它关系召回不受影响 |
| 4 | `relation_candidates._add` | 类型匹配通过后调用 `_role_gate`，失败则不建候选 | 门禁发生在召回，减少送模量（053304：待模型 448→312） |
| 5 | `relation_extraction._quote_covers_endpoints` | 见 §4.6 表：local/同片邻接双端；锚点一侧；跨片邻接/条款引用「片段并集双端 + quote 一侧」 | 挡同片共现假正例，保住跨片指代召回 |
| 6 | `relation_extraction._quote_is_name_cooccurrence` + `_quote_acceptable` | 同片双端且两端均 &lt;20 字时，引文去掉两端名后无剩余 → `RELATION_EVIDENCE_NAME_ONLY`；长端点跳过 | 通用挡短名纯共现，不针对某一文档；不收缩跨片 |
| 7 | `relation_extraction._apply_decisions` / Clef 落地 | `supported` 与预判正例均走 `_quote_acceptable` | 可观测；不当成缺决策重试抹掉 |
| 8 | `prompt_router.build_relation_task_messages` | output contract 明确：禁止只粘两端名而无关系表述 | 与落地门禁同向，降低模型滥标 supported |

### 8.3 单测（`tests/test_relation_stage.py`）

- `test_related_to_is_not_recalled`：弱共现边不进候选。
- `test_issued_by_keeps_office_and_skips_recipients`：办公室签发保留；收文对象 / 联系人拒绝。
- `test_quote_must_cover_both_endpoint_names`：同片引文只含一端名时不入库。
- `test_short_name_only_quote_is_rejected`：短端点纯共现引文拒绝。
- `test_long_endpoint_name_only_quote_is_kept`：长端点标题式引文放行。
- 原有同句多签名、跨行表格、跨片邻接、条款引用、批上限等用例继续约束召回不被误伤。

### 8.4 效果与残留风险

| 项 | 结论 |
| --- | --- |
| 已验证（official_01） | 条数 ↓、P ↑、R 未掉（略升）、F1 ↑；`RELATED_TO` 清零 |
| 召回风险 | 真 `RELATED_TO` 黄金边会漏（当前 official 金标几乎不依赖）；真签发方若名称不含办公室且原文无印发/来文等线索，可能漏 `ISSUED_BY` |
| 仍多的边 | 结构组装边（如 `EVIDENCED_BY`）与其它语义边仍占多抽大头；下一步若继续压量，应分类型看 judge FP，而不是再砍跨片召回 |
