# 算法能力接口目标草案

> 状态：讨论稿  
> 目的：先确定算法服务需要保留和新增哪些 HTTP 接口，不作为最终字段级协议。

## 目标

算法服务当前包含知识沉淀、文本向量化和图谱关系置信度三类业务 HTTP 能力。计划保留已有业务接口，并补充知识沉淀的可复用组件接口。完整知识沉淀和组件入口必须复用同一套 Service、切片 index、LLM 调度和错误处理。

```text
文档解析 → Markdown 切片 → 分片知识抽取 → graph 去重/可选入库
                       ↓
                文本切片向量化/存储
```

## API 路径设计原则

- 统一使用 `/api/v1` 版本前缀，为后续不兼容升级保留空间。
- 路径描述业务能力，不使用 `component`、`nl2cypher`、`kg-update` 等历史模块名。
- 一级路径按稳定业务域划分：`pipelines`、`documents`、`embeddings`、`graphs`。
- 聚合编排归入 `pipelines`，同步原子算法使用清晰动作名，例如 `parse`、`chunk`、`extract`。
- 批量能力直接作为默认能力，不再为单条和批量分别制造路径层级；请求体统一使用 `items`。
- `/health` 和 `/mcp` 属于运行与协议入口，不放入 `/api/v1` 业务路径。

## 目标接口总览

### 已有能力迁移到新路径

| 能力 | 目标接口 | 主要输入 | 主要输出 | 建议 |
| --- | --- | --- | --- | --- |
| 完整知识沉淀 | `POST /api/v1/pipelines/knowledge-ingestion` | 文件、本体、解析/切片配置 | graph/graphs、可选文件服务信息、统计信息 | 迁移现有能力 |
| 通用文本向量化 | `POST /api/v1/embeddings/texts` | `index + text` 列表 | `index + text + vector` 列表 | 迁移现有能力 |
| 图谱关系置信度 | `POST /api/v1/graphs/confidence` | graph | 写入 confidence 的 graph、评分明细 | 迁移现有能力 |
| 健康检查 | `GET /health` | 无 | 后端存活状态 | 保留基础接口 |

### 第一阶段建议新增

| 能力 | 目标接口 | 主要输入 | 主要输出 | 建议 |
| --- | --- | --- | --- | --- |
| 文档解析 | `POST /api/v1/documents/parse` | 原始文件、解析配置 | Markdown、解析器元数据 | 新增 |
| Markdown 切片 | `POST /api/v1/documents/chunk` | Markdown、切片配置 | `index + text` 列表 | 新增 |
| 分片知识抽取 | `POST /api/v1/graphs/extract` | 本体、`index + text` 列表 | `index + raw + graph` 列表及合并 graph | 新增 |
| Graph 去重 | `POST /api/v1/graphs/merge` | `index + graph` 列表 | 去重后的单个 graph | 新增 |
| Graph 向量化 | `POST /api/v1/embeddings/graphs` | `index + graph` 列表 | `index + original_json + vector` 列表 | 新增 |

### 历史路径迁移映射

| 历史路径 | 目标路径 |
| --- | --- |
| `POST /api/knowledge/precipitation` | `POST /api/v1/pipelines/knowledge-ingestion` |
| `POST /api/component/nl2cypher/text-to-vectors` | `POST /api/v1/embeddings/texts` |
| `POST /api/component/kg-update/calculate-confidence` | `POST /api/v1/graphs/confidence` |

旧路径作为 deprecated alias 保留，但请求和响应字段完全使用对应 v1 协议，不提供字段级兼容或数据结构转换。确认无调用方后删除旧路径；新文档、OpenAPI 和测试以 `/api/v1` 为正式路径。

## 初步通用协议

JSON 接口统一返回：

```json
{
  "code": 0,
  "info": "success",
  "data": {},
  "error": null
}
```

失败时 `code` 非 `0`，`data` 通常为 `null`，`error` 包含稳定的 `type`、处理阶段 `stage`、`retryable` 和诊断 `details`。正式接口和 deprecated aliases 都统一使用 `info`，不再返回重复的 `message` 字段。错误码按请求、文档、切片、LLM、向量、图谱、存储和依赖分段，详见正式接口协议。

跨接口统一使用整数 `index`。标准 graph 结构为：

```json
{
  "nodes": [
    {
      "uid": "Term::采购金额",
      "label": "Term",
      "properties": {"name": "采购金额"}
    }
  ],
  "relationships": [
    {
      "from_uid": "Term::采购金额",
      "to_uid": "Metric::金额",
      "type": "MAPS_TO",
      "properties": {}
    }
  ]
}
```

## 初步输入输出

### 1. 聚合知识沉淀

```http
POST /api/v1/pipelines/knowledge-ingestion
Content-Type: multipart/form-data
```

初步请求字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `file` | file | 原始文档 |
| `ontology` | string | PlantUML 本体 |
| `options` | JSON string | 解析、切片、抽取和存储配置 |

`options` 初步结构：

```json
{
  "parser": {"engine": "auto"},
  "chunking": {
    "strategy": "recursive",
    "size": 500,
    "separators": ["。", "\n"]
  },
  "extraction": {"model": null, "merge": true},
  "storage": {
    "persist_graph": false,
    "knowledge_space_id": null
  }
}
```

初步响应 `data`：

```json
{
  "name": "采购制度",
  "summary": "共抽取 10 个节点和 6 条关系。",
  "artifacts": null,
  "extraction": {
    "ranges": [[0, 486], [486, 920]],
    "graph": {"nodes": [], "relationships": []}
  },
  "stats": {}
}
```

### 2. 文档解析

```http
POST /api/v1/documents/parse
Content-Type: multipart/form-data
```

请求包含 `file` 和 JSON 字符串 `options`。原子接口不产生存储副作用，直接返回 Markdown：

```json
{
  "file_name": "采购制度.docx",
  "markdown": "# 采购制度\n……",
  "content_length": 10240,
  "parser": {
    "preferred_engine": "docling",
    "final_engine": "docling"
  }
}
```

### 3. Markdown 切片

```http
POST /api/v1/documents/chunk
Content-Type: application/json
```

请求：

```json
{
  "file_name": "采购制度.md",
  "markdown": "# 采购制度\n……",
  "options": {
    "strategy": "recursive",
    "size": 500,
    "separators": ["。", "\n"]
  }
}
```

响应 `data`：

```json
{
  "count": 2,
  "items": [
    {
      "index": 0,
      "text": "第一个文本片段",
      "start_offset": 0,
      "end_offset": 486
    }
  ]
}
```

字符偏移以输入 `markdown` 的 Python 字符索引为准，用于回到原始 Markdown 定位和高亮。

### 4. 分片图谱抽取

```http
POST /api/v1/graphs/extract
Content-Type: application/json
```

请求：

```json
{
  "ontology": "@startuml ... @enduml",
  "items": [
    {"index": 0, "text": "第一个文本片段", "ranges": [0, 486]},
    {"index": 1, "text": "第二个文本片段"}
  ],
  "options": {"model": null, "merge": true}
}
```

响应 `data`：

```json
{
  "ranges": [[0, 486], [486, 920]],
  "graph": {"nodes": [], "relationships": []},
  "scheduler": {"max_concurrency": 4, "qps": 2, "qpm": 60}
}
```

第一阶段沿用当前策略：任一切片重试后仍失败，则请求整体失败，并在 `error.details.failed_items` 中返回失败 index。请求不允许直接指定任意 `base_url`。

`options.merge` 默认为 `true`，执行按节点 `uid`、关系三元组的确定性去重并返回 `graph`；设为 `false` 时不做跨切片去重，返回 `graphs: [{index, graph}]`。聚合流水线和抽取产物使用相同规则。

### 5. 文本向量化

```http
POST /api/v1/embeddings/texts
Content-Type: application/json
```

请求：

```json
{"items":[{"index":0,"text":"采购金额"}]}
```

响应 `data`：

```json
{
  "count": 1,
  "dimension": 1024,
  "items": [{"index": 0, "text": "采购金额", "vector": [0.1, -0.2]}]
}
```

### 6. Graph 向量化

```http
POST /api/v1/embeddings/graphs
Content-Type: application/json
```

请求：

```json
{"items":[{"index":0,"graph":{"nodes":[],"relationships":[]}}]}
```

响应 `data`：

```json
{
  "count": 1,
  "dimension": 1024,
  "items": [
    {
      "index": 0,
      "graph": {"nodes": [], "relationships": []},
      "serialized_text": "{\"nodes\":[],\"relationships\":[]}",
      "vector": [0.1, -0.2]
    }
  ]
}
```

graph JSON 由服务端按固定规则序列化，调用方不得自行传入 `serialized_text`。

### 7. 图谱关系置信度

```http
POST /api/v1/graphs/confidence
Content-Type: application/json
```

请求：

```json
{
  "graph": {
    "nodes": [],
    "relationships": [],
    "ontology_relations": []
  }
}
```

响应 `data`：

```json
{
  "evaluation_id": "EVAL-20260715...",
  "total_count": 1,
  "graph": {"nodes": [], "relationships": [], "ontology_relations": []},
  "details": {}
}
```

## 各接口的大致边界

### 文档解析

只负责把 PDF、Word、Excel、CSV、HTML 等文件解析为 Markdown，并返回最终解析引擎、fallback 和必要的解析元数据；不负责切片、知识抽取和向量化。

### Markdown 切片

只负责按统一规则切分 Markdown。第一阶段至少返回：

```json
{
  "items": [
    {"index": 0, "text": "第一个文本片段"}
  ]
}
```

目标协议包含 `start_offset/end_offset`，实现时需要升级当前只返回字符串的切片函数。

### 分片知识抽取

接收调用方提供的切片 index，使用共享 LLM 并发、QPS、QPM 调度器逐片抽取，并保持输入顺序。`merge=true` 返回确定性去重后的 graph，`merge=false` 返回分片 graphs。

### Graph 向量化

由服务端统一序列化 graph JSON 后向量化，避免不同调用方产生不同字符串格式。输出 index、原始 graph JSON、序列化文本和向量。

### 完整知识沉淀

作为编排入口调用上述共享能力，不再单独维护另一套解析、切片、抽取或向量化逻辑。

服务不做本地产物存储。未配置 `FILE_SERVICE_URL` 时返回 `artifacts: null`；配置后 `artifacts.markdown` 返回 Markdown 的 `id/name/path/url`，原始文本切片向量写入 `/third/vectors/store`，`artifacts.vector_ids` 返回其 IDs。抽取结果直接位于 `extraction`，成功响应只保留按顺序对齐的二维 `ranges` 和 `graph/graphs`，不返回切片 text/raw/items/index。独立 Graph 向量化接口继续保留，但不用于知识沉淀流水线。

### 通用文本向量化

继续提供与知识图谱无关的批量文本向量能力，保留输入顺序和空字符串。Graph 向量化接口内部可以复用相同向量模型，但负责统一 graph JSON 序列化和 index 传递。

### 图谱关系置信度

继续作为独立业务接口，对 `relationships` 和 `ontology_relations` 计算文本证据、图路径证据和综合置信度。第一阶段不拆分“文本评分”和“路径评分”两个更底层接口，避免调用方自行组合出不一致结果。

## MCP 能力边界

当前 `/mcp` 还提供以下能力，第一阶段不重复建设为 HTTP 接口：

| MCP 能力 | 处理建议 |
| --- | --- |
| 单文本知识抽取 `kg_extract_v2` | 保留；HTTP 使用批量分片抽取接口 |
| 知识空间刻度、初始化与图谱存储 | 保持 MCP-only，待权限和调用场景明确后再评估 HTTP |
| 知识空间定位、实体链接、属性查询、图谱搜索 | 保持 MCP-only，面向 Agent 自主调用 |
| SQL 查询和数据库元数据 | 保持 MCP-only，不列入算法业务 HTTP |
| 图表生成 | 保持 MCP-only，不列入算法业务 HTTP |

## 第一阶段暂不单独开放

| 能力 | 原因 |
| --- | --- |
| Graph 合并 HTTP 接口 | 纯内部计算，可随分片抽取一起返回 |
| 文件产物存储接口 | 属于部署和基础设施细节，不应成为算法公共契约 |
| Neo4j 写入 HTTP 接口 | 当前没有认证和权限边界，直接开放风险较高 |
| 任意 LLM `base_url` 代理 | 存在访问内部地址的风险，应限制为服务端配置或可信白名单 |
| 置信度文本评分/路径评分子接口 | 当前由综合置信度算法统一调度，暂不拆散 |
| SQL、图谱检索、可视化 HTTP 接口 | 已作为 Agent MCP 工具存在，不属于本轮算法 HTTP 范围 |

## 需要先确认的问题

1. 组件接口仅供内网调用，还是需要正式认证与权限控制？
2. `options.model` 是否允许调用方自由指定，还是只能从服务端白名单选择？
3. 同步接口允许的最大文件大小、切片数量和超时时间是多少？
4. Neo4j 入库继续只由完整流水线的 `storage.persist_graph` 控制，还是后续增加受保护的独立接口？
5. 图谱置信度是否长期保持一个综合接口，还是未来需要开放文本评分、路径评分子接口？
6. MCP-only 能力中是否存在必须提供给非 Agent 调用方的能力？
7. 历史路径是否需要兼容期；如果需要，保留一个版本还是按明确日期下线？

## 初步实施顺序

```text
1. 抽取共享 Service 和请求/响应模型
2. 文档解析接口
3. Markdown 切片接口
4. 分片知识抽取接口
5. Graph 向量化接口
6. 让完整知识沉淀改为编排同一组 Service
7. 补充正式接口协议、限额和安全控制
```
