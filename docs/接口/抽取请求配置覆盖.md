# 抽取请求配置覆盖

评测脚本和业务 HTTP 请求可在同一个 Backend 内选择算法版本、供应商、模型和超时预算，不需要为每个组合启动独立 Backend。供应商配置需要先由管理员在服务端登记；首次部署功能或更新容器环境变量仍需重新创建 Backend，之后每次评测不用重启。

## 命令行

在仓库根目录运行（Windows 可将 `python3` 换成 `.venv/Scripts/python.exe`）：

```sh
python3 eval/mini_eval.py --extract-version v3.1 --extract-provider siliconflow --extract-model deepseek-ai/DeepSeek-V4-Flash --extract-request-timeout 300 --extract-document-timeout 1800
```

同样的参数适用于 `eval/run.py`。只传 `--extract-version v3` 时，仅覆盖算法版本，其余采用参数文件或 Backend 默认配置。优先级为 **命令行 > params.yaml 的 options.extraction > 服务端供应商/默认配置**；`null` 表示不覆盖。参数文件显式设置的 `model` 会覆盖供应商默认模型，跨供应商比较时建议留 `null` 或显式传模型。

对比实验先冻结切片，再更换版本或供应商：

```sh
python3 eval/mini_eval.py --mode chunk-extract --extract-version v2
python3 eval/mini_eval.py --mode extract --from-run tmp/eval/runs/上一批次 --extract-version v3 --extract-provider siliconflow
```

judge 参数仍由独立的 `eval.judge_*` / `QASYSTEM_JUDGE_*` 配置决定。抽取供应商覆盖不会自动切换裁判。不要使用 `--reuse-extract-from` 比较新的抽取配置：它只对旧预测重新评分，新参数与该选项同时使用会报错。

本次覆盖支持 `--stage backend` 的 `extract`、`chunk-extract` 和 `pipeline` 模式；MCP 工具仍使用服务端默认配置。新覆盖项与 `--stage plugin/all` 同时使用会明确报错，不会静默忽略。

## 切片配置

可启动多个独立评测进程，每次分别传 CLI 参数；参数文件不会被修改。同一秒启动的批次会自动分配带随机后缀的独立结果目录。并行对比时建议传 `--runs-retention-days 0`，避免某一进程清理另一进程正在引用的历史产物。

配置和结果文件隔离不等于耗时互不影响：任务共享 Backend 算力，同一 `quota_group` 在同一进程内共享限流；不同 Worker 进程尚未共享配额计数。对比耗时建议串行执行。

切片参数也可在执行时覆盖，两种评测入口均支持：

```sh
python3 eval/mini_eval.py --mode chunk-extract --chunk-overlap 50 --chunk-size 4000 --extract-version v3.1
```

Backend 的 `options.chunking.chunk_overlap` 默认为 50，评测未传该字段时直接沿用服务端值；传 `--chunk-overlap 0` 关闭重叠。CLI 优先于 YAML，要求 `0 <= overlap < size`。实际重叠由切片策略及边界规则决定。其他解析、切片参数可通过 `--params 自定义.yaml` 中的 `options.parser`、`options.chunking` 配置。

切片覆盖仅支持 backend 的 `chunk-extract` 或 `pipeline`；`extract --from-run` 使用固定切片，不能用新 overlap 改变它，脚本会拒绝这种组合。

## Backend 供应商配置

所有部署变量登记在根 `.env.example`。`KG_EXTRACT_PROVIDERS_JSON` 是供应商名称到配置的 JSON 对象；默认 `{}`，`default` 为保留名称，表示原有 `KG_EXTRACT_LLM_*` 配置。

```json
{
  "siliconflow": {
    "base_url": "https://api.siliconflow.cn/v1",
    "api_key_env": "SILICONFLOW_API_KEY",
    "model": "deepseek-ai/DeepSeek-V4-Flash",
    "quota_group": "siliconflow-account",
    "max_concurrency": 2,
    "qps": 1,
    "qpm": 30,
    "max_input_tokens": 65536,
    "max_output_tokens": 16384,
    "request_timeout": 300,
    "disable_thinking": true,
    "api_mode": "chat",
    "thinking_parameter": "enable_thinking"
  }
}
```

以上限额仅为配置示例，应按实际账号配额填写。密钥值单独配置在 `SILICONFLOW_API_KEY`；API 和脚本只接受供应商名称，不接受 URL、密钥、配额上限。配置错误、未登记供应商或缺失凭据会在提交时被拒绝。

`max_input_tokens` 是本地输入预算，`max_output_tokens` 是发送给模型的输出上限，二者独立。旧 `max_tokens` 是输出字段的兼容别名；同时填写且不一致会拒绝配置。默认输入 65536、输出 16384。`default` 配置对应 `KG_EXTRACT_LLM_MAX_INPUT_TOKENS`、`KG_EXTRACT_LLM_MAX_OUTPUT_TOKENS`；后者为空时沿用 `KG_EXTRACT_LLM_MAX_TOKENS`。

输入预算在发送 HTTP 和领取配额之前检查 messages/input、schema、tools 等输入字段。当前使用离线 UTF-8 字节数加协议余量的保守 token 估算（不是供应商精确 tokenizer，也不是计费 token 数），不会静默截断原文。超限报 `LLM_INPUT_LIMIT`；v2/v3 可拆阶段进一步缩批，无法缩小时保留失败。整个上下文窗口仍需管理员确保能同时容纳输入、输出和模型协议开销。

两个预算在提交时固化，输出预算用于实际请求和批大小计算。不同模型能力不同时建议分别登记配置项；`--extract-model` 不会自动推断新模型上限。供应商内部更低的输出限制仍由返回的截断信号触发缩批。

`api_mode=auto` 保持各版本原有协议选择，`chat` 明确使用 Chat Completions，避免探测不支持的 Responses 接口。`thinking_parameter` 可选 `thinking`、`enable_thinking`、`none`，后者不发送关闭思考的专用参数。这些能力由管理员配置，不代表对未知供应商已做兼容认证。

供应商不支持 `json_schema` 时，可设置 `response_format: "json_object"`，将该供应商的 Chat Completions 结构化输出请求转换为 JSON 模式；算法仍执行返回内容的解析与校验。默认 `auto` 保持原请求格式，不影响其他供应商。

## HTTP 与执行结果

```json
{
  "ontology": "本体文本",
  "items": [{"text": "待抽取文本"}],
  "options": {
    "version": "v3.1",
    "provider": "siliconflow",
    "model": "deepseek-ai/DeepSeek-V4-Flash",
    "request_timeout": 300,
    "document_timeout": 1800,
    "merge": true
  }
}
```

提交到 `/api/v1/graphs/extract`；完整流水线把这些字段放到 `options.extraction`。版本支持 `v2`、`v3`、`v3.1`、`latest`，后者始终选择实体 `latest` 包。无本体的摘要模式不支持这些新覆盖项，避免误以为已切换图谱算法。

有效配置在提交时固化到任务内部数据，后续队列等待、执行和重试不重新解析供应商配置。只保存密钥环境变量引用，不保存密钥值；执行时从对应环境变量加载凭据，因此凭据轮换仍能生效。不要在同一运行中的任务期间改变该变量对应的账号身份。

结果 `quality.effective_config` 回显版本、供应商名称、模型、token 上限、思考设置和超时预算；`quality.extract_version` 保持兼容。评测原始响应和 summary 中的 quality 会保留这些字段，不包含密钥或凭据变量名。

`request_timeout` 包含该次 HTTP 调用等待限流槽位的时间。`document_timeout` 从开始抽取时计算，限制此文档的后续模型调用与响应接受时间，不包含业务队列、解析、切片或裁判耗时；v3.1 还沿用自身控制器的文档截止时间。v2/v3/latest 的本地 CPU 合并/校验不做强制线程中断，也不承诺精确墙钟终止时间。未设置时保持原有默认：v3.1 为其环境配置预算，其他版本不增加文档预算。

## 限流范围与边界

请求级客户端按 `quota_group` 共享进程内限流池，与算法版本、模型无关。每次 HTTP 调用（包括客户端协议回退）都领取配额；相同配额组的别名不会重置计数或提高已生效上限。上限冲突采用较严值，提升限额需重启进程。默认组由 `KG_EXTRACT_LLM_QUOTA_GROUP` 决定。

尚未实现 Redis 分布式供应商限流、TPM 控制或统一传输重试。多个 Worker 进程、其他容器、MCP 旧调用入口和外部裁判不共享该进程池，需要单独控制总负载。v2/v3 已接入输出预算拆批，见 [抽取截断拆批与重试](../算法/抽取截断拆批与重试.md)；明确截断不原批重复，网络错误仍有限重试。

发布前仍须通过全量单测、运行中 Backend 的 LLM 评测、基线对比和生产观测门禁。环境依赖未变化，不需要重建环境镜像。


## 评测默认调用方式

`./eval/run.sh --groups official` 默认使用 `pipeline`，按文件调用完整 `/api/v1/pipelines/knowledge-ingestion`；请求 `options: {}`，不在评测端复制解析、切片、算法、模型或存储默认值。若实际 API 请求包含显式 options，使用 `--params` 或对应 CLI 覆盖项保持同样的参数。分段及固定切片实验需显式选择 `--mode chunk-extract` 或 `--mode extract --from-run ...`。

默认 `--case-attempts 1`、`--request-attempts 1`，失败或 partial 不自动重复抽取。需要增加尝试次数时分别显式设置；算法内部重试不变。运行日志与 `params.resolved.json` 记录模式、请求 options 和尝试次数，完整 API 响应保留服务端 quality 与实际配置。

默认评分仍是 `llm`，裁判为现有 DeepSeek API `deepseek-flash`，读取 `QASYSTEM_JUDGE_API_KEY` 或 `DEEPSEEK_API_KEY`，不拿其他供应商的抽取密钥代用。Clef 需显式传 `--judge-model clef-flash`，地址可用 `--judge-base-url` 覆盖。API 和评分耗时分别记录在 `backend.system.elapsed_seconds`、`score_elapsed_seconds`；`--match-mode identity` 仅供显式选择，不是默认质量评分方式。
