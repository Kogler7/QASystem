# 算法接口协议

本文描述当前代码实际暴露的 HTTP 接口。默认宿主机地址为 `http://127.0.0.1:8006`，容器内端口为 `8000`。历史接口调用方请先阅读[算法 API v1 迁移说明](算法API迁移说明.md)。

## 1. 通用约定

成功 JSON 统一为：

```json
{
  "code": 0,
  "info": "success",
  "data": {},
  "error": null,
  "execution": null
}
```

失败结构、错误码、HTTP 状态和重试规则见[错误码协议](错误码协议.md)。

统一执行层对现有业务 API 采用增量协议：未携带 `Prefer` 时仍同步返回原 HTTP 状态和原业务 `data`，只在响应 envelope 顶层增加 `execution`。调用方发送 `Prefer: respond-async` 时立即返回 HTTP `202` 和 `job_id/status` 任务句柄；发送 `Prefer: wait=N` 时显式请求最多 60 秒的有界等待，时限内完成则返回原业务结果，否则返回 `202`，任务继续执行。新增的 `POST /api/v1/jobs` 是显式任务接口，默认返回 `202`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/jobs` | 显式提交任务，默认返回 `202` |
| `GET` | `/api/v1/jobs/{job_id}` | 查询任务状态 |
| `GET` | `/api/v1/jobs/{job_id}/result` | 成功后获取业务结果；未成功返回 `409` |
| `DELETE` | `/api/v1/jobs/{job_id}` | 请求取消任务 |
| `GET` | `/api/v1/jobs/{job_id}/events?min_level=INFO` | SSE 订阅任务事件 |
| `GET` | `/api/v1/jobs/{job_id}/executions` | 查询原子任务、尝试和资源分配 |

`execution` 是统一响应 envelope 的顶层新增字段，不改变最终业务 `data` 的内部结构。参数校验等尚未创建任务的响应中该字段为 `null`。

### 1.1 默认同步响应

现有业务 API 默认等待队列中的任务完成，并直接返回原业务 `data`。例如文档解析成功仍返回解析结果，只增加 `execution`；`execution.result_url` 与其他观测 URL 可用于后续审计：

```json
{
  "code": 0,
  "info": "文档解析完成",
  "data": {
    "file_name": "demo.pdf",
    "markdown": "# Demo\n正文",
    "parser": {"final_engine": "vlm"}
  },
  "error": null,
  "execution": {
    "mode": "async",
    "job_id": "job-uuid",
    "status": "succeeded",
    "events_url": "/api/v1/jobs/job-uuid/events",
    "executions_url": "/api/v1/jobs/job-uuid/executions",
    "result_url": "/api/v1/jobs/job-uuid/result"
  }
}
```

这里的 `execution.mode=async` 表示任务由统一队列和 Worker 执行，不表示本次 HTTP 响应采用异步任务句柄。

### 1.2 显式异步响应

请求携带 `Prefer: respond-async` 时，业务 API 立即返回 HTTP `202`：

```json
{
  "code": 0,
  "info": "任务已入队",
  "data": {
    "job_id": "job-uuid",
    "status": "queued"
  },
  "error": null,
  "execution": {
    "mode": "async",
    "job_id": "job-uuid",
    "status": "queued",
    "events_url": "/api/v1/jobs/job-uuid/events",
    "executions_url": "/api/v1/jobs/job-uuid/executions",
    "result_url": "/api/v1/jobs/job-uuid/result"
  }
}
```

前端可订阅 `execution.events_url`。收到 SSE `job.completed` 后，请求 `execution.result_url`；该接口返回包含最终业务 `data` 和最终 `execution` 的完整 envelope：

```bash
curl -N http://127.0.0.1:8006/api/v1/jobs/job-uuid/events
curl -fsS http://127.0.0.1:8006/api/v1/jobs/job-uuid/result
```

```json
{
  "code": 0,
  "info": "任务结果查询完成",
  "data": {
    "file_name": "demo.pdf",
    "markdown": "# Demo\n正文",
    "parser": {"final_engine": "vlm"}
  },
  "error": null,
  "execution": {
    "mode": "async",
    "job_id": "job-uuid",
    "status": "succeeded",
    "events_url": "/api/v1/jobs/job-uuid/events",
    "executions_url": "/api/v1/jobs/job-uuid/executions",
    "result_url": "/api/v1/jobs/job-uuid/result"
  }
}
```

任务未成功完成时读取 `result_url` 返回 `409`。客户端应以 SSE 终态或任务状态为准，不能把连接关闭本身当作任务完成。

## 3. 文档解析

```http
POST /api/v1/documents/parse
Content-Type: multipart/form-data
```

### 输入

```bash
curl -X POST 'http://127.0.0.1:8006/api/v1/documents/parse' \
  -F 'file=@./demo.docx' \
  -F 'options={"engine":"auto","mineru_options":{"language":"ch","ocr_mode":"auto","table_enable":true,"formula_enable":true}}'
```

`options` 是 JSON 字符串，结构如下：

```json
{
  "engine": "auto",
  "force": false,
  "page_sharding": "auto",
  "page_shard_size": 0,
  "max_page_shards": 16,
  "keep_page_edges": "first_page",
  "page_edge_min_chars": 3,
  "mineru_options": {
    "language": "ch",
    "ocr_mode": "auto",
    "table_enable": true,
    "formula_enable": true
  }
}
```

`engine` 支持 `auto`、`text`、`docling`、`vlm`、`mineru`、`mineru4`、`pandas` 和 `beautifulsoup`，并接受 `excel`、`html`、`bs4` 别名。`engine=auto` 时，服务根据文件类型和内容特征选择首选解析器。显式指定 `engine` 时，该解析器必须与文件类型兼容；默认它可能成为首选解析器，也可能作为首选解析失败后的候选解析器。需要强制指定解析路线时设置同层字段 `force=true`；此时必须指定兼容的 `engine`，系统跳过自动选择和 fallback。客户端不能仅根据请求配置推断实际使用的解析器，应读取响应中的 `data.parser`：

- `preferred_engine`：服务根据文件判断出的首选解析器。
- `requested_engine`：客户端显式请求的解析器；请求为 `auto` 时不返回。
- `request_handling`：本次请求解析器的处理方式，例如命中首选、作为 fallback 候选或因不兼容被忽略。
- `force`：请求是否强制使用指定引擎；仅在 `force=true` 时返回。
- `final_engine`：最终成功生成 Markdown 的解析器。
- `fallback`：实际发生回退时返回原解析器及失败原因；未回退时不返回。

按文件类型还可能返回其他可选字段，例如纯文本/网页的 `encoding`、表格类文件的 `sheets` 与 `table_semantics`。

`mineru_options` 是 MinerU/VLM 执行配置，只用于请求，不在 `data.parser` 中重复回显。`keep_page_edges` 控制是否保留页眉、页脚、页码等页面边缘文本，默认 `first_page`（保留本次解析范围内的首页），可设 `off`、`all` 或页码列表；`page_edge_min_chars` 是边缘文本的最小字符数（默认 3），短于该长度的边缘文本按水印/标志残片丢弃。

PDF 页段并行由服务端执行层自动完成，不要求调用方指定 VLM 或传入分片参数。规划层先确定实际解析路线；实际进入 VLM 阶段且达到服务端最小页数（默认 8 页）时，自动展开页段原子任务并投递到 `gpu.vlm` 队列。`page_sharding` 的 `auto`、`on`、`off` 以及 `page_shard_size`、`max_page_shards` 是可选调优和诊断参数，不是前端并发协议；默认 `max_page_shards=16`，允许范围为 1 到 32。容量不足时原子任务排队，失败只重试失败页段，完成后按页序合并 Markdown。仅包含页眉、页脚、页码或空白页的合法 shard 返回成功和 `empty=true`，合并时跳过空 Markdown；最终 `data.sharding.empty_shards` 列出这些 shard 的序号。非 PDF 或实际非 VLM 路线不会进入 VLM 页队列。

支持的文件类型为 PDF、OFD、DOCX、DOC、PPTX、PPT、PNG、JPG、JPEG、MD、TXT、XLSX、XLS、CSV、HTML 和 HTM。OFD 会先转换为 PDF，再应用 PDF 的自动引擎选择；响应中的 `file_type` 仍为 `ofd`。转换失败时返回 `DOCUMENT_CONVERT_FAILED`，OFD 的电子签名、印章和证书验签不属于该接口范围。

### 输出

```json
{
  "code": 0,
  "info": "文档解析完成",
  "data": {
    "file_name": "demo.docx",
    "file_size": 1024,
    "file_type": "docx",
    "markdown": "# Demo\n正文",
    "content_length": 9,
    "parser": {
      "preferred_engine": "docling",
      "requested_engine": "mineru",
      "request_handling": "fallback_candidate",
      "final_engine": "mineru",
      "fallback": {"from_engine": "docling", "reason": "Docling 解析失败"}
    }
  },
  "error": null,
  "execution": {
    "job_id": "job-uuid",
    "status": "succeeded",
    "events_url": "/api/v1/jobs/job-uuid/events",
    "executions_url": "/api/v1/jobs/job-uuid/executions",
    "result_url": "/api/v1/jobs/job-uuid/result"
  }
}
```

原子解析接口只返回 Markdown 和执行状态，不保存产物。

## 4. Markdown 切片

```http
POST /api/v1/documents/chunk
Content-Type: application/json
```

### 输入

```json
{
  "file_name": "demo.md",
  "markdown": "# Demo\n第一段。第二段。",
  "options": {
    "strategy": "recursive",
    "size": 500,
    "separators": ["。", "\n"],
    "similarity": 0.6
  }
}
```

切片策略：

| `strategy`         | 机制                                                             |
| -------------------- | ---------------------------------------------------------------- |
| `recursive`        | 使用内置分隔符递归切分，优先保持段落和句子完整，适合作为默认策略 |
| `symbols`          | 按`separators` 中的符号切分，并按 `size` 组合片段            |
| `custom_recursive` | 使用调用方提供的`separators` 执行递归切分                      |
| `markdown`         | 按 Markdown 标题和块结构切分，再受`size` 约束                  |
| `semantic`         | 按语义相似度切分，使用 `similarity` 阈值和 `breakpoint_method` |

`size` 是目标切片字符数，不保证每片严格等长。`separators` 只对 `symbols` 和 `custom_recursive` 生效。`similarity`（0 到 1）是 `semantic` 策略的相似度阈值，其他策略不使用。`chunk_overlap` 是相邻切片重叠字符数（默认 0），必须小于 `size`；`breakpoint_method`（`percentile`/`stddev`/`none`，默认 `percentile`）仅 `semantic` 使用；`size_unit` 当前仅 `char` 生效。具体切分顺序、长度控制、参数限制和 `range` 定位规则见[文档切片算法说明](../算法/文档切片算法说明.md)。

可选实体数量再切分：`adaptive_entity_count` 默认 `false`；启用后通过 `entity_count_model` 选择 `clef-flash`（默认）或 `nanojev`。复用既有模型服务与各自推理队列，不接受请求覆盖服务URL或密钥。预计≤20保留、21–40二分、>40三分，沿用 `chunk_overlap`；结构化保护与失败回退如实写入本地动作日志。该实验功能的启用示例、范围契约和限制见[文档切片算法说明](../算法/文档切片算法说明.md#11-可选实体数量再切分)。

### 输出

```json
{
  "code": 0,
  "info": "文档切片完成",
  "data": {
    "count": 1,
    "items": [
      {
        "text": "# Demo\n第一段。第二段。",
        "range": [0, 15]
      }
    ]
  },
  "error": null
}
```

偏移是输入 `markdown` 的 Python 字符索引。

## 5. 分片图谱抽取

```http
POST /api/v1/graphs/extract
Content-Type: application/json
```

### 输入

```json
{
  "ontology": "@startuml\nclass Term\n@enduml",
  "items": [
    {"text": "采购金额是采购合同的签约金额。"}
  ],
  "options": {"model": null, "merge": true}
}
```

`items[i]` 可携带可选的 `ranges`（原文字符范围）与 `metadata`（来源元数据），仅作溯源透传，不参与文档路由。`ontology` 为空字符串时接口退化为非结构化摘要模式：不执行图谱抽取，而是对每个切片生成摘要，`data` 返回 `mode`（`unstructured`）、`count` 和 `chunks[]`（每项含 `index`、`text`、`range`、`metadata`、`summary`）。

接口对全部 `items` 做**一次聚合抽取**（跨切片做实体消解、上下文补全与关系抽取），再按每个实体的证据归属把结果投影回各 `items`，因此响应仍保持输入顺序；`merge=false` 时 `items[i]` 与 `graphs[i]` 仍一一对应。调用层使用服务端配置的共享并发、QPS 和 QPM 调度器；`options.model` 可选择服务端允许的模型，但请求不能覆盖 LLM Base URL。默认降级：单个切片重试后仍失败时不作废整批，失败切片保留 `error` 标记、其余切片照常合并，失败明细记入服务端日志；全部切片失败（或设置 `KG_EXTRACT_STRICT_CHUNK_FAILURES=1` 启用严格模式）时本次批量请求整体失败，并在错误详情中给出失败位置。

### 输出

```json
{
  "code": 0,
  "info": "分片图谱抽取完成",
  "data": {
    "graph": {
      "nodes": [{"uid": "Term::采购金额", "label": "Term", "properties": {"name": "采购金额"}, "chunk_indices": [0]}],
      "relationships": []
    }
  },
  "error": null
}
```

`merge` 默认为 `true`。此时节点按 `uid` 去重，关系按 `from_uid + to_uid + type` 去重，并返回单个 `graph`。合并图节点的 `chunk_indices` 表示该节点来自哪些输入 `items` 下标。该过程是确定性去重，不是实体消歧或知识融合。

当 `merge=false` 时不执行跨切片去重，响应不包含 `graph`，而是返回：

```json
{
  "graphs": [
    {"nodes": [], "relationships": []},
    {"nodes": [], "relationships": []}
  ]
}
```

`merge=false` 时，请求 `items[i]` 与响应 `graphs[i]` 按顺序一一对应。聚合流水线会独立保留切片产生的 `ranges`。无论 `merge` 取值，响应 `data` 都附带质量门禁字段：`graph_publishable` 为 `false` 表示图谱未通过校验、下游沉淀/入库环节不得采信，但默认（`KG_EXTRACT_PUBLISH_BEST_EFFORT=1`）`graph`/`graphs` 仍返回 best-effort 结果（已抽取的节点与关系，`quality.status` 为 `partial`），`isolated_graph`/`isolated_graphs` 同步保留该图谱；设 `KG_EXTRACT_PUBLISH_BEST_EFFORT=0` 恢复旧行为（`graph`/`graphs` 置空为 `nodes`、`relationships` 空数组，未通过校验的图谱仅出现在 `isolated_graph`/`isolated_graphs`）；`quality` 给出质量状态与校验明细。

```json
{
  "code": 0,
```

## 7. 文本向量化

```http
POST /api/v1/embeddings/texts
Content-Type: application/json
```

### 输入

```json
{
  "items": [
    {"text": "知识地图"},
    {"text": ""}
  ]
}
```

### 输出

```json
{
  "code": 0,
  "info": "文本向量化完成，共 2 个向量",
  "data": {
    "count": 2,
    "dimension": 512,
    "items": [
      {"vector": [0.123, -0.456]},
      {"vector": [0.0, 0.0]}
    ]
  },
  "error": null
}
```

响应 `items[i]` 与请求 `items[i]` 按顺序对应，因此不重复返回输入文本。空字符串仍参与向量化，不会被静默删除。

## 9. 图谱关系置信度

该路径为兼容原调用协议而保留。当前已清除 Neo4j/Elasticsearch 直连，在应用团队开放 `confidence.calculate` 接口前固定返回 HTTP `503`：

```http
POST /api/v1/graphs/confidence
Content-Type: application/json
```

### 输入

```json
{
  "graph": {
    "nodes": [
      {"uid": "Term::采购金额", "label": "Term", "properties": {"name": "采购金额"}},
      {"uid": "Metric::金额", "label": "Metric", "properties": {"name": "金额"}}
    ],
    "relationships": [
      {"from_uid": "Term::采购金额", "to_uid": "Metric::金额", "type": "MAPS_TO"}
    ],
    "ontology_relations": []
  }
}
```

### 输出

```json
{
  "code": 8002,
  "info": "置信度评估失败",
  "data": null,
  "error": {
```

## 10. 知识沉淀（单文件/批量）

```http
POST /api/v1/pipelines/knowledge-ingestion
Content-Type: multipart/form-data
```

该接口组合前述底层能力，按以下顺序执行：

1. 使用文档解析能力生成 Markdown，并记录实际解析器状态。
2. 使用文档切片能力生成有序文本块和原文字符范围。
3. 传入本体时，对每个文本块并发执行图谱抽取，根据 `extraction.merge` 决定是否跨切片去重；未传本体时改为对每个切片生成非结构化摘要，不产图谱。
4. 配置文件服务时，对文本块执行向量化并写入外部向量存储。
5. `storage.persist_graph=true` 时返回 `8002 / EXTERNAL_CAPABILITY_UNAVAILABLE`，等待应用团队开放图谱写入接口；不会直连数据库。

聚合接口复用与底层接口相同的实现和配置语义，不定义另一套解析、切片、抽取或去重规则。

### 输入

| 字段         | 类型        | 必填 | 说明                                               |
| ------------ | ----------- | :--: | -------------------------------------------------- |
| `file`     | file        |  否  | 单个文档（与 `files` 至少提供一个）                |
| `files`    | file[]      |  否  | 多个文档（与 `file` 至少提供一个）                 |
| `ontology` | string      |  是  | PlantUML 本体；留空时启用非结构化摘要模式（不产图谱） |
| `options`  | JSON string |  否  | 严格流水线配置，默认`{}`                           |

`file` 和 `files` 可同时使用，所有文件会被统一收集处理。

单文件（`file`）时行为不变，响应 `stats.document` 为单对象。多文件（`files`）时：并发解析所有文件 → 拼接 Markdown → 统一切片抽取 → 跨文件去重合并为一份图谱，响应 `stats.documents` 为数组，`summary` 末尾标注文件数。

```bash
# 单文件（兼容旧版）
curl -X POST 'http://127.0.0.1:8006/api/v1/pipelines/knowledge-ingestion' \
  -F 'file=@./demo.docx' \
  -F 'ontology=<./ontology.puml' \
  -F 'options={"parser":{"engine":"auto"},"chunking":{"strategy":"recursive","size":500},"extraction":{"merge":true}}'

# 多文件 — 同一套 ontology，输出一份合并图谱
curl -X POST 'http://127.0.0.1:8006/api/v1/pipelines/knowledge-ingestion' \
  -F 'files=@./demo1.docx' \
  -F 'files=@./demo2.pdf' \
  -F 'ontology=<./ontology.puml' \
  -F 'options={"parser":{"engine":"auto"},"chunking":{"strategy":"recursive","size":500},"extraction":{"merge":true}}'
```

完整 `options`：

```json
{
  "parser": {
    "engine": "auto",
    "keep_page_edges": "first_page",
    "page_edge_min_chars": 3,
    "mineru_options": {
      "language": "ch",
      "ocr_mode": "auto",
      "table_enable": true,
      "formula_enable": true
    }
  },
  "chunking": {
    "strategy": "recursive",
    "size": 500,
    "separators": null,
    "similarity": 0.6,
    "chunk_overlap": 0,
    "size_unit": "char",
    "breakpoint_method": "percentile"
  },
  "extraction": {
    "model": null,
    "merge": true
  },
  "storage": {
    "persist_graph": false,
    "knowledge_space_id": null
  }
}
```

`parser`、`chunking` 和 `extraction` 分别采用文档解析、文档切片和分片图谱抽取章节定义的规则。当前 `storage.persist_graph` 必须保持 `false`；`storage.knowledge_space_id` 会透传给外部文件与向量服务。客户端不能通过该接口覆盖 LLM `base_url` 或 `APPLICATION_SERVICE_URL`。聚合流水线对每份文档均执行所配置的切片策略，不因文档总长度跳过切片。实际片数由策略、目标大小、重叠及结构化块保护决定；短文经切片器处理后仍可能只产生一片。

### 输出


`data.name` 来自上传文件名去除最后一个扩展名。`data.stats.document.parser` 与文档解析接口的 `data.parser` 格式一致。`data.extraction` 与分片图谱抽取接口遵循相同的 `merge` 返回规则，并按切片顺序额外返回 `ranges`、`metadata`，同时附带 `graph_publishable`、`quality` 质量门禁字段（质量门禁规则与分片图谱抽取接口一致：默认 `graph_publishable=false` 时 `graph`/`graphs` 仍返回 best-effort 图谱，`isolated_graph`/`isolated_graphs` 同步保留；`KG_EXTRACT_PUBLISH_BEST_EFFORT=0` 时恢复置空旧行为，图谱仅在 `isolated_graph`/`isolated_graphs`）。`data.ontology` 回报本次请求实际收到的本体原文、长度、指纹和类解析结果，供调用方确认本体送达与解析情况；非结构化摘要模式下 `data.extraction` 返回 `mode`、`count` 和 `chunks[]`（含 `summary`），无 `graph`/`graphs`。

**多文件时**：`data.name` 格式为 `{第一个文件名}_等{N}个文件`；`data.summary` 末尾标注 `，来源：N 个文件`；`data.stats.documents` 为数组，每项对应一个文件的解析元信息；`data.extraction.graph` 是所有文件合并去重后的一份统一图谱。任一文件解析失败时请求整体失败。

服务不做本地产物存储。配置 `APPLICATION_SERVICE_URL` 后，服务上传 Markdown，并把原始文本切片向量写入同一 Base URL 下的 `/third/vectors/store`。旧部署可继续使用 `FILE_SERVICE_URL` 作为回退变量；未配置时不会上传 Markdown 或执行向量存储，`artifacts` 为 `null`。Markdown 上传失败仍按 `7000 / FILE_SERVICE_FAILED` 使请求失败；向量写入失败或返回 ID 数量不一致不再作废整篇，而是降级返回抽取结果，失败明细记入 `stats.storage.vector_error`（`code` 为 `VECTOR_STORE_FAILED` 或 `VECTOR_ID_COUNT_MISMATCH`），`artifacts.vector_ids` 为 `null`。

`ranges[i]` 与 `artifacts.vector_ids[i]` 按切片顺序对应；`merge=false` 时，`graphs[i]` 也与二者对应。`merge=true` 时，合并图中每个节点额外返回 `chunk_indices`，其中的整数与 `ranges` 下标对应，表示该节点被哪些切片抽取到。`stats.extraction.attempts` 和 `scheduler` 是运行观测信息，不属于图谱抽取业务结果。`stats.extraction` 还包含 `quality`（质量门禁）、`warnings`（告警按 code 归类）与 `profile`（候选提议统计）；当抽取结果为 0 实体 0 关系时额外返回 `empty_reason`，取值为 `all_chunks_failed`、`filtered_by_validation`、`llm_no_proposal` 或 `unknown`，用于区分“全部切片失败”“有候选但全部被校验拒绝”“模型未产生候选”和“原因不明”。`stats.chunking` 还包含 `separators`、`vector_storage_enabled`、`vector_dimension` 和 `vector_source`；`stats.storage` 记录文件服务启用状态、已上传的 `origin` 和向量入库结果。

## 11. 健康检查

```http
GET /health
```

```json
{"status":"ok"}
```

基础健康检查只表示后端进程可以响应。`full=true` 或 `validate_models=true` 时执行完整检查：运行环境（解析模块、LibreOffice、OFD 转换器、模型目录等）与已配置的 SQL、知识抽取 LLM 和应用团队统一服务；remote-only 模式还要求配置远程文档解析与向量服务地址。不再检查 Neo4j 或 Elasticsearch。
