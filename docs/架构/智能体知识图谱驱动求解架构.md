# 智能体知识图谱驱动求解架构

## 1. 目标与原则

本系统采用“Agent 自主决策、Skill 约束方法、知识图谱提供知识、MCP 提供原子能力”的问题求解架构。

四个组成部分的职责分别是：

| 组成部分 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| Agent | 理解请求、选择探索路径、调度工具、处理失败和组织答案 | 凭模型记忆生成业务事实、规则或方案 |
| Skill | 规定问题求解、语义对齐和方案执行的方法与质量门 | 固化具体领域知识或代替图谱保存方案 |
| 知识图谱 | 保存业务概念、事实、关系、规则、ProblemClass、SolutionClass 和资源映射 | 决定当前会话的工具调用顺序 |
| MCP | 提供知识空间定位、图谱查询、SQL、知识处理和可视化等原子操作 | 在工具内部完成整套意图识别或方案规划 |

核心约束如下：

- 用户输入可以作为目标和约束，但不能自动成为业务事实。
- Agent 可以使用推理选择下一步动作，但不能把模型记忆当成业务知识。
- 指标口径、业务规则、表和字段、计算公式、问题类型及业务方案必须具有图谱证据。
- 图谱未沉淀的内容应作为知识缺口报告，不得静默回退或补写。
- 运行结果可以来自 SQL 等工具；结果的业务解释仍需图谱定义、规则或方案支撑。

## 2. 当前求解链路

已去掉独立的意图识别 / 方案规划 MCP（`recognize_intent`、`get_plan_from_intent`）以及工具内部的 ToG 剪枝。当前链路：

```text
用户问题
  → Agent 自主建立 ProblemFrame
  → problem-solve 约束总体流程
  → semantic-align 指导图谱检索
      → 定位知识空间
      → 实体链接与属性确认
      → 确定性逐层探索
      → 获取 ProblemClass / SolutionClass
      → 获取规则和执行资源
  → 证据门检查
  → plan-execute 实例化图谱方案
      → 参数溯源
      → 原子 MCP 映射
      → 执行和结果验证
  → 输出 answer-v1 JSON（结论、依据、假设、缺口、置信度）
```

只有 Agent 负责当前会话的决策，但不是无约束发挥：Skill 约束方法与质量门，知识图谱拥有业务权威，MCP 只做可观察的原子动作。

## 3. ProblemFrame：Agent 自主理解请求

Agent 不再调用意图识别 MCP，而是从对话中整理内部问题框架：

```json
{
  "raw_request": "2025 年各月采购金额有什么变化？",
  "goal": "分析采购金额的月度变化",
  "target_objects": ["采购金额"],
  "constraints": {
    "时间": "2025 年",
    "粒度": "月"
  },
  "expected_output": "趋势说明，必要时生成图表",
  "search_terms": ["采购金额"],
  "ambiguities": []
}
```

ProblemFrame 只描述用户目标、约束和需要检索的表达，不产生业务知识。例如，Agent 可以判断用户希望查看趋势，但“采购金额”的定义、数据来源和分析方案必须继续查询图谱。

## 4. Skill 的变化

### 4.1 problem-solve

`problem-solve` 是总求解框架，负责：

- 建立 ProblemFrame；
- 调用语义对齐流程获取 GraphContext；
- 在执行前进行证据门检查；
- 调用图谱方案执行流程；
- 在最终答案中区分事实、运行结果、假设和知识缺口。

证据门至少检查：

- 是否定位了可回答的知识空间；
- 关键术语是否有可信图谱实体；
- 业务方案是否来自 SolutionClass 或等价图谱节点；
- 方案所需规则和资源是否已经找到；
- 是否存在由模型自行设计并冒充图谱方案的步骤。

如果图谱没有 SolutionClass，Agent 应继续探索、请求补充或报告“知识图谱尚未沉淀该方案”，不得自行创造业务方案。

### 4.2 semantic-align

`semantic-align` 将用户表达转换为可追溯的 GraphContext。

旧版 Skill 偏向固定关系链，例如：

```text
Term → Stakeholder → ProblemClass → SolutionClass
```

新版改为图驱动探索：

1. 定位知识空间。
2. 链接少量高信息密度的关键词。
3. 读取关键候选节点的标签和完整属性。
4. 从已确认节点进行确定性单跳搜索。
5. 根据实际返回的关系和节点决定下一跳。
6. 找到 ProblemClass、SolutionClass、方案步骤、规则和资源节点。
7. 为关键结论记录实体、关系路径和工具来源。

遍历过程中维护 `visited_entity_ids`，避免循环；工具空结果只表示“本次未检索到”，不能直接解释为“不存在”。

GraphContext 的主要结构为：

```json
{
  "knowledge_space": {},
  "aligned_entities": [],
  "problem_class": {},
  "solution_class": {
    "id": "",
    "steps": [],
    "input_spec": {},
    "output_spec": {},
    "resource_requirements": [],
    "evidence_path": []
  },
  "resource_nodes": [],
  "business_rules": [],
  "evidence_ledger": [],
  "gaps": [],
  "failed_tool_calls": []
}
```

### 4.3 plan-execute

`plan-execute` 严格区分业务方案和执行计划：

- 业务方案来自知识图谱中的 SolutionClass，定义目标、步骤、输入输出和资源要求。
- 执行计划由 Agent 根据当前用户约束，将图谱方案实例化为本次工具调用。

关键参数的来源优先级为：

1. 用户明确给出的约束；
2. SolutionClass 和业务规则节点；
3. 图谱资源节点中的表、字段、模板和配置；
4. 已验证的前序步骤输出。

Agent 可以自主决定并发、重试和具体工具，但不得自行补出表名、字段、公式、阈值或额外业务流程。每个关键参数都应保留 `value_source`。

## 5. MCP 的变化

### 5.1 删除的非原子能力

以下工具已删除：

- `recognize_intent`
- `batch_recognize_intent`
- `get_plan_from_intent`
- 未实际实现的 `get_reasoning_rules`

旧 `reasoning` MCP 域已经删除，图谱能力迁移到 `graph` 域。

### 5.2 保留的 graph 原子工具

| 工具 | 作用 |
| --- | --- |
| `locate_knowledge_space` | 根据问题和应用要求定位知识子空间 |
| `get_all_subspaces` | 获取候选知识子空间，用于失败回退和消歧 |
| `search_space_units` | 按空间名/ID 一跳取回子空间直接包含的知识单元 |
| `link_entities` | 使用图谱数据和语义排序将关键词链接到候选节点 |
| `get_stakeholders` | 获取干系人实例列表（问题链固定起点） |
| `query_entity_properties` | 获取一个节点的标签和完整属性（含逻辑属性） |
| `search_graph` | 确定性查询一个节点的一跳关系和邻居 |
| `find_problem_classes` | 干系人 → 问题类：沿关系返回邻接问题类候选 |
| `find_solution_classes` | 问题类 → 方案类：沿关系返回邻接方案类候选（含完整属性） |

### 5.3 search_graph 的变化

重构前：

```text
search_graph
  → AnswerGenerationTool
  → LLM 关系判断
  → ToG 剪枝
  → 返回筛选后的三元组
```

重构后：

```text
search_graph
  → 应用团队 Cypher API 的确定性单跳查询
  → 返回节点、关系和属性
  → Agent 根据 semantic-align 决定下一跳
```

该工具支持：

- `relationship_types`：可选关系类型过滤；
- `direction`：`outgoing`、`incoming` 或 `both`；
- `limit`：返回数量限制；
- `depth`：固定为 1，多跳由 Agent 逐层完成。

返回内容包括真实边方向、节点标签、节点完整属性和关系属性。工具不再使用 LLM 隐式隐藏关系。

### 5.4 统一 MCP 工具集

统一 `qasystem-tools` 当前包含 32 个工具：

| 领域 | 数量 | 主要能力 |
| --- | ---: | --- |
| knowledge | 4 | 知识抽取、维度刻度、知识空间初始化、图谱存储 |
| graph | 9 | 知识空间定位、子空间与单元检索、实体链接、属性查询、单跳搜索、问题类/方案类导航、干系人 |
| data | 5 | 数据库信息、表结构和只读 SQL 执行 |
| visualization | 11 | 图表类型查询和十类图表生成 |
| execution | 3 | 任务状态查询、结果获取、任务取消 |

所有工具统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "error": null
}
```

失败时返回非零错误码、`data: null` 和可诊断的 `error.details`，禁止静默成功。

## 6. 图谱检索 LLM 的收缩

原 `QA_LLM` 同时承担实体提取、候选排序、关系剪枝、ToG 搜索和答案生成，职责过宽。

重构后配置改为 `GRAPH_LLM_*`，只服务于：

- 知识空间语义定位；
- 图谱实体候选的语义排序；
- 必要的查询词提取辅助。

系统已删除旧答案生成器、ToG 编排和提示词中的硬编码采购规则。图谱检索 LLM 只能依据问题文本和图谱候选信息进行判断，不得引入外部业务知识。

`algorithm/ans/QA` 当前是历史目录名，内部保留知识空间定位、实体链接和应用服务图谱查询适配，不再负责最终答案生成，也不直接连接 Neo4j。

## 7. 与旧链路的差异

| 维度 | 重构前 | 重构后 |
| --- | --- | --- |
| 意图理解 | 独立意图识别组件 | Agent 自主建立 ProblemFrame |
| 问题类型 | 意图模型分类或 Skill 推断 | 从图谱获取 ProblemClass |
| 方案来源 | 规划 MCP、Skill 回退和图谱混合 | 必须来自 SolutionClass |
| 图谱搜索 | MCP 内部 LLM/ToG 剪枝 | 确定性单跳查询 |
| 图谱路径 | Skill 预设关系链 | Agent 根据实际图谱逐层探索 |
| 业务知识 | 可能来自提示词、模型记忆或硬编码 | 必须来自图谱证据 |
| 工具调度 | 多个算法组件共同决定 | Agent 自主决定 |
| 参数来源 | 允许较宽松的上下文推断 | 用户、图谱或已验证运行结果，必须可追溯 |
| 图谱缺失 | 容易推断或静默回退 | 明确报告知识缺口 |
| 审计能力 | 难以判断结论来源 | evidence ledger、图谱路径和工具结果 |

最终职责链为：

```text
Skill 决定应该遵循怎样的求解方法
  → Agent 决定当前下一步动作
  → 知识图谱决定业务上什么是真的、应该采用什么方案
  → MCP 可靠执行一次原子读取或操作
```

## 8. 维护约束

后续扩展应遵循以下规则：

- 新业务知识应进入图谱，不应写进 Skill、Prompt 或 MCP 源码。
- Skill 可以增加通用求解策略、证据检查和失败处理，不应绑定单一领域关系名。
- 新 MCP 应优先设计为参数清晰、结果可观察、无隐藏规划的原子能力。
- 如果需要多步业务流程，应先将方案沉淀为 SolutionClass，再由 Agent 根据 Skill 执行。
- 修改图谱工具名称或 Schema 时，必须同步 Skill 和契约测试。
- 对关键 Agent 行为保留 Skill 发现、禁用旧规划工具、图谱证据约束和 MCP Schema 测试。
