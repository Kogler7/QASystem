# 文档解析部署与依赖

本文记录文档解析组件的格式转换、镜像依赖、模型挂载、GPU 配置和运行检查。解析参数与引擎选择行为见[文档解析行为规范](文档解析行为规范.md)。

## 1. 格式转换

| 输入与引擎 | 前置处理 |
|---|---|
| OFD | ofdrw 转 PDF，再按 PDF 的自动引擎选择进入解析流程 |
| DOCX/DOC/PPTX/PPT 使用 `vlm` 或 `mineru` | LibreOffice 转 PDF，再进入解析流程 |
| PNG/JPG/JPEG 使用 `vlm` 或 `mineru` | Pillow 封装为单页 PDF，再进入解析流程 |
| PPT 使用 `docling` | LibreOffice 转 PPTX，再由 Docling 解析 |
| PPTX、图片使用 `docling` | Docling 原生解析 |
| Markdown、TXT | 按 UTF-8 BOM/UTF-8 或 GB18030 直接解码 |

## 2. 镜像依赖

| 依赖 | 安装来源 | 用途 |
|---|---|---|
| LibreOffice Core | Dockerfile 系统包 | Office 格式转换基础能力 |
| LibreOffice Writer | Dockerfile 系统包 | DOC/DOCX 转换 |
| LibreOffice Impress | Dockerfile 系统包 | PPT/PPTX 转换 |
| Noto CJK | Dockerfile 系统包 | 中文字体渲染 |
| Pillow | `backend/requirements.txt` | 图片转 PDF |
| Docling | `backend/requirements.txt` | `docling` 引擎；模型外置于 `models/docling-models` |
| MinerU | `backend/requirements.txt` 和 `backend/requirements.mineru-extras.txt` | `vlm` 和 `mineru` 引擎及其运行依赖；模型外置于 `models/mineru/pipeline`、`models/mineru/vlm` |
| OpenCV full/headless 4.11.0.86 | `backend/requirements.mineru-extras.txt` | MinerU、vLLM 和图像预处理；兼容目标机 Linux 3.10 内核 |
| OpenJDK 17 Runtime | Dockerfile 系统包 | 执行 OFD 转换器 |
| ofdrw 2.3.9 | Dockerfile Maven 构建阶段 | OFD 转 PDF |

镜像构建会执行 `pip check`，检查 LibreOffice、FFmpeg、Poppler、中文字体、完整 Python 模块、Backend/Agent 入口以及 Docling 的 PPTX/IMAGE 输入能力。运行时校验还要求 `opencv-python` 和 `opencv-python-headless` 均为 `4.11.0.86`。OpenCV 5.0 自带 Qt5 的 ELF ABI 下限为 Linux 3.17，无法在目标机 3.10 内核加载；禁止通过修改容器内 `libQt5Core` 的 `.note.ABI-tag` 临时绕过。模型不打入镜像，运行期固定从 `/models` 读取；必须在联网机器使用独立下载脚本准备好模型目录后再交付，部署服务器无需访问 Hugging Face、ModelScope 或互联网。

容器内 LibreOffice 路径：

```text
/usr/bin/soffice
```

容器默认通过以下命令调用镜像内置的 OFD 转换器：

```text
java -jar /opt/qasystem/ofdrw/ofd-to-pdf.jar <input.ofd> <output.pdf>
```

如需使用经验证的外部或自定义转换器，可通过 `OFD_CONVERTER_COMMAND` 覆盖命令；命令需要依次接收输入 OFD 路径和输出 PDF 路径。

## 3. 模型挂载

模型目录通过 Compose 挂载到容器 `/models`：

```env
HOST_MODELS_DIR=./deploy/models
MINERU_MODEL_PIPELINE_PATH=/models/mineru/pipeline
MINERU_MODEL_VLM_PATH=/models/mineru/vlm
```

在联网机器执行以下命令下载全部文档解析模型：

```powershell
.\download-models.ps1
```

脚本默认使用 ModelScope，可通过 `-Source huggingface` 切换 MinerU 下载源。它会下载 Docling 默认模型到 `models/docling-models`、MinerU Pipeline 的 `OpenDataLab/PDF-Extract-Kit-1.0` 到 `models/mineru/pipeline`、MinerU VLM 的 `OpenDataLab/MinerU2.5-2509-1.2B` 到 `models/mineru/vlm`，以及 512 维 BGE-small-zh 到其 `.env` 指定目录。BGE-small-zh 同时用于向量化和置信度语义评分。向量模型从 Hugging Face 下载。下载完成后将整个 `models/` 目录复制到离线部署包。`mineru` 只检查 Pipeline 模型目录，`vlm` 只检查 VLM 模型目录。

## 4. GPU 部署

默认 Compose 为 Backend 申请 GPU，并通过 `CUDA_VISIBLE_DEVICES` 限制模型进程使用宿主机后四张卡，编号由 `.env` 控制：

```yaml
services:
  backend:
    gpus: all
    environment:
      CUDA_VISIBLE_DEVICES: ${GPU_DEVICE_IDS:-4,5,6,7}
```

交付模板的默认值为 `GPU_DEVICE_IDS=4,5,6,7`。单卡部署可设置为 `GPU_DEVICE_IDS=4`，多实例部署时为每个实例分配不重叠的 GPU 编号。部署机需要安装 NVIDIA 驱动、NVIDIA Container Toolkit，并使用支持 `gpus` 字段的 Docker Compose。CPU-only 部署需要从 Compose 中移除 `gpus` 配置。

容器内检查：

```bash
docker compose exec backend python -c "import torch; print(torch.cuda.is_available(), torch.cuda.device_count())"
docker compose exec backend nvidia-smi
curl 'http://127.0.0.1:8006/health?full=true'
```

`GET /health` 默认只检查服务存活。添加 `full=true` 后会校验 Docling、MinerU 和已配置向量模型的外部目录，Python 模块、LibreOffice、Java、OFD 转换器，以及 MySQL、Neo4j、Elasticsearch、知识抽取 LLM 和文件服务的 TCP 连通性；任一项缺失时返回 `503` 与 `failed` 列表。该检查不会下载模型、初始化 GPU 模型或修改外部服务。为兼容已有调用，`validate_models=true` 也会触发同一套完整检查。

## 5. 构建与验证

```bash
.\build-image.ps1
docker run --rm qasystem-backend:latest libreoffice --headless --version
docker run --rm --entrypoint python qasystem-backend:latest /usr/local/bin/verify_qasystem_runtime.py
```

Compose 使用本地镜像并配置 `pull_policy: never`。Dockerfile 或依赖变更后需要重新构建镜像。

## 6. 运行错误

依赖或转换能力不可用时，解析错误会返回具体原因，包括：

- 未找到 LibreOffice/soffice
- LibreOffice Writer 或 Impress 转换失败及命令输出
- LibreOffice 转换超时
- 缺少 Pillow
- 图片损坏或格式不正确
- 缺少 Docling、MinerU 等 Python 模块
- MinerU 所选路线的模型目录缺失
- 缺少 Java 或镜像内置 ofdrw 转换器
- OFD 转 PDF 失败、超时或未生成目标文件
